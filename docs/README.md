
**想做性能测试**：

```

  → 12 §2（为什么必须排在 CI 之后 —— 别跳过这节）
  → 12 §13（动手顺序 P0~P10）
```

> ⚠️ **顺序很重要**：性能测试对本项目**目前还做不了**，
> 原因写在 [12](./12-性能测试与容量分析.md) §2 ——
> 三个前提里「**部署形态**」已完成（容器化，2026-09-12，本地整栈四容器跑通），
> 仍缺「**接近真实的数据量**」（现在 13 篇）与「**SLO**」。
> **这两个卡点都不需要真实服务器**：先造数据、再按 §6.4 草案拍一版 SLO，
> 就能把 12 §13 的 P1~P3 跑起来。

**想做运行时诊断 / 内存分析**：

```
13-.NET运行时诊断与内存分析 §2（先建立"托管 vs 非托管"的区分）
  → 13 §3~§6（内存结构、GC 分代与工作模式、终结器与 IDisposable）
  → 13 §7（工具链：counters → trace → gcdump → dump，不要跳步）
  → 13 §8（本项目四个诊断案例，含已验证的 API 可用性对照表）
  → 13 §11（动手顺序 D0~D8，其中 D4 是支点）
```

> 💡 **`docs/13` §8.1 的案例 A 成本极低**（只改一个 `DOTNET_gcServer` 环境变量），
> 适合作为第一个动手项目。

## 项目速览

| 项 | 内容 |
|---|---|
| 定位 | 多作者技术博客平台，前后端分离 |
| 后端 | C# / .NET 10 · ASP.NET Core · EF Core 10 · 四层整洁架构 |
| 前端 | Vue 3 · TypeScript · Vite 8 · Pinia · 自研 CSS 体系 |
| 数据库 | PostgreSQL 18.6 + **zhparser**（中文全文检索） |
| 缓存/限流 | Redis（可降级内存）· 令牌桶 |
| 认证 | JWT（仅 Access Token）· PBKDF2 · 双档角色 |
| 规模 | 后端 47 个端点 + `/health` / 10 张表；前端 23 个页面组件 / 3 套布局；测试 161 项 |
| 默认管理员 | `admin@example.com` / `Admin@12345`（**仅开发用**） |
| 后端地址 | `http://localhost:5131`（健康检查 `GET /health`） |
| 前端地址 | `http://localhost:5173` |

## 文档维护约定（摘要）

完整规范见 [00-文档规范.md](./00-文档规范.md)。三条核心：

1. **文档描述"当前快照"，不是"变更历史"。** 变更历史属于 commit message。
2. **代码是唯一事实来源。** 冲突时以代码为准，并**当场回改文档**。
3. **改了代码就同步文档，且在同一个提交里落地**，并更新"最后核对"日期。

### 该更新哪一篇

| 改动 | 要更新 |
|---|---|
| 新增/删除 API 端点 | [05-API接口清单.md](./05-API接口清单.md) |
| 实体/表结构变更 | [06-数据库设计.md](./06-数据库设计.md) + [03-后端设计.md](./03-后端设计.md) |
| 新增页面或路由 | [04-前端设计.md](./04-前端设计.md) |
| 配置项变化 | [01-项目初始化与配置.md](./01-项目初始化与配置.md) |
| 环境/命令变化 | [07-开发与运维手册.md](./07-开发与运维手册.md) |
| 功能完成 | [02-项目总览.md](./02-项目总览.md) 进度小节 |
| 发现新的坑 | [07](./07-开发与运维手册.md)（环境类）或 [08](./08-开发知识点.md)（知识类） |
| 做出/推翻一个决策 | [10-决策记录.md](./10-决策记录.md) |
| **引入/修改流水线** | [11-CI-CD与自动化交付.md](./11-CI-CD与自动化交付.md) |
| **定义/修改性能目标，或做了压测** | [12-性能测试与容量分析.md](./12-性能测试与容量分析.md) |
| **某项工程化缺口被解决** | [09](./09-已知限制与技术债.md) §6（把对应条目从缺口清单移除，或标注为已解决） |
