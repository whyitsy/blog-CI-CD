# 项目文档

> **多作者博客平台**（Vue 3 · ASP.NET Core · PostgreSQL）的文档总入口。
> **最后核对**：2026-09-14 ｜ **代码依据**：仓库 HEAD
>
> 本仓库的文档**按用途分成三区**：`docs/` 是参考手册、`learn/` 是教材、`archive/` 是留档。
> 找"是什么、怎么做"进 `docs/`；想学原理进 `learn/`；查"当初为什么这么定"进 `archive/`。
> 规则的定义见 [00-文档规范.md](./00-文档规范.md) §2。

## 1. 三区是什么，该信谁

| 区 | 它回答什么 | 谁能改 | 你在下面这些场合信它 |
|---|---|---|---|
| **`docs/`**<br>参考手册 | **当前代码事实**：端点契约、表结构、配置键、命令、部署步骤 | 事实变化就改，**改了代码要在同一次提交里改它** | ✅ **唯一事实来源**。与代码冲突以代码为准，并按"后面那句"当场回改文档 |
| **`learn/`**<br>教材 | **为什么**：原理、取舍、学习路线 | 可以持续打磨（补例子、补讲解） | ⚠️ **只信解释，不信细节**。字段名 / 端点 / 配置键一律以 `docs/` 与代码为准 |
| **`archive/`**<br>留档 | **过程与历史**：当时的决策理由、踩坑的定位过程 | **只增不改**（补索引可以，改结论不行） | ⚠️ **只信"当时"**。里面写的实现状态可能早已不是现在这样 |

> ⚠️ **最容易犯的错**：把 `learn/` 或 `archive/` 里的代码片段直接抄进项目。
> 它们写于不同的时间点，示例可能已经过期——要抄就抄 `docs/` 指向的**仓库真实文件**。

### 🔧 我遇到了一个具体问题

```
05-运维与部署手册 §9 排错速查表（现象 → 最可能的原因 → 处理）
  → 06-技术债与待办 §1 / §2（如果是"还没解决"的，只有这里才有）
  → archive/问题排查记录.md（"这问题好像见过"：看别人当时的定位过程）
```

> 💡 **查 `archive/问题排查记录.md` 的正确姿势不是找"答案"，而是看"定位过程"。**
> 例如"创建文章报服务器内部错误"那一条，值钱的是「先验证用户的前提 → 再顺着校验链路找断点
> → 最后做全库审计」这套**动作**，而不是那个结论。

## 4. 文档维护约定（摘要）

完整规范见 [00-文档规范.md](./00-文档规范.md)。三条核心：

1. **文档描述"当前快照"，不是"变更历史"。** 变更历史属于 commit message。
2. **代码是唯一事实来源。** 冲突时以代码为准，并**当场回改文档**。
3. **改了代码就同步文档，且在同一个提交里落地**，并更新"最后核对"日期。

### 该更新哪一篇

| 改动 | 要更新 |
|---|---|
| 新增 / 删除 / 改动 API 端点 | [03-API参考.md](./03-API参考.md) |
| 实体、表结构、索引或迁移 | [02-架构与数据模型.md](./02-架构与数据模型.md) |
| 新增页面或路由、前端 API 层 | [04-前端设计.md](./04-前端设计.md) |
| 配置项、开箱账号、种子数据 | [01-快速开始.md](./01-快速开始.md) |
| 命令、环境陷阱、部署流程 | [05-运维与部署手册.md](./05-运维与部署手册.md) |
| 引入 / 修改流水线配置 | [05](./05-运维与部署手册.md) §8 + `.github/workflows/ci.yml` |
| 解决了一个未决项或一条能力缺口 | [06-技术债与待办.md](./06-技术债与待办.md)（把条目**移出**清单） |
| 踩了一个新坑并定位出根因 | `archive/问题排查记录.md`（只增不改；缺口登记到 [06](./06-技术债与待办.md)） |
| 做出 / 推翻一个决策 | `archive/决策记录.md`；当前口径见 [06](./06-技术债与待办.md) §4–§5 |
| 写作规则本身要改 | [00-文档规范.md](./00-文档规范.md) |

> 各篇的完整"唯一职责 / 不写什么"对照表见 [00-文档规范.md](./00-文档规范.md) §5。
