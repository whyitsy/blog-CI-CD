### 1.1 前端「点击保存」链路缺自动化验证

后端语义有完整的自动化测试兜底（集成 / 单元 / 统一响应体契约三层，**198 项**
= 195 项实测基线 + P0 新增的 3 项契约测试；条数由数据决定，实时值看 CI 作业摘要），
乐观锁 409 本身也有集成测试。缺的是**浏览器里的端到端确认**：

| 未自动验证 | 说明 |
|---|---|
| 表单校验提示 | 前端 `@error` 回退、必填校验 |
| 保存成功后的提示与刷新 | toast、列表刷新、`refreshAll()` |
| 乐观锁冲突提示 | 409 时是否给出用户能理解的提示 |
| 骨架屏显示 | 瞬时状态，需要特殊手段才能稳定复现（方法见 [05-运维与部署手册.md](./05-运维与部署手册.md)） |

**已经实测暴露过的一个实例：自动摘要被静默固定。**

| 步骤 | 结果 |
|---|---|
| 新建文章，摘要留空 | ✅ 后端自动截取正文前 50 字 |
| 打开该文章的编辑页 | ⚠️ `PostEditor.syncFromInitial()` 把**自动生成的摘要回填进输入框** |
| 不动摘要直接保存 | ⚠️ 回填文本作为**非空**值提交 → 后端判定为"作者手写的摘要" |
| 之后再修改正文 | ❌ 摘要**不再自动更新**，永久停在第一次保存时的内容 |

**根因**：摘要规则（T4）用「传入是否为空」区分自动 / 手写，但前端**无法区分**输入框里那段文字
是自动生成的还是作者手写的，于是无条件回填、无条件回传。行为与"作者手写的摘要不会被覆盖"
的文档描述不符（不是严重故障，是**行为反直觉**）。

**候选修法**（都需先决策，**均未实施**）：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 前端不回填 | 编辑页留空，旁边提示"当前摘要（自动生成）：……" | 作者看不见、也改不了现有摘要全文 |
| B. 加 `IsSummaryAuto` 字段 | 显式区分两种状态 | ⚠️ T4 当初已否决（多一个字段、多一类状态不一致） |
| C. 接受现状，只改文档 | 把"一次保存后自动摘要被固定"写成明确行为 | 不改代码，但行为仍反直觉 |
| D. 前端加"恢复自动"按钮 | 保留回填，额外给一个清空 / 恢复按钮 | 新增交互，但语义最清晰且不动后端 |

**已具备的验证能力**：`tools/e2e/` 里有可直接运行的 CDP 检查（Node 22+ 内置全局 `WebSocket`，
**没有引入 puppeteer**），用法与无头截图 / 骨架屏技巧见 [05-运维与部署手册.md](./05-运维与部署手册.md)。缺的不是工具，是覆盖面。

### 1.2 没有 API 版本管理

所有端点路径**不含版本号**（`/api/posts`，而不是 `/api/v1/posts`）。一旦线上有客户端在运行，
**破坏性变更无法平滑过渡**——只能"改了就全改"，没有新旧并存的余地。

现在可以接受，因为：项目尚未上线；前端与后端**在同一个仓库、同一个提交里演进**，不存在"旧客户端"；
引入版本管理会增加路径噪音。

出现以下任一情况时应该引入：有第三方在调用 API；移动端 App 需要独立发版；
前后端分离部署且发布节奏不同。**建议方案：URL 版本（`/api/v1/...`）**——最直观、最易调试。

### 1.3 `FileStorage:Root` 默认值依赖进程工作目录（T19）

`FileStorage:Root` 的默认值是相对路径 `media`，解析结果**随进程工作目录变化**：
`dotnet run`、`dotnet Blog.WebApi.dll`、测试宿主的工作目录各不相同，上传的文件会散落到意外位置。
生产配置已用绝对路径 `/app/media`（并挂成数据卷），但**默认值本身仍是一个陷阱**——
换一种启动方式就可能踩到。事实描述见 [02-架构与数据模型.md](./02-架构与数据模型.md) §13.2；部署形态见 [05-运维与部署手册.md](./05-运维与部署手册.md)。

**处理时机**：上线前，或引入新的部署形态时。

### 1.4 前端 TypeScript 停在 6.x（`vue-tsc` 尚不支持 7.x）

`typescript` 刻意**不升到 7.x**：v7 是原生（Go）重写版，不再从 `package.json` 导出
`./lib/tsc` 子路径，而 `vue-tsc` 正是靠 `require('typescript/lib/tsc')` 工作的。

**实测证据（2026-09-14，在依赖升级 PR 的分支上）：**

| 步骤 | 结果 |
|---|---|
| 修好 lock（`npm install` 重生成 + `npm ci` 通过） | ✅ 通过 —— 排除"只是 lock 不同步"这个可能 |
| `npm run build`（= `vue-tsc -b && vite build`） | ❌ `Error [ERR_PACKAGE_PATH_NOT_EXPORTED]: Package subpath './lib/tsc' is not defined by "exports" in node_modules/typescript/package.json`<br>栈顶：`at resolveTscPath (node_modules/vue-tsc/index.js:73:43)` |
| `npm view vue-tsc version` | **3.3.11** —— 与仓库里用的版本相同，**没有支持 7.x 的新版本** |

⚠️ **这条为什么必须显式登记、不能靠"等 Dependabot 别再提"**：
`vue-tsc` 的 `peerDependencies` 写的是 `typescript: ">=5.0.0"`，
**7.0.2 名义上满足这个范围** —— 所以 Dependabot 会一直提这个合不了的 PR。
已在 [`.github/dependabot.yml`](../.github/dependabot.yml) 里对 `typescript` 的 major 升级加了 `ignore`
（写法与理由同那里 `SixLabors.ImageSharp` 那条：必须带 `update-types`，否则会连带关掉安全更新通道）。

**解除条件**：`npm view vue-tsc peerDependencies` 明确支持 7.x（或项目改用 `tsgo` 工具链）。
届时删掉那条 ignore 规则即可。

> 📌 附带的教训：`peerDependencies` 的 semver 范围**不等于**真实兼容性。
> 一个大版本重写（如 TS 7 这样的换语言重写）完全可能"范围满足但装上去就崩"——
> 所以**跨大版本的依赖升级必须真跑一次构建**，不能只看它有没有被 peer range 挡住。

> **G2 与 §6 第 1 条（写接口缺鉴权）是同一类错误的两面**：
> 「**前端隐藏入口不是安全边界**」与「**开发机上的文件不是项目资产**」——
> 前者的判断依据是"能不能被一个 HTTP 请求绕过"，后者是"换一台机器还在不在"。
> 两者都必须由**项目状态**（服务端策略 / 版本控制）强制，而不是靠人的自觉。

### 3.1 性能与容量：目前一条基线都没有

这一组对应 **G8**，是全项目最大的一块欠账：没有基线，"优化"无法被证明有效，单机容量只能靠猜。
它**不需要服务器**就能开始——这是最容易被"等有了服务器再说"拖住的地方。

**前置条件**

| # | 前置 | 状态 |
|---|---|---|
| 1 | CI 跑通 | ✅ |
| 2 | 部署形态（Dockerfile + compose） | ✅；**目标机器规格仍未定**（所以 SLO 第 8 条无值） |
| 3 | 造数据脚本：1,000 / 10,000 篇带长正文的文章 | ❌ **当前主要卡点**；对本地容器栈即可做 |
| 4 | SLO 定稿（确认或修正下表） | ❌ **不需要服务器** |
| 5 | 压测环境关闭限流 | 未做。⚠️ 单 IP 突发 120 后持续被限到 20 RPS，不关就会把**限流器**当成**容量** |
| 6 | 冷缓存 / 热缓存两组步骤 | 方法已定，待执行 |

> **顺序**：CI ✅ → 部署形态 ✅ → **造数据 → 定 SLO** → 压测比对 → 优化 → 复测。
> 中间的"造数据 + 定 SLO"是现在唯一真正的卡点，而且**都不需要真实服务器**。

**SLO 草案（待定稿）**

| 接口 / 场景 | SLI | 草案值 |
|---|---|---|
| `GET /api/posts` 首页列表 | 服务端 p95 | < 300 ms |
| `GET /api/posts/{id}` 文章详情 | 服务端 p95 | < 300 ms |
| `GET /api/posts/search` 全文检索 | 服务端 p95 | < 800 ms |
| `GET /api/files/{name}` 文件 / 图片 | 服务端 p95 | < 200 ms |
| `POST /api/posts` 保存文章 | 服务端 p95 | < 500 ms |
| `GET /health` 探针 | p99 | < 100 ms |
| 全局 5xx 比例 | 错误率 | < 0.1% |
| 单机吞吐 | 吞吐 | **待定** |
| 可用性 | 月度 | 99.5%（约 3.6 小时 / 月） |

> **第 8 条写着"待定"是刻意的**：容量目标必须基于目标机器规格，现在写任何数字都是猜的。
> 其余 8 条都是**建议值**，定稿时逐条确认或修正。

**一次性能测试要知道的四件事**

| 项 | 内容 |
|---|---|
| 压哪些接口（按优先级） | 首页列表 → 详情（会触发浏览量写入）→ 搜索（FTS + `ts_rank` + CTE）→ 归档（无分页 + 全量内存分组）→ 站点配置（5 次聚合）→ 写文章（低并发、高成本） |
| 分阶段执行 | B0 冒烟（`bombardier` 10 RPS × 30 秒）→ B1 基准（六接口各跑一遍）→ L1 负载（按 SLO 峰值）→ S1 压力（找拐点）→ O1 优化（**只改一处**）→ L2 复测 → S2 浸泡（4~24 小时） |
| 完成判据 | ① 有基线数字且环境规格完整记录；② 每接口都有 p50 / p95 / p99；③ 与 SLO 逐条比对；④ 不达标项有定位结论；⑤ **脚本已进仓库**；⑥ 至少跑过一次冷缓存 |
| 数据量 | 必须接近真实量级：数据太少时索引不生效、查询计划退化，测出来的数字会**给人虚假的安全感** |
| 工具与脚本 | 冒烟用 `bombardier`，正式压测用 k6（`thresholds` 里写 SLO、检查响应体的 `code === 0`、`BASE_URL` 可配置）。⚠️ **压测脚本目前还不存在**——写完必须进仓库（判据 ⑤） |

> ⚠️ **S2 浸泡测试排最后但不要跳过**：死元组堆积（实验 C）与内存泄漏**只有它能发现**。
> 跑一次 4 小时的浸泡成本很低，价值很高。

**另外两处热点**（读代码可确认，现象与原理见 [learn/03](../learn/03-性能与运行时诊断.md) §9）的观察点：

| 热点 | 观察点 |
|---|---|
| 归档接口把全部文章加载进内存后分组，且**不分页** | 归档接口的 p95 **随文章数增长的趋势**；若 10,000 篇时仍 < 300 ms，这条假设可以关闭 |
| 站点统计一次请求打 **5 个聚合查询**（含两个全表 `SUM`），结果被 Redis 缓存 | 清空 Redis 后 `GET /api/site/config` 的**首字节时间**（冷缓存下 5 个查询串行执行，是首屏最慢的一环） |

### 3.2 四个诊断实验：做透 2~3 个

**不要四个都做。** 每个实验的产出是"一个假设被证实或被推翻 + 一份可复现的脚本"，
四个各做一半不如两三个做透。推荐顺序：**A（成本最低）→ B（最贴内存分析）→ C 或 D**。

| 实验 | 要回答的问题 | 怎么做 / 看什么 | 出处 |
|---|---|---|---|
| **A. Server GC vs Workstation GC** | Server GC 是 Web SDK 给的**隐式默认值**（csproj 里一处都没写），多核上吞吐更好但内存占用显著更高；单核小内存 VPS 上可能反而更差 | 同一个压测脚本跑两组，唯一变量是 `DOTNET_gcServer`；看 RPS、p99、`gc-heap-size` 峰值、`working-set` 峰值、`% Time in GC`。产出：对比表 + **一行显式的 csproj 配置** | 原 `13 §8.1` |
| **B. 图片上传链路的内存峰值** | 4000 万像素图的像素缓冲约 160MB（推算），**它在托管还是非托管内存**——这决定后续所有分析方向 | 并发上传不同尺寸的图，同时监控 `loh-size`（应平稳）与 `working-set`（应飙升）。`loh-size` 平稳即证明像素在**非托管**，GC 调优无用；反之走 LOH 分析路径 | 原 `13 §8.2` |
| **C. 浏览量自增的行锁热点** | `IncrementViewCountAsync` 用 `ExecuteUpdateAsync` 对**同一行**高频 `UPDATE`：是否让热门文章的并发访问在这里串行化，并堆积死元组（行业里的"计数器列反模式"） | 压**同一篇**热门文章 vs 压 **100 篇不同**文章，比两组 p99；辅助看 `pg_stat_activity.wait_event`（`Lock:transactionid` / `Lock:tuple`）与 `n_dead_tup` 的增长曲线。**结论是"不成立"也要记录为已验证** | 原 `12 §9.2` 嫌疑二 ／ 原 `13 §8.3` |
| **D. 慢查询 TOP N 与索引优化** | 哪些查询真的慢、缺哪个索引 | 先做前置改造（见 §3.3 第 13 条）→ 造真实数据量 → 压测 → 收集慢查询日志 → `EXPLAIN ANALYZE` → 优化 → 复测。重点怀疑 `GetArchivesAsync`、`GetStatsAsync`、全文检索的 CTE | 原 `13 §8.4` |

> 实验 C 在原始素材里被写过两遍（`12` 从"压测时该盯哪里"、`13` 从"诊断时该查什么"），
> **此处只登记一次**——它是同一个热点。

**实验 B 的候选修法**（都需先测再改，按预期收益排序）：

1. `DecoderOptions.TargetSize` 在**解码阶段**就缩到目标尺寸——收益最大，避免"先解 160MB 再缩小"；
2. 收紧 `MaxPixels`（如 4000 万 → 1200 万），直接砍掉最坏情况（代价：拒绝部分合法大图）；
3. 给 `MemoryAllocator` 设 `MaximumPoolSizeMegabytes`，限制池**保留**的内存；
4. **限制并发上传数**（信号量 / 限流规则），把峰值从 N 倍压到常数倍；
5. 去掉 `output.ToArray()` 的那份副本（需把下游签名改成 `ReadOnlyMemory<byte>`）。

> ⚠️ **查 API 必须查锁定版本的**：ImageSharp 官方文档站是最新版（v4），而本项目因许可锁 **3.1.12**。
> 已逐条核对本地包 XML：`TargetSize` / `MaxFrames` / `SkipMetadata` / `MaximumPoolSizeMegabytes` /
> `AllocationLimitMegabytes` / `Configuration.MemoryAllocator` / `MemoryDiagnostics` ✅ 可用；
> `ImageInfo.GetPixelMemorySize()` 与 `AccumulativeAllocationLimitMegabytes` ❌ 3.1.12 没有（v4 才有）。
> 像素内存是托管还是非托管**必须实测**，不能照搬文档结论。
