## 2. 五分钟跑起来

### 2.1 前置检查

Docker Desktop 已启动，且 `pgsql` 与 `redis` 容器处于 `Up`：

```bash
docker ps --format "table {{.Names}}\t{{.Status}}"
```

### 2.2 启动后端

在仓库根目录执行，**用工具的 `run_in_background=true` 启动**（这样工具持有进程句柄与输出）：

```bash
cd Blog.Backend/Blog.WebApi/bin/Debug/net10.0 && \
env -u HTTP_PROXY -u http_proxy -u HTTPS_PROXY -u https_proxy \
./Blog.WebApi.exe --urls http://localhost:5131 --environment Development
```

- 开发地址 `http://localhost:5131`，健康检查 `GET /health`
- `env -u ...` 清除代理变量：环境里有大小写重复的代理变量，.NET 侧可能因字典重复键而报错
- `--environment Development` **不可省略**：WSL 启动 Windows exe 时 `ASPNETCORE_ENVIRONMENT` 不生效，缺了它会因连接串为空而启动失败（见 §8）
- 启动时会**自动应用迁移**（`Program.cs` 的 `dbContext.Database.Migrate()`）

> 若 `bin/Debug/net10.0` 不存在，先构建一次（命令见 [05](./05-运维与部署手册.md) §4.1）。

### 2.3 启动前端

在 `Blog.FrontEnd/` 目录执行：

```bash
"/mnt/c/Program Files/nodejs/node.exe" ./node_modules/vite/bin/vite.js --host 127.0.0.1 --port 5173
```

- 开发地址 `http://localhost:5173`
- Vite 已配置代理 `/api` → `VITE_PROXY_TARGET`（默认 `http://localhost:5131`），
  浏览器视角因此是**同源**，没有 CORS 预检
- **必须用 Windows 的 node**，WSL 的 node 缺 rolldown 原生绑定（见 §8）

### 2.4 验证

后端与前端都是 **Windows 原生进程**，WSL 里直连它们的端口不通，
验证要走 Windows 的 curl（原因见 §8 第 1 条）：

```bash
# 后端存活
/mnt/c/Windows/System32/curl.exe -s --noproxy '*' http://localhost:5131/health

# 登录拿 token
/mnt/c/Windows/System32/curl.exe -s --noproxy '*' -X POST http://localhost:5131/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@example.com","password":"Admin@12345"}'
```

> ⚠️ `*` 必须**加引号**（写成 `--noproxy '*'`）。不加引号时 shell 会把它展开成当前目录的文件名，
> 变成一串传给 curl 的垃圾参数。

### 2.5 停止

```bash
# 后端；前端 dev server 则结束对应的后台任务（走的是什么，就停什么）
/c/Windows/System32/taskkill.exe /F /IM Blog.WebApi.exe
```

## 3. 开箱账号

### 3.1 管理员

项目通过 EF Core 的 `HasData` 预置了一个开发用管理员，**全新数据库初始化后即可直接登录**。

| 项 | 值 |
|---|---|
| 登录邮箱 | `admin@example.com` |
| 登录密码 | `Admin@12345` |
| 角色 | `Admin` |
| 关联作者 | 无（管理员账号不关联署名对象） |

登录入口：前端 `/login`（管理员与作者**共用同一个登录页**，登录后按角色跳转）。

> ⚠️ **生产环境必须立即修改此密码。**
> 这个密码连同它的 PBKDF2 哈希都**公开写在仓库里**
> （`Blog.Infrastructure/Persistence/BlogDbContext.cs` 的 `SeedAdminPasswordHash`）。
> 它存在的唯一目的是"让全新开发环境开箱即可登录后台"，绝不是一个安全的默认值。
> 修改方式：登录后台 →「账号管理」→ 重置密码（会同时使旧 token 失效）。

### 3.2 作者账号怎么来

**没有预置作者账号，也没有注册端点**（决策 T1，见 [archive/决策记录.md](../archive/决策记录.md)）。
作者账号的唯一创建入口是管理员登录后的「账号管理」页面（`POST /api/users`）：

```
管理员登录 → 创建作者（POST /api/authors，建立署名身份）
          → 创建账号（POST /api/users，邮箱 + 密码 + 角色 Author + 关联上面那位作者）
          → 该作者即可用该邮箱密码登录 /login
```

> 关于「作者（Author）」与「账号（User）」为什么要分开，见 [02-架构与数据模型.md](./02-架构与数据模型.md)。

### 3.3 签名密钥（JWT）

| 项 | 值 |
|---|---|
| 配置键 | `Jwt:SigningKey` |
| 开发值 | 存在于 `appsettings.Development.json`，形如 `dev-only-insecure-signing-key-...`（≥ 32 字节） |
| 生产要求 | **任何 appsettings 都不含此键**，必须用环境变量 `Jwt__SigningKey`（注意双下划线）或 user-secrets 注入 |

**行为**：应用启动时校验签名密钥。若缺失或长度不足 32 字节，**直接中止启动并打印指引**，
而不是退化成弱密钥。理由：静默使用弱密钥意味着"任何人都能伪造 token"，后果远比启动失败严重。

```bash
openssl rand -base64 48                # 生成密钥；再用 export Jwt__SigningKey="<随机串>" 注入（.NET 用双下划线表示层级）
```

### 4.6 种子数据的主键规律

`HasData` 要求固定主键，因此用同一前缀加不同后缀区分（定义在 `BlogDbContext.cs`）：

```
…-0001 默认作者    …-0010/0011/0012 SiteName / HeroSubtitles / FoundingDate
…-0020 GitHub 链接 …-0021 Bilibili 链接
…-0030 管理员账号  …-0040 示例专栏
（前缀统一为 6f2a1b3c-0000-0000-0000-0000000000xx）
```

> 改种子数据的**内容**是安全的（生成 `UpdateData` 迁移）；改主键会让旧数据变成孤儿。

## 5. 数据库

### 5.1 连接信息（开发环境）

| 项 | 值 |
|---|---|
| 容器名 | `pgsql` |
| 镜像 | **`blog-postgres-zhparser:18`**（自定义镜像，含 SCWS + zhparser，见 §5.4） |

> **为什么库名带 `stage2`**：本机另有一个旧项目的库 `blog`，**不要动它**。

### 5.2 迁移

应用启动时会自动执行迁移，正常不需要手工跑命令；生成/回退迁移的命令见 [05-运维与部署手册.md](./05-运维与部署手册.md) §4.4。当前迁移清单如下（**数量会随开发增长，以这里的清单与迁移目录为准**）：

| 迁移 | 内容 |
|---|---|
| `20260906040849_InitCreate` | 初始 7 张表 + 种子数据 |
| `20260910205225_AddAuthCollectionsAndFts` | 认证（Users）、专栏（Collections / PostCollections）、中文全文检索（zhparser + SearchVector 生成列 + GIN） |
| `20260911213214_FixSeedAuthorAvatar` | 修正种子作者头像为 `/api/files/avatar-default.webp`（原 `/media/avatar-default.png` 后端不提供） |
| `20260913161423_ExtendPostSummaryLength` | `Posts.Summary` `varchar(120)` → `varchar(200)`；因 `SearchVector` 生成列依赖该列，迁移里必须先拆生成列与索引、改类型、再按原表达式重建 |

### 5.3 Redis

| 项 | 值 |
|---|---|
| 容器名 | `redis` |
| 镜像 | 仓库声明 **`redis:7.4.11-alpine`**（`docker-compose.yml` 与 `.github/workflows/ci.yml` 用的是同一个 tag，都写死到 patch 位）；本机这个独立开发容器实测是 `redis:latest`（Redis 8.x）——两者都可用，排查版本相关问题时以仓库声明的版本为准 |
| 连接 | `localhost:6379` |
| 用途 | 缓存（`Cache:Provider=Redis`）与分布式令牌桶限流 |

Redis 不是硬性必须：`Cache:Provider` 可切 `Memory`，限流在 Redis 故障时可按 `RateLimit:FallbackToMemory`
降级为内存桶。但**多实例部署时 Redis 是强制的**——`DeploymentGuard` 会在启动期直接拒绝"多实例 + 非 Redis"的危险配置。

### 5.4 PostgreSQL 的中文分词扩展

站内搜索用 **全文检索（FTS）**，而 PG 内置分词器对中文会把整句当成一个词元，因此必须装中文分词器
**`zhparser`**（依赖 SCWS）。它**不在官方 postgres 镜像里**，本项目用自定义镜像 `deploy/postgres-zhparser.Dockerfile` 编译进去。

```bash
# 验证分词（在容器内）
docker exec -it pgsql psql -U kky -d blog_stage2 -c \
  "SELECT to_tsvector('chinese', '使用 EF Core 做数据库优化与全文检索');"
```

预期是**词级切分**（而不是逐字或整句）：`'core':3 'ef':2 '优化':6 '使用':1 '做':4 '全文检索':7 '数据库':5`。

镜像构建、初始化脚本与"容器重建后扩展如何自动恢复"见 [05-运维与部署手册.md](./05-运维与部署手册.md) §2.7 与
`deploy/README.md`；检索的设计见 [02-架构与数据模型.md](./02-架构与数据模型.md)。

## 6. 配置速查

配置文件分三层，按环境加载（后加载的覆盖先加载的）：

| 文件 | 何时加载 | 内容 | 是否入库 |
|---|---|---|---|
| `Blog.WebApi/appsettings.json` | 总是 | 只有日志与 `AllowedHosts` | ✅ |
| `Blog.WebApi/appsettings.Development.json` | `--environment Development` | 开发用连接串、缓存、限流、文件、**开发签名密钥** | ✅（密钥仅限开发） |
| `Blog.WebApi/appsettings.Production.json` | `--environment Production` | 缓存、文件、限流规则、部署拓扑、CORS | ✅（**刻意不含任何密钥**） |

> ⚠️ **密钥一律不在这三个文件里（开发签名密钥除外）**：连接串密码与 `Jwt:SigningKey` 必须由
> 环境变量 `ConnectionStrings__DefaultConnection` / `Jwt__SigningKey` 注入（12-Factor 的配置外置）。
> 缺失时应用**拒绝启动**，见 §3.3。

| 配置节 | 关键键 | 开发值 | 说明 |
|---|---|---|---|
| `ConnectionStrings` | `DefaultConnection` | 见 §5.1 | 生产必须由环境变量注入 |
| `Cache` | `Enabled` / `Provider` / `RedisConnection` | `true` / `Redis` / `localhost:6379` | 生产连接串是服务名 `redis:6379` |
| `Cache` | `NullTtl` / `LockWaitTimeout` / `TtlJitterRatio` | `00:02:00` / `00:00:03` / `0.2` | 缓存三防：穿透 / 击穿 / 雪崩 |
| `FileStorage` | `Root` | `media`（生产 `/app/media`） | 上传目录，**可写**，已 gitignore |
| `FileStorage` | **`SeedRoot`** | `media-seed`（生产 `/app/media-seed`） | 随仓库分发的**只读**种子资源目录（默认头像等），作为 `Root` 未命中后的回退；为空则禁用回退 |
| `FileStorage` | `MaxFileSize` | `10485760`（10 MB） | 单文件上限 |
| `FileStorage:ImageOptimization` | `Enabled` / `WebpQuality` / `MaxDimension` / `MaxPixels` / `ConvertExtensions` | `true` / `82` / `2560` / `40000000` / `.png .jpg .jpeg` | 上传位图自动转 WebP；失败一律原样保存 |
| `RateLimit` | `Enabled` / `FallbackToMemory` | `true` / `true` | 规则按顺序匹配、命中即停；触发返回 429 + `Retry-After` |
| `Cors` | `Origins` | `["http://localhost:5173"]`（生产 `[]`） | 生产同源部署不需要 CORS；未启用 `AllowCredentials` |
| `Jwt` | `Issuer` / `Audience` / `AccessTokenMinutes` | `blog-api` / `blog-frontend` / `30` | 见下方说明 |
| `Jwt` | `SigningKey` | 仅开发配置有 | 见 §3.3；生产必须环境变量注入 |
| `Deployment` | `InstanceCount` / `RequireRedis` | `1` / `false` | `InstanceCount > 1` 或 `RequireRedis = true` 时强制要求 `Cache:Provider = Redis`，否则启动即失败 |

> ⚠️ **`Jwt:Issuer` / `Audience` / `AccessTokenMinutes` 在生产没有 appsettings 节点**：
> `appsettings.Production.json` 里**完全没有 `Jwt` 节**，这三个值直接取
> `Blog.Application/Interfaces/JwtOptions.cs` 的 **C# 默认值**（`blog-api` / `blog-frontend` / `30`）。
> 也就是说它们**不会**因环境切换而变化；要改就得改代码，或用环境变量显式覆盖
> （`docker-compose.yml` 就是这么做的：`Jwt__Issuer` / `Jwt__Audience` 从 `.env` 取，默认值与 C# 默认值一致）。
> 只有 `SigningKey` 是**强制项**——没有默认值，缺失即拒绝启动。

> **上线前必须做的配置项清单**见 [05-运维与部署手册.md](./05-运维与部署手册.md) §8.3；
> `DeploymentGuard` 的启动期校验规则见 §8.10（T5）。

## 8. 环境陷阱（精简版）

Windows + WSL2 组合踩过的坑里，只列**会让项目跑不起来或看起来跑不起来**的几条。
完整清单（含每条的现象 / 根因 / 解法 / 实测记录）在 [05-运维与部署手册.md](./05-运维与部署手册.md) §2。

| # | 现象 | 原因 | 解法 |
|---|---|---|---|
| 1 | WSL 里 `curl 127.0.0.1:5131` 连接被拒 | **只有 Windows 原生进程**（Kestrel 5131 / Vite 5173 / Chrome 9222）不监听 WSL 能到达的地址；**Docker 发布的端口是通的**（实测 5432 / 6379 / 8080 均可连） | 验证 API 用 Windows 的 curl；连数据库/网关可以直接 `localhost`，见 §2.4 |
| 2 | `The ConnectionString property has not been initialized` | WSL 启动 Windows exe 时 `ASPNETCORE_ENVIRONMENT` 不生效 | 加 `--environment Development` 参数 |
| 3 | `Cannot find native binding` | WSL 的 node 缺 rolldown 原生绑定 | 用 `/mnt/c/Program Files/nodejs/node.exe` |
| 4 | `dotnet build` 报 `MSB3027` / `MSB3021`（文件被占用） | 运行中的 `Blog.WebApi.exe` 锁住了输出 DLL | 先 `taskkill /F /IM Blog.WebApi.exe`（csproj 有自动任务，偶尔仍需手工再杀） |
| 5 | `dotnet` 找不到 | 不在 WSL 的 PATH 里 | 用 `/mnt/c/Program Files/dotnet/dotnet.exe` |
| 6 | 前端全部 `ECONNREFUSED` | **最常见的原因是后端根本没在跑或已中途退出**（实测：`nohup` / `&` 启动的进程**不会**随 bash 会话结束而被清理，所以"随会话消失"不是可靠根因） | 先看后端后台任务的输出与 `/health`；启动时用 `run_in_background=true`，让工具持有句柄 |
| 7 | 全文检索报 `configuration "chinese" does not exist` | 连到了非自定义镜像的 PG（如官方镜像容器） | 确认 `pgsql` 用的是 `blog-postgres-zhparser:18`，见 §5.4 |
