## 2. 先建立正确的诊断思维

### 2.1 三条纪律

| # | 纪律 | 反面教材 |
|---|---|---|
| 1 | **先测量，再下结论** | 「我觉得是 GC 的问题」→ 改了半天发现是数据库慢 |
| 2 | **一次只改一个变量** | 同时调了 GC 模式、线程池、连接串，快了也不知道是谁的功劳 |
| 3 | **记录环境** | 没有 CPU 核数、内存、数据量、配置的记录，数字无法复现也无法比较 |

### 2.2 诊断的三层递进

```
① 症状     「接口慢 / 内存涨 / 进程被杀」
              ↓  用 dotnet-counters 拿到指标
② 指标     「GC 占 23% CPU / LOH 持续增长 / 工作集 1.8GB」
              ↓  用 trace / gcdump / dump 深入
③ 根因     「大图解码产生 160MB 非托管缓冲，并发 5 路把内存打满」
```

**每一层都有对应的工具**，不要一上来就抓 dump——那是最重的手段。

### 2.3 一个贯穿全篇的关键区分：托管内存 vs 非托管内存

**这是本文最重要的一条认知**，也是本项目案例的核心：

| | 托管内存（Managed） | 非托管内存（Native / Unmanaged） |
|---|---|---|
| 谁管 | .NET 的 GC | 你（或库）自己，用 `Marshal.AllocHGlobal` 之类 |
| 在哪看到 | `dotnet-counters` 的 `gc-heap-size` / `loh-size` | ⚠️ **GC 计数器看不到**，只能看**进程工作集 / 私有字节** |
| 谁释放 | GC 自动回收 | `Dispose()` / `free()`，否则泄漏 |
| 本项目里的例子 | `byte[]`、DTO 对象、字符串 | ⚠️ **ImageSharp 的像素缓冲** |

> ⚠️ **推论**：**GC 计数器一切正常，不代表进程内存没问题。**
> 一个典型的误判是：`loh-size` 平稳，于是断定"没有内存问题"，
> 而实际进程工作集已经 2GB——因为大头在非托管。
>
> **必须同时看两组指标**，见 §7.2。

## 3. 内存结构：从栈到堆

### 3.1 栈与栈帧

| 概念 | 说明 |
|---|---|
| **栈（Stack）** | 每个线程一块，**固定大小**（默认 1MB）。**后进先出** |
| **栈帧（Stack Frame）** | 一次方法调用压入一帧，保存参数、局部变量、返回地址。方法返回即弹出 |
| 存什么 | **值类型**（`int`/`bool`/`struct`）与**引用**（指向堆的地址） |
| 生命周期 | 与方法调用绑定，**不需要 GC** |

**为什么栈溢出是 `StackOverflowException` 且无法捕获**：栈是固定大小的，
挖穿了进程直接终止——没有恢复的余地。典型诱因是**无限递归**。

> 💡 **与 GC 的关系**：栈上放的都是"活着的引用"。**GC 标记阶段的起点就是所有线程的栈**
> （加上静态字段、GC 句柄等，统称 **root**）。见 §4.2。

### 3.2 托管堆与 LOH

```
                    托管堆（Managed Heap）
   ┌──────────────────────────────────────────────────────┐
   │  Gen0（小、新）  │  Gen1（缓冲）  │  Gen2（老、大）      │
   └──────────────────────────────────────────────────────┘
   ┌──────────────────────────────────────────────────────┐
   │  LOH 大对象堆（≥ 85,000 字节）                        │
   │  ⚠️ 默认**不压缩**，只做标记-清除 → 会产生碎片          │
   └──────────────────────────────────────────────────────┘
```

| 区域 | 放什么 | 回收成本 |
|---|---|---|
| **Gen0** | 新分配的小对象 | 极低（大部分对象在这里就死了） |
| **Gen1** | Gen0 幸存者，作为缓冲 | 低 |
| **Gen2** | 长期存活的对象 | **高**（全堆扫描，可能暂停较长） |
| **LOH** | **≥ 85,000 字节**的对象 | 高，且**默认不压缩** |

### 3.3 为什么阈值是 85,000 字节

这不是随便定的，也不是"内存页大小"（4KB）——它是**权衡后的经验值**：

| 考虑 | 说明 |
|---|---|
| 压缩大对象太贵 | 移动一个 10MB 的数组要**内存拷贝 10MB**，而移动 100 个小对象只拷贝几百字节 |
| 所以大对象**不参与压缩** | 代价是**碎片化**（见 §4.4） |
| 阈值越低 → 越多对象进 LOH | 碎片与 GC 压力上升 |
| 阈值越高 → 大数组占用 Gen0 | 复制成本上升 |

**结论**：85KB 是一个让"复制成本"与"碎片成本"平衡的经验值。

> 💡 **实践含义**：你的代码里凡是 `new byte[N]`、`new T[N]`，
> 只要 **N × 元素大小 ≥ 85,000**，就进 LOH。
> 常见的触发点：文件读写缓冲、图片/音视频、`MemoryStream.ToArray()`、大 JSON 字符串。

### 3.4 ★ 本项目真实的分配点

**下面全部来自实际代码**，不是假设。文件：`Blog.Infrastructure/Images/ImageSharpOptimizer.cs`

一次大图上传（`.png` / `.jpg`，≤ 10 MiB）会依次产生这些分配：

| # | 代码位置 | 分配 | 大小量级 | 落在哪 |
|---|---|---|---|---|
| 1 | `ReadAllAsync` → `buffer.ToArray()` | `byte[]` 原图 | 最大 **10 MiB** | ⚠️ **LOH** |
| 2 | 同上，`new MemoryStream()` 的内部缓冲 | `byte[]` | 同上量级 | LOH（>85KB 时） |
| 3 | `Image.Load(original)` | 解码后的**像素缓冲** | 见下 | ⚠️ **非托管**（由 `MemoryAllocator` 池化） |
| 4 | `image.Mutate(x => x.Resize(...))` | 缩放后的**新图** | 缩放后尺寸 | ⚠️ **非托管**；旧缓冲同期仍存活 |
| 5 | `new MemoryStream()` + `SaveAsWebpAsync` | WebP 输出缓冲 | 压缩后尺寸 | LOH（>85KB 时） |
| 6 | `output.ToArray()` | WebP 字节副本 | 同上 | ⚠️ **LOH** |

**第 3 项的大小**（这是大头）：

```
像素数 = 宽 × 高
内存   = 像素数 × 每像素字节数

本项目 MaxPixels = 40,000,000（防解压炸弹的上限）
默认像素格式 Rgba32 = 4 字节/像素

40,000,000 × 4 = 160,000,000 字节 ≈ 160 MB   ← 单张图
```

**关键事实：这 160MB 是「允许通过」的。** `MaxPixels` 只挡超过 4000 万像素的图，
4000 万及以下一律放行——而 4000 万像素解码出来就是 160MB。

> ⚠️ **`ResizeIfNeeded` 发生在整图解码之后**（先 `Image.Load`，再 `Mutate(Resize)`），
> 所以**缩放并不能减少峰值**——那 160MB 已经花掉了。
> 这是本项目最值得优化的一处，解决方案见 §8.2。

## 4. 垃圾回收：分代与算法

### 4.1 弱代假设（Weak Generational Hypothesis）

> **绝大多数对象都很年轻就死了。**

这一条经验规律是整个分代 GC 的基础。它带来一个巨大的优化：

| 做法 | 代价 |
|---|---|
| 每次都扫描整个堆 | 堆越大越慢 |
| ✅ **只扫描 Gen0**（新对象区） | 区域小 → 快。且大部分对象在这里就被回收，**根本不需要碰 Gen2** |

### 4.2 标记 → 清除 → 压缩

| 阶段 | 做什么 | 比喻 |
|---|---|---|
| **标记（Mark）** | 从 **root**（线程栈、静态字段、GC 句柄）出发，遍历所有可达对象并打标 | 从家门口出发，把能走到的房间都贴个条 |
| **清除（Sweep）** | 未打标的对象 = 垃圾，回收其内存 | 没贴条的房间清空 |
| **压缩（Compact）** | 把存活对象**挪到一起**，消除空洞，并修正所有引用 | 把家具搬到一起，腾出连续空间 |

**压缩的代价与收益**：

| | 收益 | 代价 |
|---|---|---|
| 压缩 | 消除碎片，分配更快（只需移动指针） | **要拷贝对象**，且要**修正所有指向它们的引用** |

因此：**Gen0/Gen1 总是压缩**（对象少，便宜）；**Gen2 视情况**；**LOH 默认不压缩**。

### 4.3 什么时候会触发 GC

| 触发条件 | 说明 |
|---|---|
| **Gen0 预算耗尽** | 最常见。分配累计到阈值就触发 |
| Gen1 预算耗尽 | 类似 |
| **Gen2 满 / 系统内存压力** | 完整 GC |
| `GC.Collect()` | ⚠️ **生产代码里几乎不该出现**，见 §10.6 |
| AppDomain 卸载等 | 罕见 |

> 💡 **本项目的一个真实诱因**：并发上传大图会**快速吃掉 Gen0 预算**，
> 同时产生大量 LOH 分配 → GC 频率上升 → `% Time in GC` 飙升。
> 这正是案例 B（§8.2）要测的东西。

### 4.4 ⚠️ LOH 的特殊性：默认不压缩 ⇒ 碎片

**这是 LOH 最重要的性质**，也是很多内存问题的根源：

```
   LOH（不压缩）
   ┌──────┬──────┬──────────┬────┬──────────────┐
   │ 存活 │ 垃圾 │  存活    │垃圾│    空闲      │
   └──────┴──────┴──────────┴────┴──────────────┘
      ↑ 清除后空洞仍在，无法合并

   现在要分配一个 20MB 的数组 → 虽然总空闲够，但没有 20MB 连续空间
                              → 触发一次完整 GC，甚至 OutOfMemoryException
```

| 现象 | 说明 |
|---|---|
| **内存不降反升** | LOH 上的空洞不会被归还，进程工作集看起来"只涨不跌" |
| **"明明有内存却 OOM"** | 碎片导致找不到连续空间 |
| 可用手段 | `GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce;` 请求**一次性压缩**（慎用，代价高） |

> **实践结论**：**减少 LOH 分配次数** 比"事后压缩"有效得多。
> 常用手法：**对象池**（`ArrayPool<T>.Shared`）、复用缓冲、避免无谓的 `ToArray()` 副本。

> 💡 **本项目的第 6 项分配**（`output.ToArray()`）就是典型的"可以避免的副本"。
> 如果下游能接受 `ReadOnlyMemory<byte>` 或直接用 `MemoryStream`，
> 就省掉一份完整拷贝。

## 5. GC 的工作模式

### 5.1 Workstation vs Server

| | **Workstation GC** | **Server GC** |
|---|---|---|
| 堆的数量 | **1 个** | **每个逻辑 CPU 一个** |
| GC 线程 | 1 个（或被抢占的线程） | 每核一个，**并行** |
| 吞吐 | 低 | **高** |
| **内存占用** | **低** | ⚠️ **高**（堆数 × 每堆开销 + 更大预算） |
| 默认用于 | 桌面 / 客户端应用 | **ASP.NET Core**（由 Web SDK 默认开启） |
| 适合 | 单核 / 小内存机器 | 多核、内存充足 |

**开关方式**：

| 方式 | 写法 |
|---|---|
| 环境变量 | `DOTNET_gcServer=1`（开）/ `=0`（关） |
| runtimeconfig | `"System.GC.Server": true` |
| csproj | `<ServerGarbageCollection>true</ServerGarbageCollection>` |

### 5.2 后台 GC（Background / Concurrent GC）

| 项 | 说明 |
|---|---|
| 配置 | `System.GC.Concurrent`（**默认 true**） |
| 作用 | **Gen2 回收在后台线程进行**，减少长时间暂停 |
| 代价 | 后台 GC 期间会**额外占用内存**（为了让应用继续分配） |

背景 GC 是为"**低延迟**"服务的：完整的 Gen2 暂停可能长达数百毫秒，
对 Web 服务是不可接受的。

### 5.3 ★ 本项目的 GC 配置现状

**已核实的事实**：`Blog.WebApi.runtimeconfig.json` 里是

```json
"System.GC.Server": true
```

**但整个解决方案的 csproj 里，没有任何一处写着 GC 相关配置**：

```bash
# 实际执行结果
$ grep -rn "ServerGarbageCollection\|ConcurrentGarbageCollection" Blog.Backend --include=*.csproj
（无任何 GC 相关配置）
```

**这说明两件事**：

| 事实 | 含义 |
|---|---|
| **Server GC 是 Web SDK 隐式给的默认值** | 你没有显式选择过它，它是"继承来的" |
| **项目里没有任何地方记录过这个事实** | 换台机器、换个部署方式，没人知道当前是什么模式 |

> ⚠️ **这就是一个值得调查的点**：**默认值不一定适合你的部署形态。**
> Server GC 在**多核大内存**上是优势，在**单核小内存 VPS**（个人博客的常见选择）上
> 可能因为堆数开销与更大的预算而**更差**。
>
> **这是一个只需改一个环境变量就能做完的对比实验**，见 §8.1。

## 6. 资源的确定性释放：终结器与 IDisposable

### 6.1 为什么需要终结器

GC 只管**托管内存**。但对象可能持有**非托管资源**：

| 资源 | 谁分配 |
|---|---|
| 文件句柄 | 操作系统 |
| 网络连接 / socket | 操作系统 |
| 非托管内存（`Marshal.AllocHGlobal`） | 你 |
| GDI / 图形资源 | 操作系统 |

**GC 不知道怎么释放这些。** 终结器（Finalizer）就是让对象在**被回收之前**
有机会执行清理代码——它是**最后一道安全网**。

### 6.2 ⚠️ 终结器的代价与陷阱

| 陷阱 | 说明 |
|---|---|
| **不可预测** | 终结器在**专用终结器线程**上运行，时机不确定。可能几秒后，也可能到进程退出才跑 |
| **对象会被"复活"一代** | 有终结器的对象第一次变成垃圾时**不会被真正回收**，而是扔进 **f-reachable 队列**等终结器执行。这意味着它会**被提升到下一代**，至少需要**两次 GC** 才真正释放 |
| **终结器线程会被阻塞** | 终结器里做耗时操作（如等网络），会**堵住整个终结器队列**，导致内存无法释放 |
| **顺序不确定** | 不能假设 A 的终结器先于 B 运行 |
| **异常会被吞** | 终结器里抛出的异常会终止终结器线程（.NET Core 中进程可能直接崩溃） |

> **结论：终结器是安全网，不是释放手段。** 正确做法永远是**主动 `Dispose()`**。

### 6.3 正确实现 IDisposable 的完整模板

```csharp
public sealed class ResourceHolder : IDisposable
{
    private IntPtr _native;              // 非托管资源
    private readonly Stream _stream;     // 托管但可释放的资源
    private bool _disposed;

    public void Dispose()
    {
        Dispose(disposing: true);
        GC.SuppressFinalize(this);   // ★ 关键：告诉 GC「不用再跑终结器了」
    }

    private void Dispose(bool disposing)
    {
        if (_disposed) return;
        _disposed = true;

        if (disposing)
        {
            _stream?.Dispose();      // 托管资源：只有显式 Dispose 时才动
        }

        // 非托管资源：无论走哪条路径都要释放
        if (_native != IntPtr.Zero)
        {
            Marshal.FreeHGlobal(_native);
            _native = IntPtr.Zero;
        }
    }

    ~ResourceHolder() => Dispose(disposing: false);   // 终结器兜底
}
```

**几个必须记住的点**：

| 点 | 为什么 |
|---|---|
| `Dispose(bool disposing)` 区分两条路径 | `disposing == false` 表示"终结器调用的"，此时**不能碰其他托管对象**（它们可能已被回收） |
| `GC.SuppressFinalize(this)` | 已经显式释放了，再跑一次终结器是纯浪费。**漏写它 = 对象被提升一代 + 终结器线程白跑** |
| `_disposed` 标志 | 让 `Dispose` **可重入**（多次调用安全） |
| **优先用 `SafeHandle`** | 它自己实现了完整的终结器逻辑，是官方推荐的封装非托管句柄的方式 |

> 💡 **现代 C# 的简化**：如果你的类**不持有非托管资源**（大多数情况），
> 就**不要写终结器**，只实现 `IDisposable` 即可。
> 无谓的终结器是纯负担。

### 6.4 ★ 本项目的资源释放审查

实际审计结果（`grep` 全后端源码，排除 `obj/`、`bin/`）：

**终结器**：整个后端**没有任何终结器**（无 `~TypeName()`）。

**`RedisCacheService` 值得单独表扬**：

```csharp
private readonly Lazy<ConnectionMultiplexer> _multiplexer;
// ...
public void Dispose()
{

        _multiplexer.Value.Dispose();
}
```

| 设计 | 为什么正确 |
|---|---|
| `Lazy<T>` 延迟连接 | 应用启动时不连 Redis；配合"Redis 故障自动降级"，**Redis 没起也不影响启动** |
| `IsValueCreated` 守卫 | 如果整个生命周期内没访问过 Redis，`Dispose` 不会去触发一次连接 |
| **Singleton 注册** | ⚠️ 这是关键。`ConnectionMultiplexer` **必须**是单例——它内部有连接池与后台线程。若注册成 Scoped，每个请求都会新建并释放一个多路复用器，**性能灾难** |

**一个可以改进的点（轻微）**：

| 项 | 现状 | 建议 |
|---|---|---|
| `UnitOfWork` 只实现 `IDisposable` | 事务是 `BeginTransactionAsync` 开的，提交时用的是 `_transaction.DisposeAsync()` | 可考虑同时实现 **`IAsyncDisposable`**，让异常路径也走异步释放，与 `CommitTransactionAsync` / `RollbackTransactionAsync` 保持一致 |

> 这**不是 bug**（同步 `Dispose` 事务在 Npgsql 上工作正常），
> 而是**一致性**问题。提出来是为了说明：**审查资源释放时要看"成对性"**——
> 异步创建的东西，是否也在异步路径上释放。

**`ImageSharpOptimizer` 的释放**：`using var image = Image.Load(original);` ✅
——**这一句是必须的**，因为官方文档明确写着 `Image` 持有非托管资源：

> "Image and Image<TPixel> own unmanaged resources. Always dispose them with using..."
> —— [SixLabors 官方内存管理文档](https://docs.sixlabors.com/articles/imagesharp/memorymanagement.html)

## 7. 诊断工具链

### 7.1 工具全景

| 工具 | 回答什么问题 | 产物 | 侵入性 |
|---|---|---|---|
| **`dotnet-counters`** | «现在的指标是多少» | 实时数字 | 极低 ✅ |
| **`dotnet-trace`** | «CPU/分配时间花在哪» | `.nettrace`（火焰图） | 低 |
| **`dotnet-gcdump`** | «堆上有什么类型的对象» | `.gcdump` | 中（会扰动） |
| **`dotnet-dump`** | «此刻的完整现场» | `.dmp`（可事后分析） | ⚠️ 高（会暂停进程） |
| **`dotnet-stack`** | «线程现在卡在哪» | 调用栈 | 低 |
| **BenchmarkDotNet** | «这段代码到底多快» | 微基准报告 | 无（独立进程） |
| **PerfView / VS 诊断工具** | 可视化分析 | GUI | — |

**使用顺序建议**：`counters` → `trace` → `gcdump` → `dump`。
**越往后越重，不要跳步。**

### 7.2 `dotnet-counters`：先看什么

**本项目已安装（但版本需要升级，见下）**：

```bash
# ⚠️ 当前版本 9.0.x，而项目是 .NET 10 —— 建议先升级
dotnet tool update -g dotnet-counters
dotnet tool update -g dotnet-trace
dotnet tool update -g dotnet-gcdump
dotnet tool update -g dotnet-dump
```

> ⚠️ **本项目实测到的版本差异**：机器上装的是 **9.0.661903**，
> 而被诊断的应用跑在 **.NET 10**。
> **诊断工具原则上应与目标运行时版本匹配或更新**，否则可能遇到
> 事件管道（EventPipe）不兼容、指标名缺失等问题。
> 排查工具"连不上/看不到指标"时，**先怀疑版本**。

**基本用法**：

```bash
# 1) 找到进程 Id
dotnet-counters ps

# 2) 监控（<pid> 换成实际值）
dotnet-counters monitor --process-id <pid> \
  --counters System.Runtime,Microsoft.AspNetCore.Hosting
```

**必须盯的指标**：

| 指标 | 含义 | 什么时候算异常 |
|---|---|---|
| `gc-heap-size` | **托管堆**总大小 | 持续增长不回落 |
| `loh-size` | **LOH** 大小 | 持续阶梯式增长 ⇒ LOH 泄漏或碎片 |
| `gen-0-gc-count` / `gen-1` / `gen-2` | 各代回收次数 | `gen-2-gc-count` 快速上升 ⇒ 有大量长命对象 |
| **`% Time in GC`** | GC 占总 CPU 时间的比例 | **> 10% 就该查，> 25% 是严重问题** |
| `alloc-rate` | 分配速率（B/s） | 异常高 ⇒ 有热路径在疯狂分配 |
| `working-set` / `private-bytes` | **进程**内存 | ⚠️ **非托管内存只能从这里看** |
| `threadpool-queue-length` | 线程池排队任务数 | 持续 > 0 ⇒ 线程池饥饿 |
| `exception-count` | 异常抛出次数 | 异常是**昂贵**的（见 §10.5） |
| `requests-per-second` / `failed-requests` | ASP.NET Core 请求指标 | 配合压测看 |

> ⚠️ **`System.Runtime` 里有一些指标名带空格**（如 `% Time in GC`），
> 在命令行里需要引号。不同版本的指标名略有差异，用 `dotnet-counters list` 查看当前可用项。

### 7.3 `dotnet-trace`：CPU 与分配火焰图

```bash
# 采集 30 秒
dotnet-trace collect --process-id <pid> --duration 00:00:30

# 指定采集提供程序（CPU 采样 / 分配采样）
dotnet-trace collect --process-id <pid> \
  --providers Microsoft-DotNETCore-SampleProfiler

# 转换成可在浏览器里看的格式
dotnet-trace convert --format speedscope <file>.nettrace
```

**看什么**：

| 视图 | 用途 |
|---|---|
| **调用树（Call Tree）** | 按耗时排序，直接找到最热的调用路径 |
| **火焰图（Flame Graph）** | 宽度 = 时间占比，一眼看出大头在哪 |
| **分配采样** | 哪个方法在疯狂分配对象（对应 `alloc-rate` 高） |

> 💡 **重要**：trace 会**捕获方法名**。所以**不要在生产环境随意采集**，
> 它可能泄露内部实现细节；同时采集本身有性能开销。

### 7.4 `dotnet-gcdump`：堆上有什么

```bash
dotnet-gcdump collect --process-id <pid>
# 产物 <name>.gcdump，用 Visual Studio 打开（双击即可）
```

**它能回答**：

| 问题 | 怎么看 |
|---|---|
| 哪些类型占内存最多 | 按 **Size** 排序的类型列表 |
| 对象在**哪一代** | Gen0 / Gen1 / Gen2 / LOH 的分组 |
| **LOH 上到底是什么** | 切到 LOH 视图 |
| 是不是泄漏 | **间隔一段时间采两次**，对比同一类型的数量增长 |

> ⚠️ **gcdump 会扰动运行时**（采集过程需要对堆做快照）。
> **不要在流量高峰采集**，也不要指望用它测"正常状态下的性能"。

**本项目用 `MemoryDiagnostics` 做辅助验证**（3.1.12 可用）：

```csharp
using SixLabors.ImageSharp.Diagnostics;
Console.WriteLine(MemoryDiagnostics.TotalUndisposedAllocationCount);
```

若这个值在稳定后**持续增长**，说明有 `Image` 没被 `Dispose`——
本项目用的是 `using var image = ...`，预期为 **0**。

### 7.5 `dotnet-dump`：抓现场，事后分析

```bash
# 抓完整 dump（进程会被暂停，写完才恢复）
dotnet-dump collect --process-id <pid> --type Full

# 进入交互式分析
dotnet-dump analyze <file>.dmp
```

**常用 SOS 命令**：

| 命令 | 作用 |
|---|---|
| `clrstack` | 当前线程托管调用栈 |
| `dumpheap -stat` | 按类型统计堆上对象（⭐ 最常用） |
| `dumpheap -mt <MT> -min 85000` | 看某个类型的**大对象** |
| `gcroot <address>` | ⭐ **谁在引用这个对象**（找泄漏根源的关键） |
| `eeheap -gc` | 各代与 LOH 的地址范围 |
| `syncblk` | 锁与死锁信息 |
| `printexception` | 查看异常对象 |

> 💡 **`gcroot` 是找内存泄漏的杀手锏**：
> 先 `dumpheap -stat` 找到异常的大的类型，再用 `dumpheap -mt <方法表>` 拿地址，
> 最后 `gcroot <地址>` 一路回溯到 root——**就知道是谁没放手**。

### 7.6 BenchmarkDotNet：微基准

**别用 `Stopwatch` 测性能。** JIT 预热、GC、CPU 频率、死代码消除都会让结果失真。
BenchmarkDotNet 帮你处理了这些：

```csharp
[MemoryDiagnoser]          // ★ 顺带报告「分配了多少字节」与 Gen0/1/2 次数
public class SummaryBenchmark
{
    private const string Content = "...长正文...";

    [Benchmark]
    public string BuildAutoSummary() => /* 被测方法 */;
}
```

| 特性 | 价值 |
|---|---|
| **自动预热** | 排除 JIT 与缓存冷启动的影响 |
| **多次迭代 + 统计** | 给出误差范围，而不是一个孤零零的数字 |
| **`[MemoryDiagnoser]`** | ⭐ 报告 **Allocated** 与 **Gen0/1/2 次数**——直接看分配 |
| **防止死代码消除** | 保证被测代码真的跑了 |

**适合本项目的微基准候选**：

| 候选 | 为什么值得测 |
|---|---|
| `Post.BuildAutoSummary` | 每次创建/更新文章都跑，且**每次分配一个新字符串** |
| `Pbkdf2PasswordHasher.Hash / Verify` | 迭代次数是**刻意的 CPU 成本**，需要知道具体多少 ms |
| `CacheKeys.PostList` | 每次列表请求都要拼字符串 + 可能算 SHA256 |
| `ImageSharpOptimizer` 的 WebP 编码 | 已知是最重的操作，量化它 |

> ⚠️ **BenchmarkDotNet 必须在 Release 下运行**，否则数据没有意义。

### 8.2 案例 B：图片上传链路的内存峰值（最贴"内存分析"）

| 项 | 内容 |
|---|---|
| **现象** | 并发上传大图时进程内存飙升，可能出现 OOM 或被容器 OOM Killer 杀掉 |
| **假设** | ① 单张 4000 万像素图的像素缓冲 ≈ **160MB**（推算）；② 这些缓冲在**非托管内存**里，**GC 计数器看不到**；③ 并发 N 路时峰值 ≈ N × (160MB + 其他缓冲) |
| **怎么测** | 用压测工具**并发上传**不同尺寸的图；同时监控 `loh-size`（应该平稳）与 `working-set`（应该飙升） |
| **关键验证点** | **确认像素内存在托管还是非托管**——这决定了后续所有分析方向 |

**⚠️ 这一步是本案的核心，也是最容易搞错的地方**：

| 观察结果 | 结论 |
|---|---|
| `loh-size` 飙升 | 像素在**托管 LOH** → 走 §3.3/§4.4 的 LOH 分析路径 |
| `loh-size` **平稳**，`working-set` 飙升 | 像素在**非托管** → 走 §2.3 的非托管分析路径，**GC 调优无用** |

**依据（已核实）**：ImageSharp 官方文档明确写着
[`Configuration.MemoryAllocator`](https://docs.sixlabors.com/api/ImageSharp/SixLabors.ImageSharp.Configuration.html)
默认使用**池化分配器**，且 `Image` 持有**非托管资源**。
因此**大概率是第二种**——但这必须**实测确认**，不能照搬文档结论。

**已核实的可用优化手段**（针对 ImageSharp **3.1.12**，逐条查过本地包的 XML 文档）：

| 手段 | 3.1.12 可用？ | 作用 |
|---|---|---|
| **`DecoderOptions.TargetSize`** | ✅ **可用** | ⭐ **在解码阶段就缩到目标尺寸**，避免"先解 160MB 再缩小" |
| `DecoderOptions.MaxFrames` | ✅ 可用 | 限制帧数，防多帧图爆内存 |
| `DecoderOptions.SkipMetadata` | ✅ 可用 | 跳过元数据，略省内存与时间 |
| `MemoryAllocatorOptions.MaximumPoolSizeMegabytes` | ✅ 可用 | **限制池保留的内存上限** |
| `MemoryAllocatorOptions.AllocationLimitMegabytes` | ✅ 可用 | 限制单次分配组的上限 |
| `Configuration.MemoryAllocator` | ✅ 可用 | 替换为自定义分配器 |
| `MemoryDiagnostics.TotalUndisposedAllocationCount` | ✅ 可用 | 检测未释放的 `Image` |
| `ImageInfo.GetPixelMemorySize()` | ❌ **3.1.12 没有**（v4 才有） | 用 `Width × Height × 4` 自行估算 |
| `MemoryAllocatorOptions.AccumulativeAllocationLimitMegabytes` | ❌ **3.1.12 没有**（v4 才有） | — |

> ⚠️ **不要照搬官方文档站的 API**。`docs.sixlabors.com` 是**最新版（v4）**的文档，
> 而本项目因许可原因**锁定 3.1.12**。上面这张表是我**读本地 NuGet 包里的
> `SixLabors.ImageSharp.xml`** 得到的，才是这个版本的确切事实。
>
> **通用教训**：锁定依赖版本的项目，**查 API 要查对应版本的文档**，
> 或者直接读包里的 XML/反编译。照搬最新版文档会写出编译不过的代码。

**候选修法**（按预期收益排序，**都需先测再改**）：

| # | 修法 | 预期效果 | 风险 |
|---|---|---|---|
| 1 | 用 `DecoderOptions.TargetSize` 在解码时缩放 | ⭐ 最大。峰值像素内存按 `(目标/原始)²` 下降 | 需验证各格式的支持情况（现有测试工程可加用例） |
| 2 | 收紧 `MaxPixels`（如 4000 万 → 1200 万） | 直接砍掉最坏情况 | 会拒绝一些合法大图，需权衡 |
| 3 | 给 `MemoryAllocator` 设 `MaximumPoolSizeMegabytes` | 限制池**保留**内存，防止只涨不跌 | 池太小会降低复用率，可能变慢 |

### 8.3 案例 C：浏览量自增的行锁热点

| 项 | 内容 |
|---|---|
| **现象** | 未知（待验证） |
| **假设** | `PostRepository.IncrementViewCountAsync` 用 `ExecuteUpdateAsync` 对**同一行**高频 UPDATE。PostgreSQL 的 UPDATE 会加**行级排他锁**，导致热门文章的并发访问在这里**串行化**；同时产生大量**死元组**，加重 autovacuum 负担（即"计数器列反模式"） |

## 9. 症状 → 根因对照表

| 症状 | 优先怀疑 | 怎么确认 |
|---|---|---|
| **`% Time in GC` 很高，CPU 打满** | 分配速率过高 | 看 `alloc-rate`；用 trace 的分配视图找热点方法 |
| **`gen-2-gc-count` 快速上升** | 大量对象晋升到 Gen2 | `gcdump` 看 Gen2 里是什么类型 |
| **`loh-size` 阶梯式增长不降** | LOH 泄漏或碎片 | `gcdump` 看 LOH 的类型分布；间隔采样对比 |
| **`loh-size` 平稳，但进程内存飙升** | ⚠️ **非托管内存**（本项目 §8.2 的情形） | 看 `working-set` / `private-bytes`；排查图像/原生库 |
| **内存"只涨不跌"但不 OOM** | LOH 碎片 / 池保留内存 | 属正常现象。看是否**持续**增长；对比 `GC.GetTotalMemory` |
| **`OutOfMemoryException` 但系统还有内存** | 进程位宽（32 位）或**碎片** | 确认 64 位；`eeheap -gc` 看碎片 |
| **`threadpool-queue-length` 持续 > 0** | 线程池饥饿（同步阻塞异步） | 找 `.Result` / `.Wait()`；对照 §15.9 的"同步 getter 查库"反例 |
| **`exception-count` 异常高** | 用异常做流程控制 | 异常会**捕获堆栈**，成本高。改 `TryXxx` 模式 |
| **响应时间周期性抖动** | 完整 GC / 后台 GC | `counters` 看 gen2 次数与时间是否吻合 |
| **`MemoryDiagnostics.TotalUndisposedAllocationCount` 增长** | `Image` 未 `Dispose` | 定位缺少 `using` 的地方 |

## 10. ⚠️ 坑清单

### 10.1 在 Debug 下测量

**Debug 构建没有开优化**，代码更慢、内联被禁用、临时变量可能不被消除。
用它测出来的数字**不能代表生产**。

> ✅ **规则**：所有基准与压测**必须用 Release**。

### 10.2 观察者效应

**采集本身会改变被观测对象**：

| 工具 | 影响 |
|---|---|
| `dotnet-counters` | 很小，可长时间开 |
| `dotnet-trace` | 有开销，CPU 采样会略微降速 |
| `dotnet-gcdump` | 需要遍历堆，**明显扰动** |
| `dotnet-dump` | **暂停整个进程**（可能数秒），写文件期间服务不可用 |

> ⚠️ **`dotnet-dump` 绝不要在生产的高峰期执行。** 它会让进程停住。

### 10.3 ⚠️ Server GC 在小内存机器上可能更差

这是**反直觉但对本项目很重要**的一条：

| 场景 | Server GC | Workstation GC |
|---|---|---|
| 8 核 16GB | ✅ 吞吐明显更好 | 一般 |
| **1~2 核 1~2GB VPS** | ⚠️ **堆数与预算开销可能拖垮它** | ✅ 往往更合适 |

而本项目**没有显式配置过 GC**——它继承的是 Web SDK 的默认值（Server）。
**默认值是按"典型服务器"设计的，不是按"最便宜的 VPS"设计的。**

→ 这就是案例 A（§8.1）要回答的问题。

### 10.4 LOH 不压缩 ⇒ 碎片

见 §4.4。**减少 LOH 分配 > 事后压缩。**

### 10.5 异常是昂贵的

抛异常不只是"控制流跳转"，运行时会：

| 动作 | 成本 |
|---|---|
| 捕获并构造**堆栈跟踪** | 很贵（要遍历栈帧并查符号） |
| 可能分配多个对象 | 增加 GC 压力 |

> 💡 **本项目有 4 处用对了异常过滤器**（`catch (X) when (...)`）：
> `RedisCacheService`（2 处）、`RateLimitingMiddleware`、`Program.cs` 的顶层兜底。
> 过滤器在**栈展开之前**执行，不匹配时**不展开堆栈**——比"先捕获再 `if` 判断"更便宜。
>
> ⚠️ **但本项目也有一处刻意的反例**：`ImageSharpOptimizer.OptimizeAsync` 用的是
> **裸 `catch (Exception ex)`**。这是**有意的**（注释写明「优化失败绝不能导致上传失败，
> 所以返回原图而不是抛异常」），设计上完全合理。
>
> **但它带来一个排查隐患**：它会吞掉**所有**异常类型——包括
> `OutOfMemoryException` 这类本不该被静默处理的。真出内存问题时，
> 表现是「图片偶尔没被转换」，日志里只有一句 `WRN`，**很容易被忽略**。
> 这正是案例 B（§8.2）要特别留意的地方：**先把日志级别和内容确认清楚，再开始压测。**

### 10.6 `GC.Collect()` 几乎总是错的

| 为什么不该调 | |
|---|---|
| 打断 GC 自己的节奏 | GC 比你更了解什么时候该收 |
| 通常是**完整 GC** | 可能造成数百毫秒暂停 |
| 只解决症状 | 真有泄漏，调它也没用 |

**唯一合理的场景**：性能测试的**两次测量之间**，用于把环境拉回已知状态
（且要明确记录这一行为，否则数据不可比）。

### 10.7 ⚠️ 文档站版本与锁定版本不一致

**写这篇文档时亲身踩到**：`docs.sixlabors.com` 是 **v4** 文档，
而本项目因许可原因**锁定 3.1.12**。照搬 v4 文档会用到 3.1.12 里**不存在**的 API
（如 `ImageInfo.GetPixelMemorySize()`、`MemoryAllocatorOptions.AccumulativeAllocationLimitMegabytes`）。

**正确做法**（按可靠性排序）：

| 优先级 | 方法 |
|---|---|
| 1 | 读 **NuGet 包里的 `.xml` 文档**（`~/.nuget/packages/<包>/<版本>/lib/**/*.xml`）—— 这就是该版本的确切 API |
| 2 | 用 IDE 的 IntelliSense（会按实际引用的版本提示） |
| 3 | 找**带版本号**的文档站（如 `docs-v3.sixlabors.com`） |
| 4 | ❌ 不要直接照搬最新版文档 |

### 10.8 `dotnet-counters` 的指标名会变

不同版本的 `System.Runtime` 提供程序，指标名与数量都有差异
（例如 `% Time in GC` 这类名字带空格/百分号的指标）。

**遇到"指标不存在"，先 `dotnet-counters list` 看当前版本有什么**，别照着旧文章抄。

## 11. 学习路径与动手顺序

| 阶段 | 做什么 | 完成判据 |
|---|---|---|
| **D0** | 升级诊断工具到与 .NET 10 匹配的版本 | `dotnet-counters --version` 与运行时不脱节 |
| **D1** | 服务跑起来，挂上 `dotnet-counters` 看 5 分钟 | 能说出当前 `gc-heap-size` / `% Time in GC` 的量级 |
| **D2** | 做**案例 A**（GC 模式对比） | 一张两组对比表 + 一个明确结论 |
| **D3** | 用 `dotnet-gcdump` 采两次，对比类型分布 | 能指出堆上占用最大的 3 个类型 |
| **D4** | 造大图，做**案例 B** 的第一步：**确认像素内存在托管还是非托管** | ⭐ 一个明确的"是/否"结论 |
| **D5** | 用 `dotnet-trace` 抓一次上传过程的火焰图 | 能指出内存/CPU 的时间大头 |
| **D6** | 跑通一个 BenchmarkDotNet 微基准 | 一份带 `Allocated` 列的报告 |
| **D7** | 抓一次 `dotnet-dump`，用 `dumpheap -stat` + `gcroot` 找引用链 | 能完整走通一次"找泄漏根源" |
| **D8** | 选 C 或 D，做完一个完整闭环 | 现象→假设→测量→结论，有数据 |

> ⚠️ **D4 是整个路径的支点**。
> 它决定后面的分析是走"GC 调优"还是"非托管内存管理"——
> **方向错了，后面全白做**。这也正是 §2.1 第一条纪律（先测量再下结论）的意义。
