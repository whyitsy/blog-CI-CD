## 1. 项目定位

**多作者技术博客平台**，前后端分离（Vue3 SPA + ASP.NET Core REST API）。

| 维度 | 内容 |
|---|---|
| 内容载体 | Markdown 文章，前端渲染 + DOMPurify 消毒 |
| 作者规模 | **多作者**，每篇文章归属一个署名作者 |
| 内容组织 | 分类（单值）+ 标签（多值）+ **专栏（多对多系列，带专栏内排序）** |
| 账号体系 | `User`（登录账号）与 `Author`（内容署名）**分离** |
| 评论 | 外挂 giscus（GitHub Discussions），本站**不存评论数据** |
| 面向角色 | 匿名访客 / Author（作者）/ Admin（管理员） |

### 1.1 两个塑造了整个设计的定位变化

**变化一：从「单作者博客」改为「多作者博客」。** 一个改动带来一连串连锁需求：
文章归属需要越权校验、草稿需要权限保护、作者需要可增删改、内容需要专栏来组织。
早期的"单人博客"隐含前提已全部作废。

**变化二：`User` 与 `Author` 分离。** 直觉上"作者"就该是登录账号，但本项目把两者拆开：
**`User` 是账号**（承载登录凭据、角色、启用状态）；
**`Author` 是内容属性**（只承载署名信息：姓名、头像、简介，与 Post/Tag/Category 同层）。
好处是**可以存在没有账号的作者**（例如只挂名的合作者），也可以让一个账号更换署名身份。
两者通过 `User.AuthorId` 弱关联（可空），作者被删时账号仍能登录（`SetNull`）。

> ⚠️ 这个分离导致一条**必须记住的规则**：判断"谁能改这篇文章"时，
> **只认 `Post.CreatedByUserId`（账号维度），绝不能认 `AuthorId`**。
> 多个账号可以关联同一个 Author，用 AuthorId 判断会造成互相越权。

## 2. 角色、权限边界与内容组织

只有两档角色，**刻意不引入细粒度 RBAC**：角色多一分，测试成本就多一倍，而本项目只有两类真实用户。

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| **匿名访客** | 浏览首页/文章/标签/分类/归档/专栏、搜索、评论（经 giscus） | 看到草稿、进入任何管理界面 |
| **Author（作者）** | 撰写并管理**自己的**文章（草稿/发布/下架/删除）、维护**自己的**署名资料 | 改他人文章、动分类/标签/专栏/账号/站点配置 |
| **Admin（管理员）** | 全部内容的增删改、账号管理、作者管理、专栏管理、站点配置 | — |

后端用两个授权策略表达（`Program.cs`）：

| 策略 | 要求 | 用在 |
|---|---|---|
| `AdminOnly` | 角色 = `Admin` | 账号管理、作者增删、分类/标签/专栏写接口、站点配置写接口 |
| `ContentWriter` | 角色 ∈ {`Admin`, `Author`} | 文章增删改、发布、只读详情、作者资料更新、`/api/authors/me` |

> **登录入口是合一的**：管理员与作者**共用同一个登录接口** `POST /api/auth/login` 与同一个登录页 `/login`。
> 登录入口不承担权限边界——它只负责发 token，权限由具体接口上的策略强制。

三层界面（公开站点 `/`、作者工作区 `/me/**`、管理后台 `/admin/**`）各自包含哪些页面与路由，
见 [04-前端设计.md](./04-前端设计.md)；端点的权限标记逐个列在 [03-API参考.md](./03-API参考.md)。

### 2.1 内容组织维度：分类 / 标签 / 专栏

| 概念 | 维度 | 与文章的关系 | 说明 |
|---|---|---|---|
| **分类 Category** | 广度、单值 | 一篇文章最多 1 个分类 | 像书架的层 |
| **标签 Tag** | 广度、多值 | 一篇文章可打多个标签 | 像关键词 |
| **专栏 Collection** | 深度、系列 | 一篇文章可属于多个专栏，且有**专栏内排序** | 像连载目录 |
| **作者 Author** | 署名 | 一篇文章最多 1 个署名 | 内容属性，非账号 |

**分类 vs 专栏是最容易混淆的一对**：分类回答"这篇文章属于哪个领域"，专栏回答"这篇文章在一个
阅读序列里排第几"——后者带 `SortOrder`，顺序**人为编排**，不能按发布时间推导。

> **代码里的 `taxonomy` 是什么**：它不是一张表，而是代码里对「分类 / 标签 / 专栏这一组
> 内容组织维度」的统称（缓存前缀 `blog:taxonomy:`、共用查询仓储 `TaxonomyQueryRepository`、
> 管理页 `TaxonomyManager.vue`）。⚠️ 其中 **Collection 是"半加入"的**：它在缓存键与
> 骨架屏上算作 taxonomy，但在领域模型与仓储上是独立的（`ICollectionRepository` /
> `CollectionQueryRepository`）——因为它比分类/标签复杂得多（有 `Slug`、`SortOrder`、
> 发布状态、多对多文章编排）。

### 2.2 文章生命周期

```
创建 ──publish=false──► 草稿(PublishedAt=null) ──发布──► 已发布(PublishedAt=时间) ──下架──► 草稿
                                                              │
                                              软删除(IsDeleted=true) ◄── 删除（列表与详情均不可见，数据保留）
```

关键规则：**是否发布**由 `PublishedAt` 是否有值决定（`IsPublished` 是计算属性，
**不入库、无对应列**）；**发布幂等**（重复发布不覆盖首次发布时间，否则归档排序会被打乱）；
**草稿保护**（`includeUnpublished=true` 需登录，且 Author 只能看到自己创建的）；
**删除是软删除**（置 `IsDeleted` + `DeletedAt`，由全局查询过滤器自动排除）。

## 3. 解决方案结构与分层

```
Blog.Backend/  (Blog.Backend.slnx + dotnet-tools.json)
├─ Blog.Domain/          实体 + 仓储接口（零框架依赖）
│   ├─ Entities/         Post / Author / Category / Tag / Collection / User / SiteConfig / SocialLink
│   │   └─ Base/         BaseEntity（公共字段 + 乐观锁 Version）
│   └─ IRepository/      8 个写侧仓储接口
├─ Blog.Application/     用例编排 + DTO + 横切接口
│   ├─ Common/           ApiResponse / PagedResult / ErrorCodes / BusinessException / MediaPath / FieldLimits
│   ├─ Interfaces/       缓存 / 限流 / 文件 / 安全接口 + Options 类 + CacheKeys
│   ├─ Services/         Auth（含 `UserService`）/ Author / Category / Collection / Post / Site / Tag
│   └─ DependencyInjection.cs
├─ Blog.Infrastructure/  外部世界的实现
│   ├─ Persistence/      BlogDbContext + 迁移 + 仓储实现 + 拦截器
│   ├─ Caching/ RateLimiting/    Null / Memory / Redis 三实现 · Redis Lua + 内存令牌桶
│   ├─ Files/ Images/    本地文件存储 · ImageSharp WebP 优化
│   └─ Security/         JWT / PBKDF2 / 当前用户解析 / 部署校验 · DependencyInjection.cs
├─ Blog.WebApi/          HTTP 入口：Controllers（9 个）· Middleware · HealthChecks · Program.cs · appsettings*.json
└─ Blog.Tests/           xUnit 单元测试 + 集成测试
```

### 3.1 依赖方向（不可违反）

```
Blog.WebApi ──► Blog.Application ──► Blog.Domain
     │                 ▲                  ▲
     └──► Blog.Infrastructure ────────────┘
```

| 层 | 职责 | 硬性约束 | 为什么 |
|---|---|---|---|
| **Blog.Domain** | 实体、值对象、写侧仓储接口 | **零外部依赖**（连 Npgsql 类型都不允许出现） | 领域模型不被框架污染，可独立测试与演进 |
| **Blog.Application** | 用例编排（Service）、DTO、横切接口定义、统一响应 | 不依赖 Infrastructure；不直接依赖 EF Core | 用例逻辑与持久化技术解耦，仓储以接口注入 |
| **Blog.Infrastructure** | EF Core 映射与仓储、缓存/限流/文件/安全的实现 | **只实现** Application 定义的接口 | 依赖倒置：外层依赖内层定义的抽象 |
| **Blog.WebApi** | HTTP 入口、控制器、中间件、DI 组合根 | 不含业务逻辑，只做参数绑定与调用 | 业务规则集中在 Application，不随协议扩散 |

`Blog.Domain` 的"零框架依赖"是最容易被破坏、也最值得守住的一条约束：Post 的 `SearchVector`
是 `NpgsqlTsVector` 类型，**不能出现在 Domain 实体上**，只能在 Infrastructure 里声明为
**影子属性**（`BlogDbContext.cs:106`）。详见 §9.2。

## 4. 统一响应体与异常

### 4.1 响应体

所有接口（含错误）统一返回 `{ "code": 0, "message": "ok", "data": { } }`：

- `code = 0` 表示成功，其余为业务错误码（对照表见 [03-API参考.md](./03-API参考.md) §1.2）
- HTTP 状态码**同时**被设置成语义正确的值（401/403/404/409/413/429），不只是 200
- 序列化用 `JsonSerializerDefaults.Web`，即 **camelCase**；
  `ApiResponse` / `ApiResponse<T>` 定义在 `Blog.Application/Common/ApiResponse.cs`

> ⚠️ **"所有接口都返回统一体"这句话，是 P0（提交 `76cc0d7`）之后才真正成立的。**
>
> 在此之前它**不成立**：`[ApiController]` 会在 Action 执行**之前**做模型校验，
> 失败时短路返回 400，默认输出 RFC 7807 **ProblemDetails**（`{type,title,status,errors,traceId}`），
> 与 `{code,message,data}` 是**两套结构**。实测缺口（`GET /api/posts/search` 不带 `keyword`）：
> 响应体是 `{"type":"…rfc9110#section-15.5.1","title":"One or more validation errors occurred.","status":400,…}`。
>
> 后果不是"不好看"，而是调用方必须写两套解析逻辑：前端拦截器按 `{code,message}` 处理，
> 一旦某次请求在校验阶段就被拦下，它拿到的是 `{title,errors}`，用户看到的就是空白或 `undefined`。
>
> 现在由 `ApiBehaviorOptions.InvalidModelStateResponseFactory` 接管（`Program.cs:57-75`），
> 把模型校验失败也构造成 `ApiResponse.Fail(4001, ...)`，于是统一响应体
> 从**多数情况成立**变成**无条件成立**。端点契约见 [03-API参考.md](./03-API参考.md)。

### 4.2 异常 → 响应

`ExceptionHandlingMiddleware` 是唯一的异常出口：

| 异常 | HTTP | code | 说明 |
|---|---|---|---|
| `BusinessException` | 由 code 映射（见 [03-API参考.md](./03-API参考.md) §1.2） | 异常自带 | 可预期的业务失败 |
| `DbUpdateConcurrencyException` | 409 | 4090 | 乐观锁冲突，统一文案"数据已被其他请求修改，请刷新后重试" |
| `DbUpdateException` 且内层是 PG `22001` | 400 | 4001 | **字段超长兜底**：Application 层的 `FieldLimits` 应当先拦下，万一漏了也不给用户看"服务器内部错误"。记 WARNING，让"漏了校验"在日志里可见 |
| 其他 `Exception` | 500 | 5000 | 记 ERR 级日志（含堆栈），对外只回"服务器内部错误" |

业务异常全部用 `BusinessException` 抛出，**不在控制器里写 try/catch**：

```csharp
throw new BusinessException("文章不存在", ErrorCodes.NotFound);
```

> **上传接口的错误也走异常**：`return ApiResponse.Fail(...)` 会得到 **HTTP 200**、
> 只有 body 里的 `code` 是错误码，于是"参数不合法"在上传接口是 200、在别处是 400。
> 现在统一为 400/413（§13.2）。

### 4.3 错误码表

错误码共 **11 个**（含成功），定义在 `Blog.Application/Common/ErrorCodes.cs`。
code ↔ HTTP ↔ 典型场景的对照表、以及映射规则（`ExceptionHandlingMiddleware.MapStatusCode`，
未列出的业务码一律落 **400**）见 [03-API参考.md](./03-API参考.md) §1.2 —— 那里是唯一权威清单。

### 4.4 JWT 的 401/403 也走统一响应体

`Program.cs` 为 `JwtBearerEvents.OnChallenge` / `OnForbidden` 注册了处理器（`Program.cs:116-139`），
让认证/授权失败也返回 `{code:4010/4030, ...}`，而不是 ASP.NET Core 默认的**空响应体**
（否则前端解析 JSON 会失败，只能靠状态码硬编码兜底）。
`OnChallenge` 对应 **401**（认证阶段：没带/无效/过期 token）；
`OnForbidden` 对应 **403**（授权阶段：token 有效但角色或权限不足）。

## 5. 实体模型

### 5.1 BaseEntity（公共字段）

`Blog.Domain/Entities/Base/BaseEntity.cs`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `Id` | `Guid` | 主键，`init` 只读 |
| `CreatedAt` | `DateTimeOffset` | 创建时间（带时区） |
| `IsDeleted` | `bool` | 软删除标记 |
| `DeletedAt` | `DateTimeOffset?` | 删除时间 |
| `Version` | `int` | **乐观锁版本号**，从 1 开始，`protected set` |

`Delete()` 方法只打标记（`IsDeleted = true; DeletedAt = now`），不提交——
由调用方通过 UnitOfWork 统一保存。

> ⚠️ **"所有实体继承 BaseEntity"是错的。** 准确的说法是：
> **除 `PostCollection` 外的业务实体都继承 `BaseEntity`**。
> `PostCollection`（`Blog.Domain/Entities/Collection.cs:62`）是纯连接实体，只有
> `PostId` / `CollectionId` / `SortOrder` + 两个导航属性，**没有 `Id`、`CreatedAt`、
> `IsDeleted`、`DeletedAt`、`Version`**，也没有全局查询过滤器——它随文章/专栏级联删除。
>
> 这触发一条 EF Core 警告：`Collection` 带查询过滤器而 `PostCollection` 是必需端，
> EF 提示"必需端被过滤可能导致意外结果"。项目**从不单独查询 PostCollection**
> （始终经 Post/Collection 导航访问），因此在 `BlogDbContext.OnConfiguring`
> （`BlogDbContext.cs:57-64`）里显式抑制了它。

### 5.2 实体一览

| 实体（表） | 继承 `BaseEntity` | 职责 |
|---|---|---|
| `Post`（`Posts`） | ✅ | 文章 |
| `Author`（`Authors`） | ✅ | **署名**作者（不是登录账号） |
| `Category`（`Categories`） | ✅ | 分类（单值） |
| `Tag`（`Tags`） | ✅ | 标签（多值） |
| `Collection`（`Collections`） | ✅ | 专栏 |
| `PostCollection`（`PostCollections`） | ❌ | 文章 ↔ 专栏 **显式**连接实体（带排序） |
| `User`（`Users`） | ✅ | 登录账号（凭据 + 角色） |
| `SiteConfig`（`SiteConfigs`） | ✅ | 站点配置（Key-Value） |
| `SocialLink`（`SocialLinks`） | ✅ | 社交链接 |

`PostTag` **没有对应的 C# 实体**——它是 EF Core 隐式多对多生成的纯连接表。

### 5.3 User（账号）

`Email`：登录邮箱，唯一（**过滤唯一索引**，软删除后允许复用同一邮箱）。
`PasswordHash`：PBKDF2 哈希，格式 `pbkdf2-sha512$迭代次数$base64盐$base64哈希`。
`Role`：`UserRole` 枚举（`Author = 0` / `Admin = 1`），**以字符串存库**。
`IsActive`：是否启用，禁用后不能登录。`AuthorId`：关联的署名对象，可空。
`LastLoginAt`：最近登录时间（审计）。`TokenVersion`：Token 版本号，见 §10.3。

行为方法：`UpdateProfile(role, authorId, isActive)` 改角色/关联/启停但**不动凭据**；
`ResetPassword(hash)` 改密码并 `TokenVersion++`；`SetActive(bool)` 值未变直接返回、
停用时 `TokenVersion++`（立即踢下线）；`LogoutAllDevices()` 也是 `TokenVersion++`；
`MarkLoggedIn()` 记录登录时间。

> `TokenVersion` 的"只在失效场景自增"这个设计很关键：正常改资料不会踢人下线，
> 只有改密码 / 停用 / 主动注销才会。

### 5.4 Author / Category / Tag

| 实体 | 字段 | 备注 |
|---|---|---|
| `Author` | `Name` / `Email` / `Avatar` / `Bio` + `Posts` 导航 | `Email` 是**展示用联系方式**，与 `Users.Email`（登录邮箱）**不是一回事** |
| `Category` | `Name` + `Posts` 导航 | 自带过滤唯一索引，软删除后可重建同名分类 |
| `Tag` | `Name` + `Posts` 导航 | 同上；`Name` 上限 **50**（比 Category 的 100 更短） |

分类与标签结构几乎相同，分开建表而不是合并成"术语表"，是因为二者的业务语义与
UI 呈现完全不同（分类是单值、实心徽章；标签是多值、细边框徽章），未来演进方向也不同。

### 5.5 Post（文章）

字段清单与列定义见 §6.4（实体属性与数据库列一一对应）。要点：
`Summary` 为空时由实体自动截取正文前 **50** 字；`PublishedAt` 是否有值决定是否发布
（`IsPublished` 是**计算属性**，不入库）；`ViewCount` 走原子自增（§8.5）；
`CoverImage` 必须过媒体白名单（§10.6）。

行为方法：`Update(...)` 更新内容，摘要规则是**空则重新自动截取、非空则用传入值**
（因此作者手写的摘要不会被覆盖）；`Publish()` 幂等（`PublishedAt ??= now`，
重复发布不覆盖首次发布时间，否则归档排序会被打乱）；`Unpublish()` 置空 `PublishedAt`。

> **摘要为什么不额外加"是否自动"字段**：用"传入是否为空"来区分即可。
> 作者想保留自动摘要就传空，想固定就填内容。少一个字段，少一类状态不一致。
>
> ⚠️ **这条规则的边界**："填了就不再被自动覆盖"的前提是**客户端每次都把摘要原样回传**。
> 而编辑器会把当前摘要回填到输入框，于是**一次保存之后，原本自动生成的摘要就被"固定"下来了**——
> 之后再改正文，摘要不再跟着变。这是已知行为而非缺陷，记录见 [06-技术债与待办.md](./06-技术债与待办.md)。

### 5.6 Collection 与 PostCollection

`Collection` 的字段：`Title` / `Slug` / `Description` / `CoverImage`（`Slug` 唯一，
用于 `/collections/{slug}`）、`SortOrder`（**专栏之间**的排序）、`IsPublished`
（未发布的专栏对匿名表现为**不存在**，即 404）、`PostLinks` 导航。

`PostCollection` 是**显式连接实体**（而不是 EF 隐式多对多），因为它要携带
`SortOrder`——专栏内的文章顺序是人为编排的，不是按发布时间。

> ⚠️ **多对多连接行必踩的坑**：`BaseRepository.GetByIdAsync` **不加载导航集合**，直接改
> `collection.PostLinks` 会让 EF 把已存在的连接行当成新增 INSERT，报
> `23505 duplicate key ... PK_PostCollections`（表现为"保存必 500"）。必须用
> `ICollectionRepository.GetWithPostsAsync`（内部 `Include(c => c.PostLinks)`）。
> 文章标签同理，必须**增量同步**。两条坑的完整排查过程见
> [archive/问题排查记录.md](../archive/问题排查记录.md)，连接表定义见 §6.7。

### 5.7 SiteConfig 与 SocialLink

| `SiteConfigKeys` 键 | 值格式 | 说明 |
|---|---|---|
| `SiteName` | 字符串 | 站点名（导航栏/首屏大标题），读取侧缺省 `"My Blog"` |
| `LogoName` | 字符串 | Logo 圆点里的文字，缺省 `"k"`。**与 `SiteName` 刻意分开**：站点名可能是「kky's blog」这样一句话，而圆点里只放得下 1~2 个字符 |

> ⚠️ **`Versions` 的字典 Key 保留原始大小写**（`"SiteName"` 而非 `"siteName"`）。
> `JsonSerializerDefaults.Web` 只设置 `PropertyNamingPolicy`，**不设置**
> `DictionaryKeyPolicy`，所以字典键原样输出。前端依赖这一点做精确取值。

`SocialLink` 字段：`Name`（≤50）/ `Icon`（≤50，前端图标映射用，如 `github`）/
`Url`（≤500）/ `SortOrder` / `IsVisible`；数量极少，除主键外无额外索引。

| 表 | 特有列（长度） | 约束与索引 |

| `Authors` | `Name` 100 / `Email` 100 / `Avatar` 200 / `Bio` 500 | 除主键外无额外索引 |
| `Categories` | `Name` 100 | `IX_Categories_Name`（唯一，过滤 `"IsDeleted" = false`） |

| `Collections` | `Title` 200 / `Slug` 200 / `Description` 500 / `CoverImage` 500 / `SortOrder` int / `IsPublished` bool | `IX_Collections_Slug`（唯一，过滤 `"IsDeleted" = false`）；`IX_Collections_SortOrder` |
| `Users` | `Email` 100 / `PasswordHash` 500 / `Role` 20 / `IsActive` bool / `AuthorId` uuid 可空 / `LastLoginAt` timestamptz 可空 / `TokenVersion` int | 外键 `FK_Users_Authors_AuthorId` → `Authors.Id`（**SetNull**，作者被删时账号仍可登录，只是失去署名身份）；`IX_Users_Email`（唯一，过滤 `"IsDeleted" = false`）、`IX_Users_AuthorId` |

> **过滤唯一索引**（partial unique index）是关键：只在未删除的行之间保证唯一，
> 因此**软删除后可以重建同名分类/标签**。这是软删除与唯一约束共存的正确做法。
> 另注意 `Authors.Email`（展示用联系方式，无唯一约束）与 `Users.Email`（登录邮箱，唯一）是两回事。
>
> ⚠️ `Collection.IsPublished` 是**表上真实存在的列**，与 `Post.IsPublished`
> （C# 计算属性、无列）语义相近但实现完全不同。
>
> **为什么 `Role` 存字符串而不是整数**：可读性显著更好（直接查库就能看懂），
> 且将来加角色时**不需要改数据库类型**，只需新增枚举值。代价是索引效率略低，
> 但用户表行数极少，不构成问题。
>
> **为什么站点配置用 Key-Value 而不是固定列**：配置项会随需求增加，固定列每加一项
> 就要写迁移。KV 结构**加配置项不需要改表**，代价是失去数据库层的类型约束
> ——类型由应用层按 Key 解释。

### 6.6 连接表

**`PostTag`** — 文章 ↔ 标签（EF 隐式多对多）。只有 `PostsId` / `TagsId` 两列（都是 uuid、非空），
无公共字段；主键 `(PostsId, TagsId)`；两个外键都是 **`Cascade`**（删文章/删标签时自动清理连接行）；
索引 `IX_PostTag_TagsId`。

> ⚠️ **更新标签时必须做"增量同步"，不能整体替换。**
> 若把 `post.Tags` 整体替换（先清空再加回），EF 会把仍存在的连接行也当成新增 INSERT，
> 报 `23505 duplicate key ... PK_PostTag`。
> 正确做法（`PostService.ApplyTagsAsync`）：只移除"取消关联的"、只添加"新增的"。

**`PostCollections`** — 文章 ↔ 专栏（显式连接实体）：`PostId` / `CollectionId`（uuid，非空）
+ `SortOrder` int（**该文章在此专栏内的排序**）。主键 `(PostId, CollectionId)`（`PK_PostCollections`）；
两个外键都是 **`Cascade`**；索引 `IX_PostCollections_CollectionId`。这个实体**不继承
`BaseEntity`**（§5.1），因此没有软删除与乐观锁版本号，也不能用
`BaseRepository<T> where T : BaseEntity` 泛型化。

**为什么专栏内的顺序要单独存**：专栏是"人为编排的系列"，阅读顺序由作者决定，
不能按发布时间推导。这是它与分类/标签最本质的区别。

## 7. 仓储、乐观锁与写入语义

### 7.1 乐观锁实现（核心机制）

**决策**：用 `int Version` + SQL 条件手动控制，而不是 EF 的 `[Timestamp]` / `byte[] RowVersion`
——**整数版本号与数据库无关**，可跨 PostgreSQL / MySQL / SQLite 等任意 EF 支持的库。

核心逻辑收敛在 `BaseRepository.ApplyOptimisticVersion`（`BaseRepository.cs:66-73`）：

```csharp
public void ApplyOptimisticVersion(TEntity entity, int expectedVersion)
{
    if (expectedVersion < 1)
        throw new ArgumentOutOfRangeException(nameof(expectedVersion), "版本号必须 >= 1");

    var version = _context.Entry(entity).Property(nameof(BaseEntity.Version));
    version.OriginalValue = expectedVersion;   // 作为 WHERE 条件
    version.CurrentValue  = expectedVersion + 1; // 作为 SET 值
}
```

配合 §6.3 的 `IsConcurrencyToken` 配置，EF 生成的 SQL 是
`UPDATE "Posts" SET ..., "Version" = @expected + 1 WHERE "Id" = @id AND "Version" = @expected`
受影响行数为 0 → EF 抛 `DbUpdateConcurrencyException` → 中间件映射为 **409 / 4090**。

这是贯穿全栈的一条约定：前端拿到详情时必须保存 `version`，保存时原样回传。
**唯一例外**：文章浏览量的累加用 `ExecuteUpdate` 绕过乐观锁（§8.5）。

### 7.2 读写分离的仓储划分

**写侧仓储**（8 个接口）：定义在 `Blog.Domain/IRepository/`，实现在
`Infrastructure/Persistence/Repositories/`，负责增删改与乐观锁更新。
**读侧查询仓储**（5 个注册）：`Blog.Application/Interfaces/I*QueryRepository.cs`，
只读的复杂查询与投影，直接返回 DTO。

**为什么分开**：查询需要"一次查完并投影成 DTO"（避免 N+1 与无谓的实体追踪），
而写入需要"取实体 → 调领域方法 → 保存"。两种诉求放同一个接口里会互相牵制。

`TaxonomyQueryRepository` 一个类**显式实现**分类与标签两个查询接口（逻辑完全一致）。
`BaseRepository.GetByIdAsync` **默认不加载导航集合**——这一点直接导致 §5.6 的两个必踩坑。

### 7.3 工作单元

`IUnitOfWork` 封装 `SaveChangesAsync` 与事务（`BeginTransactionAsync` / `Commit` / `Rollback`）。
`BlogDbContext` 的生命周期由 DI 管理（Scoped），UnitOfWork **不负责释放它**，只释放自己的事务。

### 7.4 写入语义统一约定

| 情形 | 语义 |
|---|---|
| 实体/Key **不存在** | 视为**新增**，忽略传入 version |
| 实体/Key **已存在** | 走**乐观锁**，version 必须 ≥ 1，否则 4001 |

站点配置的逐项更新就依赖这条规则：前端对"尚不存在的 Key"传 `version = 0`，
后端走新增分支；对已存在的 Key 传实际版本号。

## 8. 缓存

### 8.1 三实现 + 开关

| 实现 | 何时使用 |
|---|---|
| `NullCacheService` | `Cache:Enabled = false`，缓存完全旁路 |
| `MemoryCacheService` | `Cache:Provider = Memory`，单实例 |
| `RedisCacheService` | `Cache:Provider = Redis`，多实例或需要跨进程共享 |

选择逻辑写在 `Blog.Infrastructure/DependencyInjection.cs:51-60`：先看总开关，再按 Provider 二选一。
Redis 实现中，**任何 Redis 故障（连接断开、超时）都降级为直查回源，不向调用方抛异常**——
对业务而言"缓存坏了"绝不该表现为"接口 500"。

### 8.2 缓存三防

| 问题 | 现象 | 本项目对策 |
|---|---|---|
| **穿透** | 查询不存在的数据，每次都打到 DB | 写入**空值哨兵** `∅`，TTL 用更短的 `Cache:NullTtl`（默认 2 分钟） |
| **击穿** | 热点 key 过期瞬间，大量请求同时回源 | key 级**互斥重建**：内存用信号量，Redis 用分布式锁；抢不到锁的直接回源（不阻塞），等待超时 `Cache:LockWaitTimeout`（3 秒） |
| **雪崩** | 大批 key 同时过期，DB 瞬时压力 | TTL 加 **±`Cache:TtlJitterRatio`**（默认 20%）随机抖动 |

`GetOrCreateAsync` 的 `cacheNull` 参数按场景选择：列表类传 `true`（查不到就是查不到，
缓存空结果防穿透）；详情类传 `false`（避免"新建后立即读到空哨兵"）。

### 8.3 缓存 Key 规范

```
blog:{模块}:{操作}:v{版本}:{固定维度}:{可选hash}
```

| 规则 | 理由 |
|---|---|
| 固定前缀 `blog:` | 便于按前缀失效；与其他应用共用 Redis 时不冲突 |
| 带 `v{版本}` | 缓存结构不兼容变更时整体失效——改版本号即可，旧 key 靠 TTL 自然消失，无需 `SCAN` 清理 |
| 固定维度用短键名，缺省值用 `-` 占位 | 保持 key 段数固定，便于排查 |
| 不可枚举的长文本（如搜索关键词）做 SHA256 取前 16 位 | 避免超长或特殊字符污染 key |

示例（`CacheKeys.cs`）：`blog:posts:list:v1:p1s12:c-t-col-a-o-k-:u0`、
`blog:posts:detail:v1:{guid}`、`blog:taxonomy:collections:v1:published`、`blog:site:config:v1:-`。

### 8.4 缓存 TTL

核心 TTL 组合：文章**列表 5 分钟**（`PostService.ListCacheTtl`）、
**详情 10 分钟**（`DetailCacheTtl`）、**归档 30 分钟**（`ArchiveCacheTtl`）。
分类 / 标签 / 专栏同为 30 分钟（`CategoryService` / `TagService` / `CollectionService`），
站点统计 10 分钟（`SiteService.StatsTtl`）。

### 8.5 浏览量的特殊处理

浏览量累加**跳过乐观锁**，用 `ExecuteUpdate` 做数据库侧原子自增——浏览量是高频写且允许丢失
精度，"两人同时看同一篇文章导致一方 409"是荒谬的体验。缓存侧同步刷新：详情缓存里的
`ViewCount + 1` 后重新写回，避免缓存与 DB 长时间不一致。

## 9. 中文全文检索（FTS）

### 9.1 方案

| 组件 | 说明 |
|---|---|
| `SearchVector` 列 | `tsvector` **生成列**（stored），由数据库在插入/更新时自动维护，应用层**永远不写这一列** |
| 权重 | 标题 A / 摘要 B / 正文 C |
| 索引 | GIN 索引 `ix_posts_search` |
| 查询 | `plainto_tsquery('chinese'::regconfig, @keyword)` |

生成列表达式（`BlogDbContext.cs:109-113`，迁移中的 SQL 与之逐字一致）：

```sql
setweight(to_tsvector('chinese', coalesce("Title", '')), 'A') ||
setweight(to_tsvector('chinese', coalesce("Summary", '')), 'B') ||
setweight(to_tsvector('chinese', coalesce("Content", '')), 'C')
```

**权重含义**：标题 A（最高）> 摘要 B > 正文 C；权重只影响相关度评分（`ts_rank`），**不影响是否匹配**。

### 9.2 EF Core 侧的映射（影子属性）与两个必踩的坑

`NpgsqlTsVector` 来自 Npgsql，**不能出现在 `Blog.Domain`**（该层零框架依赖）。
因此它只在 Infrastructure 的 `OnModelCreating` 里声明为**影子属性**：

```csharp
entity.Property<NpgsqlTypes.NpgsqlTsVector>("SearchVector")
      .HasColumnName("SearchVector").HasColumnType("tsvector")
      .HasComputedColumnSql("...", stored: true);
```

> ⚠️ **正是"影子属性"这个身份导致了两个必踩的坑**（可翻译性下降）：
>
> **坑一：`EF.Functions.PlainToTsQuery` 在"影子属性 + 参数"形态下被判客户端求值。**
> 因为 `SearchVector` 不在实体上，EF Core 无法把这种组合翻译成 SQL，于是回退到客户端求值
> ——表现为"查询报错"或"结果不对"。**解法**：改用**参数化原生 SQL**（`SqlQuery` / `FromSqlInterpolated`）。
>
> **坑二：`plainto_tsquery` 必须显式 `::regconfig` 转型。**
> PostgreSQL 的 `plainto_tsquery` 重载是 `(regconfig, text)` / `(text)`。不转型会尝试匹配
> `(text, text)`，报 `42883: function plainto_tsquery(text, text) does not exist`。
> **解法**：写成 `plainto_tsquery({config}::regconfig, {keyword})`。

### 9.3 相关度排序：CTE + `ts_rank`

搜索结果**按相关度降序**（同分再按 Id 降序，保证分页稳定）。
实现方式：用 **CTE + `Database.SqlQuery<Guid>`** 拿到「按相关度排好序的 Id 列表」，
外层仍用 `Contains` 关联回 Posts：

```sql
WITH ranked AS (
    SELECT p."Id" AS "Value",
           ts_rank(p."SearchVector", plainto_tsquery('chinese'::regconfig, @kw)) AS rank
    FROM "Posts" AS p
    WHERE p."SearchVector" @@ plainto_tsquery('chinese'::regconfig, @kw))
SELECT r."Value" FROM ranked AS r ORDER BY r.rank DESC, r."Value" DESC
```

| 取舍 | 原因 |
|---|---|
| 用 **CTE** | PostgreSQL 的 `ts_rank` 属窗口函数类，**不能直接写进 WHERE**（会报 `0A000`） |
| 用 **`SqlQuery<Guid>` 标量查询**，而不是映射 keyless 实体 | 试过 `HasNoKey()` 映射：`Id IN (...)` 可用，但改成 `Join` 带出 rank 列后投影 `Tags` 集合会报 **"cannot correlate on keyless entity type"**；标量查询不引入新实体 |
| 外层 `Contains` + 内存重排本页 | 保留「过滤后再分页」的语义（`total` 是过滤后的数量）；每页至多 `pageSize` 条且列表不加载正文，内存排序代价可忽略 |

> **为什么不在原生 SQL 里直接 `ORDER BY rank` 再 `LIMIT`**：那样分类 / 标签 / 专栏 /
> 作者 / 归属等过滤就无法安全叠加，会出现「先分页再过滤」导致的错页与错误总数。
>
> **不存在 SQL 注入**：参数由 `SqlQuery` 自动参数化；且 `plainto_tsquery`（而非 `to_tsquery`）
> 会把自然语言安全地转成查询，用户输入的 `&` `|` `!` 等不会被当作 tsquery 操作符。
> 实现见 `Infrastructure/Persistence/Repositories/PostQueryRepository.cs`。

### 9.4 扩展与检索配置的创建

| 来源 | 覆盖场景 | 内容 |
|---|---|---|
| **EF 迁移 `20260910205225`（权威来源）** | **全新库 + 已有库，两种都覆盖** | `CREATE EXTENSION IF NOT EXISTS zhparser` + 建 `chinese` 配置 + 创建 `SearchVector` 生成列 + GIN 索引 |
| `deploy/postgres-init/01-zhparser.sql` | 仅全新数据库（entrypoint 只在数据目录为空时执行） | 同样的扩展与配置语句 + 一条自检输出 |

**权威来源必须是迁移**：`postgres` 官方镜像的 entrypoint **只在数据目录为空时**执行
`/docker-entrypoint-initdb.d/` 下的脚本——对已存在的库它不会重跑，而迁移每次启动都会应用；
init 脚本只是让全新环境开箱可用、少一步手工 SQL。

#### ⚠️ 这两段 SQL 在迁移里的**位置是有约束的**

同一个迁移在后面会 `AddColumn<SearchVector>`，而它是**生成列**，
表达式引用了 `to_tsvector('chinese', …)` —— 也就是**依赖 `chinese` 配置已存在**。

因此创建扩展与配置的两段 SQL **必须排在那条 `AddColumn` 之前**。原先它们排在后面，
后果是**整条迁移链无法在干净的 PostgreSQL 上从零建库**（`42704: text search
configuration "chinese" does not exist`），而失败发生在应用启动时的 `Database.Migrate()`
——表现为**应用起不来**。它长期没暴露，是因为 entrypoint 脚本总会先把配置建好：
**靠部署巧合，而不是靠迁移自己能站得住**。两段 SQL 都是幂等的，且 EF 按 ID 跳过
已应用的迁移，所以调整顺序对**已迁移的库没有任何影响**。

**映射的 token 类型**：`n`(名词) `v`(动词) `a`(形容词) `i`(成语) `e`(叹词)
`l`(习用语) `j`(简称) `q`(量词)。用 `simple` 字典（只做小写归一化，不做词干还原与停用词过滤）——
中文不需要词干还原，且这样能让中英混合文本里的英文词原样保留。

**部署保障**：`zhparser` 不在官方 postgres 镜像中，必须自行编译。上表两行就是**双重保障**
——迁移是权威来源（全新库 + 已有库都覆盖），
`deploy/postgres-zhparser.Dockerfile` + `deploy/postgres-init/01-zhparser.sql` 只是便利。
这个"必需 vs 便利"的区分是可运维性的关键：即使哪天有人把 init 脚本删掉，
应用依然能在任何带 zhparser 扩展的 PostgreSQL 上从零建库。

## 10. 认证与授权

### 10.1 整体结构

均在 `Blog.Infrastructure/Security/`：`Pbkdf2PasswordHasher`（密码哈希与校验）、
`JwtTokenService`（签发与解析 JWT）、`CurrentUserResolutionMiddleware`（每请求解析并校验登录用户）、
`HttpCurrentUser`（同步读取解析结果，供 `ICurrentUser` 使用）。授权策略 `AdminOnly` /
`ContentWriter` 定义在 `Blog.WebApi/Program.cs`。

### 10.2 密码哈希

格式自描述（`pbkdf2-sha512${iterations}${base64(salt)}${base64(hash)}`），
便于将来提升迭代次数后仍能校验旧密码。

| 参数 | 值 |
|---|---|
| 算法 | PBKDF2-HMAC-SHA512 |
| 迭代次数 | 210,000（OWASP 对该算法的建议量级） |
| 盐 | 每用户 16 字节随机 |
| 输出 | 32 字节 |

- 校验用 `CryptographicOperations.FixedTimeEquals`（**恒定时间比较，防时序攻击**）；
  校验时**按存储中记录的迭代次数**重算，因此提高默认迭代次数不会让旧密码失效，
  `NeedsRehash()` 可用于登录成功时静默升级
- **绝不**使用 MD5/SHA1/SHA256 直接哈希密码

### 10.3 JWT 与"主动失效"补偿

算法 **HS256**（对称密钥，长度必须 ≥ 32 字节）；有效期 **30 分钟**
（`Jwt:AccessTokenMinutes`，缺省即 30）；**不做 Refresh Token**（决策 T7）；
时钟偏移 `ClockSkew = 30 秒`（默认 5 分钟会让"刚过期"的 token 仍可用，显式收紧）。
标准 claim：`sub`（用户 id）、`role`（标准 `ClaimTypes.Role`）、`jti`；
自定义 claim：`authorId`（可空，仅在非空时加入）、`tv`（TokenVersion）。

**JWT 是无状态的，天然无法主动失效**——用户改了密码、账号被停用，
旧 token 在过期前依然有效。本项目的补偿方案：

1. 签发时把 `User.TokenVersion` 写入 `tv` claim
2. 每个请求由 `CurrentUserResolutionMiddleware` 校验四件事：JWT 签名与过期时间
   （由 JwtBearer 中间件完成）、账号存在（软删除的账号查不到）、账号处于 `IsActive`、
   **claim 中的 `tv` 与数据库一致**
3. 需要踢下线时把 `TokenVersion + 1`（改密码 / 停用 / 注销），旧 token 立即全部失效

> 相比 Redis 黑名单方案，它**不引入新的运行时依赖**，且多实例下天然有效（校验读的是数据库，不是某个实例的内存）。

**一个刻意的细节**：校验失败时中间件**不直接返回 401**，而是不写入当前用户信息，
让后续的 `[Authorize]` 去拒绝。这样公开接口即使携带一个过期 token 也能正常访问
（否则一个过期 token 会让用户连首页都打不开）。

### 10.4 归属校验必须在 Service 层

角色策略只能回答"这类角色能不能用这个端点"，**不能**回答"这个人能不能动这条数据"。
后者必须先查到实体才知道归属，因此必须在服务层做（`PostService.EnsureCanManage`）：

```csharp
private void EnsureCanManage(PostEntity post)
{
    if (_currentUser.IsAdmin) return;
    if (!_currentUser.IsAuthenticated) throw new BusinessException("未登录", ErrorCodes.Unauthorized);

    var isOwner = post.CreatedByUserId.HasValue && post.CreatedByUserId == _currentUser.UserId;
    if (!isOwner) throw new BusinessException("无权操作他人的文章", ErrorCodes.Forbidden);
}
```

> ⚠️ **只认 `CreatedByUserId`（账号维度），绝不能认 `AuthorId`。**
> 多个账号可以关联同一个 Author，用 AuthorId 判断会导致它们互相越权。

`[Authorize]` 属性式鉴权的能力边界（它只管角色，管不了归属），
原理见 [learn/01-后端知识地图.md](../learn/01-后端知识地图.md)。

### 10.5 草稿与未发布内容的可见性

`includeUnpublished=true` 且非 Admin 时强制 `OwnedByUserId = 当前用户`（未登录则 403）；
`mine=true` 且不是自己 → 403；直接读未发布文章详情仅 Admin 与创建者可读，
**不可读时返回 404（不是 403）**；未发布专栏按 slug 访问时匿名得到 404。

**为什么不可读返回 404 而不是 403**：403 等于告诉攻击者"这个 id 确实存在，只是你没权限"，
可以据此探测草稿的存在性。404 不泄露存在性。

### 10.6 媒体地址白名单（`MediaPath`）

**要解决的问题**：作者头像、文章封面、站点 Logo、首屏背景图这四个字段本质上是
「一个图片地址」。改造前前端把它们做成**自由文本框**，后端**原样存库、原样下发**，
于是任何能调写接口的人（**作者也能改自己的头像、也能发文章**）都能塞进任意 URL：

| 注入值 | 危害 |
|---|---|
| `https://evil.com/x.png`、`//evil.com/x.png` | 外链图片：访客 IP/UA 泄露给第三方，还会触发混合内容告警 |
| `javascript:alert(1)` | 今天只进 `<img src>` 看似无害，但哪天被复用到 `<a href>` 或 `window.open` 就是 XSS |
| `data:image/svg+xml;base64,…` | data URI，SVG 内部可携带脚本 |
| `/api/files/../../etc/passwd` | 目录穿越（读取层还会再挡一次，见下） |

**为什么用白名单而不是黑名单**：不去写"禁止 `http:` / `javascript:` / `data:`"这种规则——
黑名单只能挡住已经想到的写法。`MediaPath.IsOwned` 只认两件事：

1. 空值（表示未设置，归一化为空串）
2. 以 `/api/files/` 开头，且路径部分**只含** `[A-Za-z0-9._/-]` 白名单字符、长度 ≤200 的地址

第 2 条顺带挡掉 `%`（编码绕过）、`:`（scheme）、`?`/`#`（查询与片段）、`\`（Windows 分隔符）；
再单独挡 `..` 与 `//`（它们完全由合法字符组成，字符集过滤拦不住），以及「路径以 `/` 开头」
和「以 `/` 结尾」两种畸形形状。

**放在 Application 层而不是 Controller**，理由有三条：三个服务共用（`AuthorService` 头像、
`PostService` 封面、`SiteService` Logo/背景图）；`Blog.Domain` 要保持零框架依赖；不依赖 HTTP
因此可纯单元测试（`MediaPathTests` 同时覆盖攻击样本与**合法样本**，只测拒绝的话
"一律拒绝"的退化实现也会全绿）。

**与文件读取层是纵深防御**：真正的路径穿越防护仍在 `LocalFileStorageService.TryResolveSafePathIn`
（拒绝 `..` 与绝对路径，并校验解析后的绝对路径仍在根目录下）；即使 `MediaPath` 被绕过，读文件那一层依然会挡。

**读写两侧刻意不对称**：读侧（`SiteService.GetConfigAsync` → `MediaPath.ParseList`）对**改造前存下的**
历史形态宽容（精确边界见下），因为一次校验规则升级不应该让历史数据读不出来、把整个站点配置
接口打挂；写侧（`UpdateConfigAsync` → `MediaPath.ValidateJsonList`）JSON 格式错误**直接 4001**，
因为写入侧若也静默兜底，一段打错的 JSON 会被悄悄存成空数组，配置就丢了。

> ⚠️ **`ParseList` 的宽容边界，别记成"解析失败就回退"**：它的分支判断是
> 「**首字符不是 `[`** 才回退为单元素」——空/空白 → 空列表；裸地址
> （如 `/api/files/2026/09/old.webp`）→ 单元素列表；合法 JSON 数组 → 逐项（并丢掉空白项）；
> **以 `[` 开头的坏 JSON（如 `[这不是 JSON`）会被 `catch (JsonException)` 吞掉，返回空列表**，
> 而不是退回单元素。所以"读侧宽容"只对"整串不是数组"这一种历史形态生效。
>
> **最重要的教训**：**"前端藏起来"不等于"修好了"。** 把文本框删掉，界面上确实没地方填 URL 了
> —— 但 `curl` 依然能 PUT 成功。所以 `MediaUrlValidationTests` 刻意**绕开前端直接打 HTTP**，
> 并做过**反向验证**（临时短路 `MediaPath.Validate`，确认负向用例成批变红，再还原复测全绿）。
> 该文件（`MediaUrlValidationTests`）逐个罗列**攻击样本与合法样本**，其中包含 SVG 上传拒收等不走 `MediaPath` 的用例。
> ⚠️ **不在这里写用例条数**：加一个用例就错，实时条数以 CI 作业摘要为准（见 [00-文档规范.md](./00-文档规范.md) §3）。

## 11. 请求管道与中间件顺序

`Program.cs` 里**中间件的注册顺序即执行顺序**：

```
UseSerilogRequestLogging → ExceptionHandlingMiddleware → RateLimitingMiddleware → UseCors
→ UseAuthentication → CurrentUserResolutionMiddleware → UseAuthorization → MapControllers
```

本项目有**两个顺序敏感点**：

- **请求日志必须在异常处理中间件的"外层"（即先注册）。** 否则 `BusinessException`
  会先冒泡穿过日志中间件，日志里记录的是"异常发生时的 500 + 完整堆栈"，而客户端实际
  收到的是映射后的 404/403/409——**日志与事实不符**，且"文章不存在""邮箱重复"这类
  正常业务失败会刷满 ERR，淹没真正的故障。
- **`CurrentUserResolutionMiddleware` 必须在 `UseAuthentication` 之后。**
  它需要先有 `ClaimsPrincipal` 才能解析出用户，并做 `TokenVersion` 等数据库侧校验。

这两条不是本项目独有的——中间件顺序效应的通用原理与另外几个案例见
[learn/01-后端知识地图.md](../learn/01-后端知识地图.md)「中间件管道与顺序效应」；
此处只保留本项目的具体顺序与后果。

管道之外还有两处启动期行为：`Jwt:SigningKey` 缺失或不足 32 字节 →
**直接抛异常，应用拒绝启动**（`Program.cs:87-97`）；启动时 `Database.Migrate()`
自动应用迁移（`Program.cs:218-222`）。

## 12. 限流

### 12.1 令牌桶

| 实现 | 特点 |
|---|---|
| `RedisTokenBucketLimiter` | **Lua 脚本**保证"补令牌 + 取令牌"原子性；多实例共享同一桶 |
| `InMemoryTokenBucketLimiter` | `ConcurrentDictionary` + 每桶锁；单实例默认，也是 Redis 故障时的降级实现 |

Redis 故障时由 `RateLimitingMiddleware` 决定：`RateLimit:FallbackToMemory = true` 则降级内存桶，
否则直接放行（记 WARN）。限流只作用于 `/api` 下的路径。

### 12.2 规则匹配

规则来自配置（`RateLimit:Rules`），**按顺序匹配，命中即停**；匹配条件是路径前缀 +
HTTP 方法（方法为空表示不限），`Granularity` 支持三种粒度：

粒度三种：`Ip`（默认，客户端 IP —— **优先取 `X-Forwarded-For` 的第一个 IP**，
否则 `RemoteIpAddress`）、`Global`（固定字符串 `global`）、`Endpoint`（`{方法}:{路径}`）。
桶 key 形如 `blog:ratelimit:{规则名}:{标识}`。

### 12.3 响应

触发限流返回 HTTP **429** + `Retry-After` 头（秒，向上取整，最小 1）
+ 响应体 `{code: 4091, message: "请求过于频繁，请稍后再试"}`。
未触发时返回 `X-RateLimit-Remaining` 头，便于调试。

## 13. 文件上传与图片优化

### 13.1 为什么不用静态文件中间件

**本项目的事实**：所有文件都经独立接口 `/api/files/**` 读写（`FilesController`），而不是 `UseStaticFiles`。
这么做的三个通用理由（路径穿越防护、精确控制缓存头、可插入处理管线）见
[learn/01](../learn/01-后端知识地图.md)（为什么不用静态文件中间件）——本文不复述。

**换来的约束**：响应头由方法体自己下发，`Cache-Control: public,max-age=86400` 只在**命中文件**时设置。
不用 `[ResponseCache]` 标注 action：特性作用于整个方法，会把"文件不存在"的 404 也缓存一整天。
（当时的定位过程见 [archive/决策记录.md](../archive/决策记录.md)。）

### 13.2 目录穿越防护与上传限制

| 项 | 值 / 行为 |
|---|---|
| 存储根目录 | `FileStorage:Root`（默认 `media`），相对应用工作目录 |
| 只读种子目录 | `FileStorage:SeedRoot`（默认 `media-seed`），**只读回退**，不参与上传写入 |
| 单文件上限 | `FileStorage:MaxFileSize`（默认 10 MB）；控制器另有 `[RequestSizeLimit(50MB)]` 作为框架层上限 |
| 存储路径 | 按年月分目录（如 `2026/09/{32位十六进制}.webp`） |
| 空文件 / 扩展名非法 | **HTTP 400** + `{code:4001}` |
| 超过业务上限 | **HTTP 413** + `{code:4130}` |
| 文件不存在 | **HTTP 404** + `{code:4040}` |

### 13.3 上传格式白名单：为什么不收 SVG

`LocalFileStorageService` 有两张表，它们**必须保持一致**：`AllowedExtensions` 是
**上传入口**的白名单（不在表里 → `ArgumentException` → 4001），`ContentTypes` 是
**读取出口**的扩展名 → `Content-Type` 映射。两张表里都**刻意没有 `.svg`**。

**为什么不收 SVG**：SVG 是可以内嵌 `<script>` 的格式，而 `FilesController.Get()`
用 `File(stream, contentType)` **同源内联**下发（没有 `Content-Disposition: attachment`）。
拥有 ContentWriter 的账号（**作者即可**）上传一个恶意 SVG，再把
`/api/files/xxx.svg` 的地址发给管理员 —— 管理员**直接打开这个链接**时，
脚本就在站点源上执行，构成**存储型 XSS**。

> ⚠️ **区分两种加载方式**：`<img src="x.svg">` 是「被动图像」，脚本**不会**执行；
> 真正的风险是**把 SVG 当作顶层文档导航过去**。
> 所以「反正只允许用在 `<img>` 里」不能作为放过 SVG 的理由 —— 那个 URL 本身是可以被直接访问的。

**为什么两张表都要改**：上传入口已经拒绝 SVG，`ContentTypes` 是**兜底**——万一有人手工把
svg 放进媒体目录（绕过上传接口），它只会被当作 `application/octet-stream` 下载，
而不会以 `image/svg+xml` 渲染成文档。

**为什么选择「直接不支持」**：另一条路是保留 SVG、改用 `Content-Disposition: attachment`
下发；但那样 SVG 就不能再当 `<img>` 源（功能上等于也不支持），还要额外区分哪些路径走
attachment、哪些走 inline。**直接禁用更简单、更不容易出错**，而博客里 SVG 的实际用途
（Logo / 头像 / 封面）都可以用位图替代。将来若确实需要矢量图，正确做法是**先转成位图再入库**。

`git blame` 到这个文件的人请注意：`AllowedExtensions` 的注释里写明了**不要把 `.svg` 加回来**及其原因。

### 13.4 图片自动转 WebP

`ImageSharpOptimizer` 在保存前把位图转成 WebP：

| 配置 | 默认 | 说明 |
|---|---|---|
| `Enabled` | `true` | 总开关 |
| `WebpQuality` | `82` | 质量 |
| `MaxDimension` | `2560` | 最长边上限，超出等比缩小 |
| `MaxPixels` | `40000000` | 像素总数上限（**防解压炸弹**） |
| `ConvertExtensions` | `.png .jpg .jpeg` | 参与转换的扩展名 |

**失败即原样保存**：转换失败、或"不该转"的情况（如扩展名不在列表里）一律原样保存，
不因为优化失败而拒绝上传。响应里带回 `originalBytes` / `storedBytes` / `converted`。
**为什么锁 ImageSharp 3.x**：v4 起要求构建期许可密钥 `sixlabors.lic`，社区许可虽免费
但需先申请，否则**构建直接报错**；v3 为纯托管实现（无原生依赖），部署最简。

## 14. 日志与可观测性

输出：控制台（始终开启）+ 滚动文件 `logs/blog-.log`（按天滚动，保留 30 天）。
启动早期用 `CreateBootstrapLogger()`，这样"应用构建前"的异常也能记录；
`HostAbortedException` 被显式排除——那是 EF Core 设计期工具正常中止宿主，不是启动失败。

`UseSerilogRequestLogging` 按响应状态码分级，避免日志噪音掩盖真故障：
**≥ 500（或抛异常）记 `Error`，400–499 记 `Warning`，其余记 `Information`**
（分级规则与顺序敏感点见 §11）。

`SlowQueryInterceptor`（`DbCommandInterceptor`）在任意命令超过 **500ms** 时记 WARN（含完整 SQL
与耗时），覆盖 Reader / NonQuery / Scalar 的同步与异步共 6 个方法。

## 15. 健康检查

`GET /health`（实现见 `Blog.WebApi/HealthChecks/HealthCheckSetup.cs`）。
用共享框架内置的 `Microsoft.Extensions.Diagnostics.HealthChecks`，**不引入第三方健康检查包**。

### 15.1 检查项（四项）

- PostgreSQL **连通性**：能连上
- **`zhparser` 扩展**：`pg_extension` 里有它
- **`chinese` 检索配置**：`pg_ts_config` 里有它，且**实际执行一次 `to_tsvector('chinese', ...)`**
- **迁移 / Redis**：`GetPendingMigrationsAsync()` 为空；Redis 能 Ping 通，
  且**仅当 `Cache:Provider = Redis` 时视为必需**，否则跳过（缓存可降级）

前三项合并在一个 `DatabaseHealthCheck` 里完成（都需要打开一次数据库连接，可少一次往返），
Redis 单独一个 `RedisHealthCheck`。任一项失败则整体 `Unhealthy` → **503**。

> 为什么要真跑一次分词：只查 `pg_extension` / `pg_ts_config` 查不出「配置存在但不可用」，实际执行才能证明检索真的能用。

### 15.2 ⚠️ 对外只回状态，详情只写日志

响应体固定为**纯文本** `Healthy`（200）或 `Unhealthy`（503），**不含任何内部信息**。

`/health` 通常对编排系统与负载均衡开放（本项目未加鉴权），在响应里带上「哪个依赖挂了 +
报什么错」等于向匿名访问者泄露内部结构（数据库地址、依赖拓扑、异常栈）。排障信息看服务端
日志即可——未通过时日志里会有结构化详情（检查项 / 状态 / 耗时 / 错误）。

## 16. 部署拓扑校验

`DeploymentGuard.Validate()` 在 **DI 注册阶段**（即启动期）执行硬校验：

| 条件 | 结果 |
|---|---|
| `InstanceCount ≤ 1` 且 `RequireRedis = false` | 放行（允许内存实现） |
| 否则（多实例 或 显式要求 Redis） | 必须 `Cache:Enabled = true` **且** `Provider = Redis`，否则**抛异常，应用启动失败** |

**为什么用"启动即失败"而不是"运行期静默降级"**：每台实例各自用内存缓存 →
DB 压力变成实例数的倍数；每台实例各自一个内存令牌桶 →
实际限流阈值被放大到"配置值 × 实例数"，**限流形同虚设**。这类问题靠静默降级
极难排查，因此把"部署拓扑"当作运维必须显式声明的输入，而不是让代码去猜。
异常信息里会打印当前配置值与两条修法。
