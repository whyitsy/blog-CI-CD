## 2. 开箱账号（重要）

### 2.1 管理员账号

项目通过 EF Core 的 `HasData` 预置了一个开发用管理员，**全新数据库初始化后即可直接登录**。

| 项 | 值 |
|---|---|
| 登录邮箱 | `admin@example.com` |
| 登录密码 | `Admin@12345` |
| 角色 | `Admin` |
| 是否启用 | 是 |
| 关联作者 | 无（管理员账号不关联署名对象） |

登录入口：前端 `/login`（管理员与作者**共用同一个登录页**，登录后按角色跳转）。

> ⚠️ **生产环境必须立即修改此密码。**
> 这个密码连同它的 PBKDF2 哈希都**公开写在仓库里**
> （`Blog.Infrastructure/Persistence/BlogDbContext.cs` 的 `SeedAdminPasswordHash` 常量）。
> 它存在的唯一目的是"让全新开发环境开箱即可登录后台"，绝不是一个安全的默认值。
> 修改方式：登录后台 →「账号管理」→ 重置密码（会同时使旧 token 失效）；
> 或部署脚本自行创建专属管理员，不依赖此种子账号。

### 2.2 作者账号

**没有预置作者账号，也没有注册端点。** 这是刻意的设计（决策 T1）：

- 作者账号的唯一创建入口是管理员登录后的「账号管理」页面（`POST /api/users`）
- 作者没有自助注册能力

因此新环境的账号建立流程是：

```
管理员登录 → 创建作者（/api/authors，建立署名身份）
          → 创建账号（/api/users，邮箱 + 密码 + 角色 Author + 关联上面那位作者）
          → 该作者即可用该邮箱密码登录 /login
```

> 关于「作者（Author）」与「账号（User）」为什么要分开，见 [03-后端设计.md](./03-后端设计.md) §3。

### 2.3 签名密钥（JWT）

| 项 | 值 |
|---|---|
| 配置键 | `Jwt:SigningKey` |
| 开发值 | 存在于 `appsettings.Development.json`，形如 `dev-only-insecure-signing-key-...`（长度 ≥ 32 字节） |
| 生产要求 | `appsettings.json` **不含**此键，必须通过环境变量 `Jwt__SigningKey`（注意双下划线）注入 |

**行为**：应用启动时校验签名密钥。若缺失或长度不足 32 字节，**直接中止启动并打印指引**，
而不是退化成弱密钥。设计理由：静默使用弱密钥意味着"任何人都能伪造 token"，
后果远比启动失败严重。

```bash
# 生成一个可用的密钥
openssl rand -base64 48

# 注入（.NET 用双下划线表示配置层级）
export Jwt__SigningKey="<生成的随机串>"
```

| 项 | 值 |
|---|---|
| 容器名 | `redis` |
| 镜像 | `redis:latest` |
| 连接 | `localhost:6379` |
| 用途 | 缓存（`Cache:Provider=Redis`）与分布式令牌桶限流 |

## 5. 启动项目

### 5.1 前置检查

1. Docker Desktop 已启动
2. `pgsql` 与 `redis` 容器处于 `Up` 状态

```bash
docker ps --format "table {{.Names}}\t{{.Status}}"
```

### 5.2 后端

**必须使用 `run_in_background=true` 启动，不要加 `&` 或 `nohup`。**
原因：Bash 会话结束后，用 `&` 启动的进程会被系统清理，
表现为前端突然全部 `ECONNREFUSED`（本项目踩过此坑）。

```bash
# 在仓库根目录执行
cd Blog.Backend/Blog.WebApi/bin/Debug/net10.0 && \
env -u HTTP_PROXY -u http_proxy -u HTTPS_PROXY -u https_proxy \
./Blog.WebApi.exe --urls http://localhost:5131 --environment Development
```

- 开发地址：`http://localhost:5131`
- `--environment Development` 参数**不可省略**：在 WSL 里启动 Windows exe 时，
  环境变量 `ASPNETCORE_ENVIRONMENT` 不生效，会导致连接串为空而启动失败（见 §7）。

### 5.3 前端

```bash
# 在 Blog.FrontEnd/ 目录执行
"/mnt/c/Program Files/nodejs/node.exe" ./node_modules/vite/bin/vite.js --host 127.0.0.1 --port 5173
```

- 开发地址：`http://localhost:5173`
- Vite 已配置代理：`/api` → `http://localhost:5131`，因此浏览器视角是同源，无 CORS 预检
- **必须用 Windows 的 node**，WSL 的 node 缺少 rolldown 原生绑定，会报 `Cannot find native binding`

### 5.4 快速验证

```bash
# 后端存活（WSL 不能直连 localhost，必须用 Windows 的 curl）
/mnt/c/Windows/System32/curl.exe -s --noproxy '*' http://localhost:5131/

# 取站点配置
/mnt/c/Windows/System32/curl.exe -s --noproxy '*' http://localhost:5131/api/site/config

# 登录（拿 token）
/mnt/c/Windows/System32/curl.exe -s --noproxy '*' -X POST http://localhost:5131/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@example.com","password":"Admin@12345"}'
```

## 6. PostgreSQL 的中文分词扩展（关键依赖）

### 6.1 为什么需要

站内搜索使用 PostgreSQL **全文检索（FTS）**。PG 内置分词器对中文会把整句当成一个词元，
因此必须安装中文分词器 **`zhparser`**（依赖 **SCWS** 词法库）。

**`zhparser` 不在官方 postgres 镜像里，必须自行编译。**

### 6.2 当前状态

| 项 | 状态 |
|---|---|
| 自定义镜像定义 | ✅ 已编写并**实测通过**：`deploy/postgres-zhparser.Dockerfile` |
| 初始化脚本 | ✅ `deploy/postgres-init/01-zhparser.sql`（新建库时自动执行） |
| EF 迁移中的保障 | ✅ 已包含 `CREATE EXTENSION` + 创建 `chinese` 配置（覆盖"已有库"场景） |
| **开发容器是否已换成自定义镜像** | ✅ **已切换**。`pgsql` 容器运行 `blog-postgres-zhparser:18`，数据卷沿用原卷 |

**切换已完成的含义**：zhparser 现在**存在于镜像里**，
因此容器被 `docker rm` / 重建后，扩展与 `chinese` 检索配置会由
`/docker-entrypoint-initdb.d/01-zhparser.sql` **自动重建**，全文检索不会失效。

> 旧容器已保留为 `pgsql-old`（`postgres:18.6`，已停止）作为回退点。
> 确认新容器稳定后可删除：`docker rm pgsql-old`。
>
> 切换与验证的完整过程见 `deploy/README.md` §4、§5。

### 6.3 构建与验证

```bash
# 构建自定义镜像（在仓库根目录）
docker build -f deploy/postgres-zhparser.Dockerfile -t blog-postgres-zhparser:18 .

# 验证分词（在容器内）
docker exec -it pgsql psql -U kky -d blog_stage2 -c \
  "SELECT to_tsvector('chinese', '使用 EF Core 做数据库优化与全文检索');"
```

预期输出（词级切分，而非逐字或整句）：

```
'core':3 'ef':2 '优化':6 '使用':1 '做':4 '全文检索':7 '数据库':5
```

## 7. 环境陷阱速查

本项目的 Windows + WSL2 组合踩过一批坑，完整版在 [07-开发与运维手册.md](./07-开发与运维手册.md) §2。
这里只列**会不会让项目跑不起来**的几条：

| # | 现象 | 原因 | 解法 |
|---|---|---|---|
| 1 | WSL 里 `curl 127.0.0.1:5131` 连接被拒 | WSL2 的 localhost 转发未生效 | 用 Windows 的 curl，见 §5.4 |
| 2 | `The ConnectionString property has not been initialized` | WSL 启动 Windows exe 时 `ASPNETCORE_ENVIRONMENT` 不生效 | 加 `--environment Development` 参数 |
| 3 | `Cannot find native binding` | WSL 的 node 缺 rolldown 原生绑定 | 用 `/mnt/c/Program Files/nodejs/node.exe` |
| 4 | `dotnet build` 报 `MSB3027` / `MSB3021`（文件被占用） | 运行中的 `Blog.WebApi.exe` 锁住了输出 DLL | 先 `taskkill /F /IM Blog.WebApi.exe`（csproj 里已有自动任务，但偶尔仍需手工再杀） |
| 5 | `dotnet` 找不到 | 不在 WSL 的 PATH 里 | 用 `/mnt/c/Program Files/dotnet/dotnet.exe` |
| 6 | 前端全部 `ECONNREFUSED` | 后端进程随 Bash 会话被清理 | 用 `run_in_background=true` 启动，不要 `&` / `nohup` |
| 7 | 全文检索报 `configuration "chinese" does not exist` | 连到了非自定义镜像的 PG（如官方镜像容器） | 确认 `pgsql` 用的是 `blog-postgres-zhparser:18`，见 §6 |

## 8. 配置项总表

以下配置节位于 `Blog.WebApi/appsettings.json`（基础）与 `appsettings.Development.json`（开发覆盖）。

### 8.1 `ConnectionStrings`

| 键 | 说明 |
|---|---|
| `DefaultConnection` | PostgreSQL 连接串，仅开发配置里有值 |

### 8.2 `Cache`

对应 `Blog.Application/Interfaces/CacheOptions.cs`。

| 键 | 开发值 | 说明 |
|---|---|---|
| `Enabled` | `true` | 总开关。`false` 时使用 `NullCacheService`，缓存完全旁路 |
| `Provider` | `Redis` | `Redis` 或 `Memory` |
| `RedisConnection` | `localhost:6379` | `Provider=Redis` 时必填 |
| `NullTtl` | `00:02:00` | 空值哨兵 TTL（防穿透）；**必须短于正常 TTL** |
| `LockWaitTimeout` | `00:00:03` | 重建互斥锁等待超时（防击穿），超时直接回源 |
| `TtlJitterRatio` | `0.2` | TTL 随机抖动比例（防雪崩），`0.2` 表示 ±20% |

### 8.3 `FileStorage` 与 `FileStorage:ImageOptimization`

| 键 | 开发值 | 说明 |
|---|---|---|
| `Root` | `media` | 上传文件的本地根目录（相对应用工作目录） |
| `MaxFileSize` | `10485760`（10 MB） | 单文件大小上限 |
| `ImageOptimization:Enabled` | `true` | 上传的位图自动转 WebP |
| `ImageOptimization:WebpQuality` | `82` | WebP 质量 |
| `ImageOptimization:MaxDimension` | `2560` | 最长边上限（超出的等比缩小） |
| `ImageOptimization:MaxPixels` | `40000000` | 像素总数上限（防解压炸弹） |
| `ImageOptimization:ConvertExtensions` | `.png .jpg .jpeg` | 参与转换的扩展名 |

> 转换失败或"不该转"的情况一律**原样保存**，不因优化失败而拒绝上传。

### 8.4 `RateLimit`

| 键 | 开发值 | 说明 |
|---|---|---|
| `Enabled` | `true` | 总开关 |
| `FallbackToMemory` | `true` | Redis 不可用时降级为内存桶；`false` 则故障时放行 |

规则按**顺序匹配，命中即停**：

| 规则名 | 路径前缀 | 方法 | 粒度 | 容量 | 速率(个/秒) |
|---|---|---|---|---|---|
| `search` | `/api/posts/search` | GET | Ip | 20 | 2 |
| `write` | `/api` | POST | Ip | 30 | 2 |
| `default` | `/api` | 全部 | Ip | 120 | 20 |

触发限流返回 **HTTP 429** + `Retry-After` 头 + `code=4091`。

### 8.5 `Cors`

| 键 | 开发值 | 说明 |
|---|---|---|
| `Origins` | `["http://localhost:5173"]` | 允许的前端来源 |

> 生产同源部署（Nginx 反代 `/api`）时其实不需要 CORS，此项主要服务本地开发。
> 注意当前的 CORS 策略**未启用 `AllowCredentials`**，因此不能带 cookie 跨域——本项目用 Bearer token，不受影响。

### 8.6 `Jwt`

| 键 | 开发值 | 说明 |
|---|---|---|
| `Issuer` | `blog-api` | 签发者，校验时会比对 |
| `Audience` | `blog-frontend` | 受众，校验时会比对 |
| `AccessTokenMinutes` | `30` | Access Token 有效期；**无 Refresh Token**（决策 T7） |
| `SigningKey` | 仅开发配置有 | 见 §2.3；生产必须用环境变量 |

### 8.7 `Deployment`

| 键 | 开发值 | 说明 |
|---|---|---|
| `InstanceCount` | `1` | 实例数。`> 1` 时强制要求 Redis |
| `RequireRedis` | `false` | 即使单实例也强制要求 Redis |

**校验规则**：当 `InstanceCount > 1` **或** `RequireRedis == true` 时，
必须同时满足 `Cache:Enabled == true` **且** `Cache:Provider == Redis`，
否则**应用启动即失败**并打印明确原因。这是刻意的"启动期硬校验"，
因为多实例下用内存限流会把实际阈值放大到"配置值 × 实例数"，让限流形同虚设。
