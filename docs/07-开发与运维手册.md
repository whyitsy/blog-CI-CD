## 2. 环境陷阱清单（重要）

这一节是本项目**耗时最多的部分**，全部是实测踩出来的。

### 2.1 WSL 无法直连 localhost

**现象**：在 WSL 里 `curl 127.0.0.1:5131` 一律 connection refused，
但 Windows 浏览器访问 `http://localhost:5131` 正常。

**根因**：WSL2 的 localhost 转发未生效。

**解法**：所有接口验证走 Windows 的 curl。

```bash
/mnt/c/Windows/System32/curl.exe -s --noproxy '*' http://localhost:5131/api/site/config
```

> ⚠️ **`--noproxy` 与 `*` 必须分成两个参数。**
> 写成 `--noproxy=*` 会被 shell 把 `*` 展开成当前目录的文件名。

### 2.2 环境变量 `ASPNETCORE_ENVIRONMENT` 不生效

**现象**：用 WSL 启动 `Blog.WebApi.exe` 时报
`The ConnectionString property has not been initialized`。

**根因**：通过 WSL 启动 Windows exe 时，WSL 的环境变量不会传递给 Windows 进程。

**解法**：用**命令行参数**指定环境，而不是环境变量。

```bash
./Blog.WebApi.exe --urls http://localhost:5131 --environment Development
```

### 2.3 WSL 的 node 不能用于前端

**现象**：`npx vite` 报 `Cannot find native binding`。

**根因**：WSL 的 node 缺少 `@rolldown/binding-linux-x64-gnu` 原生绑定
（依赖是在 Windows 侧安装的）。

**解法**：一律用 Windows 的 node。

```bash
"/mnt/c/Program Files/nodejs/node.exe" ./node_modules/vite/bin/vite.js --host 127.0.0.1 --port 5173
cmd.exe /c "npx vue-tsc -b --force"     # 类型检查
cmd.exe /c "npx vite build"             # 构建
```

### 2.4 dotnet 构建被文件占用

**现象**：`dotnet build` 报 `MSB3027` / `MSB3021`（无法复制 DLL）。

**根因**：运行中的 `Blog.WebApi.exe` 锁住了输出目录的 DLL。

**解法**：

```bash
/c/Windows/System32/taskkill.exe /F /IM Blog.WebApi.exe
```

> `Blog.WebApi.csproj` 里已经有一个 `KillRunningBlogWebApi` 的 MSBuild Target，
> 会在构建前自动执行 `taskkill`。但**偶尔仍会失败**（时序问题），此时手工再杀一次。

### 2.5 后端进程随 Bash 会话消失

**现象**：前端突然全部 `ECONNREFUSED`，但刚才明明启动过后端。

**根因**：用 `&` / `nohup ... &` 启动的进程，在 Bash 会话结束后被系统清理。

**解法**：用**工具的 `run_in_background=true`** 启动，让工具持有进程句柄。
**不要**加 `&`，也**不要**用 `nohup`。

### 2.6 dotnet 不在 PATH

**现象**：`dotnet: command not found`。

**解法**：用绝对路径 `/mnt/c/Program Files/dotnet/dotnet.exe`。

**若还报 NuGet 恢复失败**（`ArgumentNullException: path1`，
来自 `NuGetEnvironment.CalculateFolderPath`）：说明当前 bash 会话缺少 Windows 环境变量。
用如下包装脚本补齐后调用（按本机用户名调整路径）：

```bash
#!/bin/bash
# /mnt/d/tmpbuild/dn.sh
exec env \
  APPDATA="C:\\Users\\<用户名>\\AppData\\Roaming" \
  LOCALAPPDATA="C:\\Users\\<用户名>\\AppData\\Local" \
  USERPROFILE="C:\\Users\\<用户名>" \
  ProgramData="C:\\ProgramData" \
  ProgramFiles="C:\\Program Files" \
  "ProgramFiles(x86)=C:\\Program Files (x86)" \
  ProgramW6432="C:\\Program Files" \
  CommonProgramFiles="C:\\Program Files\\Common Files" \
  "CommonProgramFiles(x86)=C:\\Program Files (x86)\\Common Files" \
  CommonProgramW6432="C:\\Program Files\\Common Files" \
  ALLUSERSPROFILE="C:\\ProgramData" \
  OS="Windows_NT" \
  dotnet "$@"
```

### 2.7 全文检索报配置不存在

**现象**：搜索接口报 `ERROR: text search configuration "chinese" does not exist`。

**根因**：连到了一个**不含 zhparser 的 PostgreSQL**——
通常是误用了官方 `postgres` 镜像起的容器（扩展不在镜像里）。

**解法**：确认 `pgsql` 容器用的是带扩展的自定义镜像：

```bash
docker inspect pgsql --format '{{.Config.Image}}'      # 期望 blog-postgres-zhparser:18

# 若不是，按 deploy/README.md §4 用自定义镜像重建容器（数据卷沿用，不丢数据）
docker build -f deploy/postgres-zhparser.Dockerfile -t blog-postgres-zhparser:18 .
```

> **现在容器重建不会再有这个问题**：扩展已在镜像内，
> 且新数据卷会由 `/docker-entrypoint-initdb.d/01-zhparser.sql` 自动初始化。
> 详见 [01-项目初始化与配置.md](./01-项目初始化与配置.md) §6。

### 2.8 Chrome 无头截图挂住

**现象**：`chrome.exe --headless ... --screenshot=...` 不退出。

**解法**：截图前清残留进程，并在命令行加 `--virtual-time-budget`。

```bash
/c/Windows/System32/taskkill.exe /F /IM chrome.exe
```

### 3.2 启动后端

在仓库根目录执行，**用 `run_in_background=true`**：

```bash
cd Blog.Backend/Blog.WebApi/bin/Debug/net10.0 && \
env -u HTTP_PROXY -u http_proxy -u HTTPS_PROXY -u https_proxy \
```

在 `Blog.FrontEnd/` 目录执行：

```bash
"/mnt/c/Program Files/nodejs/node.exe" ./node_modules/vite/bin/vite.js --host 127.0.0.1 --port 5173
```

### 3.4 停止

```bash
# 后端
/c/Windows/System32/taskkill.exe /F /IM Blog.WebApi.exe
# 前端 dev server：结束对应后台任务即可
```

#### ⚠️ 集成测试的环境要求与行为

集成测试会**真实启动宿主 + 连真实 PostgreSQL**（用 `WebApplicationFactory`），因此：

| 事项 | 说明 |
|---|---|
| 需要 PG 在跑 | 测试库是 `blog_stage2_test_{8位随机}`，每次运行**自动创建、结束自动删除**，不污染开发库 |
| 需要 `zhparser` | 建库后测试会先创建扩展与 `chinese` 配置，再跑迁移。否则生成列会因 `to_tsvector('chinese', ...)` 失败（`42704`） |
| **关闭了限流** | 测试连发大量请求，且限流桶存在 **Redis** 里、是跨运行共享的外部状态，会污染后续运行 |
| 需要先停后端 | `dotnet build` 会因运行中的 `Blog.WebApi.exe` 锁文件而失败（先 `taskkill`，见 §2.4） |

#### 为什么测试工程要用 `GenerateProgramFile=false`

`Blog.Tests` 引用 `Blog.WebApi` 后，SDK 仍会为 Exe 类工程自动生成一个空的 internal `Program`，
它与 WebApi 顶层语句生成的 `Program` **同名**，导致 `WebApplicationFactory<Program>`
解析到错误的类型，报 **"The server has not been started or no web application was configured"**。
因此测试工程关掉自动生成（`GenerateProgramFile=false`），并由 `TestEntryPoint.cs`
提供自己的入口点。

> ⚠️ **排查提示**：`WebApplicationFactory` 会把宿主启动的真实异常**完全吞掉**，
> 只留上面那句话。若集成测试报这个错，**不要相信它** ——
> 真正的失败原因通常是「库不存在 / 缺扩展 / 连不上 / 依赖版本冲突」，
> 需要绕过工厂直接构造宿主或临时打日志才能看到。

### 4.4 数据库迁移

`dotnet-ef` 版本固定在 `Blog.Backend/dotnet-tools.json`（10.0.11）。

```bash
cd Blog.Backend

# 生成迁移（在 Blog.Infrastructure 项目上操作）
"/mnt/c/Program Files/dotnet/dotnet.exe" ef migrations add <迁移名> \
  --project Blog.Infrastructure --startup-project Blog.WebApi

# 应用迁移（通常不需要：应用启动时会自动执行）
"/mnt/c/Program Files/dotnet/dotnet.exe" ef database update \
  --project Blog.Infrastructure --startup-project Blog.WebApi

# 查看已应用的迁移
"/mnt/c/Program Files/dotnet/dotnet.exe" ef migrations list \
  --project Blog.Infrastructure --startup-project Blog.WebApi
```

#### ⚠️ 迁移的两个坑

| 坑 | 说明 | 正确做法 |
|---|---|---|
| 用 `--no-build` 生成迁移 | 会读到**旧的编译产物**，迁移生成不完整 | **不要加 `--no-build`** |
| 用 `migrations remove` 撤销未应用的迁移 | **不会回退模型快照**，残留不一致 | `git checkout -- Blog.Infrastructure/Persistence/Migrations/BlogDbContextModelSnapshot.cs` + 手工删迁移文件，然后重新 `add` |

> **迁移与宿主解耦**：`BlogDbContextFactory`（`IDesignTimeDbContextFactory`）
> 让 `dotnet ef` 不依赖 `Program.cs` 的启动配置。
> 因此即使应用因缺少 `Jwt:SigningKey` 而无法启动，依然可以生成迁移。

## 5. 接口验证

### 5.1 用 Windows curl 直连后端

```bash
# 存活检查
/mnt/c/Windows/System32/curl.exe -s --noproxy '*' http://localhost:5131/
```

```bash
TOKEN=$(/mnt/c/Windows/System32/curl.exe -s --noproxy '*' \
  -X POST http://localhost:5131/api/auth/login \

/mnt/c/Windows/System32/curl.exe -s --noproxy '*' \
  -H "Authorization: Bearer $TOKEN" \
  "http://localhost:5131/api/posts?includeUnpublished=true"
```

> ⚠️ 环境里某些工具的 localhost 请求**会被 mock 层拦截并返回伪造数据**，
> 不能用于接口验证。
>
> **可靠判据**：查后端日志是否有对应请求记录。

```bash
tail -f Blog.Backend/Blog.WebApi/logs/blog-$(date +%Y%m%d).log
```

日志中的请求行形如：

```

```

### 5.4 PostgreSQL 直查

```bash
# 进入 psql
docker exec -it pgsql psql -U kky -d blog_stage2

# 常用查询
docker exec pgsql psql -U kky -d blog_stage2 -c "\dt"
docker exec pgsql psql -U kky -d blog_stage2 -c 'SELECT "Email", "Role", "IsActive", "TokenVersion" FROM "Users";'
docker exec pgsql psql -U kky -d blog_stage2 -c 'SELECT "Title", "PublishedAt", "Version" FROM "Posts" LIMIT 10;'
```

> ⚠️ **PostgreSQL 标识符大小写敏感**。EF Core 建的表名与列名都是 **PascalCase**，
> 因此 SQL 里必须写双引号（`"Users"` 而非 `users`）。
> 在 bash 里用 `-c "..."` 时需要转义内层双引号，或用单引号包裹整条 SQL（如上）。

验证全文检索：

```bash
docker exec pgsql psql -U kky -d blog_stage2 -c \
```

### 6.3 ⚠️ 如何验证骨架屏等瞬时状态

骨架屏是**瞬时状态**，数据一回来就消失，直接截图抓不到。

| 做法 | 结果 |
|---|---|
| ✅ `Page.addScriptToEvaluateOnNewDocument`，把 `/api/posts*` 的 `fetch` 替换成**永不 resolve 的 Promise** | 稳定复现 loading 态后再断言/截图 |

| ❌ `Network.emulateNetworkConditions` 加高延迟 | 连 JS bundle 一起卡住，页面直接空白 |

> 这个坑曾经导致数轮无效排查，因此单独列出。

## 7. 版本控制纪律

### 7.1 ⚠️ 提交前必须复核

```bash
git status --short
git show --stat HEAD
```

**本项目历史上多次发生"无关文件被误删/误加并混入提交"**，
以及"工作区 39 个文件仅因行尾 CRLF/LF 差异被整体纳入提交"。
因此：

- 用 `git add -A` / `git add .` 前**先看清范围**，**优先按路径精确 add**
- 改动前用 `git ls-files <path>` 确认文件是"已跟踪"还是"计划新增"，避免误判为删除
- 未跟踪文件丢失**不可恢复**，**建议高频提交**

### 7.2 行尾统一 LF

仓库根有 `.gitattributes`：

```
* text=auto eol=lf
```

**编辑文件时不要整文件覆盖写回 CRLF**，否则会产生整文件 diff（历史上真的发生过）。

```bash
# 检查：正常应为空
git ls-files --eol | grep w/crlf
```

### 7.3 提交信息风格

参考现有历史，格式为 `类型(范围): 中文描述`：

```
feat(files): 上传图片自动转 WebP 以节省传输流量
fix(files): 文件不存在时不再下发 24 小时缓存头
docs: 同步 WebP、首个测试工程与 hero 压缩结果
refactor(auth)!: 合并两个登录页与两个登录端点为单一入口
```

| 类型 | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 Bug |
| `docs` | 文档 |
| `refactor` | 重构（不改变行为） |

## 8. 部署要点

### 8.1 部署形态

**Linux + Nginx + 容器化**，Nginx 作为反向代理置于 Kestrel 之前。

```
浏览器 ──→ Nginx ──→ Kestrel(ASP.NET Core)
                └──→ 静态文件（前端构建产物）
```

### 8.2 三个必须处理的点

| # | 问题 | 解法 |
|---|---|---|
| 1 | **SPA 的 history fallback**：前端用 `createWebHistory()`，直接刷新 `/post/xxx` 会 404（磁盘上没有这个文件） | Nginx 加 `try_files $uri $uri/ /index.html;` —— 已落地在 `deploy/nginx.conf` |
| 2 | **`X-Forwarded-For`**：加 Nginx 后 Kestrel 看到的来源 IP 全是 Nginx 的 IP，"按 IP 限流"退化成"全局限流" | ⚠️ **必须用 `$remote_addr` 覆盖，不能用 `$proxy_add_x_forwarded_for` 追加**——后者会保留客户端伪造值，而应用取的是第一段，**限流可被完全绕过**。详见 §8.6.3 |
| 3 | **工作目录**：`Logs` 与 `media` 是相对路径 | 容器里已用绝对路径 `FileStorage:Root=/app/media`，并把 `/app/media`、`/app/logs` 挂成数据卷 |
| 4 | **上传体积**：Nginx 默认 `client_max_body_size` 只有 1 MiB，而上传接口允许 10 MiB | Nginx 设 `client_max_body_size 12m;`。不设的后果很隐蔽：**nginx 直接 413，后端日志里一片空白** |

> **开发期测不出第 1 点**：Vite dev server 内置了 fallback，
> 所以"刷新 404"这个坑**只会在部署后暴露**。
>
> 第 1、2、3、4 点现在**都能在本地 compose 里复现**（见 §8.6），
> 不必等到买服务器才发现。

### 8.3 生产必须做的配置

| 项 | 要求 |
|---|---|
| `Jwt:SigningKey` | 必须通过环境变量 `Jwt__SigningKey` 注入（≥32 字节）；`appsettings.*.json` 里**都没有**这一项 |
| 管理员密码 | **立即修改** `admin@example.com` 的密码（种子密码公开在仓库里） |
| `ConnectionStrings__DefaultConnection` | 同样必须由环境变量注入（含密码），三个 appsettings 里都没有 |
| `Cache:Provider` | 生产用 `Redis`；`Deployment:InstanceCount > 1` 时 `DeploymentGuard` 会在启动期强制校验 |
| PostgreSQL | 必须使用带 zhparser 的镜像（`deploy/postgres-zhparser.Dockerfile`） |
| `RateLimit` | 规则现已落在 `appsettings.Production.json`；上线后按真实流量复查容量与速率 |
| `Cors:Origins` | 同源部署（Nginx 同时提供前端与 `/api`）时不需要 CORS，留空数组即可 |

> ⚠️ **`appsettings.Production.json` 是 2026-09 新增的**，它修复了一个隐蔽缺陷：
> 在此之前 `Cache` / `FileStorage` / `RateLimit` 三节**只存在于开发配置**，
> 生产环境会以「限流开关开着、但规则列表为空」运行 —— **限流静默失效**。
> 这类"开关是开的、你以为它在工作"的配置缺陷，比直接报错危险得多。

### 8.4 前端构建产物

```bash
cd Blog.FrontEnd
cmd.exe /c "npx vite build"
# 产物在 dist/（已 gitignore）
```

### 8.5 部署拓扑校验（T5）

| `Deployment` 配置 | 结果 |
|---|---|
| `InstanceCount ≤ 1` 且 `RequireRedis = false` | 放行（允许内存实现） |
| 其他 | 必须 `Cache:Enabled = true` 且 `Provider = Redis`，否则**启动即失败** |

**失败信息示例**：

```
检测到「多实例 / 强制要求 Redis」的部署配置，但缓存未使用 Redis：Cache:Provider = "Memory"（不是 Redis）。
  Deployment:InstanceCount = 2
  Deployment:RequireRedis   = False
多实例下使用进程内缓存与内存限流会导致：限流阈值被放大到实例数倍、缓存不共享。
请二选一：① 配置 Cache:Provider = Redis；② 若确实是单实例，把 Deployment:InstanceCount 设为 1。
```

这是刻意的"启动期硬校验"——这类问题靠运行期静默降级极难排查。

### 8.6 容器化部署（本地整栈 → 线上）

**这是当前推荐的部署路径**：用 `docker-compose.yml` 在本地就跑起「生产形态」，
确认无误后再原样搬到服务器。

#### 8.6.1 产物

| 文件 | 职责 |
|---|---|
| `docker-compose.yml`（仓库根） | 四服务编排：`nginx` / `webapi` / `pgsql` / `redis` |
| `deploy/webapi.Dockerfile` | 后端镜像（多阶段：SDK 构建 → ASP.NET 运行时） |
| `deploy/nginx.Dockerfile` | 前端构建（Node）→ Nginx 网关镜像 |
| `deploy/nginx.conf` | 静态文件 + `/api` 反代 + SPA fallback |
| `.env.example` | 环境变量模板（真实 `.env` 已 gitignore） |
| `.dockerignore` | 构建上下文排除规则（**必需**，见 8.6.3） |

#### 8.6.2 用法

```bash
# 在仓库根目录
cp .env.example .env                    # 填 JWT_SIGNING_KEY（openssl rand -base64 48）与 POSTGRES_PASSWORD
docker compose up -d --build            # 首次构建慢（拉 SDK/Node 镜像）
docker compose ps                       # 期望：pgsql/redis/webapi 都是 healthy
curl -i http://localhost:8080/health    # 期望 200 + Healthy
docker compose logs -f webapi
docker compose down                     # 停止，数据保留在命名卷
```

> 只发布 `nginx` 的 `8080` 端口。`pgsql` / `redis` **刻意不映射到宿主机**：
> ① 避开开发用独立容器的 5432/6379；② 更接近生产。
> 直连数据库用 `docker compose exec pgsql psql -U kky -d blog_stage2`。

#### 8.6.3 ⚠️ 容器化踩过的坑（三个都真实发生过）

**坑 A：缺少 `.dockerignore` → Windows 的 `obj/` 污染 Linux 构建**

``` 
error MSB4018: NuGet.Packaging.Core.PackagingException:
  Unable to find fallback package folder
  'C:\Program Files (x86)\Microsoft Visual Studio\Shared\NuGetPackages'
```

在 Linux 容器里报 Windows 路径 —— 因为 `COPY Blog.Backend/ ./` 把宿主机上
**Windows 生成的 `obj/`**（内含记录 Windows 路径的 `project.assets.json`）复制了进去。

**迷惑点**：`dotnet restore` 在容器里**已经成功**，是随后的 `COPY` 把正确结果**覆盖**了。
所以看日志会误以为是 restore 的问题。**解法**：`.dockerignore` 排除 `**/bin`、`**/obj`。

**坑 B：Docker Hub 在部分网络下不可达**

```
failed to resolve reference "docker.io/library/redis:7-alpine"
```

`mcr.microsoft.com`（.NET 官方镜像）通常可达，但 Docker Hub 不一定。
**解法**：给 Docker Desktop 配 registry mirror（Settings → Docker Engine 加
`"registry-mirrors": ["https://docker.m.daocloud.io"]`），配完需重启 Docker Desktop。

**坑 C：限流可被 `X-Forwarded-For` 绕过**（安全缺陷，已修复）

| 测试 28 次请求 | 修复前 | 修复后 |
|---|---|---|
| 正常请求 | 第 21 次起 `429` ✅ | 同左 ✅ |
| 每次伪造不同的 `X-Forwarded-For` | **0 次 `429`**（完全绕过）❌ | 26 次 `429` ✅ |

根因见 §8.2 第 2 点：nginx 用 `$proxy_add_x_forwarded_for` **追加**，
而应用取 `Split(',')[0]`（第一段，客户端可控）。
**已改为 `proxy_set_header X-Forwarded-For $remote_addr;`（覆盖）。**

> ⚠️ 该修复的前提是 **nginx 是唯一入口**（本项目 `webapi` 不对外发布端口）。
> 若前面再加 CDN / 云负载均衡，需改用 `ngx_http_realip_module` 信任上游网段。
> 更彻底的做法是应用侧改用 `ForwardedHeadersMiddleware` + `KnownProxies`，
> 即把「信任边界」表达在代码里而不是部署配置里 —— 见
> [09-已知限制与技术债.md](./09-已知限制与技术债.md)。

逐项实测结果见 [`deploy/README.md`](../deploy/README.md) §6.5（2026-09-12）。

## 9. 排错速查表

| 现象 | 最可能的原因 | 处理 |
|---|---|---|
| 前端全部 `ECONNREFUSED` | 后端进程已退出 | 用 `run_in_background=true` 重启后端（§2.5） |
| `curl` 连接被拒（WSL 内） | WSL2 localhost 转发未生效 | 用 Windows curl（§2.1） |
| `ConnectionString ... not initialized` | 环境变量没传进 Windows 进程 | 加 `--environment Development`（§2.2） |
| `Cannot find native binding` | 用了 WSL 的 node | 用 Windows node（§2.3） |
| `MSB3027` / `MSB3021` | 运行中的 exe 锁了 DLL | `taskkill /F /IM Blog.WebApi.exe`（§2.4） |
| `text search configuration "chinese" does not exist` | PG 容器重建，zhparser 丢失 | 换自定义镜像（§2.7） |
| 接口 500 且无业务日志 | 未处理异常 | 查日志 ERR 级 + 完整堆栈（§3.2） |
| 返回 401 但前端没跳登录 | 该请求不是经 `http.ts` 发出的 | 检查是否绕过封装 |
| 400/404 却记成 ERR 500 | 请求日志中间件注册顺序错了 | 见 [03-后端设计.md](./03-后端设计.md) §10.2 |
| 保存文章必 500，日志有 `23505 ... PK_PostCollections` | 改多对多连接集合时没 Include 导航 | 用 `GetWithPostsAsync`（§[06](./06-数据库设计.md) §5.2） |
| 保存文章必 500，日志有 `23505 ... PK_PostTag` | 标签整体替换而非增量同步 | 用增量同步（§[06](./06-数据库设计.md) §5.1） |
| 列表"共 N 篇"显示 `undefined` | 后端字段是 `total`，前端写成 `totalCount` | 对齐为 `total` |
| 后台点一次编辑，浏览量 +1 | 编辑器用了计数的详情接口 | 改用 `/readonly` |
| 搜索结果相关度不对 | 检查 `zhparser`/`chinese` 配置是否可用：`GET /health` 会直接验一次分词 | [03](./03-后端设计.md) §7.4 |
| 浏览器一直显示空白背景 | 曾经的 404 被缓存一整天（已修复） | 强刷；若复现见 §[03](./03-后端设计.md) §9.1 |
| `git status` 一片红但内容没变 | 行尾被写成了 CRLF | 见 §7.2 |
| `dotnet` 报 `path1` 空引用 | 沙箱会话缺 Windows 环境变量 | 用 `dn.sh` 包装（§2.6） |
