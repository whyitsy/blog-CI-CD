### 1.1 依赖方向（不可违反）

```
Blog.WebApi ──► Blog.Application ──► Blog.Domain
     │                 ▲                  ▲
     └──► Blog.Infrastructure ────────────┘
```

| 规则 | 为什么 |
|---|---|
| `Blog.Domain` **不引用任何 NuGet 包** | 领域模型不被任何框架污染，可独立测试与演进 |
| `Blog.Application` **不引用 EF Core** | 用例逻辑与持久化技术解耦；仓储以接口形式注入 |
| `Blog.Infrastructure` 只**实现** Application 定义的接口 | 依赖倒置：外层依赖内层定义的抽象 |
| `Blog.WebApi` 不含业务逻辑 | 控制器只做参数绑定 + 调用服务 + 包装响应 |

> ⚠️ **`Blog.Domain` 零依赖是本项目最容易被破坏的约束。**
> 一个真实案例：Post 的中文全文检索列需要 `NpgsqlTsVector` 类型，
> 但该类型来自 Npgsql，**不能出现在 Domain 实体上**。
> 解法是在 Infrastructure 的 `OnModelCreating` 里声明为**影子属性**
> （`entity.Property<NpgsqlTsVector>("SearchVector")`），查询时用 `EF.Property` 访问。
> 详见 §7。

## 2. 统一响应与异常

### 2.1 响应体

所有接口（含错误）统一返回：

```json
{ "code": 0, "message": "ok", "data": { } }
```

- `code = 0` 表示成功，其余为业务错误码（见 §2.3）
- HTTP 状态码**同时**被设置成语义正确的值（401/403/404/409/429），不只是 200
- 序列化用 `JsonSerializerDefaults.Web`，即 **camelCase**

`ApiResponse` 与 `ApiResponse<T>` 定义在 `Blog.Application/Common/ApiResponse.cs`。

### 2.2 异常 → 响应

`ExceptionHandlingMiddleware` 是唯一的异常出口：

| 异常 | HTTP | code | 说明 |
|---|---|---|---|
| `BusinessException` | 由 code 映射 | 异常自带 | 可预期的业务失败 |
| `DbUpdateConcurrencyException` | 409 | 4090 | 乐观锁冲突，统一文案"数据已被其他请求修改，请刷新后重试" |
| 其他 `Exception` | 500 | 5000 | 记录 ERR 级日志（含堆栈），对外只回"服务器内部错误" |

业务异常全部用 `BusinessException` 抛出，**不在控制器里写 try/catch**：

```csharp
throw new BusinessException("文章不存在", ErrorCodes.NotFound);
```

### 2.3 错误码表

定义在 `Blog.Application/Common/ErrorCodes.cs`：

| code | HTTP | 常量名 | 含义 |
|---|---|---|---|
| 0 | 200 | `Ok` | 成功 |
| 4001 | 400 | `InvalidArgument` | 参数校验失败（含缺少/非法的版本号） |
| 4002 | 400 | `BusinessRule` | 业务规则不满足（如分类名重复） |
| 4003 | 400 | `DuplicateResource` | 资源重复（如邮箱已被占用） |
| 4010 | 401 | `Unauthorized` | 未认证：缺 token / 无效 / 过期 / 账号被禁用 |
| 4030 | 403 | `Forbidden` | 已认证但无权限（角色不足，或越权访问他人资源） |
| 4040 | 404 | `NotFound` | 资源不存在 |
| 4090 | 409 | `ConcurrencyConflict` | 乐观锁并发冲突 |
| 4091 | 429 | `RateLimited` | 触发限流 |
| 4130 | 413 | `PayloadTooLarge` | 请求体过大（如上传超限） |
| 5000 | 500 | `InternalError` | 系统异常 |

> **为什么 4010/4030 必须映射成 HTTP 401/403 而不是 400**：
> 前端的 401 拦截器（自动清登录态并跳登录页）依赖 HTTP 状态码；
> 如果都返回 400，前端就无法区分"请求写错了"与"该重新登录了"。

### 2.4 JWT 的 401/403 也走统一响应体

`Program.cs` 里为 `JwtBearerEvents.OnChallenge` / `OnForbidden` 注册了处理器，
让认证失败也返回 `{code:4010/4030, ...}`，而不是 ASP.NET Core 默认的**空响应体**。
否则前端解析 JSON 会失败，只能靠状态码硬编码兜底。

> `JwtBearerEvents.OnChallenge`和`JwtBearerEvents.OnForbidden`是 ASP.NET Core JWT Bearer 认证中两个关键的事件钩子，它们分别处理认证失败和授权失败的情况，是自定义 401 和 403 响应的主要入口。
>
> **`OnChallenge` 对应 401 Unauthorized**：发生在**认证（Authentication）阶段**。当请求没有携带 Token、Token 无效或过期时触发。
>
> **`OnForbidden` 对应 403 Forbidden**：发生在**授权（Authorization）阶段**。当用户已通过认证（Token 有效），但其角色或权限不足以访问目标资源时触发。

## 3. 实体模型

### 3.1 BaseEntity（公共字段）

所有实体继承 `BaseEntity`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `Id` | `Guid` | 主键，`init` 只读 |
| `CreatedAt` | `DateTimeOffset` | 创建时间（带时区） |
| `IsDeleted` | `bool` | 软删除标记 |
| `DeletedAt` | `DateTimeOffset?` | 删除时间 |
| `Version` | `int` | 乐观锁版本号，从 1 开始 |

`Delete()` 方法只打标记，不提交——由调用方通过 UnitOfWork 统一保存。

### 3.2 User（账号）

| 字段 | 说明 |
|---|---|
| `Email` | 登录邮箱，唯一（**过滤唯一索引**：软删除后允许复用同一邮箱） |
| `PasswordHash` | PBKDF2 哈希，格式 `pbkdf2-sha512$迭代次数$base64盐$base64哈希` |
| `Role` | `Admin` / `Author`，**以字符串存库**（可读性优于魔法数字） |
| `IsActive` | 是否启用。禁用后不能登录 |
| `AuthorId` | 关联的署名对象，可空 |
| `LastLoginAt` | 最近登录时间（审计） |
| `TokenVersion` | Token 版本号，见 §5.3 |

关键方法：

| 方法 | 行为 |
|---|---|
| `UpdateProfile(role, authorId, isActive)` | 改角色/关联/启停，**不动凭据** |
| `ResetPassword(hash)` | 改密码并 `TokenVersion++`（旧 token 立即失效） |
| `SetActive(bool)` | 停用时 `TokenVersion++`（立即踢下线） |
| `LogoutAllDevices()` | `TokenVersion++` |
| `MarkLoggedIn()` | 记录登录时间 |

> `TokenVersion` 的"只在失效场景自增"这个设计很关键：正常改资料不会踢人下线，
> 只有改密码/停用/主动注销才会。

### 3.3 Author（署名对象）

| 字段 | 说明 |
|---|---|
| `Name` / `Email` / `Avatar` / `Bio` | 纯展示信息 |
| `Posts` | 导航属性（该作者署名的文章） |

**与 User 的分工**见 [02-项目总览.md](./02-项目总览.md) §1.1。

### 3.4 Post（文章）

| 字段 | 说明 |
|---|---|
| `Title` | 必填，≤200 字符 |
| `Content` | 必填，Markdown 原文 |
| `Summary` | ≤120 字符。为空时由实体自动截取正文前 **50** 字 |
| `CoverImage` | 封面图 URL，≤500 |
| `AuthorId` | 署名作者，**可空**（Author 删除时 SetNull） |
| `CreatedByUserId` | **创建者账号**，可空。归属校验与审计用 |
| `CategoryId` | 可空（分类删除时 SetNull） |
| `PublishedAt` | 可空。**是否发布由它是否有值决定** |
| `IsPublished` | 计算属性：`PublishedAt.HasValue` |
| `ViewCount` | 浏览量，原子自增 |
| `WordCount` | 字数（`Content.Length`），写入时计算，用于站点统计 |
| `UpdatedAt` | 更新时间 |

行为方法：

| 方法 | 行为 |
|---|---|
| `Update(...)` | 更新内容。摘要规则：**空则重新自动截取，非空则用传入值**，因此作者手写的摘要不会被覆盖 |
| `Publish()` | 幂等：`PublishedAt ??= now`，重复发布不覆盖首次发布时间 |
| `Unpublish()` | `PublishedAt = null` |

> **摘要为什么不额外加"是否自动"字段**：用"传入是否为空"来区分即可。
> 作者想保留自动摘要就传空，想固定就填内容。少一个字段，少一类状态不一致。
>
> ⚠️ **这条规则的边界**（读代码实测得出）：
> "填了就不再被自动覆盖"的前提是**客户端每次都把摘要原样回传**。
> 而编辑器会把当前摘要回填到输入框（`PostEditor.vue` 的 `syncFromInitial()`），
> 于是**一次保存之后，原本自动生成的摘要就被"固定"下来了**——
> 之后再改正文，摘要不再跟着变。详见 [09](./09-已知限制与技术债.md) §1。

### 3.5 Category / Tag

两者结构几乎相同（只有一个 `Name`），各自带**过滤唯一索引**
（`IsDeleted = false` 时唯一），因此软删除后可以重建同名分类/标签。

分开建表而不是合并成"术语表"，是因为二者的业务语义与 UI 呈现完全不同
（分类是单值、实心徽章；标签是多值、细边框徽章），未来演进方向也不同。

> **术语：代码里的 taxonomy（分类法）是什么**
>
> **taxonomy 不是数据库里的一张表**，而是代码里对「**组织内容的那些维度**」的统称。
> 此词借自生物分类学与信息架构领域，在博客/CMS 语境下泛指"内容分类体系"，
> 与"内容本身（`Post`）"相对。**本项目里它覆盖 Category（分类）、Tag（标签）、Collection（专栏）。**
>
> | 代码里的名字 | 实际指什么 | 为什么这么命名 |
> |---|---|---|
> | `TaxonomyQueryRepository` | 分类 + 标签**共用一个查询仓储** | 两者查询逻辑完全一致，只是返回类型不同（所以显式实现两个接口） |
> | `CacheKeys.TaxonomyPrefix`（`blog:taxonomy:`） | 分类 / 标签 / 专栏的**缓存键前缀** | 三者属于同一类东西——内容的组织维度 |
> | `TaxonomyManager.vue` | 分类与标签**共用的管理 UI** | 行内改名 + 乐观锁 + 软删除，交互完全一样 |
> | `TaxonomySkeleton.vue` | 标签墙 / 分类墙 / 专栏列表的骨架屏 | 这三页都是网格列表，骨架形状一致 |
> | `canManageTaxonomy` | "能否管理分类/标签"（即 `isAdmin`） | 对应「分类/标签写接口仅 Admin 可用」的决策，见 [10-决策记录](./10-决策记录.md) |
>
> ⚠️ **注意 Collection 的归属是"半加入"的**：
> 它**在缓存键与骨架屏上被算作 taxonomy**，但在**领域模型与仓储上是独立的**
> （`ICollectionRepository` / `CollectionQueryRepository`）——
> 因为它比分类/标签复杂得多（有 `Slug`、`SortOrder`、发布状态、多对多文章编排）。
>
> **一句话**：看到 `taxonomy`，把它读成「分类 / 标签 / 专栏这一组东西」即可。

### 3.6 Collection 与 PostCollection

| Collection 字段 | 说明 |
|---|---|
| `Title` / `Slug` / `Description` / `CoverImage` | `Slug` 唯一（过滤唯一索引），用于 `/collections/{slug}` |
| `SortOrder` | 专栏之间的排序 |
| `IsPublished` | 未发布的专栏对匿名表现为**不存在**（404） |

`PostCollection` 是**显式连接实体**（而不是 EF 隐式多对多），因为它要携带
`SortOrder`——专栏内的文章顺序是人为编排的，不是按发布时间。

> ⚠️ **多对多连接行必踩的坑**：`BaseRepository.GetByIdAsync` **不加载导航集合**。
> 如果直接改 `collection.PostLinks`，EF 会把已存在的连接行当成新增 INSERT，
> 报 `23505 duplicate key ... PK_PostCollections`（表现为"保存必 500"）。
> 必须用 `ICollectionRepository.GetWithPostsAsync`（内部 `Include(c => c.PostLinks)`）。
> 同理，文章的标签同步采用**增量同步**（只增/删差异项），不做整体替换。

### 3.7 SiteConfig / SocialLink

均为 Key-Value 或简单列表型配置，供首屏与 Footer 使用：

| SiteConfig `Key` | 值类型 | 说明 |
|---|---|---|
| `SiteName` | 字符串 | 站点名 |
| `HeroSubtitles` | JSON 数组字符串 | 打字机文案 |
| `FoundingDate` | `yyyy-MM-dd` | 建站日期 |
| `HeroBackground` | URL | Hero 背景图（可选，无种子） |

`SiteConfigDto.Versions` 会下发**每个配置项各自的版本号**（`Key -> Version`），
因为配置是逐项保存的，一个统一版本号无法表达"我只改了站点名"。

## 4. 仓储与 UnitOfWork

### 4.1 读写分离的仓储划分

项目把仓储**分成两套**：

| 类别 | 位置 | 职责 |
|---|---|---|
| **写侧仓储** | `Blog.Domain/IRepository/` + `Infrastructure/Persistence/Repositories/` | 增删改、乐观锁更新 |
| **读侧查询仓储** | `Blog.Application/Interfaces/I*QueryRepository.cs` | 只读的复杂查询与投影（直接返回 DTO） |

**为什么分开**：查询需要"一次查完并投影成 DTO"（避免 N+1 与无谓的实体追踪），
而写入需要"取实体 → 调领域方法 → 保存"。两种诉求放同一个接口里会互相牵制。

`TaxonomyQueryRepository` 一个类**显式实现** `ICategoryQueryRepository` 与
`ITagQueryRepository` 两个接口（因为分类和标签的查询逻辑完全一致）。

### 4.2 工作单元

`IUnitOfWork` 封装 `SaveChangesAsync` 与事务（`BeginTransactionAsync` / `Commit` / `Rollback`）。
`BlogDbContext` 的生命周期由 DI 管理（Scoped），UnitOfWork **不负责释放它**，只释放自己开的事务。

### 4.3 乐观锁实现（核心机制）

**决策**：用 `int Version` + SQL 条件手动控制，而不是 EF 的 `[Timestamp]` / `byte[] RowVersion`。
理由：**整数版本号与数据库无关**，可跨 PostgreSQL / MySQL / SQLite 等任意 EF 支持的库。

核心逻辑收敛在 `BaseRepository.ApplyOptimisticVersion`：

```csharp
public void ApplyOptimisticVersion(TEntity entity, int expectedVersion)
{
    if (expectedVersion < 1)
        throw new ArgumentOutOfRangeException(nameof(expectedVersion), "版本号必须 >= 1");

    var version = _context.Entry(entity).Property(nameof(BaseEntity.Version));
    version.OriginalValue = expectedVersion;   // 作为 WHERE 条件
    version.CurrentValue  = expectedVersion + 1; // 作为 SET 值
}
```

配合 `ModelBuilder` 中把 `Version` 标记为乐观并发令牌，让 EF Core 在更新或删除这些实体时，自动把 `Version` 作为 WHERE 条件，从而检测并发冲突：

```C#
foreach (var entityType in modelBuilder.Model.GetEntityTypes())
{
    var versionProperty = entityType.FindProperty(nameof(BaseEntity.Version));
    if (versionProperty is not null)
        versionProperty.IsConcurrencyToken = true;
}
```

EF 生成的 SQL 是：

```sql
UPDATE "Posts" SET ..., "Version" = @expected + 1
WHERE "Id" = @id AND "Version" = @expected;
```

受影响行数为 0 → EF 抛 `DbUpdateConcurrencyException` → 中间件映射为 **409 / 4090**。

### 4.4 写入语义统一约定

全项目遵循同一条规则，避免各处判断不一致：

| 情形 | 语义 |
|---|---|
| 实体/Key **不存在** | 视为**新增**，忽略传入 version |
| 实体/Key **已存在** | 走**乐观锁**，version 必须 ≥ 1，否则 4001 |

站点配置的逐项更新就依赖这条规则：前端对"尚不存在的 Key"传 `version = 0`，
后端走新增分支；对已存在的 Key 传实际版本号。

## 5. 认证与授权

### 5.1 整体结构

| 组件 | 位置 | 职责 |
|---|---|---|
| `Pbkdf2PasswordHasher` | Infrastructure/Security | 密码哈希与校验 |
| `JwtTokenService` | Infrastructure/Security | 签发与解析 JWT（HS256） |
| `CurrentUserResolutionMiddleware` | Infrastructure/Security | 每请求解析并校验登录用户 |
| `HttpCurrentUser` | Infrastructure/Security | 同步读取解析结果（`ICurrentUser`） |
| 授权策略 | `Program.cs` | `AdminOnly` / `ContentWriter` |

### 5.2 密码哈希

格式自描述，便于将来提升迭代次数后仍能校验旧密码：

```
pbkdf2-sha512${iterations}${base64(salt)}${base64(hash)}
```

| 参数 | 值 |
|---|---|
| 算法 | PBKDF2-HMAC-SHA512 |
| 迭代次数 | 210,000（OWASP 对该算法的建议量级） |
| 盐 | 每用户 16 字节随机 |
| 输出 | 32 字节 |

要点：

- 校验用 `CryptographicOperations.FixedTimeEquals`（**恒定时间比较，防时序攻击**）
- 校验时**按存储中记录的迭代次数**重算，因此提高默认迭代次数不会让旧密码失效
- `NeedsRehash()` 可用于登录成功时静默升级
- **绝不**使用 MD5/SHA1/SHA256 直接哈希密码

### 5.3 JWT 与"主动失效"补偿

| 项 | 值 |
|---|---|
| 算法 | HS256（对称密钥） |
| 有效期 | 30 分钟（`Jwt:AccessTokenMinutes`） |
| Refresh Token | **不做**（决策 T7） |
| 标准 claim | `sub`（用户 id）、`role`（标准 `ClaimTypes.Role`）、`jti` |
| 自定义 claim | `authorId`（可空）、`tv`（TokenVersion） |

**JWT 是无状态的，天然无法主动失效**——用户改了密码、账号被停用，
旧 token 在过期前依然有效。本项目的补偿方案：

1. 签发时把 `User.TokenVersion` 写入 `tv` claim
2. 每个请求由 `CurrentUserResolutionMiddleware` 校验四件事：
   - JWT 签名与过期时间（由 JwtBearer 中间件完成）
   - 账号存在且未被软删除
   - 账号处于 `IsActive`
   - **claim 中的 `tv` 与数据库一致**
3. 需要踢下线时把 `TokenVersion + 1`，该用户所有旧 token 立即失效

> 相比 Redis 黑名单方案，它**不引入新的运行时依赖**，且多实例下天然有效
> （校验读的是数据库，不是某个实例的内存）。

**一个刻意的细节**：校验失败时中间件**不直接返回 401**，而是不写入当前用户信息，
让后续的 `[Authorize]` 去拒绝。这样公开接口即使携带一个过期 token 也能正常访问
（否则一个过期 token 会让用户连首页都打不开）。

### 5.4 授权策略

| 策略 | 要求 | 典型用途 |
|---|---|---|
| `AdminOnly` | 角色 = `Admin` | 账号管理、作者增删、分类/标签/专栏写、站点配置写 |
| `ContentWriter` | 角色 ∈ {`Admin`, `Author`} | 文章增删改、发布、只读详情、作者资料更新 |

控制器上标注 `[Authorize(Policy = "...")]`，整个 `UsersController` 用类级标注。

### 5.5 归属校验必须在 Service 层

角色策略只能回答"这类角色能不能用这个端点"，**不能**回答"这个人能不能动这条数据"。
后者必须先查到实体才知道归属，因此必须在服务层做：

```csharp
private void EnsureCanManage(PostEntity post)
{
    if (_currentUser.IsAdmin) return;
    if (!_currentUser.IsAuthenticated) throw new BusinessException("未登录", ErrorCodes.Unauthorized);

    var isOwner = post.CreatedByUserId.HasValue && post.CreatedByUserId == _currentUser.UserId;
    if (!isOwner) throw new BusinessException("无权操作他人的文章", ErrorCodes.Forbidden);
}
```

> ⚠️ **只认 `CreatedByUserId`（账号维度），绝不能认 `AuthorId`。**
> 多个账号可以关联同一个 Author，用 AuthorId 判断会导致它们互相越权
> （本项目已实测踩坑并修复）。

### 5.6 草稿权限保护

| 场景 | 规则 |
|---|---|
| `includeUnpublished=true` 且非 Admin | 强制 `OwnedByUserId = 当前用户`，只返回自己创建的；未登录则 403 |
| `mine=true` 且不是自己 | 403 |
| 直接读未发布文章详情 | 仅 Admin 与创建者可读；**不可读时返回 404（不是 403）** |
| 未发布专栏（按 slug 访问） | 匿名得到 404 |

**为什么不可读返回 404 而不是 403**：403 等于告诉攻击者"这个 id 确实存在，只是你没权限"，
可以据此探测草稿的存在性。404 不泄露存在性。

## 6. 缓存设计

### 6.1 三实现 + 开关

| 实现 | 何时使用 |
|---|---|
| `NullCacheService` | `Cache:Enabled = false`，缓存完全旁路 |
| `MemoryCacheService` | `Cache:Provider = Memory`，单实例 |
| `RedisCacheService` | `Cache:Provider = Redis`，多实例或需要跨进程共享 |

Redis 实现中，**任何 Redis 故障（连接断开、超时）都降级为直查回源，不向调用方抛异常**。
对业务而言"缓存坏了"绝不该表现为"接口 500"。

### 6.2 缓存三防

| 问题 | 现象 | 本项目对策 |
|---|---|---|
| **穿透** | 查询不存在的数据，每次都打到 DB | 写入**空值哨兵** `∅`，TTL 用更短的 `Cache:NullTtl`（默认 2 分钟） |
| **击穿** | 热点 key 过期瞬间，大量请求同时回源 | key 级**互斥重建**：内存用信号量，Redis 用分布式锁；抢不到锁的直接回源（不阻塞），等待超时 `Cache:LockWaitTimeout`（3 秒） |
| **雪崩** | 大批 key 同时过期，DB 瞬时压力 | TTL 加 **±`Cache:TtlJitterRatio`**（默认 20%）随机抖动 |

`GetOrCreateAsync` 的 `cacheNull` 参数按场景选择：

- 列表类 → `true`（查不到就是查不到，缓存空结果防穿透）
- 详情类 → `false`（避免"新建后立即读到空哨兵"）

### 6.3 缓存 Key 规范

```
blog:{模块}:{操作}:v{版本}:{固定维度}:{可选hash}
```

| 规则 | 理由 |
|---|---|
| 固定前缀 `blog:` | 便于按前缀失效；与其他应用共用 Redis 时不冲突 |
| 带 `v{版本}` | 缓存结构不兼容变更时整体失效——改版本号即可，旧 key 靠 TTL 自然消失，无需 `SCAN` 清理 |
| 固定维度用短键名，缺省值用 `-` 占位 | 保持 key 段数固定，便于排查 |
| 长文本（如搜索关键词）做 SHA256 取前 16 位 | 避免超长或特殊字符污染 key |

示例（`CacheKeys.cs`）：

```
blog:posts:list:v1:p1s12:c-t-col-a-o-k-:u0
blog:posts:detail:v1:{guid}
blog:taxonomy:collections:v1:published
blog:site:config:v1:-
```

### 6.4 缓存 TTL

| 数据 | TTL |
|---|---|
| 文章列表 | 5 分钟 |
| 文章详情 | 10 分钟 |
| 归档 | 30 分钟 |

### 6.5 浏览量的特殊处理

浏览量累加**跳过乐观锁**，用 `ExecuteUpdate` 做数据库侧原子自增。
理由：浏览量是高频写且允许丢失精度，"两人同时看同一篇文章导致一方 409"是荒谬的体验。

缓存侧同步刷新：详情缓存里的 `ViewCount + 1` 后重新写回，避免缓存与 DB 长时间不一致。

## 7. 中文全文检索（FTS）

### 7.1 方案

用 PostgreSQL **全文检索** + **zhparser** 中文分词器：

| 组件 | 说明 |
|---|---|
| `SearchVector` 列 | `tsvector` **生成列**（stored），由数据库自动维护 |
| 权重 | 标题 A / 摘要 B / 正文 C |
| 索引 | GIN 索引 `ix_posts_search` |
| 查询 | `plainto_tsquery('chinese'::regconfig, @keyword)` |

生成列表达式：

```sql
setweight(to_tsvector('chinese', coalesce("Title", '')), 'A') ||
setweight(to_tsvector('chinese', coalesce("Summary", '')), 'B') ||
setweight(to_tsvector('chinese', coalesce("Content", '')), 'C')
```

### 7.2 两个必踩的坑

> ⚠️ **坑一：`EF.Functions.PlainToTsQuery` 在"影子属性 + 参数"形态下被判客户端求值。**
> 因为 `SearchVector` 是影子属性（不在实体上），EF Core 无法把这种组合翻译成 SQL，
> 于是回退到客户端求值——表现为"查询报错"或"结果不对"。
> **解法**：改用**参数化原生 SQL**（`FromSqlInterpolated`）。
>
> ⚠️ **坑二：`plainto_tsquery` 必须显式 `::regconfig` 转型。**
> PostgreSQL 的 `plainto_tsquery` 重载是 `(regconfig, text)` / `(text)`。
> 不转型会尝试匹配 `(text, text)`，报：
> ```
> 42883: function plainto_tsquery(text, text) does not exist
> ```
> **解法**：写成 `plainto_tsquery({config}::regconfig, {keyword})`。

### 7.3 为什么用 `Id IN (子查询)` 而不是直接 `FromSql` 包整表

```sql
SELECT p."Id" FROM "Posts" p
WHERE p."SearchVector" @@ plainto_tsquery('chinese'::regconfig, @keyword)
```

外层仍然是正常的 LINQ 查询。这样做的原因：

1. 外层可以自由组合分类 / 标签 / 作者 / 分页等过滤与投影
2. 避免 `FromSql` 与后续 `Where` 的组合限制（`FromSql` 后不能随意追加任意 LINQ）

参数由 `FromSqlInterpolated` 自动参数化，**不存在 SQL 注入**。
且 `plainto_tsquery`（而非 `to_tsquery`）会把自然语言安全地转成查询，
用户输入的 `&` `|` `!` 等不会被当作 tsquery 操作符。

### 7.4 相关度排序（T12，已实现）

搜索结果**按相关度降序**（同分再按发布时间、Id 降序，保证分页稳定）。

实现方式：用 **CTE + `Database.SqlQuery<Guid>`** 拿到「按相关度排好序的 Id 列表」，
外层仍用 `Contains` 关联回 Posts：

```sql
WITH ranked AS (
    SELECT p."Id" AS "Value",
           ts_rank(p."SearchVector", plainto_tsquery('chinese'::regconfig, @kw)) AS rank
    FROM "Posts" AS p
    WHERE p."SearchVector" @@ plainto_tsquery('chinese'::regconfig, @kw)
)
SELECT r."Value" FROM ranked AS r
ORDER BY r.rank DESC, r."Value" DESC
```

三个关键取舍：

| 取舍 | 原因 |
|---|---|
| 用 **CTE** | PostgreSQL 的 `ts_rank` 属窗口函数类，**不能直接写进 WHERE**（会报 `0A000`） |
| 用 **`SqlQuery<Guid>` 标量查询**，而不是映射 keyless 实体 | 试过 `HasNoKey()` 映射：`Id IN (...)` 形式可用，但一旦改成 `Join` 带出 rank 列，投影 `Tags` 集合就会报 **"cannot correlate on keyless entity type"**（keyless 类型无法唯一标识父行）。标量查询不引入新实体，没有这个负担 |
| 外层 `Contains` + 内存重排本页 | 保留「过滤后再分页」的语义（`total` 是过滤后的数量）。每页至多 `pageSize` 条且列表不加载正文，内存排序代价可忽略 |

> **为什么不在原生 SQL 里直接 `ORDER BY rank` 再 LIMIT**：
> 那样分类 / 标签 / 专栏 / 作者 / 归属等过滤就无法安全叠加，
> 会出现「先分页再过滤」导致的错页与错误总数。

### 7.5 扩展的部署保障

`zhparser` 不在官方 postgres 镜像中，必须自行编译。项目做了**双重保障**：

| 保障 | 覆盖场景 |
|---|---|
| `deploy/postgres-zhparser.Dockerfile` + `postgres-init/01-zhparser.sql` | **全新环境**：容器首次初始化时自动执行 |
| EF 迁移中的 `CREATE EXTENSION IF NOT EXISTS` + 创建 `chinese` 配置 | **已有库**：entrypoint 脚本不会重跑，只能靠迁移 |

迁移里还包含 GIN 索引：`CREATE INDEX ix_posts_search ON "Posts" USING gin ("SearchVector");`

## 8. 限流

### 8.1 令牌桶

| 实现 | 特点 |
|---|---|
| `RedisTokenBucketLimiter` | **Lua 脚本**保证"补令牌 + 取令牌"原子性；多实例共享同一桶 |
| `InMemoryTokenBucketLimiter` | `ConcurrentDictionary` + 每桶锁；单实例默认，也是 Redis 故障时的降级实现 |

Redis 故障时由 `RateLimitingMiddleware` 决定：`FallbackToMemory = true` 则降级内存桶，
否则直接放行（记 WARN 日志）。

### 8.2 规则匹配

规则来自配置（`RateLimit:Rules`），**按顺序匹配，命中即停**。匹配条件是
路径前缀 + HTTP 方法（方法为空表示不限）。

`Granularity` 支持三种粒度：

| 粒度 | 桶 key 的标识部分 |
|---|---|
| `Ip`（默认） | 客户端 IP |
| `Global` | 固定字符串 `global` |
| `Endpoint` | `{方法}:{路径}` |

客户端 IP 的获取**优先取 `X-Forwarded-For` 的第一个 IP**（反向代理场景），
否则用 `RemoteIpAddress`。

桶 key 形如 `blog:ratelimit:{规则名}:{标识}`。

### 8.3 响应

触发限流返回：

- HTTP **429**
- `Retry-After` 头（秒，向上取整，最小 1）
- 响应体 `{code: 4091, message: "请求过于频繁，请稍后再试"}`

未触发时返回 `X-RateLimit-Remaining` 头，便于调试。

## 9. 文件上传与图片优化

### 9.1 为什么不用静态文件中间件

所有文件都经独立接口 `/api/files/**` 读写（`FilesController`），而不是 `UseStaticFiles`：

| 理由 | 说明 |
|---|---|
| 可做路径穿越防护 | `LocalFileStorageService` 校验解析后的绝对路径仍在根目录内 |
| 精确控制缓存头 | 只在**命中文件**时下发 `Cache-Control: public,max-age=86400` |
| 可插入处理管线 | 上传时自动转 WebP |

> ⚠️ **一个已修复的真实 Bug**：此前用 `[ResponseCache]` 标注 action，
> 会把"文件不存在"的 404 也盖上 `public, max-age=86400`，
> 于是浏览器把 404 缓存一整天——文件补回来后用户仍看到空白，必须手动强刷。
> 现在改为在方法体内、**确认命中后**才设置响应头。

### 9.2 目录穿越防护与上传限制

| 项 | 值 / 行为 |
|---|---|
| 存储根目录 | `FileStorage:Root`（默认 `media`），相对应用工作目录 |
| 单文件上限 | `FileStorage:MaxFileSize`（默认 10 MB）；控制器另有 `[RequestSizeLimit(50MB)]` 作为框架层上限 |
| 存储路径 | 按年月分目录（如 `2026/09/xxx.webp`） |
| 文件不存在 | 返回 404 + 统一响应体 `{code:4040}` |

### 9.3 图片自动转 WebP

`ImageSharpOptimizer` 在保存前把位图转成 WebP：

| 配置 | 默认 | 说明 |
|---|---|---|
| `Enabled` | `true` | 总开关 |
| `WebpQuality` | `82` | 质量 |
| `MaxDimension` | `2560` | 最长边上限，超出等比缩小 |
| `MaxPixels` | `40000000` | 像素总数上限（**防解压炸弹**） |
| `ConvertExtensions` | `.png .jpg .jpeg` | 参与转换的扩展名 |

**失败即原样保存**：转换失败、或"不该转"的情况（如扩展名不在列表里）一律原样保存，
不因为优化失败而拒绝上传。

响应里带回 `originalBytes` / `storedBytes` / `converted`，便于前端提示压缩效果。

**为什么锁 ImageSharp 3.x**：v4 起要求构建期许可密钥 `sixlabors.lic`，
社区许可虽免费但需先申请，否则**构建直接报错**。v3 为纯托管实现（无原生依赖），部署最简。

## 10. 日志与可观测性

### 10.1 Serilog 配置

| 输出 | 配置 |
|---|---|
| 控制台 | 始终开启 |
| 滚动文件 | `logs/blog-.log`，按天滚动，保留 30 天 |

启动早期用 `CreateBootstrapLogger()`，这样"应用构建前"的异常也能记录。
`HostAbortedException` 被显式排除——那是 EF Core 设计期工具正常中止宿主，不是启动失败。

### 10.2 请求日志分级

`UseSerilogRequestLogging` 按响应状态码分级，避免日志噪音掩盖真故障：

| 状态码 | 级别 |
|---|---|
| ≥ 500（或抛异常） | `Error` |
| 400–499 | `Warning` |
| 其余 | `Information` |

> ⚠️ **请求日志中间件必须注册在异常处理中间件的"外层"（先注册）。**
> 否则 `BusinessException` 会先冒泡穿过日志中间件，日志记录的是"异常发生时的 500 + 完整堆栈"，
> 而客户端实际收到的是映射后的 404/403/409——日志与事实不符。
> 更糟的是"文章不存在""邮箱重复"这类可预期的业务失败会刷满 ERR，淹没真正的故障。

### 10.3 慢查询拦截

`SlowQueryInterceptor`（`DbCommandInterceptor`）在任意命令执行超过 **500ms** 时记录 WARN，
包含完整 SQL 文本与耗时。覆盖 Reader / NonQuery / Scalar 的同步与异步共 6 个方法。

## 11. 健康检查

`GET /health`（实现见 `Blog.WebApi/HealthChecks/HealthCheckSetup.cs`）。
用共享框架内置的 `Microsoft.Extensions.Diagnostics.HealthChecks`，**不引入第三方健康检查包**。

### 11.1 检查项

| 检查 | 判定 |
|---|---|
| PostgreSQL | 能连上 + `zhparser` 扩展存在 + `chinese` 检索配置存在 + **实际执行一次 `to_tsvector('chinese', ...)`** |
| 迁移 | `GetPendingMigrationsAsync()` 为空 |
| Redis | 能 Ping 通；**仅当 `Cache:Provider = Redis` 时视为必需**，否则跳过（缓存可降级） |

> 为什么要真跑一次分词：只查 `pg_extension` / `pg_ts_config` 是查不出
> 「配置存在但不可用」的。实际执行才能证明中文全文检索真的能用。

### 11.2 ⚠️ 对外只回状态，详情只写日志

响应体固定为**纯文本** `Healthy`（200）或 `Unhealthy`（503），**不含任何内部信息**。

`/health` 通常对编排系统与负载均衡开放（本项目未加鉴权），
在响应里带上「哪个依赖挂了 + 报什么错」等于向匿名访问者泄露内部结构
（数据库地址、依赖拓扑、异常栈）。排障需要的信息看服务端日志即可 ——
未通过时日志里会有结构化详情：

```
[WRN] 健康检查未通过（Unhealthy），详情：[{"Check":"database","Status":"Unhealthy",
      "Duration":"...","Error":"An exception has been raised that is likely due to a transient failure."},
      {"Check":"redis","Status":"Healthy","Duration":"...","Error":"Redis 正常，Ping 1 ms"}]
```

### 11.3 实测

| 场景 | 结果 |
|---|---|
| 一切正常 | `200` + `Healthy`（7 字节） |
| 停掉 PostgreSQL | `503` + `Unhealthy`（9 字节），响应体无内部信息 |
| 恢复数据库 | 自动回到 `200 Healthy` |

## 12. 部署拓扑校验

`DeploymentGuard.Validate()` 在 **DI 注册阶段**（即启动期）执行硬校验：

| 条件 | 结果 |
|---|---|
| `InstanceCount ≤ 1` 且 `RequireRedis = false` | 放行（允许内存实现） |
| 否则（多实例 或 显式要求 Redis） | 必须 `Cache:Enabled = true` **且** `Provider = Redis`，否则**抛异常，应用启动失败** |

**为什么用"启动即失败"而不是"运行期静默降级"**：

- 每台实例各自用内存缓存 → DB 压力变成实例数的倍数
- 每台实例各自一个内存令牌桶 → 实际限流阈值被放大到"配置值 × 实例数"，**限流形同虚设**

这类问题靠静默降级极难排查，因此把"部署拓扑"当作运维必须显式声明的输入，
而不是让代码去猜。异常信息里会打印当前配置值与两条修法。
