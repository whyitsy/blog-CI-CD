## 1. CI/CD 到底是什么

### 1.1 先把术语拆开

这三个缩写是行业里最常被含糊使用的词。它们的准确含义是：

| 缩写 | 全称 | 直译 | 人话 |
|---|---|---|---|
| **CI** | Continuous Integration | 持续集成 | 代码**频繁合回主干**，且每次合并都**立刻由机器验证**没坏 |
| **CD** | Continuous Delivery | 持续交付 | 验证通过后**自动产出一个随时能上线的包**，但"上线"这一步由人点 |
| **CD** | Continuous Deployment | 持续部署 | 验证通过后**自动上线**，没有人点 |

> ⚠️ **CD 有两个含义**，这是行业里一个长期存在的混乱。
> 本文用 **CD 特指「持续交付」**；需要「持续部署」时会写全称。

### 1.2 一个必须纠正的误解

> ❌ 「CI 就是"自动跑测试"。」

不对。**CI 的第一个关键词是"集成"（Integration），不是"测试"。**

这个词是 1990 年代极限编程（XP）提出来的，针对的是当时团队开发最大的痛苦——
**"集成地狱"**：每个人在各自的分支上开发几周，等到合并那天，几百个冲突一起爆发，
没人知道是谁弄坏的，修好要花好几天。

CI 的解法是两条：

1. **频繁合并**（至少每天一次），让冲突小到当场就能解决；
2. **每次合并都自动验证**，让"弄坏了"这件事在**几分钟内**被发现，而不是几周后。

**关键点：CI ≠ 有测试。CI = 频繁集成 + 自动验证。**
一个没有测试但有自动构建的项目，也是有 CI 的（只是验证很弱）。

### 1.3 一次完整的流程长什么样

```
   你写完代码                     机器接手                       人决策
┌──────────────┐          ┌────────────────────┐        ┌──────────────┐
│ git commit   │          │  ① 拉取代码         │        │  评审并合并   │
│ git push     │ ───────► │  ② 还原依赖         │ ─────► │  （或自动）   │
│              │  触发    │  ③ 编译             │  结果  │              │
└──────────────┘          │  ④ 静态检查/格式    │        └──────┬───────┘
                          │  ⑤ 跑测试           │               │
                          │  ⑥ 安全扫描         │               ▼
                          │  ⑦ 产出制品         │        ┌──────────────┐
                          └────────────────────┘        │  部署到环境   │
                                    │                   │ （CD 的范畴） │
                                    ▼                   └──────────────┘
                          通过 ✅ / 失败 ❌
                        （失败时通知你）
```

**①~⑦ 是 CI，部署那一段是 CD。**

### 1.4 关键词：清室验证（Clean-room Verification）

CI 真正在做的事，用一句话概括：

> **在一台"什么都没装过、跟你的开发机毫无关系"的机器上，把你的项目从零构建一遍。**

这句话里最重要的四个字是**"什么都没装过"**。

你的开发机上装过什么，你自己都不完全记得了：某个 SDK、某个环境变量、某个手工编译的
Docker 镜像、某个 PATH 里的工具。这些东西**不会出现在别人的机器上，也不会出现在服务器上**。

CI 机器每次都是干净的。**凡是"只在你机器上能跑"的东西，CI 会立刻把它暴露出来。**

## 2. 为什么本项目需要（以及什么时候不需要）

### 2.1 本项目的核心风险：开发环境 ≠ 部署环境

这不是一句空话。本项目有**两份文档白纸黑字地记录了这条鸿沟**：

| 维度 | 开发时（[07](./07-开发与运维手册.md) §1） | 部署时（[07](./07-开发与运维手册.md) §8.1） |
|---|---|---|
| 操作系统 | **Windows** 编译，WSL 发命令 | **Linux** |
| Web 服务器 | Kestrel 直连，Vite dev server | **Nginx 反向代理** + Kestrel |
| 前端路由 | Vite dev server **内置 history fallback** | Nginx 必须手工配 `try_files` |
| 数据库 | 你机器上的 `pgsql` 容器（手工编译过 zhparser） | 全新容器，靠镜像内建扩展 |
| 配置来源 | `appsettings.Development.json`（含开发密钥） | 环境变量 `Jwt__SigningKey` |
| 来源 IP | 直连，`X-Forwarded-For` 用不上 | 必须信任转发头，否则限流退化成全局限流 |

而 [07](./07-开发与运维手册.md) §8.2 里已经自己写下了那句最要命的话：

> **开发期测不出第 1 点**（SPA history fallback）：Vite dev server 内置了 fallback，
> 所以"刷新 404"这个坑**只会在部署后暴露**。

**这就是 CI 存在的理由**：用一台干净的 Linux 机器，在每次提交时把验证跑一遍。
它正好覆盖了这个盲区，而且覆盖得比部署那天早得多。

### 2.2 三个具体收益（都是本项目实测存在的痛点）

| # | 收益 | 针对本项目哪个具体问题 |
|---|---|---|
| 1 | **测试环境可复现** | 集成测试需要**真实 PostgreSQL + zhparser**（[09](./09-已知限制与技术债.md) §5.7）。现在这个依赖靠"你的开发机上恰好有个定制容器"。换台机器、或半年后重装系统，195 项测试就跑不起来——而 CI 每次都用全新环境跑一遍 |
| 2 | **仓库外的资产回家** | 前端 CDP 自动化脚本现在放在 `/mnt/d/tmpbuild/*.mjs`（[07](./07-开发与运维手册.md) §6.2 指向它们），**不在仓库里**。它们是项目资产，却没有版本控制，换机即丢，也永远进不了流水线 |
| 3 | **把"人肉纪律"变成"机器强制"** | [07](./07-开发与运维手册.md) §7.1 记录了两次真实事故：无关文件被误提交、39 个文件因 CRLF/LF 差异被整体纳入提交。这类问题**靠自觉是防不住的**，靠 CI 里一条 `git ls-files --eol \| grep w/crlf`（见 §7.1）就能防住 |

### 2.3 诚实的边界：什么情况下可以不搞 CI

行业文章常常把 CI 说成"必须做的事"，这是不诚实的。CI 也有成本：

| 成本 | 具体表现 |
|---|---|
| 学习成本 | 要学 YAML、平台概念、容器、调试流水线 |
| 维护成本 | 依赖升级会让流水线突然坏掉；过期的 Action 会有安全告警 |
| 等待成本 | 每次提交多等几分钟（但可以并行/缓存优化） |
| **心智成本** | 流水线挂了要先修流水线，而不是先写功能 |

**如果你的项目满足以下全部条件，CI 的收益确实很低：**

- 单人开发，没有第二个人要合并代码
- 一天提交不到一次，且从不回滚
- **永远不部署**（只在本机跑）
- 不依赖任何外部服务（数据库、缓存都是内存实现）

**本项目不满足其中两条**：它**要部署**（[07](./07-开发与运维手册.md) §8），
并且**依赖两个外部服务**（PostgreSQL + Redis）。所以 CI 对本项目是**有正收益**的。

> **判断准则**：只要存在「代码要离开你的开发机」这个事实，
> 就存在「环境差异会咬你」的风险，CI 就有价值。

## 3. CI 流水线的通用结构

### 3.1 标准阶段

不管用哪个平台，一条 CI 流水线的阶段几乎是固定的：

| 阶段 | 做什么 | 失败意味着 | 耗时量级 |
|---|---|---|---|
| **触发** | push / PR / 定时 / 手动 | — | — |
| **检出** | 拉代码（`git clone`） | 几乎不会失败 | 秒 |
| **还原依赖** | NuGet / npm 下载 | 依赖被删、版本冲突、网络问题 | **最慢**（可缓存） |
| **编译** | `dotnet build` / `vite build` | 代码有语法/类型错误 | 分钟 |
| **静态检查** | 格式、lint、分析器 | 代码风格不达标 | 秒~分钟 |
| **测试** | 单元 / 集成 / E2E | 行为不符合预期 | 分钟 |
| **安全扫描** | 依赖漏洞、密钥泄漏 | 用了有已知漏洞的包 | 秒~分钟 |
| **打包** | 产出可部署制品 | 打包配置错 | 分钟 |
| **发布**（CD） | 推镜像 / 传文件 / 重启服务 | — | — |

### 3.2 两条铁律

这两条是行业共识，比任何工具选型都重要：

> **铁律一：主干永远是可构建的（Green Main）。**
> 任何时刻，`main` 分支上最新的一次提交，都必须能通过全部流水线。
> 如果它红了，**修它是全项目最高优先级**——因为其他人（未来的你）会基于它继续开发。

> **铁律二：失败必须阻断合并（Required Status Checks）。**
> 光"跑流水线"是不够的。如果流水线红了还能合并，那 CI 就**只是多跑了一遍**，
> 完全没有起到拦截作用。必须在托管平台上开启**分支保护**，
> 把 CI 设为合并的必要条件。

> ⚠️ **第二条是最容易被跳过的，也是让 CI 从"有用"变成"摆设"的分界线。**
> 对单人项目尤其如此：你会觉得"我自己知道就行"。
> 但正因如此，**这条纪律才是 CI 对你唯一的强制力来源**。

### 3.3 快反馈原则（Fail Fast）

流水线的价值与「你多久知道结果」成反比。

| 做法 | 效果 |
|---|---|
| ✅ 快的任务排前面（格式检查 → 编译 → 单元测试 → 集成测试） | 最常见的问题最快报出来 |
| ✅ 各任务**并行**（后端与前端互不依赖，同时跑） | 总时长 ≈ 最慢的那条 |
| ✅ 用 `fail-fast` 让第一个失败就中止同组任务 | 省算力，早反馈 |
| ❌ 所有检查串成一条长链 | 第 8 步失败，前 7 步的时间全白花 |

### 3.4 缓存：CI 性能的关键

CI 机器**每次都是全新的**，所以每次都要重新下载全部依赖。这是 CI 里最大的时间开销。

| 生态 | 缓存什么 | 缓存键（Key）怎么写 |
|---|---|---|
| .NET | `~/.nuget/packages` | 按 `*.csproj` 的哈希 |
| Node | npm 缓存 | 按 `package-lock.json` 的哈希 |
| Docker | 镜像层 | 按 Dockerfile 的哈希 |

**缓存键的核心思想**：把「依赖清单文件的哈希」作为键的一部分。
清单没变 → 命中缓存；清单变了 → 自动换新缓存。

### 3.5 触发策略

| 触发方式 | 什么时候用 | 本项目的建议 |
|---|---|---|
| `push` 到某分支 | 保证主干始终绿 | ✅ 对 `main` 开启 |
| `pull_request` | 合并前验证 | ✅ 开启，且这是**门禁生效的地方** |
| `schedule`（定时） | 依赖漏洞扫描、夜间全量测试 | 🟡 可选，个人项目不急 |
| `workflow_dispatch`（手动） | 手动触发部署 | ✅ CD 用它 |
| `tag`（打标签） | 发版 | ✅ CD 用它 |

## 4. 行业规范：哪些对你有用，哪些是过度设计

CI/CD 领域有一堆"规范"。下面这张表的价值在于**明确区分"该学"和"该跳过"**——
个人项目最容易犯的错，是把大厂流程整套搬过来，然后被流程压死。

| 规范 | 内容 | 出处 | 对本项目的判断 |
|---|---|---|---|
| **Conventional Commits** | 提交信息写成 `类型(范围): 描述` | conventionalcommits.org | ✅ **已经在用**（[07](./07-开发与运维手册.md) §7.3）。它本身价值有限，但**是自动生成 CHANGELOG 和推导版本号的前提**，所以留着 |
| **GitHub Flow** | 主干 + 短命分支 + Pull Request | GitHub 官方文档 | ✅ **推荐**。注意：单人项目也建议走 PR，理由是**门禁只能挂在 PR 上**，直接推主干就没有拦截点 |
| **分支保护 / Required Status Checks** | 主分支必须通过检查才能合并 | 各托管平台的内置功能 | ✅ **必做**。这是让 CI 产生实际约束力的唯一手段（见 §3.2 铁律二） |
| **12-Factor App** | 配置放环境变量，不写进代码 | 12factor.net | ✅ 本项目已部分做到（`Jwt__SigningKey` 必须走环境变量、`Cache:Provider` 可切换）。引入 CD 会**强制你补全剩下的部分**（见 §8.5） |
| **语义化版本 SemVer** | 版本号 `主.次.补丁`，含义有严格定义 | semver.org | 🟡 **需要对外发布制品时才需要**。个人博客用**日期版本**（`2026.09.12`）更省事，且信息量更大 |
| **Trunk-Based Development** | 所有人直接提交主干，用特性开关隔离未完成功能 | trunkbaseddevelopment.com | 🟡 单人项目**天然就是主干开发**。但要清楚代价：没有 PR 就没有门禁，只能靠"本地先跑一遍"的自觉 |
| **DORA 四指标** | 部署频率 / 变更前置时间 / 变更失败率 / 恢复时间 | Google DORA 年度报告 | 🟡 这是**团队**度量。个人项目只需关注其中两个：**变更失败率**（部署后出问题的比例）和**恢复时间**（从出事到恢复多久） |
| **Keep a Changelog** | 面向使用者的变更日志 | keepachangelog.com | 🟡 有外部使用者时再引入。个人博客的变更日志就是 git log |
| **Git Flow** | 五种分支（main/develop/feature/release/hotfix） | Vincent Driessen, 2010 | ❌ **过度设计**。作者本人 2020 年已加注记表示不再推荐用于持续交付场景。单人项目引入它只会产生大量无意义的分支操作 |
| **100% 测试覆盖率** | — | ❌ 非标准 | ❌ **这不是行业规范**，是讹传。详见 §9.2 |

> **学规范的元原则**：先问「这条规范在防止什么具体的失败？」
> 如果答不出来，或者那个失败在你的项目里根本不会发生，就跳过它。

而且它的成本不在"加检查"，在"先把存量代码格式化一遍"。

## 6. 流水线设计 `[计划中]`

### 6.1 作业划分

按「依赖关系」和「耗时」划分成四个并行作业：

```
                   ┌─────────────────────────┐
   push / PR ────► │  job: backend           │  编译 + 195 项测试
                   │  （需要 PG + Redis）     │
                   ├─────────────────────────┤
                   │  job: frontend          │  类型检查 + 构建
                   │  （独立，无依赖）        │
                   ├─────────────────────────┤
                   │  job: hygiene           │  行尾检查（秒级）
                   │  （最快，最先失败）      │
                   ├─────────────────────────┤
                   │  job: security          │  依赖漏洞扫描（只报告）
                   └─────────────────────────┘
```

| 作业 | 包含步骤 | 需要外部服务 | 预估耗时 |
|---|---|---|---|
| `hygiene` | 检出 → 行尾检查 | 无 | < 1 分钟 |
| `security` | 检出 → `restore` → NuGet 扫描 → `npm audit` → 写作业摘要 | 无 | 1~2 分钟 |
| `frontend` | 检出 → `npm ci` → `vue-tsc` → `vite build` | 无 | 1~3 分钟 |
| `backend` | 检出 → `dotnet restore` → `build` → 起 PG/Redis → `dotnet test` → 覆盖率 | **PG + Redis** | 3~8 分钟 |

> **为什么 `hygiene` 要单独拆出来**：它最快（秒级），也最容易失败（格式问题最常见）。
> 把它排在最前面，能让大部分小问题在 1 分钟内反馈，而不是等 8 分钟。
>
> **为什么依赖扫描也单独拆一个作业**（而不是塞进 `hygiene`）：
> 它回答的是**另一个问题** —— `hygiene` 和 `backend` 问"我写的代码对不对"，
> 它问"我依赖的代码还安全吗"。后者会在你一行代码都没改的情况下变坏。
> 拆开还带来一个好处：它有了独立的检查名，将来想设成 Required 时不必动其它作业。

### 6.2 关键难点：集成测试怎么在 CI 里拿到 PG + zhparser

这是本项目上 CI 的**唯一真正难点**，值得展开讲。

**问题的根源**：`Blog.Tests` 的集成测试会真实启动宿主并连真实 PostgreSQL
（`Blog.Tests/Infrastructure/BlogApiFactory.cs`）。而它需要的东西比"一个 PostgreSQL"多：

| 需要什么 | 为什么 | 由谁提供 |
|---|---|---|
| PostgreSQL 18 | 测试要跑真实迁移 | 镜像 |
| **`zhparser` 扩展** | `Posts.SearchVector` 是**生成列**，表达式用了 `to_tsvector('chinese', ...)`。没有扩展和 `chinese` 配置，**迁移直接失败**：`42704: text search configuration "chinese" does not exist` | **必须在镜像里**（扩展不能运行时装） |
| `chinese` 检索配置 | 同上 | **EF 迁移自己建**（2026-09-13 起）。⚠️ 此前是 `BlogApiFactory.InitializeChineseTextSearch()` 预建 —— 那个绕过把「迁移链无法从零建库」这个缺陷**掩盖在了测试里**，已删除。现在集成测试在**完全干净的库**上跑迁移，本身就是回归防护（[14](./14-开发问题记录.md) 第 7 条） |
| **连接串与开发配置一致** | `BlogApiFactory.ResolveDevelopmentConnectionString()` 会**读取 `appsettings.Development.json`** 拿主机/端口/用户名/密码（→ `localhost:5432`，`kky` / `123456`），只替换库名 | **CI 里的 PG 必须用这套凭证** |
| Redis | 开发配置里 `Cache:Provider = "Redis"`。缓存会降级，但**限流桶存在 Redis 里**（[09](./09-已知限制与技术债.md) §5.7） | 建议起一个 redis 容器 |

> 💡 **好消息**：测试夹具已经关掉了限流（`["RateLimit:Enabled"] = "false"`），
> 并且**强制 `UseEnvironment("Development")`**——这意味着它会读到
> `appsettings.Development.json` 里的**开发密钥**，所以 **CI 里不需要注入 `Jwt__SigningKey`**。
> 密钥注入是 **CD（部署）** 阶段才需要的事。

**难点的解法：自定义 PG 镜像从哪来。** 有三条路：

| 方案 | 做法 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| **A. 流水线里现构建** | 在 job 里先 `docker build -f deploy/postgres-zhparser.Dockerfile`，再 `docker run` 起容器（**不能用 `services:`**，因为服务在步骤之前就启动了） | 不需要任何镜像仓库；镜像定义与使用永远同步 | 每次跑都要编译 SCWS + zhparser，**慢**（分钟级）；依赖 Docker 可用 | ✅ **推荐起步用这个**，简单直接 |
| **B. 预构建推到镜像仓库** | 手工或单独一条流水线把镜像推到 GHCR / 私有仓库，然后 `services:` 直接引用 | 快（拉现成镜像） | 多一条流水线要维护；镜像与 Dockerfile 可能不同步 ⚠️ | 🟡 流水线跑顺之后再换 |
| **C. 用官方 `postgres:18.6`** | 不用自定义镜像 | 最简单 | ❌ **不可行**：没有 zhparser，迁移必然失败 | ❌ 排除 |

> ⚠️ **方案 B 有一个隐蔽的坑**：镜像一旦推上去，`deploy/postgres-zhparser.Dockerfile`
> 改了但没重新推，CI 就一直在测一个**过期的数据库环境**，
> 而且它还是绿的——这种"假绿"比红更危险。
> 若选 B，务必让「推镜像」与「改 Dockerfile」绑定在同一条流水线里。

### 6.3 触发策略 `[计划中]`

| 事件 | 跑什么 | 理由 |
|---|---|---|
| `pull_request` → `main` | 全部四个作业 | **门禁的主战场**（其中三个是 Required，依赖扫描刻意不是） |
| `push` → `main` | 全部四个作业 | 保证主干永远绿 |
| `push` tag `v*` | 全部 + CD | 发版 |
| 手动触发 | CD | 回滚、重部署 |

## 7. 示例：一份可读的 CI 配置（逐段讲解）

> ⚠️ **下面这份文件目前不在仓库里**，它是一份**教学示例**。
> 语法是 **GitHub Actions** 的（因为生态最成熟、资料最多），
> 但**你还没决定托管平台**，所以请把它当作"读懂一份流水线"的教材，而不是可直接复制的产物。
> GitLab CI 的对应写法见 §7.3。

### 7.1 完整示例

```yaml
name: CI

# ── 触发：PR 与主干推送 ──────────────────────────────────────
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  # ══════════════════════════════════════════════════════════
  # 作业一：卫生检查（最快，最先失败）
  # ══════════════════════════════════════════════════════════
  hygiene:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # 行尾检查：把 07 §7.2 的人肉纪律变成机器强制。
      # 仓库历史上真发生过「39 个文件仅因 CRLF/LF 差异被整体纳入提交」。
      - name: 检查行尾是否被写成 CRLF
        run: |
          if git ls-files --eol | grep -q 'w/crlf'; then
            echo "::error::检测到 CRLF 行尾，请检查编辑器设置（见 docs/07 §7.2）"
            git ls-files --eol | grep 'w/crlf'
            exit 1
          fi

  # ══════════════════════════════════════════════════════════
  # 作业二：前端（与后端无依赖，完全并行）
  # ══════════════════════════════════════════════════════════
  frontend:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: Blog.FrontEnd
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '24'
          # setup-node 内置缓存：按 package-lock.json 的哈希做缓存键
          cache: npm
          cache-dependency-path: Blog.FrontEnd/package-lock.json

      # ci 而不是 install：严格按 lock 文件装，装不上就失败。
      # 这能顺带验证「package-lock.json 与 package.json 一致」。
      - run: npm ci

      # 与 07 §4.3 的手工命令完全一致
      - run: npx vue-tsc -b --force
      - run: npx vite build

  # ══════════════════════════════════════════════════════════
  # 作业三：后端（需要 PostgreSQL + zhparser）
  # ══════════════════════════════════════════════════════════
  backend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '10.0.x'

      # NuGet 包缓存：CI 里 restore 通常是最大时间开销
      - uses: actions/cache@v4
        with:
          path: ~/.nuget/packages
          key: nuget-${{ runner.os }}-${{ hashFiles('**/*.csproj') }}
          restore-keys: nuget-${{ runner.os }}-

      # ── 起数据库：方案 A（现构建自定义镜像）────────────────
      # 注意用的是 docker run 而不是 services:，
      # 因为 services: 在 steps 之前就启动了，来不及先 build 镜像。
      - name: 构建带 zhparser 的 PostgreSQL 镜像
        run: docker build -f deploy/postgres-zhparser.Dockerfile -t blog-postgres-zhparser:18 .

      - name: 启动 PostgreSQL
        run: |
          # 凭证必须与 Blog.FrontEnd 无关、但与 appsettings.Development.json 一致：
          # BlogApiFactory 会去读那个文件拿连接串，只替换库名。
          docker run -d --name pgsql \
            -e POSTGRES_USER=kky \
            -e POSTGRES_PASSWORD=123456 \
            -e POSTGRES_DB=blog_stage2 \
            -p 5432:5432 \
            blog-postgres-zhparser:18

      - name: 启动 Redis
        run: docker run -d --name redis -p 6379:6379 redis:7

      - name: 等待 PostgreSQL 就绪
        run: |
          for i in $(seq 1 60); do
            if docker exec pgsql pg_isready -U kky -d blog_stage2; then exit 0; fi
            sleep 2
          done
          echo "::error::PostgreSQL 未在 120 秒内就绪"
          docker logs pgsql
          exit 1

      # ── 编译与测试：与 07 §4.1 / §4.2 的命令一致 ──────────
      - run: dotnet restore Blog.Backend/Blog.Backend.slnx
      - run: dotnet build Blog.Backend/Blog.Backend.slnx --no-restore --configuration Release

      # ⚠️ 用 --settings 而不是 --collect:"XPlat Code Coverage"：
      #    排除 EF 迁移与源生成代码的规则**只能**通过 runsettings 传。
      #    不排除的话数字没有意义（§9.2 有实测对照）。
      #    代价是覆盖率从此依赖这个文件，所以真正的 ci.yml 里还有一步
      #    「找不到报告就报错」的哨兵，防止它被删掉后静默失效。
      - name: 跑测试并收集覆盖率
        run: >
          dotnet test Blog.Backend/Blog.Tests/Blog.Tests.csproj
          --no-build --configuration Release
          --logger "trx;LogFileName=results.trx"
          --settings Blog.Backend/coverage.runsettings

      # 无论成功失败都上传，失败时才能看到测试报告
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: backend-test-results
          path: '**/TestResults/**'

      # 失败时把数据库日志打出来，否则排查无门
      - name: 失败时输出数据库日志
        if: failure()
        run: docker logs pgsql
```

### 7.2 这份配置里最值得学的四个设计

| # | 设计 | 为什么这样做 |
|---|---|---|
| 1 | **`--no-restore` / `--no-build` 串起来** | restore 只做一次，build 只做一次，test 复用产物。避免每个命令都重新还原一遍 |
| 2 | **`if: always()` 上传测试报告** | 只在成功时上传，等于"失败时什么都没有"——而失败时恰恰最需要报告 |
| 3 | **`if: failure()` 打印数据库日志** | 集成测试在 CI 上失败时，**最需要的信息在数据库容器里**，而不在测试输出里 |
| 4 | **等待就绪的轮询循环** | 容器"启动"不等于"可连接"。没有这一步，流水线会随机失败，而且你会误以为是代码问题 |

> ⚠️ **第 4 点值得单独强调**：**CI 的随机失败（flaky）比稳定失败更有害**。
> 它会训练你"重跑一遍就好了"，从而**彻底摧毁你对流水线的信任**。
> 见到随机失败，必须当成 Bug 来修，不能靠重跑绕过。

### 7.3 GitLab CI 的对应写法（简要对照）

概念是相通的，只是名字不同：

| 概念 | GitHub Actions | GitLab CI |
|---|---|---|
| 流水线定义文件 | `.github/workflows/*.yml` | `.gitlab-ci.yml` |
| 一组任务 | `jobs.<name>` | `<stage>` + `script` |
| 运行环境 | `runs-on: ubuntu-latest` | 由 Runner 决定（`tags`） |
| 依赖缓存 | `actions/cache@v4` | `cache:` 关键字 |
| 密钥 | `secrets.NAME` | CI/CD Variables（可设为 Protected/Masked） |
| 服务容器 | `services:`（但同样有"步骤之前启动"的限制） | `services:` |
| 制品 | `actions/upload-artifact@v4` | `artifacts:` |

**结论：无论选哪个平台，你在 §3.1 学到的阶段划分都完全复用。**
真正的知识是"流水线该有哪些阶段、每个阶段防什么失败"，而不是某个平台的 YAML 语法。

### 7.4 仓库里实际生效的流水线（`[已实现]`）

**文件：`.github/workflows/ci.yml`** ｜ 首次运行 2026-09-13，作业全绿，总耗时约 **2 分钟**；
2026-09-14 增加第四个作业「依赖安全扫描」（独立并行，不影响总耗时量级）。

实测耗时（GitHub 托管 runner）：

| 作业 | 耗时 | 其中最大的开销 |
|---|---|---|
| 卫生检查 | **5s** | — |
| 依赖安全扫描 | 约 **60s**（2026-09-14 新增，待 CI 实测回填） | `dotnet restore` |
| 前端（类型检查 + 构建） | **17s** | 安装依赖 6s |
| 后端（构建 + 195 项测试） | **约 117s** | **构建 PostgreSQL(zhparser) 镜像 65s**、测试约 12s。⚠️ 这个耗时测于**只有 81 项测试时**，测试数翻倍后需重测 |

**它与 §7.1 教学示例的关键差异**（教学示例保持简洁，真实文件更"防坑"）：

| # | 真实文件多了什么 | 为什么 |
|---|---|---|
| 1 | **`concurrency` 取消旧运行** | 同一分支连续推送时，旧运行没有意义，白占额度 |
| 2 | **每个作业都设 `timeout-minutes`** | 没超时的话，卡住的作业会一直占用（默认 6 小时） |
| 3 | **起库后先单独校验 zhparser 可用** | 否则环境问题会退化成那句毫无信息量的 `The server has not been started or no web application was configured` |
| 4 | ⭐ **「校验测试确实被执行（防假绿）」步骤** | **`dotnet test` 在 0 个测试被发现时同样返回 0**。路径写错、过滤器写错都会让流水线**变绿而什么都没验证**。这一步解析 trx 报告并断言 `total > 0` |
| 5 | 用 `docker run` 而不是 `services:` | `services:` 在 steps **之前**启动，来不及先 build 自定义镜像（§6.2 方案 A） |
| 6 | ⭐ **独立的「依赖安全扫描」作业** | 它回答的是另一个问题（我**依赖**的代码安全吗），且顺手补上了"`NU1903` 警告一直在打却没人看"这个缺口，见 §9.4 |
| 7 | ⭐ **覆盖率写进作业摘要 + 「报告丢失就报错」哨兵** | 摘要让数字**看得见**；哨兵防的是把 `--collect` 换成 `--settings` 之后覆盖率**静默消失**，见 §9.2 |

> ⭐ **第 4、7 两条值得单独记住，它们是同一件事的两个例子。**
> 它们直接落实了 §11 的那句判据：
> **「一条从来没红过的流水线，你并不知道它是否真的在检查。」**
>
> 并且两条都是**先做负向验证**的：
>
> | 检查 | 负向验证怎么做 | 结果 |
> |---|---|---|
> | 防假绿（trx） | 用真实 trx 确认能读出项数（写这段时 81 项，**现在 195 项**），再用一个空 trx 确认脚本**确实会失败退出** | ✅ 退出码 1 |
> | 覆盖率哨兵 | 把 `TestResults` 目录挪走再跑那一步 | ✅ 退出码 1，并打印出「最常见的原因」 |
>
> 否则你无法区分「检查通过了」和「检查根本没生效」。

#### ⚠️ 触发条件是 `push: [main]` + `pull_request: [main]`

这意味着**往功能分支单独 push 不会触发流水线**，只有两种情况会跑：

| 事件 | 什么时候跑 |
|---|---|
| `push` 到 `main` | 合并之后（或在开启分支保护之前的直推） |
| `pull_request` 目标是 `main` | **打开 / 更新 PR 时** |

所以「我推了分支，怎么 Actions 里什么都没有」不是故障，是设计 ——
它省掉了一半无效运行（没人看的分支不需要每次都跑）。

> 💡 **副作用要知道**：功能分支在**开 PR 之前拿不到任何 CI 反馈**。
> 如果你希望分支一推上去就先自查，把触发条件改成：
> ```yaml
> on:
>   push:
>     branches: ['**']      # 所有分支
> ```
> 代价是 CI 分钟数翻倍。当前选择是「开 PR 时再跑」。

> ✅ **这一步已于 2026-09-13 完成**：**分支保护（Required Status Checks）**已开启，
> 三个作业全部标记为 Required，并做了正反两个方向的实测（PR 合并按钮变灰 / 直推 main 被 `GH006` 拒绝）。
> 现在流水线不只是"会跑一遍"，而是**有约束力**（§3.2 铁律二、§9.5）。

## 8. CD：从"能构建"到"能上线"

### 8.1 CI 与 CD 的分界

| | CI | CD |
|---|---|---|
| 问题 | "这份代码是对的吗？" | "怎么把它安全地放上服务器？" |
| 产物 | 一个**结论**（通过/失败） | 一个**制品**（镜像、文件包） |
| 失败后果 | 开发者看到红叉 | **线上用户受影响** |
| 可否自动 | 完全可以 | **要谨慎**（本项目建议先做"持续交付"，人工点上线） |

> **给本项目的建议**：先做 **CI + 持续交付**（自动产出镜像，人工部署），
> **不要**一上来就做持续部署。理由：本项目的部署形态（[07](./07-开发与运维手册.md) §8）
> 还没有真正跑通过一次，自动化一个没跑通的流程只会把问题藏得更深。

### 8.2 制品与版本号

| 制品 | 从哪来 | 版本号怎么打 |
|---|---|---|
| 后端 | `dotnet publish` 的输出，或容器镜像 | git tag |
| 前端 | `vite build` 产出的 `dist/` | 跟随后端同一个 tag |
| 数据库镜像 | `deploy/postgres-zhparser.Dockerfile` | 固定 `:18`（数据无版本概念） |

> ⚠️ **镜像绝对不要只用 `:latest`**。
> `latest` 是一个**会移动的标签**——你今天部署的和明天部署的可能不是同一个东西，
> 而且出事时你**无法说出线上跑的到底是哪一版**，也就无法回滚到确定的版本。
> 正确做法：`blog-api:2026.09.12-a3f9c21`（日期 + 提交短哈希）。

**版本号方案选型**：

| 方案 | 形如 | 适合 |
|---|---|---|
| SemVer | `1.4.2` | 有外部使用者、需要表达"兼容性"的项目 |
| **日期版本（CalVer）** | `2026.09.12` | ✅ **个人博客推荐**：信息量大、无需判断"该加主版本还是次版本" |
| 提交哈希 | `a3f9c21` | 只做内部追踪时 |

### 8.3 发布策略

| 策略 | 怎么做的 | 停机 | 回滚难度 | 个人项目适用性 |
|---|---|---|---|---|
| **重建式** | 停旧 → 起新 | 有（秒~分钟） | 容易 | ✅ **推荐起步**：个人博客停机几十秒可接受 |
| **滚动** | 逐台替换实例 | 无 | 中等 | 🟡 需要多实例 |
| **蓝绿** | 两套环境，切流量 | 无 | 容易（切回去） | 🟡 资源翻倍，个人项目偏重 |
| **金丝雀** | 先放 5% 流量观察 | 无 | 容易 | ❌ 需要流量治理设施，过度设计 |

> **个人博客的诚实选择**：`重建式` + `docker compose up -d` 或一条 `docker run` 命令。
> 停机几十秒对个人博客完全可接受，**不需要**为"零停机"投入不成比例的复杂度。

### 8.4 回滚，以及数据库迁移这个特例

**应用可以随便回滚，数据库不行。** 这是 CD 里最重要的一条认知。

| 对象 | 能否回滚 | 说明 |
|---|---|---|
| 应用镜像 | ✅ 能 | 换回上一个 tag 即可 |
| 前端静态文件 | ✅ 能 | 同上 |
| **数据库迁移** | ⚠️ **非常危险** | EF Core 迁移有 `Down()`，但**它只能撤销结构变更，撤销不了数据丢失**。比如某次迁移删掉了一列，回滚迁移能加回这一列，但**里面的数据已经没了** |

**因此行业通行做法是「向前兼容」而不是「回滚」**：

| 做法 | 说明 |
|---|---|
| **迁移与应用解耦** | 先上"只增不删"的迁移（加字段/加表），确认稳定后，再在**下一个版本**里删旧字段 |
| **迁移必须向后兼容一个版本** | 新代码要能读旧结构，旧代码要能读新结构，这样回滚才是安全的 |
| **破坏性变更单独一次发布** | 删列、改类型这类操作，单独发一次，且**必须有备份** |

> **本项目的一个真实提醒**：`Program.cs` 在**应用启动时自动执行** `dbContext.Database.Migrate()`。
> 这在单实例下很方便，但**多实例下每个实例都会抢着迁移**（EF Core 默认不取分布式锁）。
> [09](./09-已知限制与技术债.md) §5.2 与 [07](./07-开发与运维手册.md) §8.3 已经为此设计了
> `DeploymentGuard`（多实例必须 Redis），但**它管的是缓存，不管迁移竞争**。
> 真正上多实例前，这一点必须单独处理：把迁移拆成**独立的、只跑一次的部署步骤**，
> 而不是让每个实例在启动时自己抢。`[计划中]`

### 8.5 密钥管理

| 层次 | 做法 | 本项目的现状 |
|---|---|---|
| **绝不进仓库** | 密钥不写进任何被跟踪的文件 | ✅ 已做对：`appsettings.json` 里**没有** `Jwt:SigningKey`，缺失时**应用直接拒绝启动**（`Program.cs`） |
| **开发期** | `dotnet user-secrets` | ✅ 已在 `Program.cs` 的错误提示里给出 |
| **CI/CD 期** | 平台的加密变量（GitHub Secrets / GitLab Variables） | `[计划中]` |
| **运行期** | 环境变量 `Jwt__SigningKey`（双下划线 = 配置的 `:`） | ✅ 已在 [07](./07-开发与运维手册.md) §8.3 写明 |
| **轮换** | 定期更换，且要有"换密钥不掉线"的过渡方案 | `[计划中]` ⚠️ 见下 |

> ⚠️ **轮换密钥对本项目是一个真问题**：本项目**只发 Access Token、没有 Refresh Token**
> （[09](./09-已知限制与技术债.md) §3，决策 T7）。
> 这意味着**一旦换了 `Jwt:SigningKey`，所有已登录用户的 token 立即全部失效**，
> 表现为"所有人被登出"。
>
> 这在个人博客上可以接受（提前公告即可），但**必须知道**，别在流量高峰换密钥。
> 若将来需要平滑轮换，方案是"同时接受新旧两个密钥一段时间"。

## 9. 质量门禁（Gate）

门禁 = **CI 里那些"不过就不许合并"的检查**。这一节回答"该设哪些、标准是什么"。

### 9.1 测试金字塔，以及本项目的实际形状

**测试金字塔**是行业里最广为接受的一条经验（Mike Cohn 提出，Martin Fowler 推广）：

```
        ╱╲          E2E / UI 测试        少量、慢、脆、贵
       ╱  ╲
      ╱────╲        集成测试            适量
     ╱      ╲
    ╱────────╲      单元测试            大量、快、稳、便宜
   ╱__________╲
```

**核心思想**：越往上的测试，跑得越慢、越容易随机失败、定位问题越难，
所以**数量应该越少**——不是因为它们不重要，而是因为它们的**单位成本高**。

**本项目的实际形状**（截至 [09](./09-已知限制与技术债.md) §5.7，共 195 项）：

| 层 | 数量 | 占比 | 需要外部依赖 | 速度 |
|---|---|---|---|---|
| 集成（真实 HTTP + 真实 PostgreSQL） | 47 | 58% | ✅ PG + zhparser | 慢 |
| 单元 | 34 | 42% | ❌ 无 | 快 |

> ⚠️ **这是一个"倒金字塔"**：集成测试比单元测试还多。

**这是问题吗？——不完全是，但要知道代价。**

| 观点 | 理由 |
|---|---|
| ✅ **对本项目是合理的** | 这是 CRUD 型应用，**业务价值密度最高的是"权限边界"和"并发语义"**，而这些恰恰只能在完整管道里验证。70 项集成测试里有 35 项是权限矩阵——它们防的是 [09](./09-已知限制与技术债.md) §5.1 那种"漏一个 `[Authorize]` 就是完全敞开"的真实事故，价值极高 |
| ⚠️ **代价是真实存在的** | ① 跑得慢（每次都要起宿主 + 迁移）；② **必须有真实 PG + zhparser**，否则**一项都跑不了**；③ 上 CI 的门槛更高 |

**结论（写给三个月后的自己）**：不加"补单元测试"的任务。但**新增功能时**，
优先把**纯逻辑**（校验、计算、状态转换）写成单元测试——它们便宜且不需要数据库。

### 9.2 覆盖率：行业没有"必须 80%"

这是最需要破除的迷思：

> ❌「测试覆盖率必须达到 80%。」

**这句话不是任何行业标准，是讹传。** 真实的行业情况是：

| 事实 | 说明 |
|---|---|
| 没有任何权威组织规定过覆盖率阈值 | 它不是 ISO、不是 IEEE、不是任何 RFC |
| "80%" 的来源不可考 | 通常被归因于某篇博客或某本书的经验值，被反复引用后变成了"规定" |
| 覆盖率**低**确实是坏信号 | 但它的**反面不成立**：覆盖率高 ≠ 测试有效 |
| 覆盖率可以被轻易刷高 | 写一堆不 assert 的测试就能达到 100%，**代码全执行了，但一个 Bug 都发现不了** |

**该看什么**（按价值从高到低）：

| 指标 | 为什么更有价值 |
|---|---|
| **关键路径是否被覆盖** | 权限校验、金额/计数计算、状态转换——这些错了后果严重，必须覆盖 |
| **变更覆盖率**（本次改动的新代码有多少被测试碰到） | 比整体数字有用得多：它能回答"我这次改的东西测了吗" |
| **趋势**（在升还是在降） | 绝对值无意义，方向有意义 |
| **分支覆盖 vs 行覆盖** | 行覆盖会把 `if` 的假分支算作已覆盖，有误导性 |

**对本项目的建议** ✅ 已落地（2026-09-14）：

| 做法 | 说明 |
|---|---|
| **先只出报告，不设阈值** | 一开始就卡阈值，会逼着人写垃圾测试来凑数。**本项目刻意不设任何阈值** |
| 关注**关键路径** | 两个授权策略、乐观锁、草稿可见性——这些已有 79 项集成测试覆盖，是真正的资产 |
| **把覆盖率写进 CI 作业摘要** | 看得见才会被关注。制品要下载才看得到，摘要打开 PR 就在眼前 |
| 等基线稳定后**再考虑**对"新增代码"设阈值 | 而不是对整体设阈值。`[计划中]` |

#### ⚠️ 落地时才发现的第一个问题：不排除生成代码，这个数字根本没有意义

本项目第一次真正量出覆盖率时，得到的是：

```
总体：行 81.8% / 分支 40.4%        行数 5173 / 6320
```

**这个 81.8% 是假的。** 拆开看 `Blog.Infrastructure` 的 91.8%：

| 文件 | 行数 | 性质 |
|---|---|---|
| `AddAuthCollectionsAndFts` | 740 | EF Core 生成 |
| `ExtendPostSummaryLength` | 615 | EF Core 生成 |
| `InitCreate` | 591 | EF Core 生成 |
| `FixSeedAuthorAvatar` | 602 | EF Core 生成 |
| `BlogDbContextModelSnapshot` | 595 | EF Core 生成 |

**这五个文件占 `Blog.Infrastructure` 全部 4288 行的 73%。**
迁移代码"被执行过"（集成测试一跑必然执行它们），但**它一行都不代表被测过** ——
它只是把分母和分子同时往上抬，把"哪部分业务代码是裸奔的"这个真正该看的问题淹没掉。

`Blog.WebApi` 同理：编译器生成的 OpenAPI XML 注释支持代码占 187 行，覆盖率恒为 0%。

**于是加了 `Blog.Backend/coverage.runsettings`，排除 `**/Persistence/Migrations/*.cs`、
`**/*ModelSnapshot.cs`、`**/obj/**/*.cs`。** 排除前后的对照：

| | 行覆盖 | 分支覆盖 | 统计行数 |
|---|---|---|---|
| 未排除（数字无意义） | 81.8% | 40.4% | 5173 / 6320 |
| **已排除（真实基线）** | **70.2%** | **49.8%** | **2027 / 2889** |

> ⚠️ **注意那个反直觉的地方：排除生成代码后，行覆盖率降了 11.6 个百分点，
> 分支覆盖率反而升了 9.4 个百分点。**
> 代码一行没改，质量一点没变 —— 变的只是统计口径。
> 这就是"覆盖率可以被轻易刷高"最直白的实证：
> **同一份代码，只要把生成代码算进去，就能白拿十几个百分点。**
> 所以看到任何覆盖率数字，第一个该问的问题是「**分子分母里都装了什么**」。

> ⚠️ **这个数字也不是逐位确定的。** 第一次量出来是 70.9%（2049/2889），
> 之后连跑三次都是 70.2%（2027/2889）—— 差 22 行。
> 原因是覆盖率受**执行路径的非确定性**影响（并行测试的调度顺序、
> 超时/重试分支、缓存的命中与穿透）。所以：
>
> - 引用它时应当说「**约 70%**」，不要当成精确值；
> - 这是**不该对总量设阈值**的又一个理由 ——
>   一个会自己漂移的指标，卡在某个具体数字上只会产生无意义的红绿闪烁。

#### 真实基线暴露出来的裸奔点（这才是有用的部分）

| 位置 | 行覆盖 | 为什么危险 |
|---|---|---|
| `RateLimitingMiddleware` | **16.7%** | ⚠️ **这是一道安全控制**。集成测试里 `RateLimit:Enabled=false` 把它关掉了，所以「防 `X-Forwarded-For` 绕过」的验证目前只在手工跑（[07](./07-开发与运维手册.md) §8.6.3 坑 C）→ 对应 [09](./09-已知限制与技术债.md) §6 的 G10 |
| `DatabaseHealthCheck` | **0%** | 健康检查是容器编排的安全网，`depends_on: service_healthy` 全靠它 |
| `MemoryCacheService` | 0% | 开发态默认缓存实现，出问题会表现为"只有开发环境能复现" |
| `InMemoryTokenBucketLimiter` | 4.8% | 同上 |
| `DeploymentGuard` | 21.1% | 多实例保护 |
| `CollectionService.SetPostsAsync` / `UpdateAsync` | **0%** | 业务写路径 |
| `CollectionQueryRepository.GetByIdAsync` | 0% | 业务读路径 |
| `CategoryService` / `TagService` | 48% / 57% | 业务读路径 |

> **下一步该补什么，这张表就是答案**（而不是"把 70.2% 提到 80%"）。
> 按风险排序，第一个是 `RateLimitingMiddleware`：它是安全控制，
> 而且现有的手工验证（28 次请求）**很容易变成 4 个自动化测试**。

#### ⚠️ 落地时发现的第二个问题：覆盖率会「静默消失」

原来 CI 里用的是 `--collect:"XPlat Code Coverage"`。改用 `--settings coverage.runsettings` 之后，
**覆盖率就依赖那个文件了** —— 而这是它比 `--collect` 脆弱的地方：

> 如果 `coverage.runsettings` 被删除、改名，或者 `--settings` 参数被谁顺手去掉，
> `dotnet test` 会**照常变绿**，制品会照常上传（只是里面没有覆盖率文件），
> 而你会以为"覆盖率一直在正常收集"。

所以 CI 里那一步兼作**哨兵**：找不到 `coverage.cobertura.xml` 时**直接报错**。
这一类"配置丢失导致检查静默失效"的问题，和 [14](./14-开发问题记录.md) 第 8 条是同一族。

### 9.3 格式与静态检查

**现状：本项目完全没有。**

| 检查 | 现状 | 该补什么 |
|---|---|---|
| C# 代码风格 | ❌ 无 `.editorconfig` | 加 `.editorconfig`（可与 Visual Studio 共享），CI 里跑 `dotnet format --verify-no-changes` |
| C# 分析器 | ❌ 未开 | `EnableNETAnalyzers`（.NET SDK 内置，只需一个属性）；`TreatWarningsAsErrors` |
| 前端 lint | ❌ `package.json` 里没有 `lint` 脚本，无 ESLint | 加 ESLint + `eslint-plugin-vue`，并在 `package.json` 加 `"lint": "eslint ."` |
| 前端格式化 | ❌ 无 Prettier | 可选。若用，必须与 ESLint 配置好分工，否则两者会互相打架 |
| **行尾一致性** | ⚠️ 有 `.gitattributes`（`* text=auto eol=lf`），但**没有检查** | ✅ CI 里加一条 `git ls-files --eol \| grep w/crlf`（见 §7.1）——**成本最低、收益最高** |

> ⚠️ **引入格式检查的正确顺序**：
> ① 先加配置 → ② 在本地**一次性格式化整个代码库**（会产生一个巨大的提交）→
> ③ 之后才在 CI 里开启检查。
>
> **不要**在没格式化的代码库上直接开检查——那会让第一次流水线产生上千条告警，
> 然后你会关掉它。

### 9.4 依赖安全扫描

**现状：✅ 已落地（2026-09-14）。** 一个独立 CI 作业 + 一份 Dependabot 配置。

| 扫描对象 | 命令 / 工具 | 输出 |
|---|---|---|
| NuGet 直接依赖 | `dotnet list package --vulnerable` | 有已知 CVE 的包 |
| NuGet **含传递依赖** | `dotnet list package --vulnerable --include-transitive` | ⚠️ **这个更重要**——漏洞通常藏在传递依赖里 |
| npm | `npm audit --registry=https://registry.npmjs.org` | 同上（⚠️ **源必须显式指定**，见下） |
| 密钥泄漏 | GitHub 的 secret scanning（平台功能） | 防止把密钥推上去 |
| 自动化 | **Dependabot**（`.github/dependabot.yml`，nuget + npm + github-actions） | 自动开 PR 升级有漏洞的依赖 |

#### ⚠️ 落地时才发现的第一个事实：这个项目**早就在扫**，只是没人看得见

这一点值得单独写出来，因为它彻底改变了 G5 的定性：

> **NuGet Audit 从 .NET 8 SDK 起是默认开启的。** `dotnet restore` / `dotnet build`
> 会直接打出 `NU1903` 警告。也就是说 **CI 每一次都在检查依赖漏洞** ——
> 只是它是**警告**：不会让流水线变红，也不会有任何人看见。

所以 G5 的准确描述不是"完全没做"，而是：

| 层面 | 原来的状态 |
|---|---|
| 信息有没有被产出 | ✅ 有（`NU1903` 警告一直在打） |
| 信息有没有被**看见** | ❌ 没有（警告混在构建输出里） |
| 信息能不能**阻止**问题 | ❌ 不能（警告不是错误） |

**这次补的是第二层**（独立作业 + 结果写进作业摘要）。
第三层刻意先不做 —— 见下"为什么只报告不阻断"。

> 将来要把它升级成阻断，最省事的路径**不是再加一个作业**，
> 而是给构建加 `-warnaserror:NU1901;NU1902;NU1903;NU1904` 一行参数。

#### ⚠️ 落地时才发现的第二个事实：`npm audit` 在默认镜像源下**根本没执行**

这是本次最值得记住的一个坑（已单独记入 [14](./14-开发问题记录.md) 第 8 条）。

本机的 npm 默认源是 `registry.npmmirror.com`（淘宝镜像），而它
**没有实现 audit 接口**。实测：

| 命令 | 结果 |
|---|---|
| `npm audit` | ❌ `404 [NOT_IMPLEMENTED] /-/npm/v1/security/* not implemented yet`，**非 0 退出** |
| `npm audit --registry=https://registry.npmjs.org` | ✅ `found 0 vulnerabilities`（不需要 `node_modules`，只读 lock 文件） |

危险的地方在于**组合条件**：

> 这个作业是 `continue-on-error`（只报告不阻断）→ 非 0 退出不会让作业变红
> → **「审计没跑成」和「审计跑了、没发现漏洞」在页面上长得一模一样**。

所以 CI 里加了一道显式检查：输出里必须出现 `found N vulnerabilities`（N 可以是 0）。
没有这行就报错，而不是当成"干净"。

**并且：换掉本机默认源不算解决。** CI 是干净的机器，正确做法是**每次显式指定 `--registry`**，
把"用哪个源做审计"这件事写在流水线里，而不是依赖某台机器的 `.npmrc`。

#### ✅ 实测结果，以及一个必要的阳性对照

| 生态 | 结果 |
|---|---|
| NuGet（5 个工程，含传递依赖） | **0 漏洞** |
| npm（含 devDependencies） | **0 漏洞** |

> ⚠️ **但"扫描器说没有漏洞"这件事本身不可信 —— 直到你验证过它会报。**
> 一个永远输出"干净"的扫描器和一台坏掉的扫描器，**输出完全一样**。
>
> 所以做了一次阳性对照：临时建一个工程引用 `Newtonsoft.Json 12.0.1`，
> 确认扫描器报出了 `GHSA-5crp-9r3c-p9vr`（High）。
>
> 顺手还测出一件事：**`dotnet list package --vulnerable` 在发现漏洞时退出码依然是 0。**
> 所以退出码只能用来判断"命令有没有跑起来"，**不能**用来判断"有没有漏洞" ——
> CI 里那道 grep 检查就是为此存在的。

#### ⚠️ `SixLabors.ImageSharp`：核实之后，风险描述要改得更准确

[09](./09-已知限制与技术债.md) 原来的说法是「锁在 3.1.12，**锁版本等于不会自动收到安全修复**」。
核对 NuGet 上的完整版本列表后（3.x 到 `3.1.12` 结束，之后直接是 `4.0.0` / `4.1.0` / `4.1.1`）：

| 说法 | 对错 |
|---|---|
| "锁 3.1.12 遗漏了 3.x 已有的安全修复" | ❌ **不成立** —— 它就是 3.x 的最新版，没有更新的 3.x 可升 |
| "未来 3.x 若出 CVE，唯一修复版在 4.x，而 4.x 需要许可密钥" | ✅ **这才是真正的风险**，而且它**没有解**，只能自己打补丁或换库 |

所以处理方式变成：**把它变成一个定期动作**（定期看一眼 3.x 有没有安全公告），
而不是指望 Dependabot —— Dependabot 会建议升 4.x，而那是不可接受的。

> `.github/dependabot.yml` 里已经为它写了 `ignore` 规则来屏蔽 4.x 的升级 PR。
> ⚠️ **那条规则有一个必须知道的陷阱**（见 [14](./14-开发问题记录.md) 第 8 条）：
> 只写 `dependency-name` 的 ignore 规则会被展开成 `>= 0`，
> **并且同时作用于安全更新通道** —— 结果是这个包的安全修复 PR 也被静默关掉。
> 必须显式写 `update-types` 才能把规则限定在版本更新通道。

#### 为什么「只报告不阻断」（这不是偷懒）

```
刚引入扫描 → 先只看结果     ← 现在在这里
结果稳定、确认"报出来的我都会修" → 再改成阻断
```

反过来做（一上来就阻断）最常见的结局是：
某天被一个**修不了**的 CVE 卡住 → 你把整个作业注释掉 → **从此它就是个摆设。**

> 这和 [09](./09-已知限制与技术债.md) §6.2 的判断一致：
> 一个"经常被迫绕过"的门禁，比没有门禁更糟 —— 它训练你忽略红色。

### 9.5 一份可执行的门禁清单 `[部分实现]`

按"先做哪个"排序。每条都给出**具体的失败条件**，否则门禁形同虚设。
**状态列反映 2026-09-14 的实际情况。**

| 顺序 | 门禁 | 失败条件 | 成本 | 状态 |
|---|---|---|---|---|
| 1 | 后端编译 | `dotnet build` 非 0 退出 | 极低 | ✅ 已落地 |
| 2 | 后端测试 | 任一测试失败 | 低（已有 195 项） | ✅ 已落地 |
| 3 | 前端类型检查 | `vue-tsc` 报错 | 极低 | ✅ 已落地 |
| 4 | 前端构建 | `vite build` 失败 | 极低 | ✅ 已落地 |
| 5 | 行尾检查 | 存在 `w/crlf` | 极低 | ✅ 已落地 |
| 6 | **分支保护开启** | 上述任一失败则**禁止合并**（直推同样被拒） | 极低（平台配置） | ✅ **已开启**（2026-09-13） |
| 7 | 依赖漏洞扫描 | 有高危 CVE（**先只报告不阻断**） | 低 | ✅ **已落地**（2026-09-14，独立作业 `security`） |
| 8 | 覆盖率（排除生成代码 + 写进作业摘要） | 不阻断，**不设阈值**；报告丢失则报错 | 低 | ✅ **已落地**（2026-09-14，基线 行 70.2% / 分支 49.8%） |
| 9 | `dotnet format --verify-no-changes` | 格式不符（**需先全量格式化**） | 中 | ❌ 未做（G6） |
| 10 | 前端 ESLint | lint 报错（**需先配置并清理存量**） | 中 | ❌ 未做（G6） |
| 11 | 前端 E2E（CDP 脚本） | 断言失败（**需先把脚本移进仓库**） | 高 | ❌ 未做（G2） |

> **第 7、8 两条的共同点**：它们都**不阻断**，但都**必须看得见**。
> 「不阻断」不等于「可以不看」—— 结果被写进作业摘要，打开 PR 就在眼前。
>
> ⚠️ 同时它们各自都配了一道**失效哨兵**，因为"非阻断检查"最容易变成摆设：
>
> | 检查 | 它的静默失效方式 | 哨兵 |
> |---|---|---|
> | 依赖扫描 | `npm audit` 在镜像源下**非 0 退出**，而作业是 `continue-on-error` → 「没跑成」和「干净」长得一样 | 输出里必须出现 `found N vulnerabilities`，否则报错 |
> | 覆盖率 | 换成 `--settings` 后，runsettings 被删 → `dotnet test` 照常变绿、制品照常上传但里面没有覆盖率 | 找不到 `coverage.cobertura.xml` 就报错 |

#### 第 6 条是怎么验的（正反两个方向都验）

分支保护的坑在于：**配好了和没配好，界面看起来差不多**。所以必须做**反向验证**——
用一个「故意失败」的提交去撞门禁，确认它真的会被拦，否则无法区分
「门禁生效了」和「测试根本没跑」。

| 方向 | 手段 | 实测结果 |
|---|---|---|
| **PR 合并**被拦 | 开一个含**故意失败测试**的 PR（`BranchProtectionCheck.cs`），看合并按钮状态 | ✅ 三条 Required 检查中「后端」变红，**Merge 按钮变灰不可点** |
| **直推 main**被拦（第一次） | 把上述**检查失败**的分支直接 `git push origin <bad-branch>:main` | ✅ 被拒：`GH006: Protected branch update failed for refs/heads/main. - Required status check "后端（构建 + 测试）" is failing.` |
| **直推 main**被拦（第二次，更关键） | 等验证分支清理后，再把**正常的功能分支**（检查根本还没跑过）直推 `main` | ✅ 被拒，且**两条规则都报了出来**：<br>`- Changes must be made through a pull request.`<br>`- 3 of 3 required status checks are expected.` |

> 第二次验证比第一次**更有价值**：第一次只报出了「状态检查失败」，
> 无法回答「如果检查是绿的，能不能直推」这个真正的问题。
> 第二次用一个**没有跑过任何检查**的分支去推，服务端明确回了
> `Changes must be made through a pull request` ——
> 这才是「Require a pull request before merging」真正生效的直接证据，
> 也是 §3.2 铁律一（不能直推主分支）的落地证明。

> ⚠️ **一个容易搞错的细节（我自己先搞错过）**：
> 「Require status checks」**不只是**管 PR 合并，它对**直接 push** 同样生效——
> 推上去的提交如果必需检查是红的，push 阶段就被服务端 hook 拒掉。
> 光靠 `git push --dry-run` **验不出来**：dry-run 只做本地协商，不会触发服务端的
> `pre-receive` 钩子，所以它照样报成功。要验就必须真推。

验证完毕后清理：删除验证分支（GitHub 会连带自动关闭对应 PR），
避免一个永远红的流水线留在仓库里制造噪音。

> ✅ **第 6 条现已完成，这份清单的核心目的（让 CI 从"信息"变成"约束"）达成。**
> 剩下 7、9、10、11 都是**增量**能力，不再是"不做就全白做"的性质。

## 10. ⚠️ 坑清单（本项目特有）

这一节是本篇最实用的部分。全部是**本项目代码实测会遇到的**，
不是通用 CI 教程里的泛泛之谈。

### 10.1 CI 里集成测试失败的头号原因

集成测试在 CI 上失败时，**错误信息几乎总是同一句**：

```
The server has not been started or no web application was configured.
```

而它**几乎从来不表示真正的原因**。真实原因按出现频率排序：

| 排序 | 真实原因 | 怎么确认 |
|---|---|---|
| 1 | **PG 连不上**（容器没起好 / 端口没映射 / 凭证不匹配） | 在 CI 里 `docker logs pgsql`；确认 `pg_isready` 通过 |
| 2 | **缺少 `chinese` 检索配置** → 迁移报 `42704` | 用镜像里的扩展；确认初始化脚本执行了 |
| 3 | **`appsettings.Development.json` 没被读到** → 连接串为空 | 该文件在仓库里（✅ 已跟踪），CI 检出后应存在 |
| 4 | **EF Core 版本冲突**（`Mvc.Testing` 传递引入了旧版 Relational） | 已由 `Blog.Tests.csproj` 显式对齐到 10.0.11 解决 ✅ |
| 5 | **PG 还没就绪就开始跑测试** | 必须有轮询等待（见 §7.1） |

> **排查原则**（源自 [09](./09-已知限制与技术债.md) §5.7 的教训）：
> **不要相信那句话**。要么绕过 `WebApplicationFactory` 直接构造宿主，
> 要么临时打开详细日志，才能看到真实异常。

### 10.2 Windows 上能过、Linux CI 上挂掉的四类原因

这是「本地绿、CI 红」的经典场景。本项目**有 Windows 开发 → Linux 部署的固定落差**，
所以这四类问题**一定会遇到**：

| # | 原因 | 表现 | 本项目状态 |
|---|---|---|---|
| 1 | **文件系统大小写敏感** | Windows 不区分 `Posts.ts` 和 `posts.ts`；Linux 区分。前端 import 路径大小写写错，**本地完全无感，CI 直接模块找不到** | ⚠️ 需注意 |
| 2 | **路径分隔符** | 代码里硬编码 `\` 在 Linux 上失效 | ✅ 目前代码用 `Path.Combine`，风险低 |
| 3 | **行尾 CRLF/LF** | 整个文件 diff | ✅ `.gitattributes` 已统一为 LF，但**无检查**（见 §9.3） |
| 4 | **区域设置（Culture / ICU）** | ⚠️ **最隐蔽的一条**：.NET 在 **Windows 用 NLS、Linux 用 ICU** 做字符串比较与排序。**同一个 `OrderBy` 在两个平台上可能给出不同顺序** | ⚠️ 本项目有中文排序场景（归档按年月、标题排序），值得留意 |

> **第 4 条的应对**：凡是**依赖排序结果**的测试，不要断言"第 1 条是 X"，
> 要么显式指定比较器（`StringComparer.Ordinal`），要么断言"集合内容相同、顺序无关"。
> 排除了文化差异的排序叫 **Ordinal 排序**，它是跨平台稳定的。

### 10.3 环境变量在 CI 里的写法

.NET 的配置系统用**双下划线**表示层级。这在 CI 的 YAML 里极易写错：

| 想配置的键 | 环境变量写法 | 常见错误 |
|---|---|---|
| `Jwt:SigningKey` | `Jwt__SigningKey` | ❌ 写成 `Jwt:SigningKey`（YAML 里会被当字符串，应用读不到） |
| `ConnectionStrings:DefaultConnection` | `ConnectionStrings__DefaultConnection` | 同上 |
| `Cache:Provider` | `Cache__Provider` | 同上 |

> ⚠️ **`Jwt__SigningKey` 的长度必须 ≥ 32 字节**，否则 `Program.cs` 会**拒绝启动**。
> 在 CI 的 secret 里存一个 base64 字符串时，注意**它的长度是编码后的长度**，
> 48 字节原始数据 base64 后是 64 个字符，远超 32，安全。

### 10.4 测试夹具是"读文件"而不是"读环境变量"

一个必须在 CI 配置时知道的事实：

```
BlogApiFactory.ResolveDevelopmentConnectionString()
  → 沿着目录向上找 Blog.Backend.slnx（定位仓库根）
  → 读取 Blog.WebApi/appsettings.Development.json
  → 取 ConnectionStrings:DefaultConnection
  → 只把 Database 换成 blog_stage2_test_{随机}
```

**三个推论**：

| 推论 | 说明 |
|---|---|
| CI 里**必须有** `appsettings.Development.json` | ✅ 它已被 git 跟踪，检出后就有 |
| **不能**靠环境变量覆盖连接串来改主机 | ❌ 夹具是从**文件**读的，环境变量在这里不起作用 |
| CI 里的 PG **必须**监听 `localhost:5432`，用户 `kky` / 密码 `123456` | 否则连不上。这也是 §7.1 里 `docker run -e POSTGRES_USER=kky ...` 的由来 |

> 💡 **这是一个可以改进的设计**（`[计划中]`）：
> 让夹具**优先读环境变量、回退到文件**，CI 就可以用任意凭证，不必和开发配置绑定。
> 现在的绑定方式虽然能用，但把"开发机的约定"泄漏进了 CI。

## 11. 动手顺序（第一次接触照着做）

**不要一次把 §7 那份完整配置写出来。** 第一次接触 CI，正确做法是**分阶段**，
每阶段都跑通了再进下一步。这样出问题时你只需要怀疑一个地方。

| 阶段 | 做什么 | 完成判据 | 预估 |
|---|---|---|---|
| **0** | **把手工命令写成脚本**（如 `Blog.Backend/build.sh`），在本地跑通 | 一条命令能完成 build + test，本地绿 | 半小时 |
| **1** | 最小流水线：**只跑 `dotnet build`** | 提交后平台页面上出现绿灯 | 1 小时 |
| **2** | 加**前端作业**（`npm ci` + `vue-tsc` + `vite build`） | 两个作业并行跑，都能绿 | 1 小时 |
| **3** | 加**后端测试**（起 PG + Redis，跑 195 项） | 测试在 CI 上全绿；**故意改坏一个测试，确认它变红** | 2~4 小时 ⚠️ 最难的一步 |
| **4** | 加**缓存**（NuGet + npm） | 流水线总时长明显下降 | 半小时 |
| **5** | 加**门禁**：行尾检查 + 分支保护 | 流水线红时**合并按钮被禁用** | 半小时 |
| **6** | 加**依赖漏洞扫描**（独立作业 + Dependabot） | 报告出现在作业摘要里；**并做一次阳性对照，确认它真的会报** | 半小时 |
| **7** | 加**覆盖率**（先排除生成代码，再谈阈值） | 作业摘要里出现行/分支覆盖率；**删掉 runsettings 确认哨兵会报错** | 1 小时 |
| **8** | 加 **CD**：构建镜像、推仓库、手工触发部署 | 能一键部署到测试环境 | 数小时 |
| **9** | 加**格式检查**与前端 ESLint（先全量清理存量） | `dotnet format` 与 ESLint 无告警 | 1~2 天 ⚠️ 清理存量最费时 |

> ⚠️ **阶段 3 的完成判据里有一句关键的**：「**故意改坏一个测试，确认它变红**」。
> 这是[09](./09-已知限制与技术债.md) §1 里那条经验的推广：
>
> > **先在"坏"的代码上跑一遍、确认它会失败，再在"好"的代码上跑通——
> > 否则你无法区分「真的通过了」和「测试根本没生效」。**
>
> 这条对整个流水线同样成立：**一条从来没红过的流水线，你并不知道它是否真的在检查。**
>
> 阶段 6、7 的完成判据里那句「确认它真的会报 / 确认哨兵会报错」是**同一条经验的延续**：
> 依赖扫描器永远输出"干净"时，和一个坏掉的扫描器**输出完全一样** ——
> 所以必须用一个已知有漏洞的包去撞它一次（实测做法见 §9.4）。
