# 第一部分 · C# 与 .NET 基础

## 1. 依赖注入（DI）与生命周期

### 1.1 原理

**依赖注入**是"控制反转"（IoC）的一种实现：类不在内部 `new` 自己的依赖，
而是**声明自己需要什么**，由外部容器构造并传进来。

```csharp
// ❌ 紧耦合：PostService 自己决定用什么仓储，无法替换、无法测试
public class PostService
{
    private readonly PostRepository _repo = new PostRepository(new BlogDbContext(...));
}

// ✅ 依赖倒置：只声明接口需求
public class PostService
{
    private readonly IPostRepository _repo;
    public PostService(IPostRepository repo) => _repo = repo;   // 构造函数注入
}
```

**为什么值得**：可替换实现（换数据库、换缓存）、可测试（注入 fake）、
生命周期集中管理（不必手工 new/dispose）。

### 1.2 三种生命周期（最重要的知识点）

| 生命周期 | 注册方法 | 实例何时创建 | 何时释放 | 适用 |
|---|---|---|---|---|
| **Singleton** | `AddSingleton` | 首次被请求时，**全局唯一** | 应用关闭 | 无状态、线程安全、创建昂贵 |
| **Scoped** | `AddScoped` | **每个 HTTP 请求**一个 | 请求结束 | DbContext、仓储、业务服务 |
| **Transient** | `AddTransient` | **每次注入**都新建 | 随持有者 | 轻量、无状态的小对象 |

**记忆要点**：Scoped 的生命周期边界就是"一个请求"。

### 1.3 ⚠️ 最容易犯的错：生命周期不匹配

> **Singleton 不能依赖 Scoped。**

原因：Singleton 活得比 Scope 长。若它持有 Scoped 实例（如 `DbContext`），
该实例会在请求结束后被释放，而 Singleton 仍持有已被释放的引用。

.NET 的 DI 容器在**启动时**会做校验，遇到"Singleton 依赖 Scoped"会直接抛
`InvalidOperationException`——这是好事，问题在启动期就暴露。

同理，**不要从 Singleton 里解析 Scoped 服务**（如通过 `IServiceProvider`）。
若确实需要，应注入 `IServiceScopeFactory` 并显式创建 Scope。

### 1.4 DI 的三种注册写法

```csharp
// 1. 直接注册类型（最常用）
services.AddScoped<IPostRepository, PostRepository>();

// 2. 注册现成实例（如无状态且已构造好的对象）
services.AddSingleton<IPasswordHasher>(_ => new Pbkdf2PasswordHasher());

// 3. 工厂委托（需要根据配置决定实现时）
services.AddSingleton<ICacheService>(sp =>
{
    var options = configuration.GetSection(CacheOptions.SectionName).Get<CacheOptions>() ?? new CacheOptions();
    if (!options.Enabled) return new NullCacheService();
    return options.Provider.Equals("Redis", StringComparison.OrdinalIgnoreCase)
        ? sp.GetRequiredService<RedisCacheService>()
        : sp.GetRequiredService<MemoryCacheService>();
});
```

## 2. async / await 与异步编程

### 2.1 原理

**同步**：线程在等待 I/O（数据库、网络、磁盘）时被阻塞，什么也做不了。
**异步**：遇到 I/O 时把线程**还回线程池**，I/O 完成后再用某个线程继续。

对 Web 服务器，这直接决定**并发能力**：异步不会让单个请求更快，
但让服务器在同样的线程数下能同时处理更多请求。

### 2.2 核心规则

| 规则 | 说明 |
|---|---|
| `async` 方法返回 `Task` / `Task<T>` | 不要把 `async void` 用于非事件处理器 |
| 一路 `await` 到底 | 不要混用 `.Result` / `.Wait()`（见 2.3） |
| 异步方法名以 `Async` 结尾 | 约定，便于识别 |
| 传递 `CancellationToken` | 让请求取消能向上传播 |

### 2.3 ⚠️ 死锁陷阱

```csharp
// ❌ 在同步上下文中阻塞等待异步结果
var user = _repository.GetByIdAsync(id).Result;   // 可能死锁
var user = _repository.GetByIdAsync(id).Wait();   // 同上
```

**为什么会死锁**：某些同步上下文（旧 ASP.NET、WPF）一次只允许一个线程进入。
`await` 完成后需要回到原上下文继续执行，但原线程正被 `.Result` 阻塞 → 互相等待。

ASP.NET Core 没有这个同步上下文，所以 `.Result` 通常**不会死锁**，
但仍会**阻塞线程**（失去异步的意义），且异常会被包成 `AggregateException`，
难以排查。因此**一律 async 到底**。

### 2.4 `Task` vs `ValueTask`

| 类型 | 何时用 |
|---|---|
| `Task` | 默认选择 |
| `ValueTask` | 结果**经常同步可得**且调用频繁（避免分配） |

`ValueTask` 有额外约束（不能多次 await），不是性能银弹。
本项目在 `DbCommandInterceptor` 的重写上用到 `ValueTask`（框架签名要求）。

### 2.5 `CancellationToken` 的正确传递

`CancellationToken` 让"客户端断开连接"能中止后端正在做的无用功。

```csharp
// 控制器接收它
public async Task<...> Get(Guid id, CancellationToken cancellationToken)

// 一路传下去
await _posts.GetDetailAsync(id, cancellationToken);

// EF Core 的每个查询方法都接受它
await _context.Posts.FirstOrDefaultAsync(p => p.Id == id, cancellationToken);
```

> ⚠️ **一个真实教训**：在属性 getter 里同步阻塞异步查询是危险的。
> 本项目的 `ICurrentUser` 若在 getter 里查数据库，就会阻塞线程。
> 解法见 §4.5 的 `CurrentUserResolutionMiddleware`：**在中间件里异步解析一次**，
> 存进 `HttpContext.Items`，之后所有 getter 都是**同步读取内存**。

## 3. 记录类型（record）与 DTO 设计

### 3.1 原理

`record` 是 C# 9 引入的**引用类型**，编译器自动生成：
值相等性（`Equals` / `GetHashCode`）、`ToString`、以及非破坏性修改的 `with` 表达式。

```csharp
public record TagBriefDto(Guid Id, string Name);

var a = new TagBriefDto(id, "C#");
var b = a with { Name = ".NET" };   // 复制并改一个字段，原对象不变
```

`record class`（默认）是引用类型；`record struct` 是值类型。
`record` 的属性默认是 `init`（只能在初始化时赋值），这带来**不可变性**。

### 3.2 为什么 DTO 用 record 而不是 class

| 理由 | 说明 |
|---|---|
| 不可变 | DTO 是数据传输的**快照**，不该在传递过程中被改 |
| 少写代码 | 一行替代几十行属性 + 构造函数 |
| 值语义 | 便于断言与比较（测试友好） |
| `with` 表达式 | 需要微调副本时很优雅 |

### 3.3 DTO 与实体的区别（重要概念）

| | 实体 Entity | DTO |
|---|---|---|
| 位置 | Domain 层 | Application 层 |
| 目的 | 表达**业务概念与不变量** | 表达**接口契约** |
| 可变性 | 有行为方法（`Publish()`、`Update()`） | 不可变数据袋 |
| 序列化 | **不应该**直接对外序列化 | 专为序列化设计 |
| 例子 | `Post` | `PostDetailDto` |

**为什么不直接返回实体**：

1. **安全**：实体会带出不该暴露的字段（`User.PasswordHash`！）
2. **解耦**：数据库结构调整不该自动改变 API 契约
3. **防懒加载意外**：序列化实体可能触发意外的关联查询（或循环引用）

本项目**不使用 AutoMapper**，DTO 全部手写映射。理由：映射代码是显式的，
出错时编译期就能发现；而 AutoMapper 的配置错误只在运行期暴露，
且"魔法映射"让"这个字段从哪来"变得难以追踪。

### 3.4 请求 DTO 与响应 DTO 分开

```csharp
// 响应：包含 Id、CreatedAt、Version（服务端生成的东西）
public record AuthorDto(Guid Id, string Name, string Email, string Avatar, string Bio,
                        DateTimeOffset CreatedAt, int Version);

// 请求：不包含 Id/CreatedAt；更新时包含 Version（乐观锁需要）
public record CreateAuthorRequest(string Name, string Email, string? Bio, string? Avatar);
public record UpdateAuthorRequest(string Name, string Email, string Bio, string Avatar, int Version);
```

把"创建请求"与"更新请求"分开，而不是用一个 DTO 加可空字段，好处是：

- 创建时**不需要**版本号，更新时**必须**有——用不同类型表达，编译器帮你检查
- 语义清晰：看到 `UpdateAuthorRequest` 就知道这是更新

### 3.5 `with` 表达式在服务层的实际用途

```csharp
// 强制给查询加上归属过滤，而不修改调用方传来的对象
normalized = normalized with { OwnedByUserId = _currentUser.UserId };
```

# 第二部分 · ASP.NET Core

## 4. 中间件管道与顺序效应

### 4.1 原理

ASP.NET Core 的请求处理是一条**管道**：每个中间件可以选择
"处理请求 → 调用下一个 → 处理后返回的响应"。

```
请求 ──► [中间件A] ──► [中间件B] ──► [终结点] 
                                          │
响应 ◄── [中间件A] ◄── [中间件B] ◄─────────┘
```

这形成"洋葱模型"：**注册顺序 = 请求经过的顺序，响应的顺序正好相反**。

```csharp
app.UseMiddleware<A>();   // A 先看到请求，最后看到响应
app.UseMiddleware<B>();   // B 后看到请求，先看到响应
```

### 4.2 三种写法

```csharp
// 1. 约定式中间件（有依赖注入需求时）
app.UseMiddleware<ExceptionHandlingMiddleware>();

// 2. 内联
app.Use(async (context, next) => { await next(); });

// 3. 终结中间件
app.Run(async context => { await context.Response.WriteAsync("end"); });
```

约定式中间件的类约定：

```csharp
public class MyMiddleware
{
    private readonly RequestDelegate _next;            // 下一个中间件
    public MyMiddleware(RequestDelegate next) => _next = next;

    // InvokeAsync 的参数会被从 DI 解析（Scoped 服务可以在这里注入）
    public async Task InvokeAsync(HttpContext context, IMyScopedService svc)
    {
        // 请求前逻辑
        await _next(context);
        // 响应后逻辑
    }
}
```

### 4.3 ⚠️ 顺序错了会怎样（本项目的两个真实案例）

**案例一：异常处理必须在最外层（最先注册）**

```csharp
// ❌ 错误顺序
app.UseMiddleware<ExceptionHandlingMiddleware>();
app.UseSerilogRequestLogging();     // 日志在里层

// ✅ 正确顺序
app.UseSerilogRequestLogging();     // 日志在外层
app.UseMiddleware<ExceptionHandlingMiddleware>();
```

**后果**：`BusinessException` 会先冒泡穿过日志中间件，
日志记录的是"异常发生时的 500 + 完整堆栈"，
而客户端实际收到的是 `ExceptionHandlingMiddleware` 映射后的 404/403/409。

于是：

- **日志与事实不符**（排查时被误导）
- "文章不存在""邮箱重复"这类**可预期的业务失败会刷满 ERR 日志**，淹没真正的故障

**案例二：解析登录用户必须在 `UseAuthentication` 之后**

```csharp
app.UseAuthentication();
app.UseMiddleware<CurrentUserResolutionMiddleware>();   // 需要 ClaimsPrincipal
app.UseAuthorization();
```

`CurrentUserResolutionMiddleware` 要从 `context.User`（由认证中间件填充）
读取 claims，再去数据库校验账号状态。放在认证之前就什么也读不到。

### 4.4 `UseXxx` vs `AddXxx`

这是一个新手常见的困惑：

| 形式 | 阶段 | 例子 |
|---|---|---|
| `builder.Services.AddXxx()` | **注册服务**（构建容器时） | `AddControllers()`、`AddAuthentication()` |
| `app.UseXxx()` | **装配管道**（运行时顺序） | `UseAuthentication()`、`UseAuthorization()` |

一句话：**Add 是"准备零件"，Use 是"决定装配顺序"**。

### 4.5 一个完整的中间件实例：解析当前登录用户

需求：每个请求都要知道"谁在访问"，且这个信息要能被 Service 层读取。

难点：

1. 校验需要查数据库（账号是否存在、是否启用、`TokenVersion` 是否一致）→ 是异步操作
2. Service 层希望**同步**读取（在 getter 里）→ 不能在那里查库（见 §2.5）

解法：**中间件里异步解析一次，存进 `HttpContext.Items`**。

```csharp
public async Task InvokeAsync(HttpContext context, ITokenService tokenService, IUserRepository users)
{
    var info = tokenService.Resolve(context.User);
    if (info is not null)
    {
        var user = await users.GetByIdAsync(info.UserId, context.RequestAborted);
        if (user is not null && user.IsActive && user.TokenVersion == info.TokenVersion)
            context.Items[ItemsKey] = new ResolvedUser(user.Id, user.Role, user.AuthorId);
    }
    await _next(context);   // 不管解析成功与否都继续
}
```

之后 `ICurrentUser` 的所有属性都是纯内存读取：

```csharp
private ResolvedUser? Current =>
    _httpContextAccessor.HttpContext?.Items[CurrentUserResolutionMiddleware.ItemsKey] as ResolvedUser;

public Guid? UserId => Current?.UserId;
```

**两个刻意的设计**：

1. **校验失败不返回 401**，只是不写入用户信息，让后续的 `[Authorize]` 去拒绝。
   这样**公开接口即使携带一个过期 token 也能正常访问**——
   否则一个过期 token 会让用户连首页都打不开。
2. **`ICurrentUser` 是 Scoped**（每请求一个），因为 `HttpContextAccessor` 是 Scoped 的。

## 5. 模型绑定、路由与授权属性

### 5.1 模型绑定

ASP.NET Core 自动把 HTTP 请求的数据填充到 action 参数。

| 来源 | 特性 | 说明 |
|---|---|---|
| 路由 | `[FromRoute]`（默认从路由模板推断） | `/api/posts/{id}` → `id` 参数 |
| 查询串 | `[FromQuery]` | `?page=1&pageSize=12` |
| 请求体 | `[FromBody]` | JSON 反序列化为 DTO |
| 表单 | `[FromForm]` | `multipart/form-data` |
| 请求头 | `[FromHeader]` | |

```csharp
[HttpGet]
public async Task<...> GetPaged(
    [FromQuery] int page = 1,
    [FromQuery] int pageSize = 12,
    [FromQuery] Guid? categoryId = null,
    CancellationToken cancellationToken = default)   // 特殊：框架自动注入
```

**约定**：简单类型从路由/查询串绑定，复杂类型从请求体绑定。

### 5.2 路由约束

```csharp
[Route("api/posts")]
[HttpGet("{id:guid}")]           // :guid 约束——不是合法 GUID 就 404
[HttpGet("{id:guid}/readonly")]
[HttpGet("archives")]            // 字面量优先于参数，不冲突
[HttpGet("search")]
```

`:guid`、`:int`、`:length(1,10)` 等路由约束让"格式不对"在路由层就被拒绝，
不必在 action 里写 `Guid.TryParse`。

> **顺序注意**：`{id:guid}` 与 `archives` 能共存，因为 `archives` 不匹配 GUID 约束。
> 若两者都匹配（如 `id` 无约束），字面量路由优先级更高。

### 5.3 统一响应的实现

项目选择**手动包装**统一响应体，而不是用 `IActionResult` + 过滤器：

```csharp
[HttpGet("config")]
public async Task<ApiResponse<SiteConfigDto>> GetConfig(CancellationToken cancellationToken)
{
    var config = await _site.GetConfigAsync(cancellationToken);
    return ApiResponse<SiteConfigDto>.Ok(config);
}
```

好处：控制器签名即契约，一眼看出返回什么类型；
错误路径由 `ExceptionHandlingMiddleware` 统一处理，控制器里**没有 try/catch**。

### 5.4 授权属性

| 写法 | 含义 |
|---|---|
| `[AllowAnonymous]` | 显式允许匿名（覆盖类级 `[Authorize]`） |
| `[Authorize]` | 仅需认证，不限角色 |
| `[Authorize(Policy = "AdminOnly")]` | 满足名为 `AdminOnly` 的策略 |
| `[Authorize(Roles = "Admin")]` | 直接限定角色（本项目用策略而非它） |

**策略 vs 角色**：策略把"授权规则"命名并集中定义，控制器只引用名字。
将来规则变了（比如 Admin 也要满足二次验证），只改策略定义，不必改每个控制器。

```csharp
// Program.cs
options.AddPolicy(AuthorizationPolicies.AdminOnly, policy =>
    policy.RequireRole(nameof(UserRole.Admin)));
options.AddPolicy(AuthorizationPolicies.ContentWriter, policy =>
    policy.RequireRole(nameof(UserRole.Admin), nameof(UserRole.Author)));
```

策略名用**常量**而不是字符串字面量，避免拼写不一致：

```csharp
internal static class AuthorizationPolicies
{
    public const string AdminOnly = "AdminOnly";
    public const string ContentWriter = "ContentWriter";
}
```

### 5.5 ⚠️ 属性式鉴权的能力边界（重要）

`[Authorize]` 只能回答：**"这类角色能不能用这个端点"**。
它**不能**回答：**"这个人能不能操作这条数据"**。

后者必须**先查到数据才知道归属**，因此必须写在 Service 层：

```csharp
private void EnsureCanManage(PostEntity post)
{
    if (_currentUser.IsAdmin) return;
    if (!_currentUser.IsAuthenticated) throw new BusinessException("未登录", ErrorCodes.Unauthorized);

    var isOwner = post.CreatedByUserId.HasValue && post.CreatedByUserId == _currentUser.UserId;
    if (!isOwner) throw new BusinessException("无权操作他人的文章", ErrorCodes.Forbidden);
}
```

> ⚠️ **本项目实测踩过的越权漏洞**：最初用 `AuthorId` 判断归属。
> 但**多个账号可以关联同一个 Author**，于是它们能互相修改对方的文章。
> 正确做法是只认 **`CreatedByUserId`（账号维度）**。

这就是"**资源级授权**"（resource-based authorization），
它永远属于业务逻辑层，不属于控制器。

### 5.6 ⚠️ 一个当前存在的真实缺口

`CategoriesController` 与 `TagsController` 的写接口**没有 `[Authorize]`**，
`SiteController` 的三个写接口和 `FilesController.Upload` 同样没有。
**设计意图是仅 Admin（或 ContentWriter），但属性漏加了。**

**教训**：前端隐藏按钮（`canManageTaxonomy`）**不是安全边界**，
直接发 HTTP 请求就能绕过。**鉴权必须在服务端**，且要**逐个端点检查**——
漏一个就是完全敞开。

详见 [05-API接口清单.md](./05-API接口清单.md) §9.4 与 [09-已知限制与技术债.md](./09-已知限制与技术债.md) §5.1。

## 6. 配置系统与 Options 模式

### 6.1 配置的来源与优先级

ASP.NET Core 的配置是**分层覆盖**的，后注册的来源覆盖先注册的：

```
appsettings.json
  → appsettings.{Environment}.json        （如 appsettings.Development.json）
  → 用户机密（user-secrets，仅开发）
  → 环境变量
  → 命令行参数                              （最高优先级）
```

**环境变量的层级用双下划线表示**：

```bash
Jwt__SigningKey="..."        # 等价于 Jwt:SigningKey
ConnectionStrings__DefaultConnection="..."
Cache__Provider="Redis"
```

> ⚠️ **本项目踩过的坑**：在 WSL 里启动 Windows 的 `Blog.WebApi.exe` 时，
> `ASPNETCORE_ENVIRONMENT` 环境变量**不会传递**给 Windows 进程，
> 导致读到的是 `appsettings.json`（没有连接串）而启动失败。
> 解法是用**命令行参数** `--environment Development`（优先级最高）。

### 6.2 Options 模式

**不要**在业务代码里直接读 `IConfiguration["Xxx:Yyy"]`。应该绑定到强类型类：

```csharp
public class CacheOptions
{
    public const string SectionName = "Cache";      // 节名常量

    public bool Enabled { get; set; } = true;
    public string Provider { get; set; } = "Memory";
    public TimeSpan NullTtl { get; set; } = TimeSpan.FromMinutes(2);
    public double TtlJitterRatio { get; set; } = 0.2;
}

// 注册
services.Configure<CacheOptions>(configuration.GetSection(CacheOptions.SectionName));

// 使用
public RedisCacheService(IOptions<CacheOptions> options) => _options = options.Value;
```

**三个好处**：

1. **编译期检查**：拼错属性名编译不过
2. **默认值集中**：类里写的默认值就是兜底
3. **`SectionName` 常量**：避免字符串 `"Cache"` 在代码里重复出现

**三种注入接口**：

| 接口 | 特点 | 何时用 |
|---|---|---|
| `IOptions<T>` | 单例，启动后不变 | 绝大多数场景 |
| `IOptionsSnapshot<T>` | Scoped，每请求重读 | 需要热更新 |
| `IOptionsMonitor<T>` | 单例 + 变更通知 | 需要监听变更 |

### 6.3 启动期校验（Fail Fast）

最有力的配置用法是**在启动时拒绝危险配置**。

```csharp
var signingKey = ...;
if (string.IsNullOrWhiteSpace(signingKey) || signingKey.Length < 32)
{
    throw new InvalidOperationException(
        "未配置 Jwt:SigningKey（或长度不足 32 字节）...");
}
```

**为什么值得**：静默使用弱密钥意味着"任何人都能伪造 token"，
后果远比启动失败严重。**能在启动期发现的错误，就不要留到运行期。**

这个思路的另一处应用是 `DeploymentGuard`：

```csharp
if (deployment.InstanceCount <= 1 && !deployment.RequireRedis) return;

// 否则必须用 Redis
if (providerIsRedis) return;
throw new InvalidOperationException("检测到「多实例 / 强制要求 Redis」的部署配置，但缓存未使用 Redis：...");
```

**理由**：多实例下用内存限流，实际阈值会被放大到"配置值 × 实例数"，
限流形同虚设；而"静默降级"会让这个问题极难排查。
**把部署拓扑当作运维必须显式声明的输入，而不是让代码去猜。**

### 6.4 ⚠️ 敏感配置绝不入库

| 配置 | 存放位置 |
|---|---|
| 开发用的 `Jwt:SigningKey` | `appsettings.Development.json`（**明确标注仅开发用**） |
| 生产的 `Jwt:SigningKey` | 环境变量 `Jwt__SigningKey` / user-secrets / 密钥库 |
| 数据库密码 | 生产用环境变量；开发配置里是本地容器密码，可接受 |

**生产 `appsettings.json` 里刻意不含 `Jwt:SigningKey`**，
因此忘记注入时应用会拒绝启动——这是**设计出来的失败**，不是缺陷。

前端同理：`VITE_` 前缀的变量会被**打包进客户端产物，任何人可读**，
因此只放公开配置（如站点兜底标题），密钥必须只存在于后端。

## 7. 日志与可观测性

### 7.1 为什么需要结构化日志

`Console.WriteLine("user " + id + " failed")` 无法检索、无法聚合、无法告警。

**结构化日志**把日志当作带字段的事件：

```csharp
_logger.LogWarning("业务异常 {Code}: {Message} {Path}", ex.Code, ex.Message, context.Request.Path);
```

占位符 `{Code}` 不是字符串拼接，而是**命名字段**。
日志系统可以按 `Code = 4040` 检索，而不是靠正则匹配文本。

### 7.2 日志级别

| 级别 | 何时用 | 本项目例子 |
|---|---|---|
| `Trace` / `Debug` | 开发调试细节 | 一般不用 |
| `Information` | 正常业务事件 | 请求完成（2xx/3xx） |
| `Warning` | **可预期**的问题 | 业务异常、权限失败、限流触发、慢查询 |
| `Error` | **故障** | 未处理异常、5xx |
| `Critical` / `Fatal` | 应用无法继续 | 启动失败 |

> **关键区分**：`Warning` 是"预期内的不好结果"，`Error` 是"我们没预料到的故障"。
> 把两者混起来，`Error` 就失去信号价值——
> 这正是本项目的请求日志按状态码分级的原因：

```csharp
options.GetLevel = (httpContext, _, ex) =>
    ex is not null ? LogEventLevel.Error
    : httpContext.Response.StatusCode switch
    {
        >= 500 => LogEventLevel.Error,      // 真故障
        >= 400 => LogEventLevel.Warning,    // 业务/权限类可预期失败
        _ => LogEventLevel.Information,
    };
```

### 7.3 Serilog 的两个实用配置

**Bootstrap Logger**：在 DI 容器建好之前就要能记日志，否则"启动阶段崩溃"没有任何记录。

```csharp
Log.Logger = new LoggerConfiguration()
    .WriteTo.Console()
    .CreateBootstrapLogger();     // 早期引导

try
{
    var builder = WebApplication.CreateBuilder(args);
    builder.Host.UseSerilog(...);   // 容器建好后换成正式配置
    ...
}
catch (Exception ex) when (ex is not HostAbortedException)
{
    Log.Fatal(ex, "应用启动失败");
}
finally
{
    Log.CloseAndFlush();
}
```

> ⚠️ **`HostAbortedException` 必须排除**：`dotnet ef` 设计期工具会正常中止宿主，
> 那不是启动失败。之前没排除，导致每次执行 EF 命令都记一条 Fatal。

**滚动文件**：`logs/blog-.log` 按天滚动，保留 30 天。

### 7.4 慢查询监控

EF Core 提供 `DbCommandInterceptor` 钩子。本项目在所有命令执行后检查耗时：

```csharp
private static readonly TimeSpan Threshold = TimeSpan.FromMilliseconds(500);

private void LogIfSlow(DbCommand command, CommandExecutedEventData eventData)
{
    if (eventData.Duration < Threshold) return;
    _logger.LogWarning("慢查询 {Duration}ms: {Sql}", eventData.Duration.TotalMilliseconds, command.CommandText);
}
```

需要重写 Reader / NonQuery / Scalar 的**同步与异步共 6 个** `...Executed` 方法。

**异步方法返回 `ValueTask<T>`**（框架签名），直接返回 `base.XxxAsync(...)`——
这里不需要 `async/await`，因为**没有后续逻辑要在 await 之后执行**（除了日志，而日志在调用前已完成）。

# 第三部分 · 架构与设计

## 8. 整洁架构与依赖倒置

### 8.1 原理

**依赖倒置原则（DIP）**：高层模块不应依赖低层模块，两者都应依赖**抽象**。

**整洁架构**把代码按"离业务核心的距离"分层，并规定**依赖只能由外向内**：

```
        ┌──────────────────────────────────────┐
        │  WebApi（HTTP、中间件、组合根）        │   最外层：易变的细节
        │  ┌────────────────────────────────┐  │
        │  │  Infrastructure（EF、Redis…）   │  │
        │  │  ┌──────────────────────────┐  │  │
        │  │  │  Application（用例编排）  │  │  │
        │  │  │  ┌────────────────────┐  │  │  │
        │  │  │  │  Domain（业务核心） │  │  │  │   最内层：最稳定
        │  │  │  └────────────────────┘  │  │  │
        │  │  └──────────────────────────┘  │  │
        │  └────────────────────────────────┘  │
        └──────────────────────────────────────┘
              依赖方向：外 → 内（只能这样）
```

**关键的思维转换**：`Infrastructure`（数据库实现）**依赖** `Domain`（实体与仓储**接口**），
而不是反过来。所以业务核心完全不知道 PostgreSQL 的存在。

### 8.2 本项目的四层

| 层 | 职责 | 硬性约束 |
|---|---|---|
| `Blog.Domain` | 实体、值对象、仓储接口 | **零外部 NuGet 依赖** |
| `Blog.Application` | 用例编排、DTO、横切接口、统一响应 | **不引用 EF Core** |
| `Blog.Infrastructure` | EF Core、缓存、限流、文件、安全 | 实现 Application 定义的接口 |
| `Blog.WebApi` | HTTP 入口、中间件、DI 组合根 | 不含业务逻辑 |

### 8.3 一个具体例子：全文检索列如何不污染 Domain

Post 的中文全文检索列需要 `NpgsqlTsVector` 类型——但 Npgsql 是外部依赖，
**不能出现在 `Blog.Domain`**。

解法：在 Infrastructure 里声明为**影子属性**（shadow property）——
它能被 EF 映射，但**不存在于 C# 实体类上**：

```csharp
// BlogDbContext.OnModelCreating —— 只在 Infrastructure 层可见
entity.Property<NpgsqlTypes.NpgsqlTsVector>("SearchVector")
      .HasColumnName("SearchVector")
      .HasColumnType("tsvector")
      .HasComputedColumnSql("...", stored: true);
```

查询时用 `EF.Property` 或原生 SQL 访问。

> **这个约束的价值在这里体现得非常清楚**：如果没有"Domain 零依赖"这条规则，
> 最省事的做法就是给 `Post` 加一个 `NpgsqlTsVector SearchVector` 属性——
> 但那会让业务实体绑定到特定数据库，Domain 项目再也无法脱离 Npgsql 编译。
>
> **代价**：影子属性导致 EF 的可翻译性下降（见 §14.4 的两个坑）。**这是自愿承担的复杂度。**

### 8.4 接口放在哪一层（一个常见困惑）

**规则：接口放在"使用方"所在层，实现放在外层。**

| 接口 | 位置 | 谁用 | 谁实现 |
|---|---|---|---|
| `IPostRepository` | **Domain**（`IRepository/`） | Application | Infrastructure |
| `ICacheService` | **Application**（`Interfaces/`） | Application | Infrastructure |
| `ICurrentUser` | **Application** | Application | Infrastructure |
| `ITokenService` | **Application** | Application | Infrastructure |

为什么 `IPostRepository` 在 Domain 而不是 Application？
因为它操作的是 **Domain 实体**，属于领域概念的一部分。
而 `ICacheService` 不涉及领域概念，是纯粹的技术能力，所以放在 Application。

### 8.5 读写分离的仓储（CQRS 的轻量版）

本项目把仓储分成两套：

| 类别 | 位置 | 返回 |
|---|---|---|
| 写侧仓储 | `Blog.Domain/IRepository/` | 实体 |
| 读侧查询仓储 | `Blog.Application/Interfaces/I*QueryRepository.cs` | **DTO 投影** |

**为什么**：查询需要"一次查完并投影成 DTO"（避免 N+1 和无谓的实体追踪），
而写入需要"取实体 → 调领域方法 → 保存"。两种诉求放同一个接口会互相牵制。

`TaxonomyQueryRepository` 一个类**显式实现两个接口**
（`ICategoryQueryRepository` 与 `ITagQueryRepository`），因为分类和标签的查询逻辑完全一致：

```csharp
public class TaxonomyQueryRepository : ICategoryQueryRepository, ITagQueryRepository
{
    Task<List<CategoryDto>> ICategoryQueryRepository.GetAllAsync(...) { ... }
    Task<List<TagDto>> ITagQueryRepository.GetAllAsync(...) { ... }
}
```

> **显式接口实现**的作用：两个接口有**同名同签名但不同返回类型**的方法，
> 用显式实现可以共存。调用方通过接口引用访问，不会混淆。

| Domain 实体与仓储接口 | `Blog.Domain/Entities/`、`Blog.Domain/IRepository/` |

## 9. 仓储模式与工作单元

### 9.1 仓储模式（Repository）

**目的**：把"数据访问"抽象成"集合操作"，让业务代码不必知道 SQL。

```csharp
public interface IBaseRepository<TEntity> where TEntity : BaseEntity
{
    Task<TEntity> AddAsync(TEntity entity, CancellationToken ct = default);
    Task<TEntity?> GetByIdAsync(Guid id, CancellationToken ct = default);
    Task<IEnumerable<TEntity>> GetAllAsync(CancellationToken ct = default);
    Task<IEnumerable<TEntity>> QueryByConditionAsync(Expression<Func<TEntity, bool>> where, CancellationToken ct = default);
    Task<int> CountAsync(Expression<Func<TEntity, bool>>? where = null, CancellationToken ct = default);
    void Update(TEntity entity);
    void Remove(TEntity entity);
}
```

**⚠️ 关于仓储模式的一个诚实评价**：在 EF Core 之上再加仓储层，
学术界有争议——`DbContext` 本身已经是 Unit of Work + Repository。
本项目的选择是保留仓储，因为它让 Application 层**不依赖 EF Core**，
从而守住整洁架构的边界。**这是自觉的取舍，不是"最佳实践"。**

### 9.2 工作单元（Unit of Work）

**目的**：把多个仓储的修改聚合成**一个事务**。

```csharp
public interface IUnitOfWork
{
    Task<int> SaveChangesAsync(CancellationToken ct = default);
    Task BeginTransactionAsync(CancellationToken ct = default);
    Task CommitTransactionAsync(CancellationToken ct = default);
    Task RollbackTransactionAsync(CancellationToken ct = default);
}
```

在本项目里，多个仓储共享**同一个 `DbContext` 实例**（都是 Scoped），
因此 `SaveChangesAsync` 天然是原子的。

```csharp
await _posts.AddAsync(post, ct);
await _uow.SaveChangesAsync(ct);      // 一次提交
```

**为什么不用 `Dispose` 释放 DbContext**：它的生命周期由 DI 容器管理（Scoped），
`UnitOfWork` 只负责释放**自己显式开启的事务**。重复释放会导致问题。

### 9.3 软删除与仓储

```csharp
public void Remove(TEntity entity)
{
    entity.Delete();                          // 只打标记：IsDeleted = true
    _context.Set<TEntity>().Update(entity);
}
```

**仓储的 `Remove` 不删数据**，只标记。真正的"排除已删除"由全局查询过滤器自动完成（§11）。

### 9.4 ⚠️ 一个真实教训：不加载导航集合会导致主键冲突

**现象**：更新专栏的文章列表时**必现 500**，日志里是：

```
23505 duplicate key value violates unique constraint "PK_PostCollections"
```

**根因**：`BaseRepository.GetByIdAsync` **不加载导航集合**：

```csharp
public virtual async Task<TEntity?> GetByIdAsync(Guid id, CancellationToken ct = default)
{
    return await _context.Set<TEntity>().FirstOrDefaultAsync(e => e.Id == id, ct);
    // 没有 Include！collection.PostLinks 是空的
}
```

当 `PostLinks` 是空集合时，EF 认为"这些连接行都是新的"，
于是对**已存在**的连接行执行 INSERT → 唯一约束冲突。

**解法**：必须用专门的方法加载导航集合：

```csharp
public async Task<Collection?> GetWithPostsAsync(Guid id, CancellationToken ct = default)
{
    return await _context.Collections.Include(c => c.PostLinks).FirstOrDefaultAsync(c => c.Id == id, ct);
}
```

**通用规律**：**修改多对多关系前，必须先 `Include` 导航集合。**
同理，文章的标签同步采用**增量同步**（只增/删差异项），而不是整体替换：

```csharp
// 只移除取消关联的
foreach (var existing in post.Tags.Where(t => !ids.Contains(t.Id)).ToList())
    post.Tags.Remove(existing);

// 只添加新增的
foreach (var tag in tags.Where(t => !post.Tags.Any(x => x.Id == t.Id)))
    post.Tags.Add(tag);
```

# 第四部分 · 数据访问（EF Core + PostgreSQL）

## 10. EF Core 变更跟踪与导航属性

### 10.1 原理：变更跟踪

EF Core 默认**跟踪**它查出来的实体：记住原始值，
`SaveChanges()` 时对比当前值生成 `UPDATE`。

```csharp
var post = await _context.Posts.FirstAsync(p => p.Id == id);   // 被跟踪
post.Publish();                                                 // 改内存对象
await _context.SaveChangesAsync();                              // 生成 UPDATE
```

**跟踪的代价**：内存占用 + 快照比较开销。只读查询应该关掉：

```csharp
await _context.Posts.AsNoTracking().ToListAsync();     // 不跟踪，更快
```

本项目的 `GetAllAsync` / `QueryByConditionAsync` 都用 `AsNoTracking()`——
它们返回的数据只用于展示。

### 10.2 导航属性与加载策略

| 策略 | 写法 | 说明 |
|---|---|---|
| **预先加载**（Eager） | `.Include(p => p.Tags)` | 一次查询带出关联（**推荐**） |
| **显式加载**（Explicit） | `.Entry(p).Collection(x => x.Tags).LoadAsync()` | 需要时再查 |
| **延迟加载**（Lazy） | 需要代理包 + 属性设 `virtual` | **本项目未启用**（易产生 N+1） |
| **投影**（Projection） | `.Select(p => new PostCardDto(...))` | 直接查成 DTO，**最高效** |

**为什么关闭延迟加载**：它让"访问一个属性"意外触发一次数据库查询，
在循环里就是经典的 **N+1 问题**（1 次查列表 + N 次查关联）。

**投影是最优解**：只查需要的列，不构造实体，也不需要跟踪。
本项目的读侧查询仓储正是这样做的（§8.5）。

### 10.3 多对多的两种建模

**隐式**（EF Core 5+ 自动生成连接表）：

```csharp
entity.HasMany(e => e.Tags).WithMany(t => t.Posts);
// 生成 PostTag 表，只有两列
```

**显式**（连接表需要携带额外数据）：

```csharp
public class PostCollection          // 显式连接实体
{
    public Guid PostId { get; set; }
    public Guid CollectionId { get; set; }
    public int SortOrder { get; set; }   // ← 额外数据
}

entity.HasKey(e => new { e.PostId, e.CollectionId });   // 复合主键
```

**本项目的选择**：标签用隐式（无需额外数据），专栏用显式（需要 `SortOrder`）。

> **什么是"复合主键"**：由多列共同构成的主键。`(PostId, CollectionId)` 唯一标识一行，
> 同时天然实现了"同一文章不能重复加入同一专栏"的约束。

### 10.4 实体内的行为方法（充血模型）

本项目的实体不是"只有属性的数据袋"，而是封装了业务规则：

```csharp
public void Publish()
{
    // 幂等处理：重复发布直接保持原发布时间，避免覆盖首次发布时间（影响归档排序）
    PublishedAt ??= DateTimeOffset.UtcNow;
}
```

```csharp
public void ResetPassword(string passwordHash)
{
    PasswordHash = passwordHash;
    TokenVersion++;        // ← 业务规则：改密码必须让旧 token 失效
}
```

```csharp
public void SetActive(bool isActive)
{
    if (IsActive == isActive) return;
    IsActive = isActive;
    if (!isActive) TokenVersion++;   // ← 停用必须踢下线
}
```

**为什么把规则放在实体里**：它无法被绕过。若放在 Service 里，
将来新写一个 Service 就可能忘记自增 `TokenVersion`。

**代价**：属性需要 `private set`，构造与修改都通过方法，代码略啰嗦。

## 11. 软删除与全局查询过滤器

### 11.1 原理

**软删除**：不真的 `DELETE`，而是标记 `IsDeleted = true`。
数据保留，可用于恢复与审计。

**麻烦**：每个查询都必须记得加 `WHERE IsDeleted = false`。
漏一个就会把已删除的数据展示出来。

**解法：全局查询过滤器（Global Query Filter）**——EF Core 自动为每个查询追加条件：

```csharp
entity.HasQueryFilter(e => !e.IsDeleted);
```

之后应用层**不需要也不应该**手写这个条件：

```csharp
var posts = await _context.Posts.ToListAsync();   // 自动带 IsDeleted = false
```

### 11.2 两个必须注意的点

**点一：过滤器可以用 `IgnoreQueryFilters()` 绕过**

```csharp
await _context.Posts.IgnoreQueryFilters().ToListAsync();   // 包含已删除
```

本项目**没有使用**它（没有"回收站"功能）。

**点二：过滤唯一索引（partial unique index）**

软删除与唯一约束会冲突：删掉分类"技术"后，就再也建不了同名分类了（唯一约束仍然占着）。

解法是**只在未删除的行之间保证唯一**：

```csharp
entity.HasIndex(e => e.Name).IsUnique().HasFilter("\"IsDeleted\" = false");
```

生成的 SQL 是：

```sql
CREATE UNIQUE INDEX "IX_Categories_Name" ON "Categories" ("Name") WHERE "IsDeleted" = false;
```

> **PostgreSQL 的标识符大小写敏感**：EF Core 建的表名列名是 PascalCase，
> 因此 SQL 里必须写 `"IsDeleted"`（带双引号）。不加引号会被折叠成小写 `isdeleted`，找不到列。

### 11.3 ⚠️ 查询过滤器与必需导航的冲突

`PostCollection` 是纯连接行（**没有**软删除，随文章/专栏级联删除），
而 `Collection` **有**查询过滤器。

EF Core 因此警告：`PossibleIncorrectRequiredNavigationWithQueryFilterInteraction`
——"必需端被过滤可能导致意外结果"（若父被过滤掉，子会莫名消失）。

本项目**从不单独查询 `PostCollection`**（始终经 Post/Collection 导航访问），
因此该场景不会发生。在 `OnConfiguring` 里显式抑制该警告，避免日志噪音：

```csharp
optionsBuilder.ConfigureWarnings(w =>
    w.Ignore(CoreEventId.PossibleIncorrectRequiredNavigationWithQueryFilterInteractionWarning));
```

**注意**：这是"我们知道自己在做什么，所以关掉警告"，
不是"警告太烦所以关掉"。**关掉警告前必须能说清为什么安全。**

## 12. 乐观锁与并发控制

### 12.1 两种并发策略

| | 悲观锁 | 乐观锁 |
|---|---|---|
| 思路 | 先锁住，别人等着 | 先改，提交时检查有没有人改过 |
| 实现 | `SELECT ... FOR UPDATE`、事务隔离 | 版本号 / 时间戳 |
| 适合 | 冲突频繁 | **冲突稀少**（绝大多数 Web 场景） |
| 代价 | 锁等待、死锁风险 | 冲突时需重试 |

**Web 应用的常态是"读多写少、冲突稀少"**，因此乐观锁更合适。

### 12.2 本项目的实现：`int Version` + SQL 条件

**方案**：每行有 `Version`（从 1 开始）。更新时带上客户端持有的版本号：

```sql
UPDATE "Posts" SET ..., "Version" = @expected + 1
WHERE "Id" = @id AND "Version" = @expected;
```

受影响行数为 0 → 说明有人先改过 → EF 抛 `DbUpdateConcurrencyException` → 映射为 **409**。

**为什么不直接用 EF 的 `byte[] RowVersion` / `[Timestamp]`**：
那是 SQL Server 的 `rowversion` 机制，在其他数据库上需要额外支持。
**整数版本号与数据库无关**，可跨 PostgreSQL / MySQL / SQLite 通用。

### 12.3 EF Core 中手动控制并发的关键代码

```csharp
public void ApplyOptimisticVersion(TEntity entity, int expectedVersion)
{
    if (expectedVersion < 1)
        throw new ArgumentOutOfRangeException(nameof(expectedVersion), "版本号必须 >= 1");

    var version = _context.Entry(entity).Property(nameof(BaseEntity.Version));
    version.OriginalValue = expectedVersion;      // 作为 WHERE 条件
    version.CurrentValue  = expectedVersion + 1;  // 作为 SET 的值
}
```

**理解 `OriginalValue` vs `CurrentValue`**：

- `OriginalValue` = "我认为数据库里现在是什么" → EF 用它生成 `WHERE`
- `CurrentValue` = "我想把它改成什么" → EF 用它生成 `SET`

配合把 `Version` 标记为并发令牌（`IsConcurrencyToken = true`），
EF 就会把 `OriginalValue` 加进 `WHERE` 子句。

> **`[ConcurrencyCheck]` vs `IsConcurrencyToken`**：前者是特性（attribute），
> 后者是 Fluent API。本项目在 `OnModelCreating` 里用**循环**给所有实体统一设置：
>
> ```csharp
> foreach (var entityType in modelBuilder.Model.GetEntityTypes())
> {
>     var versionProperty = entityType.FindProperty(nameof(BaseEntity.Version));
>     if (versionProperty is not null)
>         versionProperty.IsConcurrencyToken = true;
> }
> ```
>
> 这样**新增实体自动获得乐观锁**，不会漏配。

### 12.4 前端如何配合

乐观锁是**全链路约定**：

1. 详情接口返回 `version`
2. 前端保存时**原样回传** `version`
3. 不匹配 → 409 → 提示"数据已被其他请求修改，请刷新后重试"

```typescript
export function updatePost(id: string, payload: PostPayload): Promise<PostDetailDto> {
  if (payload.version == null) throw new Error('更新文章必须携带版本号')
  return put(`/api/posts/${id}`, { ..., version: payload.version })
}
```

### 12.5 ⚠️ 什么时候**不该**用乐观锁

**浏览量累加**：高频写、允许丢失精度。

如果用乐观锁，"两个人同时看同一篇文章"会有一方收到 409——**荒谬的体验**。
本项目用**数据库侧原子自增**绕过：

```csharp
await _posts.IncrementViewCountAsync(id);   // ExecuteUpdate，直接 UPDATE ... SET ViewCount = ViewCount + 1
```

**教训**：并发控制不是"越严格越好"，而是**与业务语义匹配**。

### 12.6 写入语义的统一约定

本项目全项目遵循一条规则，避免各处判断不一致：

| 情形 | 语义 |
|---|---|
| 实体/Key **不存在** | 视为**新增**，忽略传入的 version |
| 实体/Key **已存在** | 走**乐观锁**，version 必须 ≥ 1，否则 4001 |

站点配置的逐项更新就依赖它：前端对不存在的 Key 传 `version = 0`。

## 13. 索引设计

### 13.1 原理：B-tree 索引像书的目录

没有索引，数据库要**全表扫描**（逐行检查）。
有索引，就能像查字典一样快速定位。

**代价**：索引占空间，且**每次写入都要维护索引**。
因此索引不是越多越好，而是"为高频查询建"。

### 13.2 本项目的索引与用途

| 索引 | 列 | 服务的查询 |
|---|---|---|
| `IX_Posts_IsDeleted_PublishedAt` | `IsDeleted, PublishedAt` | 首页列表（未删除 + 按时间倒序） |
| `IX_Posts_PublishedAt` | `PublishedAt` | 归档分组 |
| `IX_Posts_CategoryId` | `CategoryId` | 按分类筛选 |
| `IX_Posts_AuthorId` | `AuthorId` | 按署名作者筛选 |
| `IX_Posts_CreatedByUserId` | `CreatedByUserId` | 作者工作区（我创建的） |
| `IX_PostTag_TagsId` | `TagsId` | 按标签筛选 |
| `IX_Collections_Slug` | `Slug`（唯一） | 按 slug 取专栏 |
| `IX_Collections_SortOrder` | `SortOrder` | 专栏列表排序 |
| `IX_PostCollections_CollectionId` | `CollectionId` | 专栏内文章 |
| `IX_Users_Email` | `Email`（唯一） | 登录查账号 |
| `IX_SiteConfigs_Key` | `Key`（唯一） | 取配置 |
| `IX_Categories_Name` / `IX_Tags_Name` | `Name`（唯一 + 过滤） | 名称唯一性 + 等值查找 |
| `ix_posts_search` | `SearchVector`（**GIN**） | 全文检索 |

### 13.3 复合索引的"最左前缀"原则

`IX_Posts_IsDeleted_PublishedAt` 是复合索引 `(IsDeleted, PublishedAt)`。

**关键规则**：复合索引只能被"从最左列开始连续匹配"的查询使用。

| 查询条件 | 能否用该索引 |
|---|---|
| `WHERE IsDeleted = false AND PublishedAt > X` | ✅ 能 |
| `WHERE IsDeleted = false` | ✅ 能（只用第一列） |
| `WHERE PublishedAt > X` | ❌ **不能**（跳过了第一列） |

所以**列的顺序很重要**：把"等值条件列"放前面，"范围条件列"放后面。

### 13.4 外键为什么也值得索引

PostgreSQL **不会自动**为外键建索引。（与 MySQL 不同！）

外键索引加速两类操作：

1. **JOIN**：`Post` 关联 `Category` 时按 `CategoryId` 查找
2. **级联/SetNull 删除**：删除一个分类时，需要找到所有引用它的文章

没有索引，删除一个分类会全表扫描 `Posts`。

### 13.5 过滤唯一索引 ← 本项目的重点技巧

```sql
CREATE UNIQUE INDEX "IX_Categories_Name" ON "Categories" ("Name") WHERE "IsDeleted" = false;
```

**`WHERE` 子句让索引只覆盖部分行**。它同时解决了两个问题：

1. 未删除的行之间名称唯一
2. 软删除的行**不参与**唯一性检查 → 可以重建同名

**这是软删除与唯一约束共存的正确做法**，值得记住。

## 14. PostgreSQL 全文检索与中文分词

### 14.1 原理：从 LIKE 到全文检索

**朴素方案**：`WHERE Content LIKE '%关键词%'`

问题：

- **无法用索引**（前置通配符）→ 全表扫描
- **无语言学处理**：`running` 匹配不到 `run`
- **无相关度排序**：要么匹配要么不匹配
- **中文更糟**：中文没有空格分隔，`LIKE '%数据库%'` 只能做子串匹配

**全文检索（FTS）**的思路：

1. **分词**：把文本切成词元（tokens）
2. **归一化**：转小写、词干还原（英文）
3. **倒排索引**：存"词 → 出现在哪些文档"
4. **查询**：把查询串也分词，然后求交集/并集
5. **排序**：按相关度（`ts_rank`）

### 14.2 PostgreSQL 的 FTS 三件套

| 概念 | 类型 | 说明 |
|---|---|---|
| `tsvector` | 类型 | 文档的词元集合，带位置与权重 |
| `tsquery` | 类型 | 查询条件（`&` `\|` `!` 组合词元） |
| `@@` | 运算符 | `tsvector @@ tsquery` 判断是否匹配 |

```sql
SELECT to_tsvector('english', 'The quick brown foxes');
-- 'brown':3 'fox':4 'quick':2        ← 注意：the 被停用词过滤，foxes → fox

SELECT to_tsvector('english', 'The quick brown foxes') @@ to_tsquery('english', 'fox');
-- t
```

### 14.3 ⚠️ 中文的坑：必须装分词器

PostgreSQL 内置分词器**只按空格和标点切分**。对中文：

```sql
SELECT to_tsvector('simple', '使用数据库优化');
-- '使用数据库优化':1       ← 整句被当成一个词元！
```

于是搜"数据库"匹配不到。**必须安装中文分词器 `zhparser`**（依赖 SCWS 词法库）：

```sql
SELECT to_tsvector('chinese', '使用 EF Core 做数据库优化与全文检索');
-- 'core':3 'ef':2 '优化':6 '使用':1 '做':4 '全文检索':7 '数据库':5
```

现在搜"数据库"能匹配到了。

**`chinese` 配置的创建**：

```sql
CREATE TEXT SEARCH CONFIGURATION chinese (PARSER = zhparser);
ALTER TEXT SEARCH CONFIGURATION chinese ADD MAPPING FOR n,v,a,i,e,l,j,q WITH simple;
```

映射的 token 类型：`n`名词 `v`动词 `a`形容词 `i`成语 `e`叹词 `l`习用语 `j`简称 `q`量词。
用 `simple` 字典（只做小写归一化，不做词干还原与停用词过滤）——
中文不需要词干还原，且这样能让中英混合文本里的英文词原样保留。

### 14.4 生成列与权重

**生成列**（Generated Column）：值由数据库根据表达式计算并存储。

```sql
ALTER TABLE "Posts" ADD COLUMN "SearchVector" tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('chinese', coalesce("Title",   '')), 'A') ||
    setweight(to_tsvector('chinese', coalesce("Summary", '')), 'B') ||
    setweight(to_tsvector('chinese', coalesce("Content", '')), 'C')
  ) STORED;
```

**好处**：插入/更新文章时数据库自动维护，**应用层永远不用管它**，
不可能出现"忘了更新索引"的不一致。

`setweight` 给不同来源的词元打权重（A 最高）——**权重只影响相关度评分，不影响是否匹配**。

`||` 是 tsvector 的**拼接**运算符（不是逻辑或）。

### 14.5 ⚠️ 两个必踩的 EF Core 坑

**坑一：`EF.Functions.PlainToTsQuery` 在"影子属性 + 参数"形态下被判客户端求值**

因为 `SearchVector` 是**影子属性**（不存在于 C# 实体上），
EF Core 无法把这种组合翻译成 SQL，于是回退到"把数据拉到内存再算"——
表现为查询报错或结果完全不正确。

**解法**：改用**参数化原生 SQL**。

```csharp
var ids = _context.Posts
    .FromSqlInterpolated($@"
        SELECT p.* FROM ""Posts"" p
        WHERE p.""SearchVector"" @@ plainto_tsquery({config}::regconfig, {keyword})")
    .Select(p => p.Id);
```

**坑二：`plainto_tsquery` 必须显式 `::regconfig` 转型**

PostgreSQL 的重载是 `plainto_tsquery(regconfig, text)` 和 `plainto_tsquery(text)`。
参数化后 Npgsql 把参数当作 `text`，于是尝试匹配 `(text, text)`：

```
42883: function plainto_tsquery(text, text) does not exist
```

**解法**：显式转型 `plainto_tsquery({config}::regconfig, {keyword})`。

> **如何避免这类坑**：当 EF Core 的 LINQ 翻译失败时，
> 不要与它搏斗——**先让功能正确（用原生 SQL），再考虑优化**。
> 本项目正是这样取舍的（`ts_rank` 因此暂缺，见 §14.7）。

### 14.6 `plainto_tsquery` vs `to_tsquery`

| 函数 | 行为 | 安全性 |
|---|---|---|
| `to_tsquery('cat & dog')` | 解析 `&` `\|` `!` 语法 | ⚠️ 用户输入含特殊字符会**语法错误** |
| `plainto_tsquery('cat dog')` | 把输入安全转成 `cat & dog` | ✅ 特殊字符被当普通文本 |

**本项目用 `plainto_tsquery`**，因此用户输入的 `&` `|` `!` 不会被当作操作符，
既避免报错也避免构造恶意查询。

### 14.7 为什么用 `Id IN (子查询)` 而不是直接 `FromSql` 包整表

```csharp
// 只查出匹配的 Id，外层仍是正常 LINQ
var ids = _context.Posts.FromSqlInterpolated(...).Select(p => p.Id);
var query = _context.Posts.Where(p => ids.Contains(p.Id));
```

**目的**：让外层可以自由组合分类/标签/作者/分页等过滤与投影。
`FromSql` 之后不能随意追加任意 LINQ，用它包整表会严重限制后续组合。

参数由 `FromSqlInterpolated` **自动参数化**，**不存在 SQL 注入**。

### 14.8 相关度排序的实现（T12）

现在搜索结果是**按相关度降序**的。实现要点值得单独记住，因为它示范了
「当 EF Core 翻译不了时，如何既拿到能力又不破坏可组合性」：

```csharp
// 用标量原生查询拿「按相关度排好序的 Id 列表」
var rankedIds = await _context.Database
    .SqlQuery<Guid>($@"
        WITH ranked AS (
            SELECT p.""Id"" AS ""Value"",
                   ts_rank(p.""SearchVector"", plainto_tsquery({config}::regconfig, {keyword})) AS rank
            FROM ""Posts"" AS p
            WHERE p.""SearchVector"" @@ plainto_tsquery({config}::regconfig, {keyword})
        )
        SELECT r.""Value"" FROM ranked AS r
        ORDER BY r.rank DESC, r.""Value"" DESC")
    .ToListAsync();

// 外层仍用 Contains：保住「过滤后再分页」的语义
var source = _context.Posts.Where(p => rankedIds.Contains(p.Id));
```

**三个坑与取舍**：

| 坑 | 说明 |
|---|---|
| `ts_rank` 不能写进 WHERE | 它属窗口函数类，PostgreSQL 报 `0A000 window functions are not allowed in WHERE`；用 **CTE** 先算再排序 |
| 映射 keyless 实体不行 | `HasNoKey()` + `Join` 带出 rank 列后，投影 `Tags` 集合会报 **"cannot correlate on keyless entity type"**（keyless 类型无法唯一标识父行） |
| 直接 `ORDER BY + LIMIT` 不行 | 那样分类/标签/作者等过滤无法安全叠加，会出现「先分页再过滤」的错页 |

**`SqlQuery<T>` 的价值**：EF Core 7+ 提供的**标量原生查询**，不需要映射任何实体类型，
因此既不污染模型、也不影响迁移 —— 这正是它比 keyless 实体更适合这里的原因。

> **方法论**：当 EF Core 的 LINQ 翻译失败时，不要与它搏斗。
> **先让功能正确（原生 SQL），再考虑优化**；本项目两次遇到这个问题
> （`plainto_tsquery` 与 `ts_rank`），都用同一个思路解决。

### 14.9 扩展的部署难题

`zhparser` **不在官方 PostgreSQL 镜像中**，必须自行编译。
如果只在容器里手工编译，**容器一重建就全丢**，搜索立即报错：

```
ERROR:  text search configuration "chinese" does not exist
```

**正确做法**：把编译步骤固化进镜像（`deploy/postgres-zhparser.Dockerfile`），
并做**双重保障**：

| 保障 | 覆盖场景 |
|---|---|
| Dockerfile + `/docker-entrypoint-initdb.d/` 脚本 | **全新环境**（数据目录为空时自动执行） |
| EF 迁移中的 `CREATE EXTENSION` + 建配置 | **已有库**（entrypoint 不会重跑） |

> **关键认知**：`postgres` 官方镜像的 entrypoint 脚本**只在数据目录为空时执行**。
> 因此对已存在的库，**扩展的权威来源必须是迁移**（迁移每次启动都会应用）。

## 15. 认证与授权

### 15.1 两个必须分清的概念

| | 认证（Authentication） | 授权（Authorization） |
|---|---|---|
| 回答 | **你是谁？** | **你能做什么？** |
| 失败返回 | **401** Unauthorized | **403** Forbidden |
| 本项目实现 | JWT | 角色策略 + 资源归属校验 |

> **命名陷阱**：HTTP 401 叫 "Unauthorized"，但它实际含义是
> **"未认证"（Unauthenticated）**。403 才是真正的"无权限"。

### 15.2 为什么用 JWT

**传统 Session**：服务端存 session，客户端拿 session id（cookie）。
问题：多实例需要共享 session 存储（Redis），否则请求打到另一台就掉登录。

**JWT**：服务端签发一个**自包含的签名令牌**，客户端每次带上。
服务端只需验签，**不需要查存储**——天然支持多实例。

JWT 三段结构：

```
header.payload.signature
  │       │        └─ 用密钥对前两段签名，防篡改
  │       └────────── 声明（claims）：sub、role、exp、jti...
  └────────────────── 算法与类型
```

**关键认知**：payload 是 **Base64 编码，不是加密**！
任何人都能解开看内容。**绝不能在 JWT 里放敏感信息**（密码、身份证号）。

### 15.3 ⚠️ JWT 的最大缺陷：无法主动失效

JWT 是**无状态**的，服务端不存它。因此：

- 用户改了密码 → **旧 token 在过期前依然有效**
- 账号被停用 → 旧 token 依然有效
- 用户点"退出登录" → 只是前端删了 token，**服务端无法阻止它被继续使用**

这是无状态性的**固有代价**，不是实现问题。

**三种常见补偿方案**：

| 方案 | 做法 | 代价 |
|---|---|---|
| 缩短有效期 | 30 分钟就过期 | 用户体验差（频繁重登） |
| **TokenVersion**（本项目） | 签发时写入版本号，每请求与库中比对；失效时 +1 | **每请求需查一次库** |
| Redis 黑名单 | 失效的 token 存 Redis | 引入 Redis 依赖 |

**本项目的选择：`TokenVersion`**。理由：

- **不引入新的运行时依赖**（校验读库，不是读 Redis）
- **多实例下天然有效**（不需要跨实例共享状态）

```csharp
// User 实体中的业务规则
public void ResetPassword(string passwordHash)
{
    PasswordHash = passwordHash;
    TokenVersion++;        // 改密码 → 所有旧 token 立即失效
}

public void SetActive(bool isActive)
{
    if (IsActive == isActive) return;
    IsActive = isActive;
    if (!isActive) TokenVersion++;   // 停用 → 立即踢下线
}
```

**为什么只在失效场景自增**：正常改资料不该踢人下线，
只有改密码/停用/主动注销才自增。

### 15.4 token 存哪里：localStorage vs Cookie

| | `localStorage` | `HttpOnly Cookie` |
|---|---|---|
| XSS 风险 | ⚠️ JS 可读，XSS 即被窃取 | ✅ JS 读不到 |
| CSRF 风险 | ✅ **不会自动发送**，无 CSRF | ⚠️ 自动发送，需 CSRF token |
| 前端可读 | ✅ 可读用户信息 | ❌ 读不到 |

**本项目的选择：`localStorage`**。理由：不引入 CSRF 问题，
并用"短有效期（30 分钟）"补偿 XSS 风险。

> 这个选择没有绝对的对错，取决于**更怕 XSS 还是更怕 CSRF**。
> 值得注意的是一旦选 localStorage，**防 XSS 就成为硬性要求**（见 §23）。

### 15.5 401 与 403 为什么要映射成正确的 HTTP 状态码

本项目定义了业务码 `4010`（未认证）与 `4030`（无权限），
映射为 HTTP **401/403** 而不是统一的 400：

```csharp
private static int MapStatusCode(int code) => code switch
{
    ErrorCodes.Unauthorized => StatusCodes.Status401Unauthorized,
    ErrorCodes.Forbidden => StatusCodes.Status403Forbidden,
    ...
};
```

**理由**：前端的 401 拦截器（自动清登录态并跳登录页）**依赖 HTTP 状态码**。
如果都返回 400，前端就无法区分"请求写错了"与"该重新登录了"。

### 15.6 认证失败也要返回统一响应体

ASP.NET Core 默认在认证失败时返回**空响应体** + 401。
这会让前端的 `res.json()` 解析失败，只能靠状态码硬编码兜底。

解法是注册 `JwtBearerEvents`：

```csharp
options.Events = new JwtBearerEvents
{
    OnChallenge = async context =>
    {
        context.HandleResponse();          // 阻止默认空响应体
        if (context.Response.HasStarted) return;

        context.Response.StatusCode = StatusCodes.Status401Unauthorized;
        context.Response.ContentType = "application/json; charset=utf-8";
        await context.Response.WriteAsync(JsonSerializer.Serialize(
            ApiResponse.Fail(ErrorCodes.Unauthorized, "未认证或登录已过期，请重新登录"),
            UnifiedJsonOptions.Value));
    },
    OnForbidden = ...   // 403 同理
};
```

### 15.7 ⚠️ 前端路由守卫不是安全边界

```typescript
router.beforeEach((to) => {
  if (!to.meta.requiresAuth) return true
  if (!auth.isAuthenticated) return { name: 'login', query: { returnUrl: to.fullPath } }
  ...
})
```

**这只是用户体验控制，可以被完全绕过**（用户改 JS、或直接调 API）。

> **真正的安全边界永远在服务端。** 前端守卫的作用是"让用户不去撞墙"，
> 不是"阻止用户撞墙"。两者都需要，但**只有后者是安全机制**。

## 16. 密码哈希与密码学基础

### 16.1 ⚠️ 绝对不能明文存密码

**为什么**：

1. 数据库泄露 → 所有用户密码泄露
2. 用户常在多个网站用同一密码 → 危害扩散到其他服务
3. 违法（GDPR 等法规要求）

### 16.2 哈希 ≠ 加密

| | 哈希（Hash） | 加密（Encryption） |
|---|---|---|
| 方向 | **单向**，不可逆 | 双向，可解密 |
| 用途 | 校验（密码、完整性） | 传输、存储机密 |
| 密码 | ✅ 用哈希 | ❌ 不用加密 |

**密码校验流程**：不存密码，存哈希；用户登录时对输入**再算一次哈希**，
与存储值比对。

### 16.3 ⚠️ 为什么不能用 MD5/SHA256 直接哈希密码

它们是**快速**哈希函数——设计目标是"算得快"。对密码来说这正是灾难：

| 攻击方式 | 说明 |
|---|---|
| **暴力破解** | 现代 GPU 每秒可算数十亿次 MD5 |
| **彩虹表** | 预计算的"哈希 → 明文"映射表，常见密码瞬间反查 |
| **相同密码识别** | 相同密码产生相同哈希，一眼看出谁和谁密码一样 |

### 16.4 正确方案：加盐 + 慢哈希

**加盐（Salt）**：给每个用户一个**随机值**，与密码一起哈希。

- 相同密码 → 不同哈希（破解彩虹表失效）
- 盐**不需要保密**，与哈希一起存储
- 盐必须**每用户不同**

**慢哈希（Key Derivation Function）**：故意设计得慢。

| 算法 | 说明 |
|---|---|
| **PBKDF2**（本项目） | 标准、广泛支持、可调迭代次数 |
| bcrypt | 经典，内存需求固定 |
| scrypt | 内存硬（抗 ASIC） |
| **Argon2** | 现代首选（抗 GPU/ASIC），需要额外库 |

**本项目的选择：PBKDF2-HMAC-SHA512**，迭代 **210,000** 次
（OWASP 对该算法的建议量级），16 字节随机盐，32 字节输出。

**为什么选它**：用**框架内置实现**（`Rfc2898DeriveBytes`），**不引入第三方包**。

### 16.5 自描述的存储格式

```
pbkdf2-sha512$210000$Rc6nVI3/2LQ+vmRlYDCCyQ==$RbxCnKNUm29IVZ72izuS7pFoH/W8t5KkIvGZiOu/YLQ=
     │            │              │                        │
  算法标识      迭代次数      base64(盐)              base64(哈希)
```

**为什么把算法与迭代次数也存进去**：将来提升迭代次数时，
**旧密码依然能被校验**（校验时按存储中记录的迭代次数重算）。

```csharp
// 按存储里记录的迭代次数重算，因此提高默认迭代次数不会让旧密码失效
var actual = Derive(password, salt, iterations, expected.Length);
```

配合 `NeedsRehash()`，可以在用户登录成功时**静默升级**哈希参数。

### 16.6 ⚠️ 时序攻击与恒定时间比较

**问题**：普通的字符串比较 `a == b` 在**第一个不同的字符**处就返回。
比较耗时因此泄露"前几个字符猜对了"。

对密码哈希比对，这足够让攻击者逐字节猜出哈希。

**解法：恒定时间比较**——无论内容如何，都花同样的时间。

```csharp
// ✅ 恒定时间比较，防时序攻击
return CryptographicOperations.FixedTimeEquals(actual, expected);
```

### 16.7 校验失败一律返回 false，不抛异常

```csharp
public bool Verify(string password, string storedHash)
{
    if (string.IsNullOrWhiteSpace(password) || string.IsNullOrWhiteSpace(storedHash))
        return false;

    var parts = storedHash.Split('$');
    if (parts.Length != 4 || parts[0] != Prefix) return false;      // 解析失败一律 false
    if (!int.TryParse(parts[1], out var iterations) || iterations < 1) return false;
    ...
    catch (FormatException) { return false; }
}
```

**为什么**：不把"格式细节"暴露成可用信号。
攻击者不该能通过"这个错误 vs 那个错误"推断出存储格式。

### 16.8 种子密码的教训

本项目**把管理员初始密码公开写在仓库里**：

```csharp
/// 初始管理员密码（开发用）：Admin@12345
private const string SeedAdminPasswordHash = "pbkdf2-sha512$210000$...";
```

**为什么可以这样做**：哈希**无法反推**密码（这正是哈希的意义），
而把哈希写进种子数据让**全新环境开箱即可登录后台**，不必手工插数据。

**但必须同时做到**：

1. **明确标注仅开发用**
2. **生产部署后立即修改密码**（或在部署流程中用脚本重置）
3. **生产不应依赖此种子账号**，建议由部署脚本创建专属管理员

**这与"不能在代码里写密码"不矛盾**：
区别在于**这个密码是公开的开发者都知道的初始值**，而不是某个真实用户的密码。
它是"默认密码"，必须被替换。

## 17. 缓存与三大经典问题

### 17.1 为什么用缓存

**根本矛盾**：读远多于写，而数据库是最难横向扩展的一层。

缓存把热点数据放在更快的地方（内存），减少数据库压力、降低响应时间。

**代价**：**一致性**。缓存与数据库可能不同步。
因此缓存的真正难点不是"怎么存"，而是**"什么时候失效"**。

### 17.2 ⚠️ 三大经典问题（必考）

#### 缓存穿透（Cache Penetration）

**现象**：查询**不存在**的数据。缓存里没有 → 每次都查数据库。

**为什么危险**：如果是恶意的（如用随机 id 疯狂请求），
数据库承受的是**全部**请求，缓存完全不起作用，等于没有缓存。

**解法：空值哨兵（Null Sentinel）**——把"查不到"也缓存起来：

```csharp
private const string NullSentinel = "∅";

public async Task<T?> GetAsync<T>(string key, CancellationToken ct = default)
{
    var raw = await db.StringGetAsync(key);
    if (!raw.HasValue || raw == NullSentinel) return default;   // ← 哨兵 → 直接返回"没有"
    return JsonSerializer.Deserialize<T>((string)raw!, SerializerOptions);
}

public async Task SetAsync<T>(string key, T value, TimeSpan ttl, CancellationToken ct = default)
{
    // 值为 null 时用短 TTL
    var effectiveTtl = ApplyJitter(value is null ? _options.NullTtl : ttl);
    var payload = value is null ? NullSentinel : JsonSerializer.Serialize(value, SerializerOptions);
    await db.StringSetAsync(key, payload, effectiveTtl);
}
```

**⚠️ 关键细节：空值哨兵的 TTL 必须比正常 TTL 短。**

本项目 `Cache:NullTtl` 默认 2 分钟，而正常列表缓存 5 分钟、详情 10 分钟。

**为什么**：如果哨兵和正常缓存一样久，"新建了一条数据但缓存里还是空的"会持续很久。
短 TTL 让"新增数据后很快可见"。

**⚠️ 但不能所有查询都缓存空值**。本项目的取舍：

```csharp
// 列表类 → cacheNull: true（查不到就是查不到，缓存空结果防穿透）
// 详情类 → cacheNull: false（避免"新建后立即读到空哨兵"）
```

#### 缓存击穿（Cache Breakdown / Stampede）

**现象**：某个**热点 key 过期**的瞬间，大量并发请求同时发现缓存没了，
**同时**去查数据库并写缓存。

**为什么危险**：一个热点 key 就能把数据库打垮。

**解法：互斥重建（Mutex Rebuild）**——只让一个请求去重建，其他等待或直接回源。

```csharp
// 内存实现用信号量；Redis 实现用分布式锁
// 抢不到锁的：等待，或超时后直接回源（不无限阻塞）
```

本项目 `Cache:LockWaitTimeout` 默认 3 秒，**超时直接回源不阻塞**。
这是重要的取舍：**宁可多一次数据库查询，也不要让请求卡住**。

#### 缓存雪崩（Cache Avalanche）

**现象**：**大批 key 在同一时刻过期**（例如同时写入、TTL 相同），
所有请求同时涌向数据库。

**为什么危险**：与击穿类似但规模大得多，数据库直接被压垮。

**解法：TTL 随机抖动（Jitter）**——给 TTL 加一个随机偏移。

```csharp
private TimeSpan ApplyJitter(TimeSpan ttl)
{
    var ratio = _options.TtlJitterRatio;      // 默认 0.2
    var factor = 1.0 + (Random.Shared.NextDouble() * 2 - 1) * ratio;   // 0.8 ~ 1.2
    return TimeSpan.FromMilliseconds(ttl.TotalMilliseconds * factor);
}
```

这样过期时间被"打散"在 ±20% 的区间内，不会同时失效。

### 17.3 ⚠️ 缓存故障必须降级，不能报错

**核心原则：缓存是优化，不是必需品。**

如果 Redis 挂了，正确的行为是"直查数据库（慢一点）"，
**而不是"返回 500"**。

```csharp
private IDatabase? TryGetDatabase()
{
    try
    {
        var db = _multiplexer.Value.GetDatabase();
        return _multiplexer.Value.IsConnected ? db : null;
    }
    catch (Exception ex) when (ex is RedisConnectionException or RedisTimeoutException or InvalidOperationException)
    {
        _logger.LogWarning(ex, "Redis 不可用，缓存操作降级");
        return null;       // ← 返回 null，调用方直接回源
    }
}
```

注意 `ICacheService` 的接口注释明确写了这条契约：

```csharp
/// 缓存抽象。实现需保证：Redis 不可用时降级（不抛异常），并在内部处理
/// 缓存穿透（空值哨兵）、缓存击穿（互斥重建）、缓存雪崩（TTL 随机抖动）。
```

### 17.4 三级实现与开关

本项目提供三个实现，用**工厂委托**按配置选择：

| 实现 | 何时使用 |
|---|---|
| `NullCacheService` | `Cache:Enabled = false`（完全旁路） |
| `MemoryCacheService` | `Provider = Memory`（单实例） |
| `RedisCacheService` | `Provider = Redis`（多实例 / 需要共享） |

**为什么要有 `NullCacheService`**：调试"怀疑缓存导致的问题"时，
一个开关就能完全旁路缓存，而不必改代码。**这是可运维性的设计。**

### 17.5 缓存 key 设计规范

```
blog:{模块}:{操作}:v{版本}:{固定维度}:{可选hash}
```

| 设计点 | 理由 |
|---|---|
| 前缀 `blog:` | 便于按前缀失效；与其他应用共用 Redis 时不冲突 |
| `v{版本}` | **缓存结构不兼容变更时整体失效**——改版本号即可，旧 key 无人访问、靠 TTL 自然消失，**无需 `SCAN` 清理** |
| 固定维度用短键名，缺省值 `-` 占位 | 保持 key 段数固定，便于排查 |
| 长文本做 SHA256 取前 16 位 | 避免超长/特殊字符污染 key |

**`v{版本}` 这个设计特别值得学习**：它把"缓存与代码结构不一致"这个运维难题，
简化成"改一个常量"。这是**为可运维性而设计**的典型例子。

### 17.6 `GetOrCreateAsync` 模式

```csharp
Task<T?> GetOrCreateAsync<T>(string key, Func<CancellationToken, Task<T>> factory, TimeSpan ttl,
    bool cacheNull = true, CancellationToken cancellationToken = default);
```

调用方只提供"怎么取数据"（factory），缓存逻辑全在内部：

```csharp
return _cache.GetOrCreateAsync(
    CacheKeys.PostList(normalized),
    ct => _postQuery.GetPagedAsync(normalized, ct),      // ← 只有这里知道怎么查
    ListCacheTtl,
    cacheNull: true,
    cancellationToken)!;
```

**好处**：缓存策略集中，不会出现"某处忘了写缓存"。

### 17.7 缓存一致性：本项目怎么处理

| 场景 | 处理 |
|---|---|
| 写操作 | 更新数据库后**删除**相关缓存（不是更新缓存） |
| 浏览量 | 更新数据库后**同步刷新**详情缓存（`ViewCount + 1`） |
| 站点配置保存 | 前端调 `refreshAll()` 刷新全站 store |
| 缓存结构变了 | 改 `Version` 常量 |

**"删除缓存"比"更新缓存"更安全**：更新缓存需要两步（改库、改缓存），
中间可能失败导致不一致；删除缓存后下次读会自然回源重建。

## 18. 限流：令牌桶算法

### 18.1 为什么需要限流

| 目的 | 说明 |
|---|---|
| 防滥用 | 防止单用户刷爆接口 |
| 保可用 | 保护后端不过载，其他用户仍可用 |
| 控成本 | 限制昂贵操作（搜索、上传）的调用频率 |

### 18.2 常见限流算法

| 算法 | 思路 | 缺点 |
|---|---|---|
| **固定窗口** | 每分钟最多 N 次 | **临界问题**：窗口边界可放行 2N 次 |
| **滑动窗口** | 统计过去 N 秒 | 实现复杂，需存时间戳 |
| **漏桶**（Leaky Bucket） | 请求排队，匀速流出 | 不允许突发 |
| **令牌桶**（Token Bucket） | 桶按速率积攒令牌，请求消费令牌 | **允许突发**（桶容量内） |

**本项目选令牌桶**，因为它**允许一定的突发流量**，
而真实用户行为本来就是突发的（打开页面时并发几个请求）。

### 18.3 令牌桶的工作原理

```
桶容量 capacity = 30
补充速率 rate   = 2 个/秒

时刻 T0：桶满（30 个令牌）
        ↓ 用户突发 20 个请求
时刻 T1：消耗 20 个 → 剩 10 个        ✅ 全部放行（突发被允许）
        ↓ 空闲 5 秒
时刻 T2：补充 5×2 = 10 个 → 20 个
        ↓ 又 25 个请求
时刻 T3：放行 20 个，剩 0 个，5 个被拒 ❌ 429
```

两个参数的含义：

| 参数 | 控制 |
|---|---|
| `Capacity` | **突发上限**（能一次性放行多少） |
| `TokensPerSecond` | **长期平均速率** |

### 18.4 ⚠️ 分布式环境下的原子性

**问题**：令牌桶的状态是"读 → 算 → 写"。并发请求会互相覆盖。

```
请求A 读到 5 个令牌
请求B 读到 5 个令牌          ← 都读到 5
请求A 写回 4
请求B 写回 4                 ← 实际消耗了 2 个，但只记了 1 个
```

**解法一：Redis Lua 脚本**（原子执行）

```lua
local bucket = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

local tokens = tonumber(bucket[1]) or capacity
local ts = tonumber(bucket[2]) or now

-- 按流逝时间补充令牌
tokens = math.min(capacity, tokens + (now - ts) / 1000 * rate)

local allowed = 0
local retryAfter = 0
if tokens >= 1 then
    tokens = tokens - 1
    allowed = 1
else
    retryAfter = math.ceil((1 - tokens) / rate * 1000)
end

redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', now)
-- 桶闲置 2 倍填满时间后自动过期，避免 key 无限增长
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 2000))
return { allowed, math.floor(tokens), retryAfter }
```

**为什么必须用 Lua**：Redis 单线程执行脚本，脚本内部不会被其他命令打断，
因此"读-算-写"是原子的。

**`retryAfter` 的计算**值得注意：需要等待的秒数 = 差几个令牌 ÷ 速率。

**自动过期**同样重要：否则每个访问过的 IP 都会留下一个永久 key，内存无限增长。

**解法二：内存锁**（单实例降级方案）

```csharp
lock (bucket.Gate)
{
    var elapsed = (nowMs - bucket.TimestampMs) / 1000.0;
    bucket.Tokens = Math.Min(capacity, bucket.Tokens + elapsed * tokensPerSecond);
    bucket.TimestampMs = nowMs;

    if (bucket.Tokens >= 1) { bucket.Tokens -= 1; return RateLimitResult.Allow((int)bucket.Tokens); }
    ...
}
```

**⚠️ 内存实现的致命局限**：**每个实例一个桶**。
2 个实例时，实际限流阈值是"配置值 × 2"，**限流形同虚设**。

这正是 `DeploymentGuard` 存在的原因——多实例 + 非 Redis 时**启动即失败**。

### 18.5 限流粒度

| 粒度 | 桶 key 的标识 | 适用 |
|---|---|---|
| **Ip**（默认） | 客户端 IP | 防单用户滥用 |
| Global | 固定字符串 | 保护后端总容量 |
| Endpoint | 方法 + 路径 | 保护特定昂贵接口 |

**⚠️ 反向代理下的 IP 识别**：加了 Nginx 后，Kestrel 看到的来源 IP 全是 Nginx 的。
不做处理的话，"按 IP 限流"退化成"全局限流"。

解法是读转发头：

```csharp
private static string GetClientIp(HttpRequest request)
{
    var forwarded = request.Headers["X-Forwarded-For"].FirstOrDefault();
    if (!string.IsNullOrWhiteSpace(forwarded))
        return forwarded.Split(',')[0].Trim();     // XFF 是逗号分隔的列表，第一个是真实客户端

    return request.HttpContext.Connection.RemoteIpAddress?.ToString() ?? "unknown";
}
```

### 18.6 规则匹配：顺序即优先级

```json
"Rules": [
  { "Name": "search", "PathPrefix": "/api/posts/search", "Method": "GET", "Capacity": 20, "TokensPerSecond": 2 },
  { "Name": "write",  "PathPrefix": "/api", "Method": "POST", "Capacity": 30, "TokensPerSecond": 2 },
  { "Name": "default","PathPrefix": "/api", "Method": "",     "Capacity": 120, "TokensPerSecond": 20 }
]
```

**按顺序匹配，命中即停**。因此**具体规则必须放在通用规则前面**——
`search` 和 `write` 都必须在 `default` 之前，否则永远命中 `default`。

### 18.7 HTTP 语义：429 与 Retry-After

| 项 | 值 |
|---|---|
| HTTP 状态码 | **429 Too Many Requests** |
| `Retry-After` 头 | 建议等待的秒数 |
| 响应体 | 统一格式，`code = 4091` |

另外在**放行**时返回 `X-RateLimit-Remaining`，便于前端/调试观察剩余额度。

## 19. 文件存储与安全

### 19.1 为什么不用静态文件中间件

ASP.NET Core 有 `UseStaticFiles()` 可以一行暴露一个目录。
但本项目选择**自己写文件接口**（`/api/files/**`），理由：

| 理由 | 说明 |
|---|---|
| 可做路径穿越防护 | 自己校验解析后的路径 |
| 精确控制缓存头 | 只在**命中**时下发缓存 |
| 可插入处理管线 | 上传时自动转 WebP |

### 19.2 ⚠️ 路径穿越攻击（Path Traversal）

**攻击方式**：请求 `GET /api/files/../../appsettings.json`，
如果服务端简单地拼接路径，就会把配置文件读出来。

```csharp
var fullPath = Path.Combine(root, userProvidedPath);   // ❌ 危险！
```

**解法：解析绝对路径后校验前缀**

```csharp
var fullPath = Path.GetFullPath(Path.Combine(root, path));
var rootFull  = Path.GetFullPath(root);
if (!fullPath.StartsWith(rootFull + Path.DirectorySeparatorChar, StringComparison.Ordinal))
    return null;   // 拒绝
```

**关键点**：必须用 `Path.GetFullPath` **先规范化**（它会解析掉 `..`），
然后再比较前缀。直接比较原始字符串会被 `..` 绕过。

### 19.3 ⚠️ 一个真实的缓存头 Bug

**现象**：上传了背景图但前端一直显示空白；文件其实已经存在了。

**根因**：当时用 `[ResponseCache]` 特性标注 action：

```csharp
[HttpGet("{**path}")]
[ResponseCache(Duration = 86400, Location = ResponseCacheLocation.Any)]   // ❌
public async Task<IActionResult> Get(string path) { ... }
```

**特性作用于整个 action，包括"文件不存在"的 404 分支**。
于是浏览器把 404 响应也缓存了**一整天**——文件补回来后用户仍看到空白，
必须手动强刷才能恢复。

**解法：在方法体内、确认命中后才设置响应头**

```csharp
var result = await _storage.GetAsync(path, cancellationToken);

if (result is null)
    return NotFound(ApiResponse.Fail(ErrorCodes.NotFound, "文件不存在"));   // ← 不带缓存头

var (stream, contentType) = result.Value;
Response.Headers.CacheControl = "public,max-age=86400";   // ← 只有命中才设置
return File(stream, contentType, enableRangeProcessing: true);
```

**教训**：**声明式的特性作用于整个方法**，无法表达"只在某分支生效"。
当缓存语义有分支时，必须用命令式代码。

### 19.4 图片转 WebP

**WebP 的优势**：同等质量下比 PNG/JPEG 小 25–35%（对流量敏感的场景很重要）。

`ImageSharpOptimizer` 在保存前转换，但**极其谨慎**：

| 情况 | 行为 |
|---|---|
| 扩展名不在 `ConvertExtensions` | 原样保存 |
| 是**动画**图片（多帧） | 原样保存（压成单帧是**数据损失**） |
| 文件损坏/无法解码 | 原样保存（**不丢用户的文件**） |
| 超过 `MaxPixels` | 原样保存（防解压炸弹） |
| 转换后**更大** | 原样保存（否则反而浪费流量） |
| 其他 | 转为 WebP，必要时等比缩小到 `MaxDimension` |

**核心原则：失败即原样保存**。优化失败绝不该导致上传失败。

**为什么锁 `SixLabors.ImageSharp` 3.x**：v4 起要求构建期许可密钥
（`sixlabors.lic`），社区许可虽免费但需先申请，否则**构建直接报错**。
v3 为纯托管实现（无原生依赖），部署最简。

### 19.5 上传大小限制的两层

| 层 | 配置 | 值 |
|---|---|---|
| 框架层 | `[RequestSizeLimit]` | 50 MB（防止请求体撑爆内存） |
| 业务层 | `FileStorage:MaxFileSize` | 10 MB（业务限制，返回 4001） |

**框架层的限制先于业务检查生效**，因为我们需要在读取请求体**之前**就拒绝超大请求。

### 19.6 上传接口的鉴权

`FilesController.Upload` 要求 **`ContentWriter`**（Admin 或 Author）。
上传是写操作，匿名开放会让任何人都能往服务器塞文件（可耗尽磁盘）。

**但读取（`GET /api/files/{**path}`）保持公开**——文章封面与作者头像
必须能被匿名访客加载。**"写要鉴权、读要公开"是文件接口的正确默认。**

> ⚠️ 这个属性**曾经遗漏过**（匿名可上传）。教训是：
> **前端隐藏按钮不是安全边界**，属性式鉴权必须逐个端点检查。
> 完整记录见 [09-已知限制与技术债.md](./09-已知限制与技术债.md) §5.1。

## 20. Vue 3 与组合式 API

### 20.1 两种 API 风格

| | Options API | **组合式 API**（本项目） |
|---|---|---|
| 组织方式 | 按选项分组（data / methods / computed） | 按**逻辑关注点**分组 |
| 复用 | mixins（来源不清晰、命名冲突） | **组合式函数**（显式、类型安全） |
| 类型推断 | 较弱 | 强 |

```vue
<script setup lang="ts">
import { ref, computed, onMounted } from 'vue'

const posts = ref<PostListItemDto[]>([])
const loading = ref(false)
const isEmpty = computed(() => !loading.value && posts.value.length === 0)

onMounted(async () => {
  loading.value = true
  try { posts.value = (await getPosts({ page: 1 })).items }
  finally { loading.value = false }
})
</script>
```

`<script setup>` 里声明的顶层变量**自动暴露给模板**，不需要 `return`。

### 20.2 响应式基础

| API | 用途 | 注意 |
|---|---|---|
| `ref(x)` | 包装任意值 | 脚本里用 `.value`，**模板里自动解包** |
| `reactive(obj)` | 包装对象 | 不能替换整个对象，解构会失去响应性 |
| `computed(fn)` | 派生值 | 有缓存，依赖不变则不重算 |
| `watch(src, fn)` | 副作用 | 异步、可拿到新旧值 |
| `watchEffect(fn)` | 自动追踪依赖 | 立即执行 |

**常见陷阱**：

```typescript
// ❌ 解构 reactive 会丢失响应性
const { open } = reactive({ open: false })

// ✅ 用 ref
const open = ref(false)

// ❌ 忘记 .value
const double = computed(() => count + 1)      // count 是 ref
// ✅
const double = computed(() => count.value + 1)
```

### 20.3 模板语法要点

| 语法 | 说明 |
|---|---|
| `v-if` / `v-else-if` / `v-else` | 条件渲染（**销毁/重建**） |
| `v-show` | 切换 `display`（**保留 DOM**，切换频繁时更优） |
| `v-for` + `:key` | 列表渲染。**`:key` 必须稳定唯一** |
| `v-bind:prop` / `:prop` | 属性绑定 |
| `v-on:event` / `@event` | 事件绑定 |
| `v-model` | 双向绑定 |
| `v-html` | **渲染原始 HTML → XSS 风险，见 §23** |

**`v-if` vs `v-show` 的选择**：`v-if` 有切换开销（销毁/重建组件），
`v-show` 有初始渲染开销（总是渲染）。**高频切换用 `v-show`。**

**`:key` 为什么要稳定唯一**：Vue 用它判断"哪个元素是哪个"。
用数组下标做 key，在列表插入/删除时会导致状态错乱（如输入框内容跑到别的行）。

## 21. 前端路由与守卫

### 21.1 两种 History 模式

| 模式 | URL | 刷新行为 |
|---|---|---|
| Hash（`createWebHashHistory`） | `/#/post/123` | 总是正常（`#` 后不发请求） |
| **HTML5 History**（`createWebHistory`，本项目） | `/post/123` | ⚠️ **刷新会 404** |

**为什么 History 模式刷新会 404**：URL `/post/123` 在服务器磁盘上**不存在**文件。
用户点链接时由前端 JS 接管（不发请求），但**直接刷新**时浏览器会真的请求这个路径。

**⚠️ 这是只会在部署后暴露的坑**（Vite dev server 内置了 fallback）：

```nginx
location / {
    root /var/www/blog;
    try_files $uri $uri/ /index.html;   # ← 兜底到 index.html
}
```

### 21.2 嵌套路由与布局

**父路由挂布局组件，子路由渲染到其 `<RouterView>`**：

```typescript
{
  path: '/admin',
  component: () => import('@/layouts/AdminLayout.vue'),   // ← 布局
  meta: { requiresAuth: true, roles: ['Admin'] },
  children: [
    { path: '', name: 'admin-posts', component: () => import('@/views/AdminPostListView.vue') },
    ...
  ],
}
```

**为什么用响应式导入**（`() => import(...)`）：**代码分割**——
每个页面单独打包，首屏只加载需要的代码。

`App.vue` 只保留一个顶层 `<RouterView>`，因为布局已经由父路由决定。

### 21.3 `meta` 与类型扩展

`meta` 是路由上的自定义数据。为获得类型安全，需扩展 `RouteMeta`：

```typescript
declare module 'vue-router' {
  interface RouteMeta {
    requiresAuth?: boolean
    roles?: UserRole[]
    guestOnly?: boolean
  }
}
```

不扩展的话，`to.meta.requiresAuth` 会是 `any` 或报错。

### 21.4 全局前置守卫

```typescript
router.beforeEach((to) => {
  const auth = useAuthStore()

  // 仅未登录可访问（登录页）：已登录则送回各自首页
  if (to.meta.guestOnly && auth.isAuthenticated) {
    return auth.isAdmin ? { name: 'admin-posts' } : { name: 'my-posts' }
  }

  if (!to.meta.requiresAuth) return true

  if (!auth.isAuthenticated) {
    return { name: 'login', query: { returnUrl: to.fullPath } }
  }

  const allowed = to.meta.roles
  if (allowed && auth.role && !allowed.includes(auth.role)) {
    // 已登录但角色不足：回到自己的地盘，而不是报错页
    return auth.isAdmin ? { name: 'admin-posts' } : { name: 'my-posts' }
  }

  return true
})
```

**两个设计决策值得注意**：

1. **返回 `false`/路由对象来取消或重定向**，而不是调用 `next()`（Vue Router 4 的新风格）
2. **角色不足时送回自己的地盘，而不是显示 403 页**。
   用户体验更好：作者误入管理端时，直接被送到自己的文章列表，不需要理解"权限不足"。

**`returnUrl` 的价值**：用户被中断的意图被保存，登录后能回到原处。

### 21.5 ⚠️ 守卫不是安全边界

再次强调（见 §15.7）：**前端守卫只是体验优化**。
所有受保护操作后端都会再校验一次角色与资源归属。

### 21.6 旧链接兼容：重定向

```typescript
// 旧的后台登录页已并入 /login，保留路径并转发查询参数（returnUrl），避免旧链接失效
{ path: '/admin/login', redirect: (to) => ({ name: 'login', query: to.query }) },

// 旧的「博主资料」页与「作者管理」职责重叠，统一到作者管理
{ path: 'profile', redirect: { name: 'admin-authors' } },
```

**重定向而不是删除**：如果用户收藏了旧链接、或某处还有硬编码引用，
删除会导致 404。**一个重定向成本极低，收益是不断链。**

### 21.7 404 页面

## 22. 前端状态管理与循环依赖

### 22.1 为什么需要状态管理

**问题**：多个组件需要共享状态（如"当前登录用户"）。
用 props 逐层传递（prop drilling）在深层次时极其痛苦。

**Pinia** 提供集中式 store：任何组件都能读写，且是响应式的。

### 22.2 Store 的三种形态

```typescript
export const useAuthStore = defineStore('auth', {
  state: () => ({ token: '', user: null }),                    // 数据
  getters: {                                                    // 派生值（有缓存）
    isAdmin(): boolean { return this.role === 'Admin' },
  },
  actions: {                                                    // 方法（可异步）
    async restore() { ... },
  },
})
```

**`state` 必须是函数**：返回对象。这样每个 store 实例有独立状态，
而不是共享同一个对象引用。

**`getters` 里用 `this`** 时**不能**用箭头函数（箭头函数不绑定 `this`）：

```typescript
getters: {
  isAdmin(): boolean { return this.role === 'Admin' },   // ✅
  isAdmin: () => this.role === 'Admin',                  // ❌ this 不对
}
```

### 22.3 ⚠️ 循环依赖问题与解法

**问题的产生**：

```
http.ts  ──需要 token──►  auth store
   ▲                          │
   └──────store 调 api────────┘
```

如果 `http.ts` 直接 `import { useAuthStore }`，而 store 又 import `api/auth.ts`，
就形成循环。JavaScript 的模块系统能处理一部分循环，但常导致
**运行时 `undefined`**（依赖在初始化时还未赋值）。

**本项目的解法：依赖注入（回调注入）**

```typescript
// http.ts —— 只声明"我需要什么"，不 import store
let tokenProvider: () => string = () => ''
let unauthorizedHandler: (() => void) | null = null

export function configureHttp(options: { getToken: () => string; onUnauthorized: () => void }) {
  tokenProvider = options.getToken
  unauthorizedHandler = options.onUnauthorized
}
```

```typescript
// main.ts —— 在应用启动时"接线"
const auth = useAuthStore(pinia)
configureHttp({
  getToken: () => auth.token,
  onUnauthorized: () => { auth.clear(); /* 跳登录页 */ },
})
```

**这是"依赖倒置"在前端的应用**：`http.ts` 定义抽象（我需要一个取 token 的函数），
`main.ts` 提供具体实现。`http.ts` 因此不知道 Pinia 的存在，可独立测试。

### 22.4 401 处理的细节

```typescript
onUnauthorized: () => {
  // 已经在登录页时不要跳转，否则会把「密码错误」提示冲掉
  const onLoginPage = router.currentRoute.value.meta.guestOnly === true
  auth.clear()
  if (!onLoginPage) {
    const returnUrl = router.currentRoute.value.fullPath
    void router.replace({ name: 'login', query: returnUrl !== '/' ? { returnUrl } : {} })
  }
}
```

**为什么判断"已在登录页"**：用户输错密码 → 后端返回 401 →
触发 `onUnauthorized` → 若不加判断，会重新导航到登录页 →
**页面重载，错误提示消失**，用户以为"点了没反应"。

### 22.5 Store 的持久化

```typescript
export const useAuthStore = defineStore('auth', {
  state: () => ({
    token: localStorage.getItem(TOKEN_KEY) ?? '',      // 启动时从 localStorage 恢复
    user: readUser(),
    verified: false,                                    // 是否已向后端确认过
  }),
  actions: {
    setSession(data: LoginResponse) {
      this.token = data.token
      localStorage.setItem(TOKEN_KEY, data.token)       // 登录时写入
      ...
    },
    async restore() {
      if (!this.token) { this.clear(); return }

      // 本地已知过期 → 直接清理，省一次请求
      if (this.expiresAt && new Date(this.expiresAt).getTime() <= Date.now()) {
        this.clear(); return
      }

      try {
        const me = await getMe()               // 向后端确认
        this.user = me
        this.verified = true
      } catch {
        this.clear()                           // 401 或其他失败 → 清空
      }
    },
  },
})
```

**`verified` 标志的作用**：避免每次路由导航都请求 `/me`。

**`restore()` 的价值**：能正确处理**"token 未过期但账号已被停用/改密"**——
本地看 token 还有效，但后端 `TokenVersion` 校验会拒绝。

### 22.6 应用启动顺序

```typescript
// main.ts
app.use(pinia)
app.use(router)
useThemeStore().apply()                 // 立刻应用主题，避免闪烁
configureHttp({ ... })                  // 接线

void auth.restore().finally(() => {
  app.mount('#app')                     // ← 等会话恢复后再挂载
})
```

**为什么等 `restore()` 再挂载**：否则首屏会短暂显示"未登录"状态
（如导航栏显示"登录"按钮），然后闪变成已登录状态。**等待后挂载避免了这次闪烁。**

## 23. 前端 XSS 防护

### 23.1 什么是 XSS

**跨站脚本攻击（Cross-Site Scripting）**：攻击者让**你的页面**执行**他的脚本**。

| 类型 | 说明 |
|---|---|
| 存储型 | 恶意内容存进数据库，所有访问者中招 |
| 反射型 | 恶意内容在 URL 里，用户点击后触发 |
| DOM 型 | 前端 JS 把不可信数据写入 DOM |

**危害**：窃取 `localStorage` 里的 token、冒充用户操作、篡改页面内容。

> ⚠️ 本项目把 token 存在 `localStorage`（§15.4），
> 因此 **XSS 的后果尤其严重**——攻击者能直接读走 token。
> **防 XSS 是本项目的硬性要求，不是可选项。**

### 23.2 本项目的关键风险点：Markdown 渲染

文章内容是 **Markdown**，前端用 `marked` 转成 HTML，再用 `v-html` 渲染。

**这是典型的 XSS 场景**：Markdown 允许内联 HTML，
恶意作者（或被攻破的账号）可以嵌入 `<script>` 或 `<img onerror=...>`。

### 23.3 防护：DOMPurify 消毒

```typescript
import { marked } from 'marked'
import DOMPurify from 'dompurify'

const rawHtml = marked.parse(markdown)                 // 1. Markdown → HTML（可能含恶意代码）
const safeHtml = DOMPurify.sanitize(rawHtml)           // 2. 消毒：移除危险标签与属性
```

**DOMPurify 做什么**：按白名单过滤 HTML，移除 `<script>`、
`on*` 事件属性（`onerror`、`onclick`...）、`javascript:` 协议等。

**为什么这一步不能省**：`v-html` 会**原样注入** HTML，
Vue 的模板转义**对它无效**（`v-html` 的语义就是"这是可信 HTML"）。

### 23.4 防护的层次

| 层 | 措施 |
|---|---|
| 输出编码 | Vue 模板默认转义 `{{ }}` 插值（**不要用 `v-html` 除非必要**） |
| HTML 消毒 | `v-html` 前必须 `DOMPurify.sanitize()` |
| 输入校验 | 后端校验长度与格式（见 `ValidateTitleAndContent`） |
| CSP | 内容安全策略，限制可执行的脚本来源（部署层配置） |
| token 短有效期 | 限制 XSS 成功后的时间窗口（30 分钟） |

### 23.5 其他 XSS 注意点

| 场景 | 风险 | 处理 |
|---|---|---|
| `v-html` | 高 | **必须消毒** |
| `:href="userUrl"` | `javascript:` 协议 | 校验协议白名单 |
| `innerHTML = x` | 高 | 避免；必须时消毒 |
| `eval()` / `new Function()` | 极高 | **绝不用** |
| CSS `url()` 注入 | 中 | 校验 URL |

**后端侧的对应责任**：本项目后端**不做 HTML 消毒**（存储原始 Markdown），
消毒发生在**渲染时**。这是合理的设计——原文保留，展示时防护。

> **一个值得思考的点**：为什么不在写入时消毒？
> 因为消毒规则会演进（今天安全的标签明天可能被发现有问题），
> 存储原始内容、渲染时消毒，意味着**改进消毒规则能立刻保护所有历史内容**。

### 24.2 什么是好的单元测试

| 特征 | 说明 |
|---|---|
| **快速** | 毫秒级，不碰数据库/网络 |
| **独立** | 不依赖其他测试的执行顺序 |
| **可重复** | 任何环境、任何次数结果一致（**固定随机种子**） |
| **自验证** | 通过/失败无需人工判断 |

### 24.3 本项目的测试方向选择

项目只有一个测试文件 `ImageSharpOptimizerTests.cs`，但**测的是最有价值的部分**：

```csharp
/// 这里的重点是「**不该转**的情况一个都不能转错**」：把动画压成单帧、把损坏文件丢掉、
/// 把已优化的小图转得更大，都是静默的数据/流量损失，比「没转成功」严重得多。
```

**为什么优先测这里**：

- 图片优化是**有损**操作。转错了**不可逆**（用户的原图没了）
- 失败是**静默的**（没有报错，只是图片不对了，可能很久才发现）
- 边界情况多（动画、损坏文件、超大图、转换后更大）

**测试设计技巧**：

```csharp
/// <summary>造一张有渐变与噪点的位图 —— 纯色图会被压得极小，不适合观察压缩效果。</summary>

**固定随机种子**让测试可重复——否则偶发失败无法复现。

              PostgreSQL(+zhparser)         Redis
```

### 25.2 为什么需要反向代理

| 理由 | 说明 |
|---|---|
| TLS 终止 | 在 Nginx 统一处理 HTTPS 证书 |
| 静态文件 | Nginx 处理静态文件比 Kestrel 高效 |
| 负载均衡 | 多实例时分发请求 |
| 缓冲慢请求 | 保护 Kestrel |
| 统一入口 | 前后端同源，避免 CORS |

### 25.3 三个必须处理的点

#### 点一：SPA history fallback

```nginx
location / {
    root /var/www/blog;
    try_files $uri $uri/ /index.html;   # ← 关键
}
```

**不做的后果**：用户直接刷新 `/post/xxx` 得到 404。
**开发期测不出来**（Vite dev server 内置了 fallback）。

#### 点二：`X-Forwarded-For`

**问题**：加 Nginx 后，Kestrel 看到的来源 IP 全是 Nginx 的 IP。
"按 IP 限流"退化成"全局限流"——一个人刷爆，所有人被限流。

**解法**：Nginx 转发真实 IP，应用侧读取（本项目已实现，见 §18.5）。

#### 点三：工作目录

`logs/` 与 `media/` 是**相对路径**（相对应用工作目录）。
若工作目录不确定，日志和上传文件会散落到意外位置。

**解法**：固定应用的工作目录，或用绝对路径配置 `FileStorage:Root`。

### 25.4 容器化 PostgreSQL 与扩展

**核心难题**：`zhparser` 不在官方镜像中，必须自行编译。
**只写文档记录手工步骤是不够的**——换人/换机/CI 起干净环境时必然出错。

**正确做法**：把编译步骤固化进 `Dockerfile`：

```dockerfile
FROM postgres:18.6
RUN apt-get install -y --no-install-recommends build-essential postgresql-server-dev-18 \
        autoconf automake libtool pkg-config git ca-certificates
# 编译 SCWS（Debian 13 源里没有 libscws-dev，也必须从源码编译）
RUN git clone --depth 1 https://github.com/hightman/scws.git /tmp/scws && ...
# 编译 zhparser
RUN git clone --depth 1 https://github.com/amutu/zhparser.git /tmp/zhparser && ...
COPY deploy/postgres-init/ /docker-entrypoint-initdb.d/
```

**⚠️ entrypoint 机制的重要限制**：

> postgres 官方镜像只在**数据目录为空**时执行 `/docker-entrypoint-initdb.d/` 下的脚本。

因此对**已存在**的数据库，初始化脚本**不会重跑**。
**这就是为什么扩展的创建必须也写进 EF 迁移**——迁移每次启动都会应用。

**双重保障**：

| 保障 | 覆盖 |
|---|---|
| Dockerfile + init 脚本 | 全新环境（开箱即用） |
| EF 迁移中的 SQL | 已有库 |

**构建期的坑**（值得记录的实战经验）：

| 坑 | 处理 |
|---|---|
| `libscws-dev` 不在 Debian 13 源 | SCWS 也从源码编译 |
| SCWS 仓库没有 `autogen.sh`，实际是 `acprep` | 用 `./acprep` |
| `Makefile.am` 里一行 Tab 缩进的 `#` 注释导致 automake 报错 | `sed` 先删掉那行 |
| `automake --warnings=no-portability` 无法抑制该错误 | 只能改源码 |

### 25.5 ⚠️ 部署时的安全清单

| 项 | 要求 |
|---|---|
| `Jwt:SigningKey` | 环境变量注入（≥32 字节）；**生产 appsettings 里没有这一项** |
| 管理员密码 | **立即修改**种子密码（公开在仓库里） |
| `Cors:Origins` | 按实际域名配置（同源部署其实不需要 CORS） |
| `Cache:Provider` | 多实例必须 Redis（否则启动失败） |
| `Deployment:InstanceCount` | 与实际实例数一致 |
| PostgreSQL | 必须带 zhparser |
| HTTPS | 必须启用 |
| 日志 | 确认日志目录可写且会被轮转 |

### 25.6 启动期校验的价值

`DeploymentGuard` 与 `Jwt:SigningKey` 校验体现了同一个理念：
**危险配置应该在启动时就失败，而不是在运行期静默降级。**

```csharp
throw new InvalidOperationException(
    "检测到「多实例 / 强制要求 Redis」的部署配置，但缓存未使用 Redis：" + reason + "。\n" +
    $"  Deployment:InstanceCount = {deployment.InstanceCount}\n" +
    $"  Deployment:RequireRedis   = {deployment.RequireRedis}\n" +
    "多实例下使用进程内缓存与内存限流会导致：限流阈值被放大到实例数倍、缓存不共享。\n" +
    "请二选一：① 配置 Cache:Provider = Redis；② 若确实是单实例，把 Deployment:InstanceCount 设为 1。");
```

**好的错误信息包含三要素**：现状（配置值是什么）、原因（为什么不行）、解法（怎么改）。

## 26. Git 工作流与行尾问题

### 26.1 行尾（Line Ending）问题 ⚠️

**背景**：Windows 用 `CRLF`（`\r\n`），Linux/macOS 用 `LF`（`\n`）。
Git 默认可能做自动转换，导致**整个文件被标记为改动**，而实际内容没变。

**本项目真实踩过的坑**：

> 工作区一度有 **39 个文件**仅存在 CRLF/LF 差异（无真实内容变更），
> 被误纳入一次提交。

**解法：`.gitattributes` 统一行尾**

```
* text=auto eol=lf       # 仓库内一律 LF
*.png binary             # 二进制文件不做转换
*.jpg binary
*.webp binary
```

**`text=auto`**：Git 自动识别文本文件并规范化。
**`eol=lf`**：检出到工作区时也用 LF（而不是跟随平台）。

**⚠️ 操作要求**：编辑文件时**不要整文件覆盖写回 CRLF**，否则会产生整文件 diff。

**检查命令**：

```bash
git ls-files --eol | grep w/crlf     # 正常应为空
```

输出含义：`w/` 是工作区（working tree），`i/` 是索引（index）。

### 26.2 提交信息的价值

```bash
git log --oneline
cabf9c3 docs: 同步上传 WebP、首个测试工程与 hero 压缩结果
130d2dc test: 建立首个测试工程 Blog.Tests 并覆盖图片优化器边界
14ad01c feat(files): 上传图片自动转 WebP 以节省传输流量
37cc124 refactor(auth)!: 合并两个登录页与两个登录端点为单一入口
```

**为什么值得认真写**：`git log` 是**唯一**记录了"当时为什么这么做"的地方
（代码只记录"结果"，文档只记录"现状"）。

**Conventional Commits 格式**：`类型(范围): 描述`

| 类型 | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 Bug |
| `docs` | 文档 |
| `refactor` | 重构（不改变行为） |
| `perf` | 性能优化 |
| `test` | 测试 |
| `chore` | 杂项 |
| `!` 后缀 | 破坏性变更 |

**为什么区分 `refactor` 和 `feat`/`fix`**：重构**不改变行为**，
因此 review 时可以只看"结构是否更好"，不必担心行为变化。
混在一起就丧失了这个信息。

### 26.3 本项目最痛的教训：误删文件

**历史事实**：本项目多次发生"无关文件被误删/误加并混入提交"。
其中 `补充具体说明.md`（原始需求文档）在**同一会话内被外部进程删除 3 次**。

**由此形成的纪律**：

| 纪律 | 命令 / 做法 |
|---|---|
| 提交前复核范围 | `git status --short` + `git show --stat HEAD` |
| 精确 add | 按路径 `git add <path>`，慎用 `git add -A` |
| 确认文件状态 | `git ls-files <path>` 判断是"已跟踪"还是"计划新增" |
| 高频提交 | 未跟踪文件丢失**不可恢复** |
| 不写绝对路径 | 本仓库目录名含非 ASCII（`dotNET项目`），文档中只写相对路径 |

**"提交前 `git show --stat HEAD`" 这一条尤其重要**：
它是发现"误删/误加"的最后一道防线，成本只有几秒。

### 26.4 文档与代码在同一提交落地

**本项目的要求**（见 [00-文档规范.md](./00-文档规范.md) §6.3）：

改了代码之后：

1. 跑通构建/测试
2. 打开受影响的文档，**逐条核对**表格里的路径、字段名、端点、配置键
3. 更新文档的"最后核对"日期
4. 文档与代码**在同一个提交里**落地

**第 2 步不能省**。文档出错最典型的方式不是"写得不对"，
而是**"改代码时忘了同步某一张表"**。

### 26.5 `.gitignore` 的要点

| 忽略 | 理由 |
|---|---|
| `bin/` `obj/` | 构建产物 |
| `node_modules/` `dist/` | 依赖与构建产物 |
| `logs/` | 运行期日志 |
| `.env.local` `.env.*.local` | **可能含个人密钥** |
| `Blog.Backend/Blog.WebApi/media/` | 上传的文件（运行期数据） |
| `.vs/` `.idea/` | IDE 配置 |

**⚠️ 关键区分**：`.env` / `.env.[mode]` **必须入库**（是可共享的默认配置），
只有 `.env.local` / `.env.*.local` 才忽略。

**为什么**：环境文件里可能有"非密钥但必要"的配置（如代理目标）。
全都不入库会导致新人无法启动；全都入库则可能泄露个人密钥。
**Vite 的 `.local` 约定正好提供这个边界。**
