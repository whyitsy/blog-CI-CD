# 00 · 文档规范

> **用途**：定义本项目的文档体系、写作规则与维护纪律。所有文档（含本文件）都遵守它。
> **读者**：项目作者本人（独立开发者），以及未来接手项目的开发者。
> **适用范围**：`docs/` 目录下的全部文档。`deploy/README.md` 属于部署产物说明，风格向本规范靠拢。
> **最后核对**：2026-09-12 ｜ **代码依据**：仓库当前 `HEAD`

---

## 1. 为什么个人项目也需要文档规范

独立开发者的文档最常见的两种死法：

1. **文档变成"迭代流水账"**：每次改动都往后追加一节，读了 3000 行还不知道"现在到底是什么样"。
2. **文档与代码脱节**：文档描述的是三个月前的设计，读者照着做必然踩坑，于是彻底不再信任文档。

本规范用两条铁律解决它们：

> **铁律一：文档描述"当前快照"，不是"变更历史"。**
> 变更历史属于 Git commit message，不属于文档。文档永远只回答"现在是什么"。
>
> **铁律二：代码是唯一事实来源（Single Source of Truth）。**
> 文档是代码的**解释与索引**。一旦发现冲突，以代码为准，并且**当场回改文档**，
> 不允许留一句"文档可能有点旧"——那等于宣布文档作废。

## 2. 文档清单与职责边界

一个人维护 14 个文件，如果职责重叠就会互相矛盾。因此每个文件必须有**唯一职责**，
写之前先问："这句话属于哪个文件？放错地方就是未来的矛盾源。"

| 文件 | 唯一职责 | 不写什么 |
|---|---|---|
| `README.md` | 文档总入口、阅读路线、文档地图 | 具体技术细节 |
| `00-文档规范.md` | 写作与维护规则（本文件） | 项目内容本身 |
| `01-项目初始化与配置.md` | 从零跑起来需要的一切：账号、环境、种子数据、配置项 | 架构设计与原理 |
| `02-项目总览.md` | 项目定位、业务模型、功能清单、整体架构、进度 | 代码级实现细节 |
| `03-后端设计.md` | 后端分层、实体、服务、关键机制、数据流 | 前端内容、通用知识教学 |
| `04-前端设计.md` | 前端路由、状态、组件、样式体系、构建 | 后端内容、通用知识教学 |
| `05-API接口清单.md` | 每个端点的路径、方法、权限、参数、响应 | 实现原理 |
| `06-数据库设计.md` | 表结构、索引、关系、迁移、全文检索落地 | 业务规则解释 |
| `07-开发与运维手册.md` | 日常命令、排错、部署、环境陷阱 | 架构决策论证 |
| `08-开发知识点.md` | 开发所需知识点的**原理讲解 + 本项目落地** | 项目进度流水账 |
| `09-已知限制与技术债.md` | 当前没做的、做得不完美的、将来要注意的 | 已修复问题的记录 |
| `10-决策记录.md` | **唯一的"历史性"文档**：已拍板决策及理由、明确不做的事、已废弃方案 | 当前实现状态（那是 02 的职责） |
| `11-CI-CD与自动化交付.md` | **交付链路**：CI/CD 原理与规范、流水线设计、质量门禁、CD 与发布 | 项目功能设计、性能度量方法 |
| `12-性能测试与容量分析.md` | **性能与容量**：指标定义与读法、测试类型、SLO 制定、压测方法与瓶颈定位 | 交付流水线本身（那是 11 的职责） |
| `13-.NET运行时诊断与内存分析.md` | **运行时内部与诊断**：栈/堆/LOH、GC 分代与工作模式、终结器与 `IDisposable`、诊断工具链、本项目诊断案例 | 压测方法学（那是 12 的职责）、语言基础（那是 08 的职责） |

**交叉引用规则**：需要解释"为什么"时，只在一个文件里详细论证，其他文件用链接指过去
（例：乐观锁的完整论证在 `03-后端设计.md`，`06-数据库设计.md` 只写"见 03 §X"）。
同一段论证抄两遍，就是在制造下一个矛盾。

## 3. 文档结构模板

每篇文档统一使用下面的骨架，保证"打开任何一篇都知道从哪读起"。

```markdown
# NN · 标题

> **用途**：一句话说明这篇文档解决什么问题。
> **读者**：谁需要读它。
> **最后核对**：YYYY-MM-DD ｜ **代码依据**：仓库 HEAD 或某次提交

---

## 1. 一级章节
### 1.1 二级章节
...

## N. 与代码的对应关系   ← 可选，列出关键文件路径
```

### 3.1 元信息块是强制的

- **用途 / 读者**：帮读者 3 秒内决定要不要读。
- **最后核对**：这是文档可信度的凭证。**每次核对完内容必须更新日期**。
  看到半年前的日期，读者就知道该怀疑它了——这正是我们想要的效果。
- **代码依据**：写 `仓库 HEAD` 即可；若文档只反映某次提交的状态，就写提交短哈希。

### 3.2 标题编号

- 文件序号 + ` · ` + 名称，例如 `## 3. 数据模型`。
- 最多到三级标题（`###`）。更细的内容用列表或表格，不要用四级标题——那说明该拆文件了。

## 4. 状态标记

文档必须能区分"已经跑通的"和"打算做的"，否则读者会把计划当事实。

| 标记 | 含义 | 判定标准 |
|---|---|---|
| `[已实现]` | 代码已落地且验证过 | 能在仓库里指出具体文件，且构建/调用通过 |
| `[已决定]` | 已拍板但还没写代码 | 有明确结论，只是尚未实施 |
| `[计划中]` | 有想法但未拍板 | 还需要决策，可能变化 |
| `[已废弃]` | 曾经存在、现已移除 | 文档保留说明是为了防止有人再提同样的方案 |

**默认是 `[已实现]`**：不写标记的内容，读者有权理解为"这是当前事实"。
因此**只有非当前事实才需要标记**，避免满屏标记反而看不清重点。

## 5. 写作风格

### 5.1 面向"三个月后的自己"

设想读者完全忘了这个项目。因此：

- **术语首次出现必须解释**，或链接到 `08-开发知识点.md` 的对应小节。
- **不要用"显然""简单""众所周知"**——三个月后的你不会觉得显然。
- **命令必须可复制粘贴**，不要写"进入目录后执行"这种含糊指代。

### 5.2 命令与路径

- 命令统一放在代码块里，并标注在哪里执行（仓库根 / `Blog.Backend/` / Windows 侧）。
- **正文中不写仓库的绝对路径**。原因：本仓库所在目录名含非 ASCII 字符（`dotNET项目`），
  且不同开发机的盘符不同。一律写仓库内相对路径（如 `Blog.Backend/Blog.WebApi/Program.cs`）。
- 确需给出 WSL/Windows 双栈命令时（本项目大量存在），写成两个代码块并注明各自环境。

### 5.3 表格优先

对比、清单、参数说明一律用表格。表格比段落更容易核对，
而"容易核对"是本规范最看重的性质。

### 5.4 记录"为什么"，但只记一次

代码里只能写出"怎么做"，写不出"为什么这样选"。文档的核心价值就是补上"为什么"。
但**同一决策只在一个文件里论证**，其他文件链接过来。

### 5.5 明确写出"坑"

踩过的坑是个人项目最宝贵的资产（时间已经付出了）。
统一写在对应主题的末尾，或用 **⚠️** 标记。写清三要素：

1. **现象**：报错信息 / 错误行为（原样抄报错，便于将来搜索）
2. **根因**：为什么会这样
3. **解法**：怎么改的

## 6. 维护纪律

### 6.1 何时必须更新文档

| 触发场景 | 必须更新的文档 |
|---|---|
| 新增/删除 API 端点 | `05-API接口清单.md` |
| 实体或表结构变更 | `06-数据库设计.md` + `03-后端设计.md` |
| 新增页面或路由 | `04-前端设计.md` |
| 配置项新增/改名 | `01-项目初始化与配置.md` |
| 环境/命令变化 | `07-开发与运维手册.md` |
| 已实现的功能 | 把 `[已决定]` 改成 `[已实现]`（或删掉标记） |
| 发现新的坑 | `07`（环境类）或 `08`（知识类） |
| 功能完成/延期 | `02-项目总览.md` 的进度小节 |
| **新增/修改流水线配置** | `11-CI-CD与自动化交付.md` |
| **定下或修改性能目标（SLO）** | `12-性能测试与容量分析.md` |
| **做了一次压测** | `12-性能测试与容量分析.md`（基线数字与结论） |
| **某项工程化缺口被解决** | `09-已知限制与技术债.md` §6（把该条目移出缺口清单） |
| **做了一次 profiling / dump 分析** | `13-.NET运行时诊断与内存分析.md`（现象、数据与结论） |
| **调整了 GC 或运行时配置** | `13-.NET运行时诊断与内存分析.md` + `01-项目初始化与配置.md`（配置项） |

### 6.2 提交纪律（本项目有惨痛教训）

> ⚠️ **提交前必须 `git show --stat HEAD` 复核。**
> 本项目历史上多次发生"无关文件被误删/误加并混入提交"，
> 以及"工作区 39 个文件仅因行尾 CRLF/LF 差异被整体纳入提交"。

- 使用 `git add -A` / `git add .` 前，先 `git status --short` 看清范围，**优先按路径精确 add**。
- 改动前用 `git ls-files <path>` 确认文件是"已跟踪"还是"计划新增"，避免误判为删除。
- **行尾统一 LF**（仓库根有 `.gitattributes`）。编辑文件时**不要整文件覆盖写回 CRLF**，
  否则会产生整文件 diff。检查：`git ls-files --eol | grep w/crlf`（正常应为空）。
- 未跟踪文件丢失不可恢复，**建议高频提交**。

### 6.3 文档的"最后核对"动作

改了代码之后，正确顺序是：

1. 跑通构建/测试
2. 打开受影响的文档，**逐条核对**表格里的路径、字段名、端点、配置键
3. 更新"最后核对"日期
4. 文档与代码**在同一个提交里**落地

第 2 步不能省。文档出错最典型的方式不是"写得不对"，而是"改代码时忘了同步某一张表"。
