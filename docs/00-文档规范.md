# 00 · 文档规范

> **用途**：定义本项目的文档分区、写作规则、维护纪律，以及**全项目代码索引总表**。
> **读者**：项目作者本人（独立开发者），以及未来接手项目的开发者。
> **适用范围**：`docs/`、`learn/`、`archive/` 三区（`deploy/README.md`、`tools/*/README.md` 风格向本规范靠拢）。
> **最后核对**：2026-09-14 ｜ **代码依据**：仓库 HEAD

---

## 1. 两条铁律

独立开发者的文档最常见的两种死法：**变成"迭代流水账"**、**与代码脱节**（读者照着做必然踩坑，于是彻底不再信任文档）。

> **铁律一：文档描述"当前快照"，不是"变更历史"。** 变更历史属于 Git commit message。
> **铁律二：代码是唯一事实来源（Single Source of Truth）。** 文档是代码的**解释与索引**；
> 一旦发现冲突，以代码为准并**当场回改文档**，不允许留"文档可能有点旧"——那等于宣布文档作废。

---

## 2. 按用途分成三区（硬规则一）

铁律一、二对所有文档都成立，但"为什么"与"当时"必须另有去处，否则手册迟早被历史撑爆。
三区各干一件事，**放错区就是未来的矛盾源**：

| 区 | 唯一用途 | 允许写 | **禁止写** |
|---|---|---|---|
| **`docs/`** 参考手册 | 描述**当前代码事实** | 端点、表结构、配置键、命令、部署步骤、未决项 | ❌ "计划中 / 打算做"（属 [06-技术债与待办.md](./06-技术债与待办.md)）<br>❌ "已修复历史 / 曾经的问题"（属 `archive/`） |
| **`learn/`** 教材 | 讲**原理与为什么** | 通用原理、取舍论证、学习路线、动手任务 | ❌ 声称自己是事实来源<br>❌ 复述 `docs/` 的实现细节（两处维护 ⇒ 迟早矛盾） |
| **`archive/`** 留档 | 保存**过程与历史** | 决策当时的理由、已废弃方案、踩坑的完整定位过程 | ❌ **只增不改**：可补索引与日期，不许回头改写结论 |

> ⚠️ **信任级别不同**：`docs/` 与代码不符即为**缺陷**；`learn/` 只保证原理正确，
> 字段名 / 端点 / 配置键**以代码与 `docs/` 为准**；`archive/` 描述的是**当时**的状态，别照抄里面的代码片段。

## 3. 不写死会变的数字（硬规则二）

**凡由数据或运行结果决定的数字，一律不写进文档。** 它们必然过期，而过期一次，整篇文档的可信度就掉一档。

| 点名反例（真实发生过） | 为什么错 | 改写为 |
|---|---|---|
| `195 项测试` / `81 项` | 加一个测试就错；同一仓库曾同时存在多个互相矛盾的值 | 删掉具体值，或"实测见 CI 作业摘要" |
| `94 条断言` | 随库里的数据变化 | 同上 |
| `13 篇文章` | 开发库实测只有 3 篇 | "远低于让查询规划器认真对待的量级" |
| 覆盖率百分比 | 随代码漂移；原作者自己都注明"不是逐位确定的" | 保留结论，删掉数字 |
| `12 项缺口` 这类清单计数 | 清单本身就在表格里，计数必然与表格脱节 | 只留表格，不再说"有几条" |

> **例外（可以写）**：**配置值与规格**——`MaxPixels`、`MaxFileSize`、镜像 tag、外部工具版本、
> 行业常量（如 LOH 的 85,000 字节）。判定方法：**它由代码 / 配置写死，还是由数据 / 运行决定？**

## 4. 写作规则

### 4.1 状态标记

| 标记 | 含义 | 判定标准 |
|---|---|---|
| `[已实现]` | 代码已落地且验证过 | 能在仓库里指出具体文件，且构建 / 调用通过 |
| `[已决定]` | 已拍板但还没写代码 | 有明确结论，只是尚未实施 |
| `[计划中]` | 有想法但未拍板 | 还需要决策，可能变化 |
| `[已废弃]` | 曾经存在、现已移除 | 保留说明是为了防止有人再提同样的方案 |

**默认是 `[已实现]`**：不写标记的内容，读者有权理解为"这是当前事实"；因此**只有非当前事实才需要标记**。
按 §2，`[已决定]` / `[计划中]` 只出现在 [06](./06-技术债与待办.md)，`[已废弃]` 只在同篇 §5 与 `archive/`。

### 4.2 面向"三个月后的自己"

设想读者完全忘了这个项目：**术语首次出现必须解释**（或链接到 [learn/01](../learn/01-后端知识地图.md) 对应小节）；
**不写"显然""简单来说""众所周知"**；**命令必须可复制粘贴**并标注在哪执行（仓库根 / `Blog.Backend/` / Windows 侧），
不写"进入目录后执行"这种含糊指代。正文**不写绝对路径**（仓库目录名含非 ASCII 字符，各机器盘符也不同），
一律用仓库内相对路径。**对比、清单、参数说明一律用表格**——表格比段落容易核对，这是本规范最看重的性质。

### 4.3 明确写出"坑"，且同一件事只讲一遍

踩过的坑是个人项目最宝贵的资产，统一用 **⚠️** 标记并写清三要素：
**现象**（报错信息，**原样抄报错**便于将来搜索）· **根因** · **解法**。
需要解释"为什么"时**只在一个文件里详细论证**，其他文件用链接指过去——同一段论证抄两遍，就是在制造下一个矛盾。
（例：乐观锁的完整论证在 [02](./02-架构与数据模型.md) §7.1，[learn/01](../learn/01-后端知识地图.md) 只讲通用原理；
交付类命令统一放 [05-运维与部署手册.md](./05-运维与部署手册.md)，别处只链接。）

## 6. 维护纪律

### 6.1 何时必须更新文档

| 触发场景 | 必须更新的文档 |
|---|---|
| 新增 / 删除 / 改动端点 | [03](./03-API参考.md) |
| 实体、表结构、索引、迁移；字段长度 / 校验规则 | [02](./02-架构与数据模型.md)（校验规则另需同步 `FieldLimits.cs`） |
| 新增页面或路由 | [04](./04-前端设计.md) |
| 配置项新增 / 改名、账号与种子数据 | [01](./01-快速开始.md) |
| 环境 / 命令 / 部署流程变化 | [05](./05-运维与部署手册.md) |
| 新增或修改流水线、门禁 | [05](./05-运维与部署手册.md) §8 + [06](./06-技术债与待办.md) §2 + **给它配一道失效哨兵** |
| 定下 / 修改性能目标、做了一次压测、解决了一个未决项 | [06](./06-技术债与待办.md) §3（结论进 `learn/03`）或把条目**移出**清单 |
| 踩了新坑并定位出根因、做出或推翻一个决策 | `archive/`（当前口径同步到 [06](./06-技术债与待办.md) §4–§5） |

### 6.2 提交纪律

> ⚠️ **提交前必须 `git show --stat HEAD` 复核。** 本项目历史上多次发生"无关文件被误删 / 误加并混入提交"，
> 以及"工作区文件仅因行尾 CRLF/LF 差异被整体纳入提交"。

- 用 `git add -A` / `git add .` 前先 `git status --short` 看清范围，**优先按路径精确 `git add <path>`**。
- 改动前用 `git ls-files <path>` 确认文件是"已跟踪"还是"计划新增"，避免误判为删除。
- **行尾统一 LF**（仓库根有 `.gitattributes`）。检查：`git ls-files --eol | grep w/crlf`（正常应为空）。
- 未跟踪文件丢失**不可恢复**，建议高频提交。

### 6.3 文档的"最后核对"动作

改了代码之后：① 跑通构建 / 测试 → ② 打开受影响的文档，**逐条核对**表格里的路径、字段名、端点、配置键
→ ③ 更新"最后核对"日期 → ④ 文档与代码**在同一个提交里**落地。

**第 ② 步不能省**。文档出错最典型的方式不是"写得不对"，而是**"改代码时忘了同步某一张表"**。
命令见 [05-运维与部署手册.md](./05-运维与部署手册.md) §7。
