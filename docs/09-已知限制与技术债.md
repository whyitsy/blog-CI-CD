## 1. 🔴 安全漏洞：多个写接口缺少鉴权

### 现象

以下写接口**没有 `[Authorize]` 属性**，**匿名可调用**：

| 端点 | 设计意图 | 实际 |
|---|---|---|
| `POST /api/categories` | 👑 AdminOnly | ⚠️ 匿名可调用 |
| `PUT /api/categories/{id}` | 👑 AdminOnly | ⚠️ 匿名可调用 |
| `DELETE /api/categories/{id}` | 👑 AdminOnly | ⚠️ 匿名可调用 |
| `POST /api/tags` | 👑 AdminOnly | ⚠️ 匿名可调用 |
| `PUT /api/tags/{id}` | 👑 AdminOnly | ⚠️ 匿名可调用 |
| `DELETE /api/tags/{id}` | 👑 AdminOnly | ⚠️ 匿名可调用 |
| `PUT /api/site/config` | 👑 AdminOnly | ⚠️ 匿名可调用 |
| `PUT /api/site/social-links` | 👑 AdminOnly | ⚠️ 匿名可调用 |
| `DELETE /api/site/social-links/{id}` | 👑 AdminOnly | ⚠️ 匿名可调用 |
| `POST /api/files/upload` | ✍️ ContentWriter（推测） | ⚠️ 匿名可调用 |

### 影响

- 任何人都能**增删改分类与标签**
- 任何人都能**改站点名称、首屏文案、背景图、社交链接**
- 任何人都能**往服务器上传文件**（可能被用来耗尽磁盘）

### 为什么没有被发现

前端按钮的可见性由角色控制（`canManageTaxonomy`、路由守卫），
所以**正常点界面时看不出任何异常**。

> ⚠️ **这正是最危险的地方：前端隐藏入口不是安全边界。**
> 直接发一个 HTTP 请求就能绕过全部前端控制。

### 根因

逐个 Action 添加 `[Authorize]` 属性时**遗漏**。

**对比参照**：`CollectionsController` 和 `UsersController` 是正确的——
前者每个写 action 都有 `[Authorize(Policy = "AdminOnly")]`，
后者整个类有 `[Authorize(Policy = "AdminOnly")]`。
`CategoriesController` / `TagsController` / `SiteController` / `FilesController`
则是完全没有任何授权属性。

### 修复方式

逐个补属性，**不需要改任何逻辑**：

```csharp
// Blog.WebApi/Controllers/CategoriesController.cs
[HttpPost]
[Authorize(Policy = "AdminOnly")]    // ← 补这一行
public async Task<ApiResponse<CategoryDto>> Create(...)

// TagsController 同理（3 个写 action）

// SiteController 同理（PUT config / PUT social-links / DELETE social-links/{id}）

// FilesController.Upload 至少要求 ContentWriter
[HttpPost("upload")]
[Authorize(Policy = "ContentWriter")]    // ← 补这一行
```

同时需要为这些文件加上 `using Microsoft.AspNetCore.Authorization;`。

### 建议的验证方式

修复后应补充**自动化测试**（见 §4）：
用匿名请求调用这些端点，期望得到 **401**；用 Author 角色的 token 期望 **403**。

## 2. 🔴 可用性风险：PG 容器未切换到带 zhparser 的镜像

### 现象

开发环境的 `pgsql` 容器是**官方 `postgres:18.6` 镜像 + 手工编译的 zhparser 扩展**。

### 风险

> ⚠️ **该容器一旦被 `docker rm` / 重建，zhparser 会全部丢失，全文检索立即失效。**

失效时的报错：

```
ERROR:  text search configuration "chinese" does not exist
```

触发场景（任一即可）：

- 容器被删除或重建
- 换一台开发机
- 部署到测试/生产环境
- CI 起一个干净的 PostgreSQL 跑集成测试

### 已经准备好的解决方案

| 产物 | 状态 |
|---|---|
| `deploy/postgres-zhparser.Dockerfile` | ✅ 已编写并**在独立端口的全新容器上实测通过** |
| `deploy/postgres-init/01-zhparser.sql` | ✅ 已编写（幂等，新建库时自动执行） |
| EF 迁移中的 `CREATE EXTENSION` + 建 `chinese` 配置 | ✅ 已包含（覆盖"已有库"场景） |
| **把开发容器换成自定义镜像** | ❌ **尚未执行** |

验证记录（来自 `deploy/README.md` §3）：

| 检查项 | 结果 |
|---|---|
| 初始化脚本自动执行 | ✅ |
| 扩展已安装 | ✅ |
| 检索配置已创建 | ✅ |
| 中文分词为词级 | ✅ |
| 检索匹配正确 | ✅ |

### 剩下的唯一一步

把开发容器 `pgsql` 换成自定义镜像。**数据在命名卷上，替换容器不会丢数据。**

```bash
# 1) 确认数据卷名
docker inspect pgsql --format '{{range .Mounts}}{{.Name}}{{end}}'

# 2) 停掉旧容器但保留（万一要回退）
docker stop pgsql && docker rename pgsql pgsql-old

# 3) 用自定义镜像启动新容器，挂同一个数据卷
docker run -d --name pgsql \
  -e POSTGRES_USER=kky -e POSTGRES_PASSWORD=123456 -e POSTGRES_DB=blog \
  -p 5432:5432 \
  -v <上一步打印的卷名>:/var/lib/postgresql \
  blog-postgres-zhparser:18

# 4) 验证既有库仍在，并创建扩展与检索配置
docker exec pgsql psql -U kky -d blog_stage2 -c "CREATE EXTENSION IF NOT EXISTS zhparser;"

# 5) 确认无误后再删除旧容器
docker rm pgsql-old
```

> ⚠️ **挂载点必须是 `/var/lib/postgresql`**（与官方镜像一致），
> **不是** `/var/lib/postgresql/data`。写错会导致容器以为数据目录为空而重新初始化，
> 表现为"数据看起来丢了"（实际还在卷里）。
>
> 详细步骤见 `deploy/README.md` §4。

### 为什么这算"高优先级"

搜索引擎依赖它，而**触发条件是运维操作**（重建容器），
不是代码问题——**无法通过测试提前发现**。

## 3. 🟡 功能缺失：全文检索缺少相关度排序

### 现象

搜索接口 `GET /api/posts/search` 的结果**按发布时间倒序**，
而不是按**相关度**排序。

### 影响

搜"数据库优化"时，一篇只在正文末尾提了一句的文章，
可能排在标题就是《数据库优化实践》的文章前面。

**功能可用，但结果质量不理想。**

### 根因

PostgreSQL 的相关度函数是 `ts_rank`。但本项目的 `SearchVector` 是
**影子属性**（不存在于 C# 实体上，见 [03-后端设计.md](./03-后端设计.md) §7），
在这种形态下 EF Core 会**把 `ts_rank` 判为客户端求值**，
无法翻译成 SQL。

目前已经用**参数化原生 SQL** 解决了"匹配"问题（`@@` 运算），
但 `ts_rank` 的排序还需要进一步处理。

### 可选方案

| 方案 | 说明 | 代价 |
|---|---|---|
| A. 在原生 SQL 里一起算 `ts_rank` 并排序 | 把排序也放进子查询，返回有序 id 列表 | 需重写查询，且与 `Id IN (...)` 的组合方式要调整 |
| B. 用 `EF.Functions` 的替代写法 | 需验证能否翻译 | 未知，可能仍失败 |
| C. 放弃相关度排序 | 维持现状 | 搜索质量不理想 |

**当前状态**：维持方案 C，等有实际需求时再实施。

## 4. 🟡 技术债：测试覆盖率低

### 现状

整个解决方案只有**一个测试文件**：

| 项目 | 内容 |
|---|---|
| `Blog.Tests` | xUnit 测试工程 |
| `Blog.Tests/Images/ImageSharpOptimizerTests.cs` | 图片转 WebP 的边界行为测试 |

### 未覆盖的部分（按风险排序）

| 未覆盖 | 风险 | 说明 |
|---|---|---|
| **权限与归属校验** | 🔴 高 | 安全相关，**且已有真实缺口**（§1） |
| **草稿保护逻辑** | 🔴 高 | 安全相关（`includeUnpublished` / `mine` / 详情 404） |
| **乐观锁并发冲突** | 🔴 高 | 核心机制，出错影响全局 |
| 缓存三防（穿透 / 击穿 / 雪崩） | 🟡 中 | 逻辑复杂，回归风险高 |
| 限流（令牌桶 + 降级） | 🟡 中 | Lua 脚本尤其值得测 |
| 全文检索 | 🟡 中 | 中文分词边界 |
| 密码哈希与 TokenVersion | 🟡 中 | 安全相关 |
| 前端组件 | 🟢 低 | 人工验证成本相对低 |

### 为什么现在只有一个测试

项目的测试建设起步较晚（首个测试工程是最近才建立的）。
当时选择**优先覆盖图片优化器**，判断依据是：

> 图片优化是**有损**操作、失败是**静默**的、边界情况多，
> 且转错了**不可逆**（用户的原图没了）。风险密度最高。

这个判断本身是合理的，但**权限相关的测试风险更高**，应当尽快补上。

### 建议的补充顺序

1. **权限矩阵测试**（配合 §1 的修复）：每个受保护端点 × 匿名/Author/Admin
2. **草稿保护测试**：`includeUnpublished`、`mine`、未发布详情
3. **乐观锁测试**：并发更新 → 期望 409
4. 缓存三防测试
5. 限流测试

## 5. 🟢 小瑕疵：种子作者头像路径已失效

### 现象

种子数据里默认作者的头像路径是：

```
/media/avatar-default.png
```

但**后端已经不提供 `/media/**` 路径**——文件接口是 `/api/files/**`。
因此这个 URL 返回 404。

### 当前影响：无

前端已经用 `@error` 事件回退到"姓名首字母"占位，
因此**页面不会破图**，只是看不到默认头像。

### 修复选项

| 选项 | 说明 |
|---|---|
| A. 更新种子数据指向一个真实存在的图片 | 需先生成/准备该图片 |
| B. 在后端补一个默认头像的静态路由 | 为一个默认图引入静态路由，不划算 |
| C. 通过「作者管理」页上传真实头像 | **最省事**，不涉及代码改动 |
| D. 保持现状（前端已优雅降级） | 可接受 |

**当前状态**：维持 D。若将来要在生产环境展示头像，用 C。

### 附带说明

`Blog.Backend/Blog.WebApi/media/.backup/` 目录的存在来源不明
（不在 `.gitignore` 的忽略逻辑里能解释，也不在代码中被引用）。

## 6. 🟡 验证缺口：前端表单保存链路缺自动化验证

### 现状

后端语义已经用 curl **逐条验证**过（CRUD、乐观锁 409、权限、限流等）。

但前端**表单的"点击保存"完整链路**没有做浏览器自动化验证——
包括：

| 未自动验证 | 说明 |
|---|---|
| 表单校验提示 | 前端 `@error` 回退、必填校验 |
| 保存成功后的提示与刷新 | toast、列表刷新、`refreshAll()` |
| 乐观锁冲突的提示 | 409 时是否给出可理解的提示 |
| 骨架屏显示 | 瞬时状态，需特殊手段（见下） |

### 已有的验证手段

项目**已经具备**自动化能力，只是没有覆盖到全部链路：

| 手段 | 位置 / 说明 |
|---|---|
| CDP（Chrome DevTools Protocol）脚本 | `/mnt/d/tmpbuild/*.mjs`（`auth-flow.mjs`、`author-flow.mjs`、`authors-ui.mjs` 等） |
| Chrome 无头截图 | 逐页截图核对布局（1440px / 800px 两档） |
| 骨架屏验证技巧 | `Page.addScriptToEvaluateOnNewDocument` 替换 fetch 为永不 resolve |

**没有用 puppeteer**：Node 22+ 内置了全局 `WebSocket`，直接用 CDP 即可，
不必引入额外依赖。

### ⚠️ 骨架屏验证的坑（已记录，避免重蹈）

| 做法 | 结果 |
|---|---|
| ✅ 把 `/api/posts*` 的 `fetch` 替换成永不 resolve 的 Promise | 稳定复现 loading 态 |
| ❌ `Fetch.enable` + glob `*/api/posts*` | **误伤 JS 模块 `src/api/posts.ts`**，页面白屏，得出错误结论 |
| ❌ `Network.emulateNetworkConditions` 加延迟 | 连 JS bundle 一起卡住，页面空白 |

## 8. 🟡 运维缺失：没有健康检查端点

### 现状

只有一个根路径存活探针：

```
GET /    →  { "name": "Blog API", "status": "running" }
```

它**只证明进程还在**，不检查任何依赖。

### 缺失的能力

| 检查 | 现状 |
|---|---|
| 数据库连通性 | ❌ 不检查 |
| Redis 连通性 | ❌ 不检查 |
| zhparser 扩展可用性 | ❌ 不检查 |
| 迁移是否已应用 | ❌ 不检查 |

### 影响

- 容器编排（K8s / Docker）的 liveness/readiness 探针无法反映真实健康状态
- 负载均衡可能把流量打到"进程活着但数据库连不上"的实例
- **zhparser 丢失这类问题不会被探针发现**（与 §2 相关）

### 建议

引入 ASP.NET Core 的 Health Checks：

```csharp
builder.Services.AddHealthChecks()
    .AddNpgSql(connectionString)
    .AddRedis(redisConnection);

app.MapHealthChecks("/health");
```

**优先级说明**：单机部署时影响有限，**多实例部署前应当补上**。

## 9. 🟢 演进风险：没有 API 版本管理

### 现状

所有端点路径都**不含版本号**（`/api/posts`，而不是 `/api/v1/posts`）。

### 影响

一旦线上有客户端在运行，**破坏性变更无法平滑过渡**——
只能"改了就全改"，没有新旧并存的余地。

### 为什么现在可以接受

- 项目尚未上线
- 前端与后端**在同一个仓库、同一个提交里演进**，不存在"旧客户端"
- 引入版本管理会增加路径噪音

### 何时需要处理

出现以下任一情况时应该引入：

- 有第三方在调用 API
- 移动端 App 需要独立发版
- 前后端分离部署且发布节奏不同

**建议方案**：URL 版本（`/api/v1/...`）——最直观、最易调试。

## 10. 明确"不做"的事项（不是技术债）

以下事项是**已经明确决定不做**的，记录在此以免被反复提起。

| 事项 | 决定 | 理由 |
|---|---|---|
| **SEO**（站点地图、结构化数据） | 不做 | 个人博客，不做搜索引擎优化 |
| **自建评论系统** | 不做 | 外挂 giscus（GitHub Discussions），本站不存评论数据 |
| **Refresh Token** | 不做（决策 T7） | 只发 Access Token（30 分钟） |
| **作者自助注册** | 不做（决策 T1） | 作者账号由管理员创建 |
| **细粒度 RBAC** | 不做 | 只有 Admin / Author 两档角色 |
| **UI 组件库** | 不做 | 自研 CSS 体系，与 Aurora 视觉深度绑定 |
| **AutoMapper** | 不做 | DTO 手写映射，显式且编译期可检查 |
| **延迟加载（EF Lazy Loading）** | 不做 | 易产生 N+1 问题 |

> 这些"不做"的决定同样是重要的信息。
> **一个项目的边界不只由"做了什么"定义，也由"明确不做什么"定义。**

## 11. 已废弃的方案（记录以免重提）

| 方案 | 为什么废弃 |
|---|---|
| 乐观锁用 `byte[] RowVersion` + `[Timestamp]` | 改为 `int Version` + SQL 条件手动控制，后者**跨数据库通用** |
| 双登录入口（`/login` + `/admin/login`、两个登录端点） | 合并为单一入口（`/login` + `POST /api/auth/login`），**权限边界交给授权策略**，登录入口不承担 |
| 静态文件中间件暴露 `/media/**` | 改为独立文件接口 `/api/files/**`（可做路径穿越防护与缓存控制） |
| 用 `pg_trgm` 模糊匹配做搜索 | 改为真全文检索（zhparser）；模糊匹配无法满足中文检索需求 |
| 前端 `/admin/profile` 独立页 | 与「作者管理」职责重叠，改为**重定向**到 `/admin/authors` |
| 静默重定向首页代替 404 | 产生**软 404**；改为真实的 404 页面 |
| `PagedResult.totalCount` 字段名 | 后端实际下发 `total`，前端写 `totalCount` 导致"共 N 篇"显示 `undefined`；已对齐 |
| `[ResponseCache]` 标注文件下载 action | 会连"文件不存在"的 404 一起缓存一整天；改为**命中后才设置响应头** |
