## 1. 🟡 验证缺口：前端表单保存链路缺自动化验证

### 现状

**后端已经有完整的自动化测试**（见 §5.7）：81 项，覆盖权限矩阵、草稿保护、
乐观锁、Service 层业务规则与图片优化边界。

但**前端「点击保存」的完整链路**仍未纳入自动化，包括：

| 未自动验证 | 说明 |
|---|---|
| 表单校验提示 | 前端 `@error` 回退、必填校验 |
| 保存成功后的提示与刷新 | toast、列表刷新、`refreshAll()` |
| 乐观锁冲突提示 | 409 时是否给出用户能理解的提示 |
| 骨架屏显示 | 瞬时状态，需特殊手段（见下） |

后端语义已用 curl 逐条验证，且乐观锁 409 本身有集成测试；
缺的是**浏览器里的端到端确认**。

### 已有的验证手段

项目**已经具备**自动化能力（本轮修专栏空态 Bug 时就用了），只是没覆盖到全部链路：

| 手段 | 位置 / 说明 |
|---|---|
| CDP（Chrome DevTools Protocol）脚本 | `/mnt/d/tmpbuild/*.mjs`（`collections-empty.mjs`、`backend-down-public-pages.mjs`、`auth-flow.mjs` 等） |
| Chrome 无头截图 | 逐页截图核对布局（1440px / 800px 两档） |
| 骨架屏验证技巧 | `Page.addScriptToEvaluateOnNewDocument` 替换 fetch 为永不 resolve |

**没有用 puppeteer**：Node 22+ 内置了全局 `WebSocket`，直接用 CDP 即可，
不必引入额外依赖。

### ⚠️ 骨架屏验证的坑（已记录，避免重蹈）

| 做法 | 结果 |
|---|---|
| ✅ 把 `/api/posts*` 的 `fetch` 替换成永不 resolve 的 Promise | 稳定复现 loading 态 |
| ❌ `Fetch.enable` + glob `*/api/posts*` | **误伤 JS 模块 `src/api/posts.ts`**，页面白屏，得出错误结论 |
| ❌ `Network.emulateNetworkConditions` 加延迟 | 连 JS bundle 一起卡住，页面空白 |

> **经验**：验证前端行为时，**先在修复前的代码上跑一遍、确认测试会失败**，
> 再在修复后跑通——否则无法区分「真的修好了」和「测试根本没生效」。

## 2. 🟢 演进风险：没有 API 版本管理

### 现状

所有端点路径都**不含版本号**（`/api/posts`，而不是 `/api/v1/posts`）。

### 影响

一旦线上有客户端在运行，**破坏性变更无法平滑过渡**——
只能"改了就全改"，没有新旧并存的余地。

### 为什么现在可以接受

- 项目尚未上线
- 前端与后端**在同一个仓库、同一个提交里演进**，不存在"旧客户端"
- 引入版本管理会增加路径噪音

### 何时需要处理

出现以下任一情况时应该引入：

- 有第三方在调用 API
- 移动端 App 需要独立发版
- 前后端分离部署且发布节奏不同

**建议方案**：URL 版本（`/api/v1/...`）——最直观、最易调试。

## 4. 已废弃的方案（记录以免重提）

| 方案 | 为什么废弃 |
|---|---|
| 乐观锁用 `byte[] RowVersion` + `[Timestamp]` | 改为 `int Version` + SQL 条件手动控制，后者**跨数据库通用** |
| 双登录入口（`/login` + `/admin/login`、两个登录端点） | 合并为单一入口（`/login` + `POST /api/auth/login`），**权限边界交给授权策略**，登录入口不承担 |

| 用 `pg_trgm` 模糊匹配做搜索 | 改为真全文检索（zhparser）；模糊匹配无法满足中文检索需求 |
| 前端 `/admin/profile` 独立页 | 与「作者管理」职责重叠，改为**重定向**到 `/admin/authors` |
| 静默重定向首页代替 404 | 产生**软 404**；改为真实的 404 页面 |
| `PagedResult.totalCount` 字段名 | 后端实际下发 `total`，前端写 `totalCount` 导致"共 N 篇"显示 `undefined`；已对齐 |

| 写接口缺少 `[Authorize]`（依赖前端隐藏按钮） | 前端隐藏不是安全边界；已给全部写接口补上策略，见 §5.1 |

## 5. 已解决的历史问题（留档）

这两项曾经是本文件里最高优先级的问题，**现已修复**。保留记录是因为它们
的**教训比结论更重要**，且代码注释与提交历史会引用到这里。

### 5.1 写接口缺少鉴权（已修复）

**当时的问题**：`Categories` / `Tags` / `Site` 三个控制器的写接口，
以及 `FilesController.Upload`，**完全没有 `[Authorize]` 属性**，匿名可调用。
任何人都能增删改分类与标签、修改站点名称/首屏文案/背景图/社交链接、
以及往服务器上传文件（可耗尽磁盘）。

**为什么长期没被发现**：前端按钮的可见性由角色控制
（`canManageTaxonomy`、路由守卫），所以**正常点界面时看不出任何异常**。

> **核心教训：前端隐藏入口不是安全边界。** 直接发一个 HTTP 请求就能绕过全部前端控制。
>
> **更普遍的教训**：属性式鉴权（`[Authorize]`）是**逐个端点**声明的，
> 漏一个就是完全敞开。因此新增写接口时必须显式检查——
> 这也正是"权限矩阵测试"应当优先补上的原因——现已有覆盖（见 §1 与 §5.1）。

**修复**：给全部写接口补上策略，并逐个用运行时请求验证。

| 控制器 | 补上的策略 |
|---|---|
| `CategoriesController` | 三个写接口 → `AdminOnly` |
| `TagsController` | 三个写接口 → `AdminOnly` |
| `SiteController` | 三个写接口 → `AdminOnly` |
| `FilesController` | `Upload` → `ContentWriter`（**读取保持公开**） |

**验证证据**（实测）：

| 检查 | 结果 |
|---|---|
| 匿名调用 12 个写接口（含上传） | 全部 **401** + 统一响应体 `code 4010` |
| 匿名读取 8 个公开接口（含搜索） | 全部 **200**（读未被误伤） |
| Admin token 创建分类 | **200** |
| Author token 创建分类（AdminOnly） | **403** |
| Author token 上传文件（ContentWriter） | **200** |

**当前完整状态**见 [05-API接口清单.md](./05-API接口清单.md) §9.4。

### 5.2 PG 容器未含 zhparser（已修复）

**当时的问题**：开发用的 `pgsql` 容器是**官方 `postgres:18.6` 镜像
+ 手工编译的 zhparser**。一旦容器被 `docker rm` / 重建，
扩展与 `chinese` 检索配置全部丢失，全文检索立即报：

```
ERROR:  text search configuration "chinese" does not exist
```

**修复**：构建 `blog-postgres-zhparser:18` 自定义镜像并**替换开发容器**，
数据卷沿用原卷（`-v <卷名>:/var/lib/postgresql`）。

> ⚠️ **挂载点必须是 `/var/lib/postgresql`**（PG18 的 `PGDATA` 实际是
> `/var/lib/postgresql/18/docker`），**不是** `/var/lib/postgresql/data`。
> 写错会让容器以为数据目录为空而重新初始化，表现为"数据看起来丢了"。

**验证证据**（实测）：

| 检查 | 结果 |
|---|---|

| 业务数据未丢 | ✅ Posts 9 / Users 7 / Authors 4 / SiteConfigs 4 / SocialLinks 3 / Collections 2 |
| 迁移记录完整 | ✅ 2 个迁移均在 |
| GIN 索引仍在 | ✅ `ix_posts_search` |
| `chinese` 配置 | ✅ parser = `zhparser`，映射 `a,e,i,j,l,n,q,v` |
| 中文分词为词级 | ✅ `'core':3 'ef':2 '优化':6 '使用':1 '做':4 '全文检索':7 '数据库':5` |
| 检索匹配 | ✅ `@@ plainto_tsquery('chinese','数据库')` → `t` |
| **全新卷自动初始化** | ✅ 在一次性容器上验证：entrypoint 自动执行 `01-zhparser.sql`，扩展与配置自动创建 |

**当前状态**：`pgsql` 运行 `blog-postgres-zhparser:18`，
**容器重建不再影响全文检索**（扩展已在镜像内，且新卷会自动初始化）。

### 5.3 全文检索缺少相关度排序（已修复，T12）

**当时的问题**：搜索结果按发布时间倒序，而不是按相关度。原因是 `ts_rank`
在「影子属性 + 参数化 tsquery」形态下会被 EF Core 判为客户端求值，无法翻译成 SQL。

**修复**：用 `Database.SqlQuery<Guid>` 直接执行一段**带 CTE 的原生 SQL**，
由数据库算好 `ts_rank` 并按分页顺序返回 Id 列表；外层仍用 `Contains` 关联回 Posts，
因此分类/标签/作者等过滤与**总数统计依然是过滤之后的**。

关键点（详见 [03-后端设计.md](./03-后端设计.md) §7.4）：

| 要点 | 说明 |
|---|---|
| 为什么用 CTE | PostgreSQL 的 `ts_rank` 属窗口函数类，**不能直接写进 WHERE**（0A000） |
| 为什么不用 keyless 实体 | 试过 `HasNoKey()` 映射，但 join 后投影 `Tags` 集合会报「cannot correlate on keyless entity type」；`SqlQuery<Guid>` 返回标量，没有这个负担 |
| 为什么在内存里重排本页 | 每页至多 `pageSize` 条（列表不加载正文），比让 EF 翻译 `ts_rank` 排序简单可靠得多 |

**验证**（实测）：

| 检查 | 结果 |
|---|---|
| 标题命中 vs 仅正文命中（标题命中发布更晚） | ✅ 标题命中排在前面（`ts_rank` 权重 A > C 生效） |
| 公开搜索接口（匿名） | ✅ 200，排序同样正确 |
| 分页稳定性 | ✅ 第 1、2 页不重复 |
| 关键词 + 分类过滤组合 | ✅ 200，`total` 为过滤后数量 |
| 非检索路径（列表/归档） | ✅ 未受影响 |

### 5.4 种子作者头像路径失效（已修复）

**当时的问题**：种子数据指向 `/media/avatar-default.png`，
但后端不提供 `/media/**` 静态路由，该 URL 恒为 404。

**修复**（三处一起改，缺一不可）：

| 改动 | 原因 |
|---|---|
| 生成 `avatar-default.webp`（**5,567,595 → 33,344 字节，−99.4%**） | 原图 1920×2742、5.31 MB，而头像显示尺寸只有几十 px。用项目自带的 ImageSharp（与上传同一套参数）转换 |
| 种子数据指向 `/api/files/avatar-default.webp` + 新迁移 | URL 必须走文件接口；已应用的库需要迁移才能拿到新值 |
| 新增只读 `FileStorage:SeedRoot`（`media-seed/`），由 csproj 复制到输出 | `media/` 是**运行期上传目录且已 gitignore**，全新克隆的仓库里没有这个文件；把只读种子资源单独跟踪并复制到输出，才能真正开箱可用 |

**踩到的坑**：应用的工作目录是 `bin/<Config>/<Tfm>`，而 `FileStorage:Root` 是相对路径，
所以它指向的是**输出目录下的 media/**，不是项目里的 media/ ——
这同时解释了为什么直接往项目 media/ 放文件不生效。

**验证**（实测）：`GET /api/files/avatar-default.webp` → **200 / image/webp / 33344 字节**
（与种子文件字节数一致）、带长缓存头；路径穿越仍被拒绝（`../` 与编码形式均 404）。

### 5.6 没有健康检查端点（已修复）

**当时的问题**：只有 `GET /` 存活探针，不检查任何依赖。

**修复**：新增 `GET /health`，实现见 `Blog.WebApi/HealthChecks/HealthCheckSetup.cs`。
用共享框架内置的 `Microsoft.Extensions.Diagnostics.HealthChecks`，**不引入第三方健康检查包**。

检查项与设计取舍：

| 检查 | 说明 |
|---|---|
| PostgreSQL 连通性 + `zhparser` 扩展 + `chinese` 检索配置 | 实际执行一次 `to_tsvector('chinese', ...)`，确保配置**真的能用**而不只是存在 |
| 迁移是否全部应用 | 避免「库结构落后于代码」这种隐蔽故障 |
| Redis 连通性 | 仅在 `Cache:Provider = Redis` 时视为必需；否则跳过（缓存可降级） |

> **对外只回 `Healthy` / `Unhealthy` 两个词，详情只写日志。**
> `/health` 通常对编排系统与负载均衡开放（甚至匿名），
> 在响应里带上「哪个依赖挂了 + 报什么错」等于向匿名访问者泄露内部结构；
> 排障需要的信息看服务端日志即可。

**验证**（实测）：

| 场景 | 结果 |
|---|---|
| 一切正常 | ✅ `200` + 响应体 `Healthy`（7 字节，无任何内部信息） |
| **停掉 PostgreSQL** | ✅ `503` + 响应体 `Unhealthy`（9 字节） |
| 详情是否泄露 | ✅ 响应体不含 `localhost` / 端口 / 异常等；日志里有结构化详情 `{"Check":"database","Status":"Unhealthy",...}` |
| 恢复数据库后 | ✅ 自动回到 `200 Healthy` |

### 5.7 测试覆盖率低（已修复）

**当时的问题**：整个解决方案只有 1 个测试文件（图片优化器）。

**修复**：建立分层测试，当前 **81 项全部通过**。

| 单元 | `PostServiceTests` | 16 | 入参校验、归属校验（非管理员改他人文章→4030）、版本号校验、摘要语义、发布幂等 |
| 单元 | `ImageSharpOptimizerTests` | 18 | WebP 转换的边界行为（原有） |

**测试基础设施要点**（`Blog.Tests/Infrastructure/BlogApiFactory.cs`）：

- 每次运行创建一个**独立的测试库** `blog_stage2_test_{8位随机}`，结束后删除，不污染开发库
- 宿主启动**之前**必须：① 建库；② 建 `zhparser` 扩展与 `chinese` 检索配置。
  否则迁移会因生成列用到 `to_tsvector('chinese', ...)` 而失败
  （`42704: text search configuration "chinese" does not exist`）
- 关闭限流：测试会连发大量请求，且限流桶存在 **Redis** 里、是**跨运行共享的外部状态**，会污染后续运行

**验证**：`dotnet test` → **失败 0，通过 81**；运行后无残留测试库。

> **一个踩坑记录**：`WebApplicationFactory` 在宿主启动失败时只抛
> 「The server has not been started or no web application was configured」，
> 把真正原因完全吞掉。上面两个问题（缺扩展、限流）都是靠**绕过工厂直接构造**
> 才把真实异常挖出来的。排查这类问题时**不要相信那句错误信息**。

## 6. 与代码的对应关系

| 内容 | 位置 |
