## 5. 流程坑：PR 合并后再往同一分支 push，CI 不会跑 `[2026-09-13]`

**现象**：PR 已经合并，之后又往同一分支推了 4 个提交（含一个安全修复）。
GitHub Actions 里**什么都没有**，`main` 上也没有这些改动。

**定位过程**：对照 `.github/workflows/ci.yml` 的触发条件：

```yaml
on:
  push:
    branches: [main]        # ← 只有 main
  pull_request:
    branches: [main]        # ← 目标是 main 的 PR
```

推功能分支两个条件都不满足；而 PR 一旦合并/关闭，分支上的新提交也不再产生
`pull_request` 事件。

**根因**：`pull_request` 事件的语义是「**这个 PR** 有变化时」，不是「这个分支有变化时」。
PR 关了，事件源就没了。

**修法**：为这 4 个提交**另开一个 PR**（同一个分支可以再次开 PR）。

**教训**：

| 结论 | 说明 |
|---|---|
| ⭐ **合并 ≠ 分支完结** | 合并后又补了东西，正确做法是**再开一个 PR**；不要以为推上去就自动进去了 |
| **"我推了但没反应"先看触发条件** | 这多半不是故障而是设计（省 CI 分钟数） |
| **想开 PR 前就有 CI 反馈** | 把 `push.branches` 改成 `['**']`，代价是 CI 分钟数翻倍 |
| ⚠️ **合并后要确认"改动到底进没进 main"** | `git merge-base --is-ancestor <commit> origin/main` 逐个核对，**不要凭感觉** |

延伸阅读：[11-CI-CD与自动化交付](./11-CI-CD与自动化交付.md) §7.4（触发条件说明）。

## 4. EF 迁移坑：改「被生成列依赖」的字段类型，PostgreSQL 直接拒绝 `[2026-09-13]`

**现象**：把 `Posts.Summary` 从 `varchar(120)` 扩到 `varchar(200)`，
EF 自动生成的迁移只有一句 `AlterColumn`，看起来完全正常。实际执行时：

```
ERROR:  cannot alter type of a column used by a generated column
DETAIL:  Column "Summary" is used by generated column "SearchVector".
```

**定位过程**：

1. `dotnet ef migrations add` 生成迁移 —— 内容是**空的**。
   原因：我加了 `--no-build`，用的是**旧程序集**，模型里还是 120。
2. 去掉 `--no-build` 重新生成，这次内容对了（`AlterColumn` 120→200）。
3. **但没有直接跑**，而是先在临时表上复现同样的结构试了一次 `ALTER COLUMN TYPE`
   —— 于是撞上了上面那个错。

**根因**：`SearchVector` 是 `GENERATED ALWAYS AS (...) STORED` 的生成列，
表达式里引用了 `Summary`。PostgreSQL 禁止修改被生成列依赖的列类型。

**修法**：迁移顺序必须是「**先拆 → 再改 → 再建**」：

```csharp
DropIndex("ix_posts_search")         // GIN 索引建在生成列上
DropColumn("SearchVector")           // 拆掉依赖 Summary 的生成列
AlterColumn("Summary", varchar(200)) // 现在才允许改
AddColumn("SearchVector", ...)       // 按原表达式重建（既有行会重算）
CreateIndex("ix_posts_search", GIN)
```

生成表达式抽成常量，保证 `Up`/`Down` 不会因为手抄不一致而产生
「来回迁移一次，检索行为就变了」。

**验证**（在**一次性库**上做，不碰开发库）：

| 项 | 结果 |
|---|---|
| `Up` 全量迁移 | ✅ `Summary` = varchar(200)、生成列与 GIN 索引都在 |
| 功能 | ✅ 插入 200 字摘要成功；`SearchVector @@ plainto_tsquery('chinese','数据库')` = true |
| `Down` 回滚 | ✅ 列回到 120，生成列与索引都还在 |
| `Down` 在有 200 字数据时 | ✅ **按预期失败**（22001），且**事务回滚、库保持完好**（没有半迁移状态） |

**教训**：

| 结论 | 说明 |
|---|---|
| ⭐ **EF 生成的迁移必须人工复核** | EF 只负责把模型差异翻译成 SQL，它**不知道**数据库层的依赖关系 |
| ⚠️ **这类错编译期不报、单测不发现** | 迁移跑在**应用启动时**（`Database.Migrate()`）—— 写错就是**应用起不来** |
| ✅ **先在一次性库上跑一遍，尤其 `Down`** | 别拿开发库当试验田 |
| ✅ **改完模型要 build 再 `add`** | 否则会得到一个**静默为空**的迁移，而且不报错 |
| ⚠️ 附带的既有脆弱点 | 从零建库依赖 PG 镜像的 init 脚本先建好 `chinese` 配置，迁移链自己不管这事（本次在探测库上就撞到了）。见文末「待跟进」 |

## 3. ⭐ 创建文章报「服务器内部错误」，实际是摘要太长（附一次全库校验审计）`[2026-09-13]`

**现象**（用户原话）：

> 我在新建文章时，遇到 BUG：`22001: value too long for type character varying(120)`，
> 这应该是摘要长度过长导致的，我删除部分摘要就能正常创建。
> **但实际上我填写的摘要只有 96 个字**，使用的是 pgsql，应该 varchar(120) 支持才对。
> 这个错误提示是"服务器内部错误"，而不是返回摘要长度过长的信息。

**定位过程**：

1. **先验证用户的前提** —— "96 字应该放得下"对不对？
   在库里实测：`varchar(120)` 插入 **120 个汉字成功**（`length=120`，字节 `360`），
   第 121 个才报错。**结论：PostgreSQL 的 `varchar(n)` 按"字符"计数，不按字节**，
   所以 96 个汉字本该通过。→ 用户看到的 96 字与实际提交长度不符。

   **为什么会有这个错觉**：摘要输入框是 `<textarea rows="2">`，
   **既没有 `maxlength` 也没有字数显示**。粘贴长文本时只露出两行，
   用户根本无法判断真实长度。

2. **看校验链路断在哪** —— Application 层的校验方法是：

   ```csharp
   private static void ValidateTitleAndContent(string title, string content)
   {
       if (string.IsNullOrWhiteSpace(title)) throw ...;
       if (title.Length > 200) throw ...;          // 标题校验了
       if (string.IsNullOrWhiteSpace(content)) throw ...;
       // ← 摘要（Summary）完全没有校验
   }
   ```

   数据库有 `varchar(120)`、前端没有 `maxlength`、**Application 层也不校验**
   → 超长值一路穿到数据库 → `DbUpdateException` → 全局中间件 → `5000 服务器内部错误`。

3. **顺着这条线做全库审计** —— 既然摘要漏了，别的字段呢？
   把「EF 模型的 `HasMaxLength`」与「Application 层的长度校验」对照了一遍，
   发现共 **7 处**「数据库有约束、应用层没有校验」：

   | 字段 | 列宽 | 前端 maxlength | Application 校验 |
   |---|---|---|---|
   | `Posts.Summary` | 120 → **200** | ❌ | ❌ ← 事故现场 |
   | `Authors.Bio` | 500 | ✅ | ❌ |
   | `Posts.CoverImage` | 500 | — | ⚠️ `MediaPath` 上限曾是 512 |
   | `Authors.Avatar` | **200** | — | ⚠️ 同上 —— 512 > 200，**过了白名单也写不进去** |
   | `Collections.Description` | 500 | ✅ | ❌ |
   | `SocialLinks.Name` / `Icon` | 50 / 50 | ❌ | ❌ |
   | `SocialLinks.Url` | 500 | ❌ | ❌ |

**根因**（三层缺了两层）：

| 层 | 问题 |
|---|---|
| 前端 | 没有 `maxlength`、没有字数显示 → 用户**看不见**自己填了多长 |
| Application | **根本没有校验** → 没有业务提示，也无法与数据库约束保持一致 |
| 数据库 | 有约束，但它成了**唯一防线**，撞上就是 500 |

**修法**：

| # | 改动 |
|---|---|
| 1 | 新增 `Blog.Application/Common/FieldLimits.cs`：所有字符串字段长度上限**集中成常量**，并提供 `EnsureLength(value, max, fieldName)` |
| 2 | 补齐 7 处 Application 层校验（`PostService` / `AuthorService` / `CollectionService` / `SiteService`） |
| 3 | `MediaPath.MaxLength` 512 → **200**（= 最小的目标列 `Authors.Avatar`，见该常量注释） |
| 4 | EF 迁移把 `Posts.Summary` 扩到 `varchar(200)`（过程见本文第 4 条） |
| 5 | 全局异常处理新增**兜底**：捕获 PostgreSQL **22001** → 返回 **4001** 而非 5000，并记 Warning |
| 6 | 前端：摘要框加 `maxlength="200"` + 实时字数；社交链接三个输入框补 `maxlength` |

**回答用户提出的架构问题 —— 校验放前端还是后端？**

> **都要，但职责完全不同。少任何一层都会出问题。**

| 层 | 职责 | 失败表现 | 能不能省 |
|---|---|---|---|
| 前端 | **体验**：让人根本填不出超长值 | 输入被挡住 | 不能省，但它**不是安全边界**（`curl` 直接绕过） |
| Application | **业务规则**：显式校验 + 可读提示 | `400 + 4001 +「摘要长度不能超过 200」` | **权威层，绝不能省** |
| 数据库 | **数据完整性**：最后一道防线 | `22001` | 不能省，但它**不该是唯一防线** |
| 全局异常处理 | **兜底**：把 `22001` 映射成 4001 | 400 + 通用过长提示 | 有了它，**漏了某个字段也不会再给用户"服务器内部错误"** |

**验证**：

| 项 | 手段 | 结果 |
|---|---|---|
| 边界 | `200` 字放行 / `201` 字被拒 | ✅ 400 + 4001 +「摘要长度不能超过 200」 |
| 不能是 5xx | 专门断言 `(int)status < 500` 且 `code != 5000` | ✅ |
| 留空不受影响 | 摘要留空仍走自动截取 | ✅ |
| **反向验证 1** | 临时**移除** Application 层的摘要校验 | ✅ 测试**变红**；失败信息显示 `"提交的内容超过了字段允许的长度，请缩短后重试"` —— 说明请求确实穿到了数据库、**被新的 22001 兜底接住并返回 400 而不是 500**（改之前这里正是"服务器内部错误"） |
| **反向验证 2** | 故意把 `FieldLimits.PostSummary` 改成 300 | ✅ 结构性护栏**变红**，打印「FieldLimits 写的是 300，而 EF 模型是 200」 |
| ⭐ **结构性护栏** | 新增测试：用 **EF 模型元数据**反查每个字段真实的 `HasMaxLength`，与 `FieldLimits` 常量逐个比对（19 个字段） | ✅ 以后改了 `BlogDbContext` 忘了同步常量，这条测试会直接红 |

**教训**：

| 结论 | 说明 |
|---|---|
| ⭐ **"数据库有约束"不等于"校验做完了"** | 约束是**最后一道防线**，不是**唯一防线**。缺了 Application 层，用户拿到的是 500 而不是可操作的提示 |
| ⭐ **一个字段漏了，就要怀疑一整类** | 发现摘要漏了之后做全库审计，又找出 6 处。**同类缺陷从不成单出现** |
| ⭐ **校验上限要有"单一来源"** | 散落在各 Service 里的裸数字必然与 `HasMaxLength` 漂移。集中成 `FieldLimits`，再加一条**用 EF 元数据反查**的测试，漂移就变成可自动发现的 |
| **注意"通用上限"与具体列的宽窄** | `MediaPath.MaxLength=512` 比 `Authors.Avatar` 的 200 还宽 —— 「通用校验比具体列宽松」这种错误很隐蔽 |
| **给不出可读提示的报错等于没有报错** | 用户看到"服务器内部错误"的第一反应是"程序坏了"，而实际只是"你填长了"。**错误信息要能指导下一步动作** |
| **长文本输入框必须给长度反馈** | `rows="2"` 又不显示字数，用户无法判断自己填了多少 —— "96 字的错觉"就是这么来的 |

## 2. 管理后台三个 UI 问题（侧栏不显眼 / 侧栏乱滚 / 按钮错位）`[2026-09-13]`

**现象**（用户原话）：

1. 左侧栏底部的「我的写作台」「返回前台」**不够显眼，第一时间找不到**
2. 左侧栏**会随着右侧页面的高度变化**，需要固定
3. 文章列表里「编辑」与「下架/删除」**没有水平对齐**

**根因**：

| # | 根因 |
|---|---|
| 1 | `.back-link` 是**透明背景 + 13px + `--text-subtle`** 的小字按钮；而上方 `.nav-item` 有 `padding`/`border-radius`/悬停底色/图标 —— **视觉权重差太远**。另外「我的写作台」连图标都没有，与「返回前台」不对称 |
| 2 | `.admin-shell` 用了 `align-items: stretch` + `min-height: 100vh`，而 `.admin-side` **没有任何高度约束** → 它跟着右侧内容一起变高，自然随页面滚走 |
| 3 | `.col-act` 是 `display: flex` 但**没写 `align-items`** → 默认 `stretch`。「编辑」是 `<a>`（文字贴顶），「下架/删除」是 `<button>`（浏览器会把内容**垂直居中**）→ 同一行里基线不一致 |

**修法**：

| # | 改动 |
|---|---|
| 1 | `.back-link` 改成与 `.nav-item` **完全同规格**（同样的 padding / 圆角 / 悬停底色 / 14px 字重），给「我的写作台」补图标，并在上方加「快捷入口」小标题 |
| 2 | `.admin-side { position: sticky; top: 0; height: 100vh; overflow-y: auto; }` —— 不改变右侧的滚动方式，只让侧栏自己固定住 |
| 3 | `.col-act { align-items: center; }`，并给 `.link` 显式 `line-height: 1.5` 统一 `<a>` / `<button>` 的默认行高差异 |

**教训**：

> ⭐ **"按钮不显眼"和"按钮错位"这类问题，根因几乎总是"两个元素用了不同的默认值"。**
> 一个是 `<a>`、一个是 `<button>`；一个有高度约束、一个没有。
> 排查时先问「这两个东西的样式**来源**一样吗」，而不是先去调数值。

**验证**：⚠️ **只能人工视觉验收** —— 自动化测不了"显不显眼"。见文末。

## 1. Markdown 里的图片会失效（语雀导出 / 本地文件）`[2026-09-13 记录，方案已定，待实现]`

**现象**：

- 把语雀文档导出为 Markdown 后复制进编辑器 → **文章里图片不显示**
- 本地带图片的 Markdown 直接复制 → 同样失效

**根因**：Markdown 的图片语法 `![alt](地址)` 里存的是**地址字符串**，而：

| 来源 | 地址长什么样 | 为什么失效 |
|---|---|---|
| 语雀导出 | `https://cdn.nlark.com/...` | 外链：可能有防盗链 / 需要登录态 / 将来会失效 |
| 本地 Markdown | `./images/a.png`、`C:\Users\...\a.png` | 相对/本地路径**只在作者本机有意义**，发布到网上必然 404 |

**已定方案**（尚未实现）：

| 阶段 | 内容 |
|---|---|
| ① | **粘贴 / 拖拽自动上传**：拦截编辑器的 `paste` / `drop`，把剪贴板或拖入的**图片数据**走 `/api/files/upload`，再把返回的站内地址写回 Markdown。覆盖「截图直接粘贴」「拖入本地图片」「从网页复制图片」三条路径 |
| ② | **「插入图片」按钮**：显式选文件上传，返回一段 Markdown 片段 |
| ③ | **手动「转存外链图片」按钮**：扫正文里的外链图片 → 服务端下载 → 存进本站 → 重写 URL。解决语雀导出的 CDN 链接 |

**为什么 ③ 做成手动按钮，而不是"保存时自动转存"**：

> 自动转存意味着**每次保存都会让服务端主动去请求一批外部 URL**，
> 这是典型的 **SSRF（服务端请求伪造）** 面：外部 URL 可以指向内网地址、
> 云元数据端点（`169.254.169.254`）等。
> 做成手动触发，用户明确知道发生了什么，攻击面也小得多；
> 且仍需配套：**只允许 http/https、禁止内网与保留地址、超时、体积上限、重定向次数上限**。

**为什么不能只在渲染时"修好"**：图片地址是**存在文章内容里**的，
渲染层拿不到原图，无法凭空补上。必须在**写文章时**把图片搬到本站 ——
这是内容入库的问题，不是显示的问题。
