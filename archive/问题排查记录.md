## 9. ⭐ 把仓库外的脚本搬进来，第一天就找出 3 个真缺陷 `[2026-09-14]`

**背景**：把散落在 `/mnt/d/tmpbuild/` 的 29 个 CDP 脚本中有断言的那些改写进 `tools/e2e/`。
预期是**搬运工**，实际是**考古**：第一次跑通就红了 6 条，而红的原因**没有一条是搬运本身写错的**。
**定位过程**（按发现顺序。每一条都值得看"表面现象 → 真因"的落差）：

| # | 表面现象（极具误导性） | 真因 | 性质 |
|---|---|---|---|
| 1 | 8 个检查全卡在登录：`res.json()` 报 `Unexpected end of JSON input` | 脚本调的是 `/api/auth/admin/login`，**这个地址早就不存在了**。后端只有一个 `POST /api/auth/login`，Admin 与 Author **共用** | 脚本过期 |
| 2 | 「未登录访问 `/admin`」期望 `/admin/login`，实际 `/login?returnUrl=/admin` | 后台登录页**已并入统一登录页**，`/admin/login` 只作为旧链接转发保留；`router/index.ts` 有注释说明这是**刻意的设计** | 脚本过期 |
| 3 | 点「创建」后页面停在原地，提示「**内容不能为空**」 | 脚本用 `placeholder.includes('正文')` 找正文框；而**摘要框的 placeholder 是「可选：留空将自动取正文前 50 字」—— 它含「正文」**，且 DOM 里排在正文框**前面**。于是脚本一直在往摘要框里填字，正文一个字都没填 | 脚本 bug |
| 4 | 归档页的断言失败 | 页面路径是 `/archive`（**单数**），但它请求的接口是 `/api/posts/archives`。我新写这个用例时，路径和接口**两个都猜错了** | 我写的 |
| 5 | 6 条「空态文案没出现」全红，而页面**其实是对的** | 我写成 `try { await page.waitForText(...) } catch { rendered = false }`，而库里的方法叫 `waitText`（少个 For）。于是 `page.waitForText is not a function` 这个 **TypeError 被那个 catch 吞掉**，伪装成了"条件不成立" | **我自己造的假红** |
| 6 | 清理测试数据静默失败（HTTP 400） | `DELETE` 也需要乐观锁版本号 `?version=N`，和 `PUT` 一样；漏了它清理就永远失败，测试数据在开发库里越积越多 | 脚本 + 我的实现 |

**顺带找出 3 个真实的产品缺陷**（这才是搬进仓库最大的收益）：
`TagsView.vue` / `CategoriesView.vue` / `ArchiveView.vue` 都只写了 `try/finally`，**没有 `catch`**：

```js
try { tags.value = await getTags() } finally { loading.value = false }
```

UI 看起来完全正常（`loading` 置回 `false`、列表仍为空 → 显示「暂无标签」），
但 Promise 的 rejection **没有人接**，控制台冒出 `Uncaught (in promise) ApiError`。
判它是缺陷而不是"设计如此"的依据：同目录的 `CollectionListView.vue` 有 `catch`，
注释里还写着 **「与分类墙/标签墙等公开页保持一致」** —— **意图是它们行为相同，实现却不同**。
一旦将来接入全局的 `unhandledrejection` 上报（错误监控、全局 toast），它立刻变成一条假告警。
（"物证"：开发库 `Authors` 表里躺着**同一邮箱的两行**测试作者、`Posts` 表里有**多篇**同名验证文章 ——
那是旧脚本"不可重复运行"留下的痕迹。）

**根因**（一句话）：**资产不在版本控制里，就不会参与变更。**
接口改名、路由合并、表单加字段 —— 这三件事发生时，**没有任何机制会提醒你那些脚本已经烂了**：

```
接口改名   →  登录全挂，报 "Unexpected end of JSON input"（看起来像后端 500）
路由合并   →  断言失败（看起来像守卫写错了）
表单加字段 →  "内容不能为空"（看起来像必填校验坏了）
```

三种表现全都指向**产品代码**，而真凶都在脚本里。这就是"假红"最贵的形态：
它不只是浪费时间，**它会让你去改本来没坏的代码**。

**修法**：① 对齐过期期望 —— 登录端点收敛成 `config.loginPath = '/api/auth/login'`，
路由期望改成统一登录页 + `returnUrl=<原地址>`；② 去掉脆弱选择器 —— 正文框改成**按 `rows` 选**
（正文 14 / 摘要 3），与文案解耦，`/archive` 与 `/api/posts/archives` 显式分别写出；
③ 让库区分错误类型 —— 新增 `WaitTimeoutError`，只有它允许被软处理（`{ soft: true }`），
**其它异常照旧往外抛**，调用方不再需要写 `try/catch`；
④ 修产品缺陷 —— 三个视图补上 `catch`，与 `CollectionListView` 对齐（失败按空列表呈现、细节只进控制台）。

**验证**：全量跑 0 失败；**连跑两次**都全绿（**可重复运行**，原来那些脚本做不到，因为账号名是写死的）；
**负向验证**：把 `TagsView` 的 `catch` 临时去掉 → **只有那一条断言变红**、`run.mjs` 退出码 1，还原后立刻回绿；
`npm run build`（含 `vue-tsc -b`）通过；跑完清理本次创建的实体，开发库里只留下**旧脚本**造成的痕迹。
（断言条数由数据决定，实测见 [`tools/e2e/README.md`](../tools/e2e/README.md)。）

**教训**：

1. ⭐ **「把资产搬进仓库」不是行政动作，而是让资产重新参与变更。** 备份只是副产品；真正的收益是"改接口的人会看见它"。
2. ⭐ **旧脚本里可能写着过期的期望。** 发现"脚本期望 ≠ 实际行为"时**先查清是哪一边过期了**，不要改代码去迎合脚本 ——
   这次两条都是**脚本过期**；图省事改前端让检查通过，就会把一个刻意的设计决定改回去。
   判断方法：去看**代码里有没有注释解释这个行为**。有，就是设计。
3. ⭐ **假红必须当成 bug 来修，不能"重跑一遍看看"。** 这次 6 条红里有 5 条是假的。
   假红的代价不只是时间 —— **它训练你忽略红色**，而那是所有检查失效的起点。
4. **断言失败时必须打印现场。** 第 4、5 条能快速定位，全靠失败信息里带了**实际正文**；只写"期望出现「暂无文章」"就只能重跑一遍去猜。

## 8. ⭐ 「检查看起来在工作」比「没有检查」更危险：三处静默失效的配置 `[2026-09-14]`

**现象**：给项目补依赖安全扫描时，在 Windows 上直接跑 `npm audit`，得到：

```
npm warn audit 404 Not Found - POST https://registry.npmmirror.com/-/npm/v1/security/advisories/bulk
         - [NOT_IMPLEMENTED] /-/npm/v1/security/* not implemented yet
npm error audit endpoint returned an error
```

第一反应是"网络问题 / 要重试"。但**换个环境跑同样的命令却完全正常**。

**定位过程**：同一份 `package.json` + `package-lock.json`，只换环境：

| 环境 | 实际生效的 npmrc | registry | `npm audit` 结果 |
|---|---|---|---|
| Windows（`cmd.exe`） | `C:\Users\JIA\.npmrc` | `registry.npmmirror.com` | ❌ `NOT_IMPLEMENTED` |
| WSL | `/home/kky/.npmrc` | `registry.npmjs.org` | ✅ `found 0 vulnerabilities` |

→ 与代码无关，与 **registry** 有关：淘宝镜像只代理"下载包"，
**没有实现 `/npm/v1/security/*` 这一族审计接口**。复现方式很干净：建一个空目录，
只放 `package.json`、`package-lock.json` 和一个写着 `registry=https://registry.npmmirror.com` 的 `.npmrc`：

```bash
npm audit                                        # ❌ NOT_IMPLEMENTED，非 0 退出
npm audit --registry=https://registry.npmjs.org  # ✅ found 0 vulnerabilities
```

> 顺带测出：`npm audit` **不需要 `node_modules`**，它只读 lock 文件 —— 便宜、快、适合放进 CI。

**根因**：这本是一个"换源"的小问题。**真正危险的是它和另一个设计撞在一起** ——
这个作业是 `continue-on-error: true`（刻意"先只报告不阻断"），于是组合出：

```
镜像源没实现 audit 接口 → npm audit 非 0 退出 → continue-on-error 把非 0 退出吃掉
  → 作业依然全绿 → 「审计没跑成」和「审计跑了、没发现漏洞」在页面上长得一模一样
```

**你会以为依赖被检查过了，其实一次都没查。** 而且它**不会报错**，只会让安静成为默认状态。
同一族还有两处（都是这次顺手补掉的）：

| # | 静默失效的写法 | 为什么会静默 | 正确写法 |
|---|---|---|---|
| 2 | Dependabot 里只写 `dependency-name: "SixLabors.ImageSharp"` 的 `ignore` 规则 | 这条规则会被展开成 `>= 0`，**并且同时作用于安全更新通道** → 这个包的安全修复 PR 也被一起关掉。表现为「Dependabot 变安静了」，没有任何显式报错 | 必须显式加 `update-types: [version-update:semver-major]`，把规则限定在**版本更新通道** |
| 3 | 把 CI 的 `--collect:"XPlat Code Coverage"` 换成 `--settings coverage.runsettings` | 覆盖率从此依赖那个文件；它被删掉或参数被去掉时，`dotnet test` **照常变绿**、制品照常上传（只是里面没有覆盖率文件） | 加一道 `找不到 coverage.cobertura.xml 就报错` 的哨兵步骤 |

> ⚠️ **第 2 条要在意：它是我在写配置时从文档里发现的，不是踩出来的。** 这类"配置写错了不报错、
> 只改变行为"的问题靠事后排查几乎发现不了 —— 只能靠**写的时候就按正确形式写**，
> 以及**事后按文档去日志里核对一次**（`Insights → Dependency graph → Dependabot → Recent update jobs`）。
> 反过来，`.github/dependabot.yml` 里那段 `ignore` 规则上方也写着「改动前请先读第 8 条」——
> **代码指向文档、文档解释代码**，这条链路本身就是防复发的一部分。

**修法**：CI 的 npm 扫描**显式** `--registry=https://registry.npmjs.org`（不依赖任何机器的 `.npmrc`），
并加哨兵：输出里必须出现 `found N vulnerabilities`，否则报错；NuGet 扫描的哨兵要求输出里出现
`vulnerable`/`易受攻击` 字样，**退出码只用来判断"命令有没有跑起来"**；覆盖率步骤新增「找不到报告就报错」的哨兵；
`.github/dependabot.yml` 的 `ignore` 规则加 `update-types`，并在注释里写清楚为什么不能只写 `dependency-name`。

> ⚠️ **补这一条时还测出一个反直觉的事实**：`dotnet list package --vulnerable`
> **在发现漏洞时退出码依然是 0**（阳性对照实测：`Newtonsoft.Json 12.0.1` 报出 High，退出码 0）。
> 所以**退出码完全不能用来判断"有没有漏洞"**。

**验证**：两个方向都做了 —— **阳性对照**：临时建工程引用 `Newtonsoft.Json 12.0.1` → 报出
`GHSA-5crp-9r3c-p9vr`（High）✅；**负向验证**：用 stub 替换 `dotnet`/`npm` 跑了 **6 条路径** ——
干净输出 ✅通过、有漏洞输出 ✅通过（不阻断）、命令崩了 ✅拦截、**静默无输出 ✅拦截**、
`found 0 vulnerabilities` ✅通过、`NOT_IMPLEMENTED` ✅拦截；两个 registry 对照见上表；
**覆盖率哨兵**：把 `TestResults` 挪走再跑那一步 → 退出码 1 并打印出「最常见的原因」✅。

**教训**：

1. ⭐ **「检查看起来在工作」比「没有检查」更危险。** 没有检查时你知道自己在裸奔；而一个永远绿着的检查，会让你**以为自己是安全的**。本文第 7 条是同一个道理的另一种形态。
2. ⭐ **「不阻断」的检查必须配「失效哨兵」。** 一旦允许一个检查失败而不变红，你就**永久失去了用红色区分「成功」和「没跑」的能力** —— 必须另外加一条断言："我确实看到了本该看到的输出"。
3. **配置类问题的通用形态**：改配置不会报错，它只会让**行为悄悄改变**。所以每一处"我以为它在做 X"的配置都值得问：**「如果它其实没做 X，我会在哪里看到？」** —— 答不上来，那里就需要一个哨兵。
4. **"永远输出没问题"的检查，必须用一次已知有问题的输入去撞。** 与第 7 条的"先在坏代码上确认它会失败"是同一条经验，只是这里的"坏代码"变成了"一个已知有漏洞的依赖"。

## 7. 迁移链无法从零建库：三处「帮忙」让缺陷变得不可见 `[2026-09-13]`

**现象**（在一次性库上验证上一个迁移时偶然撞到）：手工 `CREATE DATABASE` 后直接跑迁移，第一步就失败：
`42704: text search configuration "chinese" does not exist`。

**定位过程**：看 `20260910205225_AddAuthCollectionsAndFts` 的语句顺序 ——
`AddColumn<SearchVector>`（生成列，表达式引用 `to_tsvector('chinese', …)`）
在**第 29 行**，而创建 `chinese` 配置的 SQL 在**第 166 行**。**要用的东西后面才造。**

**根因**：顺序错误。但真正让这个问题「长期不可见」的是**三处绕过**：
PG 镜像 entrypoint 的 `deploy/postgres-init/01-zhparser.sql`（让全新环境开箱可用）、
**测试夹具 `BlogApiFactory.InitializeChineseTextSearch()`**（让集成测试跑得起来）、
以及手工建库时的经验。第 2 条最要命：**它把缺陷掩盖在了测试里** ——
CI build 同一个镜像、跑同一份 init 脚本，于是**永远是绿的**，
而「迁移链能不能从零建库」恰恰是 CI 最该验证的事情之一。

**修法**：① 把两段 SQL **移到 `Up()` 最前面**，并留注释说明**顺序是有约束的**；
② ⭐ **删掉测试夹具里的绕过** —— 删掉之后，集成测试就是在**完全干净的库**上跑迁移。

**验证**：既无 `zhparser` 扩展也无 `chinese` 配置的空库直接跑迁移 ✅ 4 个迁移全部成功；
迁移后 schema ✅ 扩展与配置已由迁移创建、生成列与 GIN 索引都在；`Down` 整链回滚 ✅ 生成列被正确移除；
已迁移的库（compose 栈）重启 ✅ 迁移未被重复应用、检索正常；
**反向验证** ✅ 临时移除「建扩展」语句 → 集成测试立刻变红（`42704`）。
（该缺口当年登记为 G12，见 [docs/06-技术债与待办.md](../docs/06-技术债与待办.md) 缺口状态表。）

**教训**：⭐ **"绕过"会削弱测试的发现能力** —— 每次为了让某个环节先跑起来而加的绕过，
都在把缺陷藏进更深的层次；**修完缺陷后要回头把绕过删掉**，否则同样的错误下次仍然会在 CI 全绿的情况下溜过去。
⭐ **"从零建库"必须被自动验证**，这是部署能力的底线，最简单的做法是**测试夹具不做任何环境预处理**、直接建空库跑迁移。
⭐ **"只在换环境时才炸"是最高危的一类** —— 它在当前环境 100% 复现不出来，只能靠**改变假设去主动试**
（这次是"故意不建配置"）发现。**改已应用的迁移**要分清情况：只调语句顺序、语句幂等、
且**目标模型不变** → 安全（EF 按 ID 跳过已应用的库）；若会改变最终 schema → **必须新增迁移**。

## 6. 上传接口用「HTTP 200 + 错误码」表达错误，与其它接口不一致 `[2026-09-13]`

**现象**：上传一个不被支持的 `.svg`，返回的是 `HTTP 200` + `{ "code": 4001, "message": "不支持的文件类型：.svg" }`，
而同样属于「参数不合法」的其它接口返回的是 `HTTP 400 + code 4001`。

**定位过程**：① 全文搜「谁在直接构造错误响应」：
`grep -rn "ApiResponse.*\.Fail(" Blog.Backend --include=*.cs` —— 除了中间件与 JWT 事件
（它们都**显式设置了 HTTP 状态码**）之外，只有 `FilesController` 的 3 处是在 action 里
`return ApiResponse.Fail(...)`。② 由此确认这是**局部问题**，而不是全局约定坏了 ——
其它 Service 都走 `throw new BusinessException(...)`，由全局中间件统一映射。

**根因**：控制器**自己 return 了错误响应体**，绕过了全局异常中间件 ——
ASP.NET Core 对「action 正常返回一个对象」一律给 200，业务码在 body 里而 HTTP 状态码表示成功，
于是同一个语义出现两种状态码，客户端必须记住「上传接口特殊，只看 code 不看状态码」。
顺带发现 `ErrorCodes.PayloadTooLarge`（4130）**定义了、也在中间件里映射了，但从来没有被抛出过** ——
是个死代码。而它恰好就是「文件太大」该用的码。

**修法**：三处全部改为抛 `BusinessException`，让中间件统一映射：
文件为空 → **`400` + 4001**；超过业务上限（10MB）→ **`413` + 4130**；扩展名不在白名单 → **`400` + 4001**。
（改前全是 `200` + 4001。）4130 这个业务码也因此第一次真正生效。

**验证**（经 nginx 打真实栈）：

| 场景 | HTTP | code | message |
|---|---|---|---|
| SVG（扩展名非法） | **400** | 4001 | 不支持的文件类型：`.svg` |
| 空文件 | **400** | 4001 | 文件不能为空 |
| 11MB（超业务上限 10MB） | **413** | **4130** | 文件大小超过限制（10MB） |
| 13MB（超 nginx `client_max_body_size 12m`） | 413 | — | nginx 自己的 HTML 页（**到不了应用**） |
| 正常 PNG | 200 | 0 | ok |

**反向验证**：把「文件为空」那处改回 `return ApiResponse.Fail(...)`，新增的测试如期变红：

```
Assert.Equal() Failure: Values differ
Expected: BadRequest
Actual:   OK          ← 正是那个缺陷
```

**教训**：

| 结论 | 说明 |
|---|---|
| ⭐ **错误必须用 HTTP 状态码表达** | 「HTTP 200 + 业务错误码」是一种**双重编码**：同一个语义有两种表示，客户端必须为「特殊接口」写特例。**状态码是给通用逻辑看的，业务码是给业务分支看的，两者不该互相替代** |
| ⭐ **「定义了但从不使用」的错误码是线索** | `PayloadTooLarge` 一直躺着没人用，说明**某条错误路径没有走统一通道**。类似信号还有：定义了却没人调的枚举值、写了却从没触发的分支 |
| **一个接口这样写，要怀疑是不是还有别的** | 但这次 grep 之后确认只有这一处 —— **怀疑之后要验证，不要直接假设「肯定还有一堆」**，否则会做无谓的大改 |
| **注意上游还有一道限制** | nginx 的 `client_max_body_size 12m` 比业务上限 10MB 大一点是**刻意**的：让业务上限先起作用、由应用给出可读提示；超过 12MB 的请求由 nginx 直接挡掉，返回它自己的 HTML 错误页而不是统一响应体 |

## 5. 流程坑：PR 合并后再往同一分支 push，CI 不会跑 `[2026-09-13]`

**现象**：PR 已经合并，之后又往同一分支推了 4 个提交（含一个安全修复）。
GitHub Actions 里**什么都没有**，`main` 上也没有这些改动。

**定位过程**：对照 `.github/workflows/ci.yml` 的触发条件：

```yaml
on:
  push:
    branches: [main]        # ← 只有 main
  pull_request:
    branches: [main]        # ← 目标是 main 的 PR
```

推功能分支两个条件都不满足；而 PR 一旦合并/关闭，分支上的新提交也不再产生 `pull_request` 事件。

**根因**：`pull_request` 事件的语义是「**这个 PR** 有变化时」，不是「这个分支有变化时」。PR 关了，事件源就没了。

**修法**：为这 4 个提交**另开一个 PR**（同一个分支可以再次开 PR）。

**教训**：⭐ **合并 ≠ 分支完结**（合并后又补了东西，正确做法是**再开一个 PR**）；
⭐ **"我推了但没反应"先看触发条件**（这多半不是故障而是设计，为省 CI 分钟数；
想开 PR 前就有 CI 反馈可把 `push.branches` 改成 `['**']`，代价是分钟数翻倍）；
⚠️ **合并后要确认"改动到底进没进 main"**：`git merge-base --is-ancestor <commit> origin/main` 逐个核对，**不要凭感觉**。

延伸阅读：触发条件说明见 [learn/02-CI-CD实践.md](../learn/02-CI-CD实践.md)。

## 4. EF 迁移坑：改「被生成列依赖」的字段类型，PostgreSQL 直接拒绝 `[2026-09-13]`

**现象**：把 `Posts.Summary` 从 `varchar(120)` 扩到 `varchar(200)`，EF 自动生成的迁移只有一句
`AlterColumn`，看起来完全正常。实际执行时：
`ERROR: cannot alter type of a column used by a generated column`
`DETAIL: Column "Summary" is used by generated column "SearchVector".`

**定位过程**：① `dotnet ef migrations add` 生成迁移 —— 内容是**空的**。
原因：我加了 `--no-build`，用的是**旧程序集**，模型里还是 120。
② 去掉 `--no-build` 重新生成，这次内容对了（`AlterColumn` 120→200）。
③ **但没有直接跑**，而是先在临时表上复现同样的结构试了一次 `ALTER COLUMN TYPE` —— 于是撞上了上面那个错。

**根因**：`SearchVector` 是 `GENERATED ALWAYS AS (...) STORED` 的生成列，
表达式里引用了 `Summary`。PostgreSQL 禁止修改被生成列依赖的列类型。

**修法**：迁移顺序必须是「**先拆 → 再改 → 再建**」：

```csharp
DropIndex("ix_posts_search")         // GIN 索引建在生成列上
DropColumn("SearchVector")           // 拆掉依赖 Summary 的生成列
AlterColumn("Summary", varchar(200)) // 现在才允许改
AddColumn("SearchVector", ...)       // 按原表达式重建（既有行会重算）
CreateIndex("ix_posts_search", GIN)
```

生成表达式抽成常量，保证 `Up`/`Down` 不会因为手抄不一致而产生「来回迁移一次，检索行为就变了」。

**验证**（在**一次性库**上做，不碰开发库）：`Up` 全量迁移 ✅ `Summary` = varchar(200)、生成列与 GIN 索引都在；
功能 ✅ 插入 200 字摘要成功，`SearchVector @@ plainto_tsquery('chinese','数据库')` = true；
`Down` 回滚 ✅ 列回到 120，生成列与索引都还在；
`Down` 在**有 200 字数据时** ✅ **按预期失败**（22001），且**事务回滚、库保持完好**（没有半迁移状态）。

**教训**：⭐ **EF 生成的迁移必须人工复核** —— EF 只负责把模型差异翻译成 SQL，它**不知道**数据库层的依赖关系；
⚠️ **这类错编译期不报、单测不发现**，因为迁移跑在**应用启动时**（`Database.Migrate()`），写错就是**应用起不来**；
✅ **先在一次性库上跑一遍、尤其 `Down`**（别拿开发库当试验田），且**改完模型要 build 再 `add`**，
否则会得到一个**静默为空**的迁移、而且不报错；
⚠️ 这次还顺带撞到另一个更严重的问题 —— 「迁移链无法从零建库」（同样是**语句顺序**问题、影响面更大，
已单独记为本文**第 7 条**并修复）。

## 3. ⭐ 创建文章报「服务器内部错误」，实际是摘要太长（附一次全库校验审计）`[2026-09-13]`

**现象**（用户原话）：

> 我在新建文章时，遇到 BUG：`22001: value too long for type character varying(120)`，
> 这应该是摘要长度过长导致的，我删除部分摘要就能正常创建。
> **但实际上我填写的摘要只有 96 个字**，使用的是 pgsql，应该 varchar(120) 支持才对。
> 这个错误提示是"服务器内部错误"，而不是返回摘要长度过长的信息。

**定位过程**：

1. **先验证用户的前提** —— "96 字应该放得下"对不对？在库里实测：`varchar(120)` 插入
   **120 个汉字成功**（`length=120`，字节 `360`），第 121 个才报错。
   **结论：PostgreSQL 的 `varchar(n)` 按"字符"计数，不按字节**，所以 96 个汉字本该通过
   → 用户看到的 96 字与实际提交长度不符。
   **为什么会有这个错觉**：摘要输入框是 `<textarea rows="2">`，**既没有 `maxlength` 也没有字数显示**，
   粘贴长文本时只露出两行，用户根本无法判断真实长度。
2. **看校验链路断在哪** —— Application 层的校验方法里标题校验了、正文校验了，
   **摘要（`Summary`）完全没有校验**：

   ```csharp
   if (string.IsNullOrWhiteSpace(title)) throw ...;
   if (title.Length > 200) throw ...;          // 标题校验了
   if (string.IsNullOrWhiteSpace(content)) throw ...;
   // ← 摘要（Summary）完全没有校验
   ```

   数据库有 `varchar(120)`、前端没有 `maxlength`、**Application 层也不校验**
   → 超长值一路穿到数据库 → `DbUpdateException` → 全局中间件 → `5000 服务器内部错误`。
3. **顺着这条线做全库审计** —— 既然摘要漏了，别的字段呢？把「EF 模型的 `HasMaxLength`」
   与「Application 层的长度校验」对照了一遍，发现共 **7 处**「数据库有约束、应用层没有校验」：
   `Posts.Summary`（120 → **200**，前端 ❌ / 应用 ❌ ← 事故现场）、`Authors.Bio`（500，前端 ✅ / 应用 ❌）、
   `Posts.CoverImage`（500）、`Authors.Avatar`（**200**，与 `Posts.CoverImage` 同受 `MediaPath` 上限曾是
   512 的影响 —— 512 > 200，**过了白名单也写不进去**）、`Collections.Description`（500，应用 ❌）、
   `SocialLinks.Name`/`Icon`（50/50，前端 ❌ / 应用 ❌）、`SocialLinks.Url`（500，前端 ❌ / 应用 ❌）。

**根因**（三层缺了两层）：前端没有 `maxlength`、没有字数显示 → 用户**看不见**自己填了多长；
Application **根本没有校验** → 没有业务提示，也无法与数据库约束保持一致；
数据库有约束，但它成了**唯一防线**，撞上就是 500。

**修法**：① 新增 `Blog.Application/Common/FieldLimits.cs`：所有字符串字段长度上限**集中成常量**，
并提供 `EnsureLength(value, max, fieldName)`；② 补齐 7 处 Application 层校验
（`PostService` / `AuthorService` / `CollectionService` / `SiteService`）；
③ `MediaPath.MaxLength` 512 → **200**（= 最小的目标列 `Authors.Avatar`，见该常量注释）；
④ EF 迁移把 `Posts.Summary` 扩到 `varchar(200)`（过程见本文第 4 条）；
⑤ 全局异常处理新增**兜底**：捕获 PostgreSQL **22001** → 返回 **4001** 而非 5000，并记 Warning；
⑥ 前端：摘要框加 `maxlength="200"` + 实时字数，社交链接三个输入框补 `maxlength`。

**回答用户提出的架构问题 —— 校验放前端还是后端？** **都要，但职责完全不同。少任何一层都会出问题。**

| 层 | 职责 | 失败表现 | 能不能省 |
|---|---|---|---|
| 前端 | **体验**：让人根本填不出超长值 | 输入被挡住 | 不能省，但它**不是安全边界**（`curl` 直接绕过） |
| Application | **业务规则**：显式校验 + 可读提示 | `400 + 4001 +「摘要长度不能超过 200」` | **权威层，绝不能省** |
| 数据库 | **数据完整性**：最后一道防线 | `22001` | 不能省，但它**不该是唯一防线** |
| 全局异常处理 | **兜底**：把 `22001` 映射成 4001 | 400 + 通用过长提示 | 有了它，**漏了某个字段也不会再给用户"服务器内部错误"** |

**验证**：**边界** `200` 字放行 / `201` 字被拒 ✅ 400 + 4001 +「摘要长度不能超过 200」；
**不能是 5xx** ✅ 专门断言 `(int)status < 500` 且 `code != 5000`；**留空不受影响** ✅ 仍走自动截取；
**反向验证 1**：临时**移除** Application 层的摘要校验 ✅ 测试**变红**，失败信息显示
`"提交的内容超过了字段允许的长度，请缩短后重试"` —— 说明请求确实穿到了数据库、
**被新的 22001 兜底接住并返回 400 而不是 500**（改之前这里正是"服务器内部错误"）；
**反向验证 2**：故意把 `FieldLimits.PostSummary` 改成 300 ✅ 结构性护栏**变红**，
打印「FieldLimits 写的是 300，而 EF 模型是 200」；
⭐ **结构性护栏**：用 **EF 模型元数据**反查每个字段真实的 `HasMaxLength`，与 `FieldLimits` 常量逐个比对
（19 个字段）✅ 以后改了 `BlogDbContext` 忘了同步常量，这条测试会直接红。

**教训**：⭐ **"数据库有约束"不等于"校验做完了"** —— 约束是**最后一道防线**、不是**唯一防线**，
缺了 Application 层，用户拿到的是 500 而不是可操作的提示。
⭐ **一个字段漏了，就要怀疑一整类**（这次全库审计又找出 6 处，**同类缺陷从不成单出现**）。
⭐ **校验上限要有"单一来源"**：散落在各 Service 里的裸数字必然与 `HasMaxLength` 漂移，
集中成 `FieldLimits` 再加一条**用 EF 元数据反查**的测试，漂移就变成可自动发现的。
⚠️ **注意"通用上限"与具体列的宽窄**（`MediaPath.MaxLength=512` 比 `Authors.Avatar` 的 200 还宽，
「通用校验比具体列宽松」这种错误很隐蔽）。
⚠️ **给不出可读提示的报错等于没有报错** —— 用户看到"服务器内部错误"的第一反应是"程序坏了"，
而实际只是"你填长了"；**错误信息要能指导下一步动作**，长文本输入框必须给长度反馈（"96 字的错觉"就是这么来的）。

## 2. 管理后台三个 UI 问题（侧栏不显眼 / 侧栏乱滚 / 按钮错位）`[2026-09-13，2026-09-14 补窄屏修复]`

**现象**（用户原话）：① 左侧栏底部的「我的写作台」「返回前台」**不够显眼，第一时间找不到**；
② 左侧栏**会随着右侧页面的高度变化**，需要固定；③ 文章列表里「编辑」与「下架/删除」**没有水平对齐**。

**根因**：

| # | 根因 |
|---|---|
| 1 | `.back-link` 是**透明背景 + 13px + `--text-subtle`** 的小字按钮；而上方 `.nav-item` 有 `padding`/`border-radius`/悬停底色/图标 —— **视觉权重差太远**。另外「我的写作台」连图标都没有，与「返回前台」不对称 |
| 2 | `.admin-shell` 用了 `align-items: stretch` + `min-height: 100vh`，而 `.admin-side` **没有任何高度约束** → 它跟着右侧内容一起变高，自然随页面滚走 |
| 3 | `.col-act` 是 `display: flex` 但**没写 `align-items`** → 默认 `stretch`。「编辑」是 `<a>`（文字贴顶），「下架/删除」是 `<button>`（浏览器会把内容**垂直居中**）→ 同一行里基线不一致 |

**修法**：① `.back-link` 改成与 `.nav-item` **完全同规格**（同样的 padding / 圆角 / 悬停底色 / 14px 字重），
给「我的写作台」补图标，并在上方加「快捷入口」小标题；
② `.admin-side { position: sticky; top: 0; height: 100vh; overflow-y: auto; }` —— 不改变右侧的滚动方式，只让侧栏自己固定住；
③ `.col-act { align-items: center; }`，并给 `.link` 显式 `line-height: 1.5` 统一 `<a>` / `<button>` 的默认行高差异。

**遗留的窄屏残留（2026-09-14 由 P0 补修）**：第 ② 条的 `sticky + height:100vh` 只在桌面态成立。
`@media (max-width: 880px)` 把侧栏折叠成**横向 tab** 后，这个高度约束就成了 bug ——
横向 tab 会撑满整个视口高度，而它本该只占一行。
**媒体查询只覆盖写在其中属性，不会自动撤销其它规则**，所以必须在窄屏里显式复位：
`.admin-side { position: static; height: auto; }`。

**教训**：⭐ **"按钮不显眼"和"按钮错位"这类问题，根因几乎总是"两个元素用了不同的默认值"** ——
一个是 `<a>`、一个是 `<button>`；一个有高度约束、一个没有。
排查时先问「这两个东西的样式**来源**一样吗」，而不是先去调数值。
⭐ **覆盖式的媒体查询必须"成对"写：改了什么，就要在窄屏里把同一组属性复位** ——
只加不复位时，症状是"窄屏下多出一大块整屏高的横条"，而**桌面端完全正常**，只有缩到窄屏才看得见。

**验证**：⚠️ **只能人工视觉验收** —— 自动化测不了"显不显眼"；窄屏那条同样要在 880px 以下实际缩窗确认。
`tools/e2e` 只覆盖**可判定**的视觉规则（如分类徽章是否渐变、与标签是否可区分）。

## 1. Markdown 里的图片会失效（语雀导出 / 本地文件）`[2026-09-13 记录，方案已定，待实现]`

**现象**：① 把语雀文档导出为 Markdown 后复制进编辑器 → **文章里图片不显示**；
② 本地带图片的 Markdown 直接复制 → 同样失效。

**根因**：Markdown 的图片语法 `![alt](地址)` 里存的是**地址字符串**，而语雀导出的
`https://cdn.nlark.com/...` 是外链（可能有防盗链 / 需要登录态 / 将来会失效），
本地 Markdown 的 `./images/a.png`、`C:\Users\...\a.png` 是**只在作者本机有意义**的相对/本地路径，
发布到网上必然 404。

**状态**：**方案已定，仍未实现** —— 决定**上线后再做**（它影响的是写作体验，不影响站点能否上线）。
已定方案三步：① **粘贴 / 拖拽自动上传**：拦截编辑器的 `paste` / `drop`，把剪贴板或拖入的**图片数据**
走 `/api/files/upload`，再把返回的站内地址写回 Markdown，覆盖「截图直接粘贴」「拖入本地图片」
「从网页复制图片」三条路径；② **「插入图片」按钮**：显式选文件上传，返回一段 Markdown 片段；
③ **手动「转存外链图片」按钮**：扫正文里的外链图片 → 服务端下载 → 存进本站 → 重写 URL，
解决语雀导出的 CDN 链接。

**为什么 ③ 做成手动按钮，而不是"保存时自动转存"**：

> 自动转存意味着**每次保存都会让服务端主动去请求一批外部 URL**，
> 这是典型的 **SSRF（服务端请求伪造）** 面：外部 URL 可以指向内网地址、
> 云元数据端点（`169.254.169.254`）等。
> 做成手动触发，用户明确知道发生了什么，攻击面也小得多；
> 且仍需配套：**只允许 http/https、禁止内网与保留地址、超时、体积上限、重定向次数上限**。

**为什么不能只在渲染时"修好"**：图片地址是**存在文章内容里**的，渲染层拿不到原图，无法凭空补上。
必须在**写文章时**把图片搬到本站 —— 这是内容入库的问题，不是显示的问题。

## 10. 头像上传的注释还写着支持 SVG —— 修完了却没留档 `[2026-09-13 已修，2026-09-14 补记]`

**现象**（用户报的是一条"文案与实现不符"）：作者管理页编辑作者时，
上传头像下方的说明写 **「支持 jpg / png / webp / gif / svg」**，
但服务端**早就不收 `.svg` 了**；个人资料页（`/me/profile`）有同一句话。
**这条从未写进任何文档** —— 补记时已逐文件核实（见下表）。

**这条为什么没有留档**：它不是"排查"出来的，而是**三处改动分了三步落地**，
每一步都漏掉了"人对它的描述"：① 媒体地址白名单（后端只接受 `/api/files/` 前缀、

漏了页面上的说明文字；③ 收尾时没有人回头看那两行 hint。

**根因**：**文案属于"另一处副本"**。格式白名单当时散在三个地方
（后端 `AllowedExtensions`、前端 `ACCEPT_IMAGE`、页面说明文字），
改前两个会被类型/测试提醒，改第三个**没有任何机制会提醒** ——
于是出现"实现禁止、文案允许"这种**只误导人、不影响功能**的偏差：
既不会被测试抓到，也不会有人报障，只能靠人工过一遍才发现。

**修法**：两处说明文字改为 **「支持 jpg / png / webp / gif」**，
与前端 `ACCEPT_IMAGE` 及后端白名单的**图片子集**对齐。

**核实到的证据**（2026-09-14 逐文件核对）：

| 位置 | 现状 |
|---|---|
| `Blog.FrontEnd/src/views/AdminAuthorListView.vue` | hint 为「头像只能上传设置，支持 jpg / png / webp / gif，单文件不超过 10MB」 |
| `Blog.FrontEnd/src/views/me/MyProfileView.vue` | 同一句，一致 |
| `Blog.FrontEnd/src/utils/media.ts` | `ACCEPT_IMAGE = 'image/png,image/jpeg,image/webp,image/gif'`，注释写明**刻意不含 `image/svg+xml`** |
| `Blog.Backend/Blog.Infrastructure/Files/LocalFileStorageService.cs` | `AllowedExtensions` = `.png .jpg .jpeg .gif .webp .ico .mp4 .webm .pdf .zip`，**无 `.svg`**；`ContentTypes` 同样无 `image/svg+xml`（兜底按 `application/octet-stream` 下载） |

> ⚠️ 上表路径以仓库现状为准：基础设施项目位于 `Blog.Backend/Blog.Infrastructure/`，
> 不是 `Blog.Infrastructure/`。

**教训**：

1. ⭐ **删功能时要连"人对它的描述"一起删。** 白名单、选择器、说明文字是**同一份事实的三个副本**，
   只改能被测试覆盖的那两个，第三个就会长期说谎。
2. **"文案与行为不一致"应记为缺陷而不是"文案小问题"。** 用户会按文案去准备一张 SVG，
   上传被拒后只会认为"程序有 bug"—— 排查成本最终仍然落在开发者身上。
3. **这类偏差没有自动化兜底。** 它既不会让测试变红，也不会让页面报错；
   能防住的只有两件事：**改动时搜一遍文案**，以及**把格式清单收敛到一处**
   （现在前端已收敛成 `ACCEPT_IMAGE` 一个常量）。

**验证**：逐文件核对上表四处；功能侧的证据是上传 `.svg` 返回
`400 + 4001「不支持的文件类型」`（见本文第 6 条的验证表，同一份实测记录）。
