## 1. 这里是教材，不是手册

`learn/` 与 `docs/` 的分工（完整规则见 [docs/00-文档规范.md](../docs/00-文档规范.md) §2）：

| | `learn/`（本区） | `docs/`（手册） |
|---|---|---|
| 回答什么 | **为什么**：原理、取舍、学习的顺序 | **是什么**：当前代码事实 |
| 篇幅 | 允许长、允许慢，讲透为止 | 尽量短，能查就行 |
| 事实责任 | ⚠️ **不承担事实准确性责任** | ✅ 与代码不符即为缺陷 |
| 过期了怎么办 | 随时可以重写讲解方式 | 改代码时必须在同一次提交里同步它 |

> ⚠️ **本区的代码片段与字段名只作讲解用，可能已经过期。**
> 要照着写代码，请去 `docs/` 找到对应的**真实文件路径**再打开仓库里的那个文件。
> 每篇末尾与正文里的 `→ 实现见 docs/0X` 就是干这个用的。

**为什么值得这样分**：教材要讲得慢、讲得全，就必然会带上具体版本号的细节；而细节一定会过期。
把"事实"和"解释"分开，手册才能保持短小可信，教材也不必因为一次重构而整篇作废。

## 3. ⚠️ 完整的学习路线图与验收标准将在这里补全

> **本节是占位，内容由后续任务（P4）撰写。** 在它落地之前，`learn/` 只提供**讲解**，
> 不提供"学到什么程度算过关"的判定依据——想先动起来，请直接按
> [learn/01](./01-后端知识地图.md) 的阶段顺序读，并做它每节末尾给出的动手实验。

补全后每篇教材都会配上一份**学习路线图**，包含三样东西：

| 组成部分 | 回答什么问题 | 形态（预告） |
|---|---|---|
| **阶段目标** | 这一阶段学完，应该能**说出**什么、**看懂**什么 | 每阶段一段"能回答的问题"清单 |
| **动手任务** | 光看不算学会——这一阶段要**动手做什么** | 具体任务 + 前置条件 + 预期现象（可复现，不依赖真实服务器） |
| **可展示的验收证据** | 怎么证明**真的**学会了，而不是"读完了" | 可提交的产物：一次跑通的命令输出、一份对照表、一个改动的 PR 或一次实测记录 |

**为什么验收要落在"可展示的证据"上**：本项目的所有事实都以代码为准（[铁律二](../docs/00-文档规范.md) §1），
所以"我懂了"也必须能被指出来——一个能跑出预期结果的命令、一处能指出文件与行号的改动，
比一份读书笔记更能说明问题。
