## 1. 这里是教材，不是手册

`learn/` 与 `docs/` 的分工（完整规则见 [docs/00-文档规范.md](../docs/00-文档规范.md) §2）：

| | `learn/`（本区） | `docs/`（手册） |
|---|---|---|
| 回答什么 | **为什么**：原理、取舍、学习的顺序 | **是什么**：当前代码事实 |
| 篇幅 | 允许长、允许慢，讲透为止 | 尽量短，能查就行 |
| 事实责任 | ⚠️ **不承担事实准确性责任** | ✅ 与代码不符即为缺陷 |
| 过期了怎么办 | 随时可以重写讲解方式 | 改代码时必须在同一次提交里同步它 |

> ⚠️ **本区的代码片段与字段名只作讲解用，可能已经过期。** 要照着写代码，请去 `docs/` 找到对应的
> **真实文件路径**再打开那个文件（正文里的 `→ 实现见 docs/0X` 就是干这个用的）。这样分的理由：教材必然带上会过期的版本细节，
> 把"事实"与"解释"分开，手册才能短小可信。

## 3. 怎么用这份路线图

**这是一条证据链，不是书单。**

| | 读懂 | 做过 | 能证明 |
|---|---|---|---|
| 标志 | "我知道中间件是洋葱模型" | "我把异常处理挪到内层，看到了 500" | "这是我改前改后的两次请求与日志，结论是……" |
| 面试里 | 追问第二层就塌 | 能讲过程，数字靠回忆 | 能讲数字、取舍与代价 |
| 三个月后 | 忘光 | 记得大概 | 有据可查 |

**为什么每个阶段都必须留下证据**：

1. **"我懂了"无法被指出来。** 本项目所有事实以代码为准（[铁律二](../docs/00-文档规范.md) §1），所以"我学会了"也只能靠一个能跑出预期结果的命令、一份带数字的记录来证明。
2. **没见过它失败，你无法确信它真的在工作。** [learn/02](./02-CI-CD实践.md) §8 的判据对学习同样成立：先在"坏"的情况跑一遍、看到它确实会红，再在"好"的情况跑通 —— 否则你分不清"真的通过了"和"根本没生效"。
3. **证据是给三个月后的自己看的。** 那时你只记得结论，不记得对照条件；没有记录，同一个坑会踩第二次（[archive/问题排查记录.md](../archive/问题排查记录.md) 存在的唯一理由就是这个）。

**证据放哪**（public 仓库，有些东西绝不能进）：

| 证据类型 | 放哪 |
|---|---|
| 脚本、配置、可复现的命令 | ✅ 进仓库：`tools/`、`deploy/`、文档里的命令块 |
| 结论 | ✅ 按三区规则回写：命令 → [docs/05](../docs/05-运维与部署手册.md)，原理 → `learn/`，过程 → [archive/](../archive/)；并把 [docs/06](../docs/06-技术债与待办.md) §3 里做完的那条删掉 |
| 服务器地址、账号口令、`.env`、密钥 | ❌ **绝不入库**，只放本地笔记 |
| 简历写法与个人数字 | ❌ 本地笔记（仓库 public，[.gitignore](../.gitignore) 已忽略该目录） |

**推进方式**：一次只做一个阶段，证据到手再进下一个。S0 → S1 是硬前置（没上过线，后面所有"性能""回滚"都没有落点）；S2 与 S3 顺序可换，但**先有基线再谈优化**（[learn/03](./03-性能与运行时诊断.md) §15）；S4 依赖 S1；S5 收口。

**卡住时的查找顺序**：[docs/05](../docs/05-运维与部署手册.md) §9 排错速查表 → [docs/06](../docs/06-技术债与待办.md) §1~§3（是不是"还没做"）→ [archive/问题排查记录.md](../archive/问题排查记录.md)（看**别人的定位过程**，不是找答案）→ 回 `learn/` 补原理。

## 5. 六个阶段

### S0 · 跑起来 + 看懂一条请求的一生

**目标**：能在一台干净机器上把项目跑起来，并按中间件顺序讲清一个请求从进到出经历了什么。

**读什么**

| 读哪 | 重点 |
|---|---|
| [learn/01](./01-后端知识地图.md) 阶段 0~2 | §2 项目结构与构建、§3 Git 与行尾、§4 DI 与生命周期、**§5 中间件与顺序（尤其 §5.4）**、§6 路由与授权属性、§7 配置与 Options、§8 认证与授权（§8.3 / §8.6 / **§8.9 五个实验**） |
| [docs/01](../docs/01-快速开始.md) §2/§3/§5 ｜ [docs/05](../docs/05-运维与部署手册.md) §3/§5/§9 | 五分钟跑起来、开箱账号、数据库（中文分词扩展）；启动与停止、**接口验证（§5.4 判断响应真伪）**、排错速查表 |
| [docs/02](../docs/02-架构与数据模型.md) §3/**§11**/§15 ｜ [docs/03](../docs/03-API参考.md) §1/§4 | 分层与依赖方向、**请求管道与中间件顺序**、健康检查；统一响应体与错误码、文章接口 |

**动手任务**（都由你自己做，不是读一遍）

1. **从零跑起来**：按 [docs/01](../docs/01-快速开始.md) §2 起后端与前端，用 `/health` 与首页各证明一次。⚠️ 判据是**后端日志里有对应请求记录** —— 某些工具环境的 localhost 响应会被 mock 层伪造（[docs/05](../docs/05-运维与部署手册.md) §5.4）。
2. **用 curl 走通一条主链路，逐步记录请求与响应**：登录拿 token → 建草稿 → 发布 → 用**中文关键词**检索到它 → 读详情；每步记下命令、HTTP 状态码、响应体业务 `code`、耗时，以及**对应的后端日志行**。
3. **追一遍 token**（[learn/01](./01-后端知识地图.md) §8.9 的五个实验）：解开 payload 看 claim（它只是 Base64，不是加密）→ 带 token 访问受保护接口期望 200 → 不带 token 期望 401 **且响应体仍是统一格式** → 注销后用同一个 token 再访问，期望 401。
4. **中间件顺序实验**：先把 [docs/02](../docs/02-架构与数据模型.md) §11 的顺序抄成清单（一行一个），每个中间件旁写一句"它必须在这里的原因"；然后**自己制造第三个顺序错误**并记录现象（例如把异常处理中间件挪到 `app.MapControllers()` 之后，再请求一次"不存在的文章"）。⚠️ 以你**实际观察到的现象**为准，不要照抄预期；实验完必须改回来，`git status` 要干净。

**验收标准（可展示的证据）**

- 能**不看代码**画/讲出这条链：浏览器 → 反向代理（或 Vite dev server）→ 管道里的每个中间件按顺序 → 控制器 → Service → 仓储 → `BlogDbContext` → PostgreSQL，并说出每层的职责边界。
- 能说出 **3 个中间件顺序错误的后果**：2 个来自 [learn/01](./01-后端知识地图.md) §5.4 的真实教训，第 3 个是你自己实验出来的；每个都要说出**观察到了什么现象**，而不是"理论上会怎样"。
- 有一份登录→发文→检索的请求/响应记录（每步含状态码、业务 `code`、耗时），至少一步能在后端日志里对上号。
- 实验全部回滚：`git status` 干净，并能指出 [docs/02](../docs/02-架构与数据模型.md) §11 里自己原先看漏的那一处。

### S1 · 上线

**目标**：把本地 compose 的生产形态搬到一台真实服务器上，拿到一个公网可访问的地址，并能解释拓扑里的每一层。

**读什么**

| 读哪 | 重点 |
|---|---|
| [learn/01](./01-后端知识地图.md) §29、§11 ｜ [learn/02](./02-CI-CD实践.md) §6.2 | 部署形态与为什么需要反向代理、三个必须处理的点、容器化 PG 与扩展、上线前安全清单与启动期校验；限流的粒度与转发头（反代之后第一个坏的就是它）；密钥管理 |
| [docs/05-运维与部署手册.md](../docs/05-运维与部署手册.md) §8 | §8.3 生产必须做的配置、§8.4 本地整栈、§8.5 三个坑、**§8.6 限流可被绕过**、§8.7 镜像交付、§8.8 HTTPS、§8.9 备份、§8.10 拓扑校验 |
| [docs/01](../docs/01-快速开始.md) §5.4 ｜ [tools/deploy/README.md](../tools/deploy/README.md)、[tools/backup/README.md](../tools/backup/README.md) | 不装中文分词扩展，检索与还原都会失败；服务器选型（"为什么优先香港节点"）、首次登录加固、八步验收（含环境预检：compose / 磁盘 / **swap**）、备份什么与不备份什么 |

**动手任务**

1. **先在本地把生产形态跑一遍，亲手复现四个"只在部署后才暴露"的点**（步骤见 [docs/05](../docs/05-运维与部署手册.md) §8.4 末尾）：① 传一张大于 1 MiB 的图**成功且后端日志有记录**；② 伪造不同的 `X-Forwarded-For` 连发**仍被限流**；③ 静态资源带长缓存头；④ 访问 `/post/<uuid>` 刷新**不 404**。每条留下命令与输出。⚠️ 这些坑项目里已踩过并修好；你要做的是**自己跑一遍**，这样上线当天不必第一次面对它们。
2. **做一次拓扑校验实验**：把 `Deployment:InstanceCount` 改成大于 1，而缓存仍是内存实现 → 期望**启动即失败**（[docs/05](../docs/05-运维与部署手册.md) §8.10）。把报错原文抄下来。
3. **买机器并上线**：选型 → 首次登录加固 → 装 Docker → 本地 `tools/deploy/pack-images.sh` 打包 → `scp` 上传 → `server-init.sh`（带八步验收：第 1 步是环境预检，其中"中文检索"那一步最能证明 PG 镜像搬对了；第 6 步会断言 webapi 的内存上限**真的生效**）。
4. **上线后立刻做两件事**：改掉管理员密码（⚠️ 种子口令**公开写在仓库里**，等于把后台钥匙挂在门上）；配 HTTPS（[docs/05](../docs/05-运维与部署手册.md) §8.8 二选一）。
   ⚠️ 做 HTTPS 之前**先读 §8.8.1**：加宿主机 TLS 层会让容器 nginx 看到的对端变成宿主机，
   「每 IP 限流」会静默退化成「全站共享一个桶」—— 修法是 4 行 `realip`，
   已经配在 `deploy/nginx.conf` 里，但**必须重建 nginx 镜像并重新部署才生效**。
5. **把每一步卡点写成过程记录**进 [archive/问题排查记录.md](../archive/问题排查记录.md) —— ⚠️ 这份记录的价值在"定位过程"，不在结论。

**验收标准（可展示的证据）**

- 一个能在手机上打开的公网地址，完成"登录 → 看文章 → 中文搜索"三件事（HTTPS 优先）；用旧种子口令登录**失败**（证明密码真的改了）。⚠️ 地址与任何凭据**只记在本地笔记**，不要写进这个 public 仓库。
- 能画出部署拓扑并**逐层解释为什么在**：宿主机 Nginx 为什么单独一层终结 TLS、容器里的 nginx 为什么既发静态又做反代、Kestrel 为什么不直接对外、PostgreSQL 为什么必须用自定义镜像、Redis 为什么在（[docs/02](../docs/02-架构与数据模型.md) §16 是启动期硬校验）。
- `docker compose ps` 四个服务全部 `(healthy)` 的输出，以及 `server-init.sh` 八步验收的输出。
- 能说出"哪一步失败会导致什么现象"，至少举出三个，并对应到 [docs/05](../docs/05-运维与部署手册.md) §9 的条目。

### S2 · 压测与基线

**目标**：用接近真实的数据量测出一份可信基线，给出 p50/p95/p99 与 SLO 达标结论 —— 从此"慢"可以被证明。

**读什么**

| 读哪 | 重点 |
|---|---|
| [learn/03](./03-性能与运行时诊断.md) §1~§10 | 三个误解、性能测试成立的三个前提、四个黄金信号、**p50/p95/p99 与平均值**、五种测试里真正重要的两个、SLO 怎么定、**数据量必须接近真实**、冷启动 vs 热缓存、工具选型；本项目的四处热点（⚠️ 限流会在压测中制造"假故障"，最高优先级）、二分法与症状→根因 |
| [docs/06-技术债与待办.md](../docs/06-技术债与待办.md) §3.1 | 前置条件清单、SLO 草案表、执行阶段、**六条完成判据** —— 这一节是你的任务书 |
| [learn/01](./01-后端知识地图.md) 阶段 5 ｜ [docs/05](../docs/05-运维与部署手册.md) §4.2、§5.5 | 缓存、全文检索、日志与慢查询监控；怎么跑测试与覆盖率、直接查 PG 自己验证 |

**动手任务**

1. **亲手造数据，并验证索引真的生效**：用 `tools/load/seed-posts.mjs` 灌 1,000 与 10,000 篇带长正文的中文文章（脚本已在仓库里：直接写库、幂等、以 `[LOADTEST]` 前缀标记，清理只删这一批）；灌完对检索接口做一次 `EXPLAIN ANALYZE`，确认走的是索引而不是顺序扫描。
2. **跑基线并读懂它**：`tools/load/run-baseline.sh` 会按顺序做完 —— 记录环境规格 → 等 `/health` 就绪 → **校验限流已关（没关直接退出）** → 预热缓存 → 冒烟 → 六接口基线 → 冷缓存探针 → 汇总成 markdown。你要能逐项解释它在做什么、以及**为什么顺序不能乱**（⚠️ 不关限流，测出来的是限流器而不是应用容量）。
3. **让 SLO 定稿**：把 [docs/06](../docs/06-技术债与待办.md) §3.1 的草案表**逐条**确认或修正，并同步 k6 的默认阈值；⚠️ 草案里"单机吞吐"写着"待定"，**必须用实测填** —— 目标机器规格没定之前，写任何数字都是猜的。
4. **把"不达标"变成定位结论**：压力阶段找拐点（k6 脚本按接口分开，深分页另有阈值）；**只改一处**再复测；有余力再跑数小时的浸泡（死元组堆积与内存泄漏只有它能发现）。
5. **回写**：按 [docs/06](../docs/06-技术债与待办.md) §3 的约定，做完一条就删掉它，命令进 [docs/05](../docs/05-运维与部署手册.md)、原理进 [learn/03](./03-性能与运行时诊断.md)。

**验收标准（可展示的证据）**

- 一份带日期、带**环境规格**（CPU / 内存 / 磁盘 / 网络 / 并发数 / 数据量 / 冷热缓存）的压测报告，每个被测接口都有 **p50 / p95 / p99**（不是平均值，理由见 [learn/03](./03-性能与运行时诊断.md) §4.1），并附一张与 SLO **逐条比对**的达标结论表（不达标的每条都有定位结论，哪怕结论是"规格不够"）。
- 工具、脚本与用法说明都在仓库里（[tools/load/](../tools/load/)），别人照着能复现出**同一量级**的结果。
- 能回答"你这台机器的容量是多少"：答案是一个**你自己测出来的 RPS 数字**，并说得出它是在什么规格、什么数据量、冷缓存还是热缓存下成立的。
- 至少一组"数据量改变结论"的实测对照（例：同一接口在 1,000 篇与 10,000 篇下的 p95）。

### S3 · 运行时诊断

**目标**：用工具在本项目里把两个性能/内存假设**证实或推翻**，并写成两份能讲 10 分钟的排查记录。

**读什么**

| 读哪 | 重点 |
|---|---|
| [learn/03](./03-性能与运行时诊断.md) §11~§17 | 内存结构（**★ 托管内存 vs 非托管内存**、栈/堆/LOH、真实的分配点）、弱代假设、**LOH 为什么不压缩**、★ GC 的工作模式与本项目现状、终结器与 `IDisposable`；诊断工具链（counters / trace / gcdump / dump / BenchmarkDotNet）、先测量再优化、坑清单、动手顺序 |
| [docs/06-技术债与待办.md](../docs/06-技术债与待办.md) §3.2 | **四个实验的做法、观察点与产出** —— 这一节是你的任务书 |
| [learn/01](./01-后端知识地图.md) 阶段 4 §17/§21、阶段 5 §24 ｜ [docs/05](../docs/05-运维与部署手册.md) §5.5 | EF 变更跟踪、索引设计（实验 C/D 的理论基础）、慢查询监控；验证要用 SQL，不是只信接口返回 |

**动手任务**

从 [docs/06](../docs/06-技术债与待办.md) §3.2 的 A/B/C/D 里**选 2 个做透**（推荐 A → B，或 A → C/D 二选一），每个都必须留下：对照组、唯一变量、工具、原样命令、前后数据表。

1. **A · Server GC vs Workstation GC**（成本最低，先做）：同一压测脚本跑两组，唯一变量是那个环境变量；看 RPS、p99、GC 堆峰值、工作集峰值、GC 时间占比。产出一张对比表 **和一行显式的项目配置**。
2. **B · 图片上传链路的内存峰值**：并发上传不同尺寸的图，同时看 LOH 大小（应平稳）与工作集（应飙升）→ **先判定像素缓冲在托管还是非托管内存**，这决定后面走"GC 调优"还是"非托管内存管理"。⚠️ 方向错了后面全白做；⚠️ 查 API 必须查**锁定版本**的（本项目因许可锁在 ImageSharp 3.1.12，官网文档是最新版，结论不能照搬）。
3. **C · 浏览量自增的行锁热点**：压**同一篇**热门文章 vs 压多篇不同文章，比两组 p99；辅助看 `pg_stat_activity` 的等待事件与死元组增长曲线。**结论是"不成立"也要记录为已验证**。
4. **D · 慢查询 TOP N 与索引优化**：先做前置改造（把硬编码的慢查询阈值改成配置项，压测时才找得到"温吞"查询），再造真实数据量 → 收集慢查询 → `EXPLAIN ANALYZE` → 优化 → 复测。

⚠️ **不要四个都做**：四个各做一半，不如两个做透。

**验收标准（可展示的证据）**

- **2 份排查记录**，每份都含 现象 / 假设 / 怎么验证 / 数据 / 结论（模板见 §6），数据是表格或图，不是形容词；每份里都有一句明确的"**假设成立**"或"**假设不成立**"（**不成立的那份同样算完成**，理由见 §6）。
- 假设成立的那份要走到"改了什么 + 复测数字"；判定"不需要改"的那份要说得出放弃的理由（候选修法见 [docs/06](../docs/06-技术债与待办.md) §3.2）。
- 能口头回答：LOH 平稳而工作集飙升说明什么、下一步走哪条路、为什么。
- 能指出你在工具里看到的**三个具体数字**（不是"内存有点高"），并说明它们分别对应 [learn/03](./03-性能与运行时诊断.md) 的哪个概念。

### S4 · 发布与回滚

**目标**：独立把一个新版本发上线，并在出问题时几分钟内退回去，同时说清"数据库那一半"为什么退不回去。

**读什么**

| 读哪 | 重点 |
|---|---|
| [learn/02](./02-CI-CD实践.md) §6、§4~§5 ｜ [learn/01](./01-后端知识地图.md) §29.4 | §6.1 回滚与**数据库迁移这个特例**（向前兼容为什么优于回滚）、§6.2 密钥管理与轮换的真实代价；流水线四个作业、发布前要过哪些门；上线前安全清单与启动期校验 |
| [docs/06-技术债与待办.md](../docs/06-技术债与待办.md) §2 G4、§3.3 | 发布流程与版本号（**未做**：无 tag、无约定、无回滚方案）；CD 还没接上的部分与顺序 |
| [docs/05](../docs/05-运维与部署手册.md) §8.7、§8.9 ｜ [tools/deploy/README.md](../tools/deploy/README.md) §5、[tools/backup/README.md](../tools/backup/README.md) §3~§5 | 镜像交付与上线、备份与回滚；回滚命令、定时备份、**恢复演练必须真做** |

**动手任务**

1. **补齐发布版本号约定并打 tag**（[docs/06](../docs/06-技术债与待办.md) §2 的 G4 就是这件事）：镜像 tag 只有时间戳（`tools/deploy/pack-images.sh` 生成的），**看不出对应哪个提交** —— 把 git tag 与镜像 tag 对应起来（时间戳 + 提交短哈希），**绝不用 `:latest`**（会移动的标签，出事时说不清线上跑的是哪一版）；把这套约定写进 [docs/05](../docs/05-运维与部署手册.md)。
2. **发一次新版本，并故意改一处可观察的行为**（例如站点配置的一个默认值或一段文案），用同一个 curl 分别记录旧版与新版的结果 —— **这是回滚能被证明的前提**。
3. **真回滚一次**：把 compose 指回旧 tag、重建 `webapi` 与 `nginx`，再用第 2 步的同一个 curl 证明**行为回到了旧版本**（而不是"容器起来了"）。
4. **把"数据库那一半"做一遍**：先备份 → 做一次破坏性迁移（删列或改类型）→ 回滚**应用镜像** → 用 `psql` 的表结构输出证明**结构没有跟着回去** → 再用 `restore.sh` 还原到临时库（⚠️ 默认还原到 `_restore` 库，**不要碰正式库**）。这一串动作就是"迁移为什么是回滚里最难的一半"的答案。
5. **做一次恢复演练**（[tools/backup/README.md](../tools/backup/README.md) §4，每季度一次的固定动作）：真还原、真核对数据，并记下**花了多久**。
6. 把发布与回滚写成可照抄的 runbook（进 [docs/05](../docs/05-运维与部署手册.md)；⚠️ 不要把密钥与口令写进去）。

**验收标准（可展示的证据）**

- `git tag` 与镜像列表里能同时看到新旧两个版本，且两者的对应关系**一眼能看出来**；一次真实发布 + 一次真实回滚的完整命令与输出，回滚的判据是第 2 步那个 curl **行为回到了旧版**。
- 一段能讲清"数据库迁移为什么是回滚里最难的一半"的说明，附表结构前后对比与那份备份文件名（⚠️ `.env`、口令、服务器地址不入库），以及恢复演练的记录（备份文件、还原耗时、核对结果）。
- 能回答：密钥轮换在本项目会有什么后果（提示：只发 Access Token、没有 Refresh Token），以及为什么"向前兼容"通常优于"回滚"。

## 6. 排查记录模板

S2 的压测、S3 的每个诊断实验、S0 的顺序实验，都用这一个结构写。面试时能讲 10 分钟的故事，靠的就是它。

```markdown
## 现象
（观察到什么，原样记录，带上数字与时间。不要写成结论）

## 假设
（我怀疑是什么，为什么这么怀疑 —— 要有依据：读过的代码、看到的指标、已知的原理）

## 怎么验证
（对照组是什么，唯一变量是什么，用什么工具，跑什么命令）

## 数据
（表格或图，前后对比。原始输出与截图放本地笔记，仓库里只放结论）

## 结论
（假设成立 / 不成立。**不成立也是有效结论**）

## 如果成立，修了什么，修完复测的数字
```

> ⚠️ **「假设不成立」的结论同样有价值。** 「我怀疑 X，设计了对照实验，结论是 X 在我的负载下不成立」比「我优化了 X」更能体现判断力 ——
> 它说明你不是凭直觉改代码。[docs/06](../docs/06-技术债与待办.md) §3.2 的实验 C 就明确写着"结论是'不成立'也要记录为已验证"。

**一份能过关的记录必须能回答这四件事**：

| 问题 | 不合格的样子 |
|---|---|
| 对照组与唯一变量是什么？ | "我压了一下，感觉快了" —— 没有对照，改了两处 |
| 数字是在什么条件下测的？ | 没写机器规格 / 数据量 / 冷热缓存 —— 数字不可比，等于没测 |
| 结论是"成立"还是"不成立"，凭什么？ | 只写"有改善"，不写证据边界 |
| 下一步是什么？ | 既不修，也不说为什么不需要修 |
