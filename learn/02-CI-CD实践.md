## 1. CI/CD 到底是什么

### 1.1 先把术语拆开

| 缩写 | 全称 | 人话 |
|---|---|---|
| **CI** | Continuous Integration | 代码**频繁合回主干**，且每次合并都**立刻由机器验证**没坏 |
| **CD** | Continuous Delivery | 验证通过后**自动产出随时能上线的包**，但"上线"由人点 |
| **CD** | Continuous Deployment | 验证通过后**自动上线**，没有人点 |

> ⚠️ **CD 有两个含义**，这是行业里长期存在的混乱。本文用 **CD 特指「持续交付」**。

### 1.2 一个必须纠正的误解

> ❌ 「CI 就是自动跑测试。」

**CI 的第一个关键词是"集成"（Integration），不是"测试"。** 这个词来自 1990 年代的极限编程（XP），
针对的是**集成地狱**：各人在各自分支上开发几周，等到合并那天几百个冲突一起爆发、没人知道是谁弄坏的。
解法是两条：**频繁合并**（至少每天一次，让冲突小到当场能解决）+ **每次合并都自动验证**。

> **CI ≠ 有测试。CI = 频繁集成 + 自动验证。** 一个没有测试但有自动构建的项目，也是有 CI 的。

### 1.3 一次完整的流程

**你写代码 → `git push` 触发 → 机器接手（①拉代码 ②还原依赖 ③编译 ④格式/静态检查 ⑤测试
⑥安全扫描 ⑦产出制品）→ 通过 ✅ / 失败 ❌ → 人评审合并 → 部署。**

**①~⑦ 是 CI，部署那一段是 CD。**

### 1.4 关键词：清室验证（Clean-room Verification）

> **在一台"什么都没装过、跟你的开发机毫无关系"的机器上，把项目从零构建一遍。**

最重要的四个字是**"什么都没装过"**。你的开发机上装过什么，你自己都不完全记得：某个 SDK、
某个环境变量、某个手工编译的镜像、某个 PATH 里的工具——它们**不会出现在别人的机器上，
也不会出现在服务器上**。**凡是"只在你机器上能跑"的东西，CI 会立刻把它暴露出来。**

## 2. 为什么本项目需要 CI

### 2.1 核心风险：开发环境 ≠ 部署环境

（完整对照见 [05-运维与部署手册](../docs/05-运维与部署手册.md)）

| 维度 | 开发时 | 部署时 |
|---|---|---|
| 操作系统 | **Windows** 编译，WSL 发命令 | **Linux** |
| Web 服务器 | Kestrel 直连，Vite dev server | **Nginx 反向代理** + Kestrel |
| 前端路由 | Vite dev server **内置 history fallback** | Nginx 必须手工配 `try_files` |
| 数据库 | 你机器上的 `pgsql` 容器（手工编译过 zhparser） | 全新容器，靠镜像内建扩展 |
| 配置来源 | `appsettings.Development.json`（含开发密钥） | 环境变量 `Jwt__SigningKey` |
| 来源 IP | 直连，`X-Forwarded-For` 用不上 | 必须信任转发头，否则限流退化成全局限流 |

最要命的是第三行：Vite dev server 内置了 SPA fallback，所以「部署后刷新页面 404」
**在开发期根本测不出来**，只会在部署当天暴露。**这就是 CI 存在的理由**：用一台干净的 Linux 机器，
在每次提交时把验证跑一遍——它正好覆盖这个盲区，而且比部署那天早得多。

### 2.2 三个具体收益，以及诚实的边界

| 收益 | 针对本项目的哪个问题 |
|---|---|
| **测试环境可复现** | 集成测试需要**真实 PostgreSQL + zhparser**（§4.2），原先靠"你的开发机上恰好有个定制容器"。换台机器、或半年后重装系统就跑不起来 |
| **仓库外的资产回家** | ✅ 已兑现：前端 CDP 检查脚本原先散在仓库外（`/mnt/d/tmpbuild/*.mjs`），项目资产却没有版本控制，换机即丢。现已改写进 `tools/e2e/` |
| **把"人肉纪律"变成"机器强制"** | 仓库历史上真发生过两次事故：无关文件被误提交、几十个文件因 CRLF/LF 差异被整体纳入提交。靠自觉防不住，靠一条 `git ls-files --eol \| grep w/crlf` 就能防住 |

**诚实的边界**：CI 也有成本——学习、维护（依赖升级会让流水线突然坏掉）、等待、**心智成本**
（流水线挂了要先修流水线）。**若满足全部条件，收益确实很低**：单人开发、一天提交不到一次且
从不回滚、**永远不部署**、不依赖任何外部服务。**本项目不满足其中两条**：它**要部署**，且
**依赖两个外部服务**。判断准则是：只要存在「代码要离开你的开发机」这个事实，就存在「环境差异
会咬你」的风险。

## 3. 一条流水线的通用结构

### 3.1 标准阶段

| 阶段 | 做什么 | 失败意味着 | 耗时量级 |
|---|---|---|---|
| **触发 / 检出** | push、PR、定时、手动；拉代码 | 几乎不会失败 | 秒 |
| **还原依赖** | NuGet / npm 下载 | 依赖被删、版本冲突、网络问题 | **最慢**（可缓存） |
| **编译** | `dotnet build` / `vite build` | 语法/类型错误 | 分钟 |
| **静态检查** | 格式、lint、分析器 | 代码风格不达标 | 秒~分钟 |
| **测试** | 单元 / 集成 / E2E | 行为不符合预期 | 分钟 |
| **安全扫描** | 依赖漏洞、密钥泄漏 | 用了有已知漏洞的包 | 秒~分钟 |
| **打包 / 发布**（CD） | 产出制品；推镜像 / 重启服务 | 打包配置错 | 分钟 |

### 3.2 两条铁律

> **铁律一：主干永远是可构建的（Green Main）。** 任何时刻 `main` 上最新提交都必须能通过全部流水线。
> 如果它红了，**修它是全项目最高优先级**——因为其他人（包括未来的你）会基于它继续开发。

> **铁律二：失败必须阻断合并（Required Status Checks）。** 光"跑流水线"是不够的：
> 如果红了还能合并，CI 就**只是多跑了一遍**。必须在托管平台上开启**分支保护**，
> 把 CI 设为合并的必要条件。

> ⚠️ **第二条最容易被跳过，也是让 CI 从"有用"变成"摆设"的分界线。** 对单人项目尤其如此：
> 你会觉得"我自己知道就行"。但正因如此，**这条纪律才是 CI 对你唯一的强制力来源**。

### 3.3 快反馈原则（Fail Fast）

流水线的价值与「你多久知道结果」成反比。

| 做法 | 效果 |
|---|---|
| ✅ 快的任务排前面（格式 → 编译 → 单元 → 集成） | 最常见的问题最快报出来 |
| ✅ 各任务**并行**（前后端互不依赖）+ `fail-fast`（第一个失败就中止同组） | 总时长 ≈ 最慢的那条，且早反馈、省算力 |
| ❌ 所有检查串成一条长链 | 第 8 步失败，前 7 步的时间全白花 |

### 3.4 缓存：CI 性能的关键

CI 机器**每次都是全新的**，所以每次都要重新下载全部依赖——这是 CI 里最大的时间开销。
**核心思想**：把「依赖清单文件的哈希」作为缓存键的一部分；清单没变 → 命中，清单变了 → 自动换新。

| 生态 | 缓存什么 | 缓存键怎么写 |
|---|---|---|
| .NET | `~/.nuget/packages` | 按 `**/*.csproj` 的哈希 |
| Node | npm 缓存 | 按 `package-lock.json` 的哈希 |
| Docker | 镜像层 | 按 Dockerfile 的哈希 |

## 4. 本项目的流水线

### 4.1 四个并行作业

`.github/workflows/ci.yml` 里是四个**互不依赖**的作业：

| 作业 | 包含步骤 | 需要外部服务 | 耗时量级 |
|---|---|---|---|
| `hygiene`（卫生检查） | 检出 → 行尾 CRLF 检查 | 无 | **秒级** |
| `security`（依赖安全扫描） | 检出 → restore → NuGet 扫描 → `npm audit` → 写作业摘要 | 无 | 约 1 分钟 |
| `frontend`（类型检查 + 构建） | 检出 → `npm ci` → `vue-tsc` → `vite build` | 无 | 十几秒 |
| `backend`（构建 + 测试 + 覆盖率） | 检出 → restore → **格式检查** → 编译 → 起 PG/Redis → 校验 zhparser → 测试 → 覆盖率 | **PG + Redis** | 约 2 分钟 |

> ⚠️ 耗时是首次跑通时的量级，**这个数字会变**；当前值看 Actions 页面。
>
> **为什么 `hygiene` 单独拆出来**：它最快也最容易失败（格式问题最常见），排前面能让大部分小问题
> 在 1 分钟内反馈。**为什么依赖扫描也单独拆一个作业**：它回答的是另一个问题——其余作业问
> "我写的代码对不对"，它问"我依赖的代码还安全吗"，后者会在你一行代码都没改的情况下变坏。

### 4.2 唯一的真难点：集成测试怎么在 CI 里拿到 PG + zhparser

集成测试会真实启动宿主并连真实 PostgreSQL（`Blog.Tests/Infrastructure/BlogApiFactory.cs`），
而它需要的东西比"一个 PostgreSQL"多：

| 需要什么 | 为什么 | 由谁提供 |
|---|---|---|
| **PostgreSQL 18 + `zhparser` 扩展** | 测试要跑真实迁移；而 `Posts.SearchVector` 是**生成列**，表达式用了 `to_tsvector('chinese', …)`。缺扩展或 `chinese` 配置，**迁移直接失败**：`42704: text search configuration "chinese" does not exist` | 镜像，且**扩展必须在镜像里**（不能运行时装） |
| `chinese` 检索配置 | 同上 | **EF 迁移自己建** ⚠️ 此前靠测试夹具预建，那会把「迁移链无法从零建库」这个缺陷**掩盖在测试里**；改成迁移自建后，集成测试在**完全干净的库**上跑迁移，本身就是回归防护 |
| **连接串与开发配置一致** | 夹具会**读取 `appsettings.Development.json`** 拿主机/端口/用户名/密码，只替换库名（§7.4） | **CI 里的 PG 必须用这套凭证** |
| Redis / 密钥 | 缓存会降级，但**限流桶存在 Redis 里**；夹具已关掉限流并**强制 `UseEnvironment("Development")`**，读到的是开发配置密钥，所以 **CI 不需要注入 `Jwt__SigningKey`**（那是 CD 的事） | 起一个 redis 容器 |

带 zhparser 的镜像有三条路，**A 是当前采用的方案**：

| 方案 | 判断 |
|---|---|
| **A. 流水线里现构建**（先 `docker build -f deploy/postgres-zhparser.Dockerfile`，再 `docker run`；**不能**用平台的 `services:`——它在 steps **之前**就启动了，来不及先 build 镜像） | ✅ **当前采用**，不需要镜像仓库，镜像定义与使用永远同步；代价是每次现编译 |
| **B. 预构建推到镜像仓库** | 🟡 跑顺之后再换。⚠️ **有"假绿"风险**：Dockerfile 改了但没重推镜像，CI 会一直测一个**过期的数据库环境**，而且它还是绿的——假绿比红更危险 |
| **C. 官方 `postgres:18`** | ❌ **不可行**：没有 zhparser，迁移必然失败 |

### 4.3 真实文件里那些"防坑"设计

教学示例保持简洁，真实文件更"防坑"。除 §3.3、§3.4 的通用原则外，多出这几样：

| # | 多了什么 | 防的是什么 |
|---|---|---|
| 1 | **`concurrency` 取消旧运行**；每个作业设 **`timeout-minutes`** | 同一分支连续推送时旧运行没有意义，白占额度；没有超时的话卡住的作业会一直占用（默认 6 小时） |
| 2 | **起库后先单独校验 zhparser 可用** | 否则环境问题会退化成那句毫无信息量的 `The server has not been started or no web application was configured`（§7.1） |
| 3 | ⭐ **校验测试确实被执行（防假绿）** | **`dotnet test` 在 0 个测试被发现时同样返回 0**。路径写错、过滤器写错都会让流水线**变绿而什么都没验证**；这一步解析 trx 报告并断言 `total > 0` |
| 4 | **等待数据库就绪的轮询循环** | 「容器启动了」≠「数据库能连了」。少了它，流水线会**随机失败**，而你会误以为是代码问题 |
| 5 | ⭐ **覆盖率写进作业摘要 + 「报告丢失就报错」哨兵** | 摘要让数字**看得见**；哨兵防的是把 `--collect` 换成 `--settings` 之后覆盖率**静默消失**（§5.3） |
| 6 | **`if: always()` 上传报告、`if: failure()` 打印数据库日志** | 只在成功时上传等于"失败时什么都没有"，而失败时恰恰最需要报告 |
| 7 | **`--no-restore` / `--no-build` 串成一条链** | `restore` → `format --no-restore` → `build --no-restore` → `test --no-build`：还原与编译**各只做一次**，后面的步骤直接复用产物，不必每条命令都重新还原一遍 |

> ⚠️ **第 4 点值得单独强调**：**CI 的随机失败（flaky）比稳定失败更有害**——它会训练你"重跑一遍
> 就好了"，从而**彻底摧毁你对流水线的信任**，所以见到随机失败必须当 Bug 修。而第 3、5 两条都
> 先做过负向验证（用空 trx、把 `TestResults` 挪走），否则无法区分「检查通过了」和「检查根本没生效」（§8）。

### 4.4 触发条件与平台差异

真实触发条件是 `push: [main]` + `pull_request: [main]` + `workflow_dispatch`（手动）。**往功能分支
单独 push 不会触发流水线**——「我推了分支，怎么 Actions 里什么都没有」不是故障，是设计；代价是
功能分支在**开 PR 之前拿不到任何 CI 反馈**。

| 概念 | GitHub Actions | GitLab CI |
|---|---|---|
| 流水线定义 / 一组任务 | `.github/workflows/*.yml` / `jobs.<name>` | `.gitlab-ci.yml` / `<stage>` + `script` |
| 运行环境 / 依赖缓存 | `runs-on: ubuntu-latest` / `actions/cache@v4` | 由 Runner 决定（`tags`） / `cache:` |
| 制品 / 密钥 / 服务容器 | `upload-artifact@v4` / `secrets.NAME` / `services:` | `artifacts:` / CI/CD Variables / `services:` |

**结论：无论选哪个平台，§3.1 的阶段划分都完全复用**——真正的知识是"流水线该有哪些阶段、每个阶段防什么失败"，而不是某个平台的 YAML 语法。

## 5. 质量门禁（Gate）

门禁 = **CI 里那些"不过就不许合并"的检查**。这一节回答"该设哪些、标准是什么"。

### 5.1 测试金字塔，以及本项目的实际形状

**测试金字塔**（Mike Cohn 提出，Martin Fowler 推广）：越往上的测试跑得越慢、越容易随机失败、
定位越难，所以**数量应该越少**——不是因为它们不重要，而是因为**单位成本高**。**本项目的实际
形状是一个"倒金字塔"**：集成测试（真实 HTTP + 真实 PostgreSQL）比纯单元测试还多（当前数量由
代码决定，实测见 CI 作业摘要）。

这在本项目是**合理的**：CRUD 型应用**业务价值密度最高的是"权限边界"和"并发语义"**，只能在完整
管道里验证——集成测试里有相当一部分是权限矩阵，防的是"漏一个 `[Authorize]` 就是完全敞开"
这类真实事故。**代价也是真实的**：跑得慢（每次都要起宿主 + 迁移）；**必须有真实 PG + zhparser**，
否则一项都跑不了；上 CI 门槛更高。**写在三个月后的结论**：不专门加"补单元测试"的任务，
但**新增功能时**优先把**纯逻辑**（校验、计算、状态转换）写成单元测试——便宜且不需要数据库。

### 5.2 覆盖率：行业没有"必须 80%"

> ❌ 「测试覆盖率必须达到 80%。」**这不是任何行业标准，是讹传。**

| 事实 | 说明 |
|---|---|
| 没有任何权威组织规定过覆盖率阈值 | 它不是 ISO、不是 IEEE、不是任何 RFC |
| "80%" 的来源不可考 | 一个被反复引用的经验值，引用多了就变成了"规定" |
| 覆盖率**低**确实是坏信号 | 但反面不成立：覆盖率高 ≠ 测试有效 |
| 覆盖率可以被轻易刷高 | 写一堆不 assert 的测试就能到 100%：**代码全执行了，一个 Bug 都发现不了** |

**该看的指标**（价值从高到低）：**关键路径是否被覆盖**（权限校验、计数/状态转换）→
**变更覆盖率**（本次改动的新代码测了多少，比整体数字有用得多）→ **趋势**（方向有意义，绝对值
无意义）→ **分支覆盖 vs 行覆盖**（行覆盖把 `if` 的假分支也算作已覆盖）。**本项目的做法是只出
报告、不设阈值**：一开始就卡阈值会逼人写垃圾测试凑数，而一个"经常被迫绕过"的门禁比没有门禁
更糟——它训练你忽略红色。关注点在关键路径（授权策略、乐观锁、草稿可见性），并把覆盖率
**写进 CI 作业摘要**：制品要下载才看得到，摘要打开 PR 就在眼前。

### 5.3 覆盖率落地时才发现的三个问题

**一、不排除生成代码，这个数字根本没有意义。** 五个 EF Core 生成的迁移与模型快照文件占了
`Blog.Infrastructure` 全部行数的**约七成**。迁移代码"被执行过"（集成测试一跑必然执行它们），但
**它一行都不代表被测过**——它只是把分母和分子同时往上抬，把"哪部分业务代码是裸奔的"这个真正
该看的问题淹没掉；`Blog.WebApi` 里编译器生成的 OpenAPI XML 注释支持代码覆盖率恒为 0%。于是有了
`Blog.Backend/coverage.runsettings`，排除 `**/Persistence/Migrations/*.cs`、
`**/*ModelSnapshot.cs`、`**/obj/**/*.cs`。

> ⚠️ **反直觉的地方：排除生成代码后，行覆盖率明显下降，分支覆盖率反而上升。** 代码一行没改，
> 质量一点没变——变的只是统计口径，所以看到任何覆盖率数字，第一个该问的问题是「**分子分母里
> 都装了什么**」。它**也不是逐位确定的**（同一提交连跑几次有小差异），这正是**不该对总量设阈值**
> 的又一个理由：会漂移的指标卡在具体数字上只会红绿闪烁。

**二、真实基线会暴露"裸奔点"（这才是有用的部分）。** 排除生成代码后立刻能看出一批**行覆盖极低
甚至为 0 的位置**：限流中间件、健康检查、内存缓存实现、集合的写路径、分类/标签的读路径。按风险
排序第一个该补的是**限流中间件**——它是一道**安全控制**，而集成测试里 `RateLimit:Enabled = false`
把它关掉了，所以「防 `X-Forwarded-For` 绕过」的验证目前只在手工跑。**下一步该补什么，这张表就是
答案**（具体数字随代码变化，以 CI 作业摘要为准）。

**三、覆盖率会「静默消失」。** 原来用 `--collect:"XPlat Code Coverage"`；改用
`--settings coverage.runsettings` 之后，**覆盖率就依赖那个文件了**。它被删除、改名，或
`--settings` 参数被顺手去掉，`dotnet test` 都会**照常变绿**、制品照常上传（只是里面没有覆盖率
文件），而你会以为"覆盖率一直在正常收集"。所以 CI 里那一步兼作**哨兵**：找不到
`coverage.cobertura.xml` 时**直接报错**。

### 5.4 依赖安全扫描：为什么「只报告不阻断」

这是本项目里**唯一一种「代码一行没改，风险却变高了」**的风险，所以它值得单独一个作业。

| 扫描对象 | 命令 / 工具 |
|---|---|
| NuGet **含传递依赖** | `dotnet list package --vulnerable --include-transitive` ⚠️ 漏洞通常藏在**传递依赖**里 |
| npm | `npm audit --registry=https://registry.npmjs.org` ⚠️ **源必须显式指定** |
| 密钥泄漏 / 自动化 | 平台的 secret scanning；**Dependabot**（`nuget` + `npm` + `github-actions`） |

> ⚠️ **一、这个项目早就在扫，只是没人看得见**：NuGet Audit 从 .NET 8 SDK 起**默认开启**，
> `dotnet restore` / `dotnet build` 会打出 `NU1903` 警告——不会让流水线变红，也没有人看见。
> 缺口的准确描述不是"完全没做"，而是"信息一直在输出，却没有任何机制让它被看见"。
>
> ⚠️ **二、危险之处在于组合条件**：`npm audit` 在默认镜像源下返回 `404 [NOT_IMPLEMENTED]` 且
> **非 0 退出**，而作业是 `continue-on-error` → **「审计没跑成」和「审计跑了、没发现漏洞」在
> 页面上长得一模一样**。所以 CI 里加了一道显式检查：输出里必须出现 `found N vulnerabilities`
> （N 可以是 0），没有就报错，而不是当成"干净"。同理，**抑制某个包的升级 PR 时只写
> `dependency-name` 的 ignore 规则会被展开成 `>= 0`，并同时作用于安全更新通道**——必须显式写
> `update-types`。

**为什么只报告不阻断**：先只看结果；等结果稳定、确认"报出来的都会修"，再改成阻断——反过来做
最常见的结局是被一个**修不了**的 CVE 卡住 → 注释掉整个作业 → **从此它就是个摆设**。

> ⚠️ **"扫描器说没有漏洞"本身不可信，直到你验证过它会报**：永远输出"干净"的扫描器和一台坏掉的
> 扫描器**输出完全一样**，所以做过一次**阳性对照**（引用一个有已知漏洞的旧版包，确认它真的报出
> 高危公告）。顺带测出：`dotnet list package --vulnerable` **发现漏洞时退出码依然是 0**。

### 5.5 一份可执行的门禁清单

每条都给出**具体的失败条件**，否则门禁形同虚设。

| 顺序 | 门禁 | 失败条件 | 状态 |
|---|---|---|---|
| 1 | 后端编译 | `dotnet build` 非 0 退出 | ✅ |
| 2 | 后端测试 | 任一测试失败；**0 个测试被执行也算失败** | ✅ |
| 3 | 前端类型检查 | `vue-tsc` 报错 | ✅ |
| 4 | 前端构建 | `vite build` 失败 | ✅ |
| 5 | 行尾检查 | 存在 `w/crlf` | ✅ |
| 6 | 分支保护开启 | 上面任一失败则**禁止合并**（直推同样被拒） | ✅ |
| 7 | C# 格式（whitespace） | `dotnet format … --verify-no-changes` 报差异 | ✅ **只查空白/行尾，不查 analyzer**（一次性把 analyzer 建议变成门禁 = 大量改动 + 长期噪音） |
| 8 | 覆盖率 | 不阻断、**不设阈值**；**报告丢失则报错** | ✅ |
| 9 | 依赖漏洞扫描 | 有高危 CVE（**先只报告不阻断**） | ✅ |
| 10 | 前端 ESLint | lint 报错（**需先配置并清理存量**） | ❌ |
| 11 | 前端 E2E（CDP） | 断言失败 | 🟡 脚本已进仓库，**未接 CI** |

> **第 10、11 条为什么先不做。** 格式检查的正确顺序是：① 加配置 → ② 本地**一次性格式化整个
> 代码库**（会产生一个巨大提交）→ ③ 之后才在 CI 里开启；**不要**在没格式化的代码库上直接开检查，
> 否则第一次流水线会冒出上千条告警，然后你会关掉它。E2E 接 CI 的成本结构完全不同（要装真浏览器、
> 随机失败来源成倍增加、断言需要真实数据）：**正确顺序**是先本地稳定跑，等它连续一段时间
> **没出现过假红**再接 CI。⚠️ 第 7、8、9 三条都**不阻断**，因此各自都配了「失效哨兵」（见
> §4.3 第 3、5 条与 §5.4）：「不阻断」不等于「可以不看」，结果写进作业摘要，打开 PR 就在眼前。

### 5.6 分支保护怎么验（正反两个方向都要验）

**配好了和没配好，界面看起来差不多**，所以必须做**反向验证**——用「故意失败」的提交去撞门禁。

| 方向 | 手段 | 预期 |
|---|---|---|
| **PR 合并**被拦 | 开一个含**故意失败测试**的 PR | 必需检查变红，**Merge 按钮变灰不可点** |
| **直推 main**（检查失败的分支） | `git push origin <bad>:main` | 被拒：`GH006: Protected branch update failed` |
| **直推 main**（正常但没跑过检查的分支） | 同上 | 被拒：`Changes must be made through a pull request.` |

> 第三个方向**最有价值**：它回答的是「如果检查是绿的，能不能直推」这个真正的问题。
> ⚠️ 「Require status checks」对**直接 push** 同样生效，而 `git push --dry-run` **验不出来**
> （dry-run 只做本地协商，不触发服务端的 `pre-receive` 钩子）。

## 6. CD：从"能构建"到"能上线"

| | CI | CD |
|---|---|---|
| 问题 / 产物 / 失败后果 | "这份代码是对的吗？" / 一个**结论** / 开发者看到红叉 | "怎么把它安全地放上服务器？" / 一个**制品** / **线上用户受影响**，所以要谨慎 |

> **建议**：先做 **CI + 持续交付**（自动产出镜像，人工部署），**不要**一上来就做持续部署——
> 部署形态还没有真正跑通过一次，自动化一个没跑通的流程只会把问题藏得更深。**发布策略**同理：
> 个人博客选**重建式**（停旧 → 起新，停机几十秒完全可接受）就够；滚动要多实例、蓝绿资源翻倍、
> 金丝雀要流量治理设施——**都不值得为零停机投入**。

后端制品是 `dotnet publish` 输出或容器镜像，前端是 `vite build` 的 `dist/`，跟同一个 git tag；
数据库镜像固定 `:18`。⚠️ **镜像绝不要只用 `:latest`**（会移动的标签，出事时说不清线上跑的是哪一版），
正确做法是 `日期 + 提交短哈希`。

### 6.1 回滚，以及数据库迁移这个特例

**应用可以随便回滚，数据库不行**：换回上一个 tag 即可，但 **EF Core 迁移的 `Down()` 只能撤销
结构变更，撤销不了数据丢失**——回滚一列能加回这一列，但**里面的数据已经没了**。因此行业通行
做法是**「向前兼容」而不是「回滚」**：迁移与应用解耦（先上"只增不删"的迁移，稳定后再在**下一个
版本**里删旧字段）；新代码能读旧结构、旧代码能读新结构；**破坏性变更单独发一次，且必须有备份**。

> **本项目的一个真实提醒**：应用启动时会自动执行数据库迁移。单实例下很方便，但**多实例下
> 每个实例都会抢着迁移**（EF Core 默认不取分布式锁）。项目已有的多实例启动校验**管的是缓存，
> 不管迁移竞争**——真正上多实例前，迁移必须拆成**独立的、只跑一次的部署步骤**。

### 6.2 密钥管理

密钥**绝不进仓库**：`appsettings.json` 里**没有** `Jwt:SigningKey`，缺失或长度不足时**应用直接
拒绝启动**；开发期用 `dotnet user-secrets`，运行期用环境变量 `Jwt__SigningKey`（双下划线 = 配置的
`:`），CI/CD 期用平台的加密变量（CI **不需要**，见 §4.2）。

> ⚠️ **轮换密钥对本项目是一个真问题**：本项目**只发 Access Token、没有 Refresh Token**
> （刻意的技术决策，见 [archive/决策记录.md](../archive/决策记录.md)），所以**一旦换了
> `Jwt:SigningKey`，所有已登录用户的 token 立即失效**。个人博客上可接受（提前公告即可）。

## 7. ⚠️ 坑清单（本项目特有）

全部是**本项目代码实测会遇到的**，不是通用教程里的泛泛之谈。

### 7.1 CI 里集成测试失败的头号原因

集成测试在 CI 上失败时，错误信息**几乎总是同一句**
`The server has not been started or no web application was configured.`
而它**几乎从来不表示真正的原因**：

| 排序 | 真实原因 | 怎么确认 |
|---|---|---|
| 1 | **PG 连不上**（容器没起好 / 端口没映射 / 凭证不匹配） | `docker logs pgsql`；确认 `pg_isready` 通过 |
| 2 | **缺少 `chinese` 检索配置** → 迁移报 `42704` | 用带扩展的镜像；确认迁移链自己建出了配置 |
| 3 | **`appsettings.Development.json` 没被读到**（连接串为空）或 **EF Core 版本冲突**（`Mvc.Testing` 传递引入旧版 Relational） | 前者：该文件已被 git 跟踪，检出后应存在；后者：已由测试工程显式对齐版本解决 ✅ |
| 4 | **PG 还没就绪就开始跑测试** | 必须有轮询等待（§4.3 第 4 条） |

> **排查原则**：**不要相信那句话**——要么绕过 `WebApplicationFactory` 直接构造宿主，要么临时打开详细日志，才能看到真实异常。

### 7.2 Windows 上能过、Linux CI 上挂掉的四类原因

本项目**有 Windows 开发 → Linux 部署的固定落差**，所以这四类问题**一定会遇到**：

| # | 原因 | 表现 | 状态 |
|---|---|---|---|
| 1 | **文件系统大小写敏感** | Windows 不区分 `Posts.ts` / `posts.ts`，Linux 区分。前端 import 路径大小写写错，**本地完全无感，CI 直接模块找不到** | ⚠️ 需注意 |
| 2 | **路径分隔符** | 代码里硬编码 `\` 在 Linux 上失效 | ✅ 目前用 `Path.Combine` |
| 3 | **行尾 CRLF/LF** | 整个文件 diff | ✅ `.gitattributes` 已统一为 LF，且 CI 有检查 |
| 4 | **区域设置（Culture / ICU）** | ⚠️ **最隐蔽的一条**：.NET 在 **Windows 用 NLS、Linux 用 ICU** 做字符串比较与排序，**同一个 `OrderBy` 在两个平台上可能给出不同顺序** | ⚠️ 本项目有中文排序场景（归档按年月、标题），值得留意 |

> **第 4 条的应对**：凡是**依赖排序结果**的测试，不要断言"第 1 条是 X"，要么显式指定比较器
> （`StringComparer.Ordinal`），要么断言"集合内容相同、顺序无关"——这就是跨平台稳定的 **Ordinal 排序**。

### 7.3 环境变量在 CI 里的写法

.NET 的配置系统用**双下划线**表示层级（`Jwt__SigningKey` 还必须 ≥ 32 字节，否则应用拒绝启动），这在 YAML 里极易写错：

| 想配置的键 | 环境变量写法 | 常见错误 |
|---|---|---|
| `Jwt:SigningKey` | `Jwt__SigningKey` | ❌ 写成 `Jwt:SigningKey`（YAML 里会被当字符串，应用读不到） |
| `ConnectionStrings:DefaultConnection` | `ConnectionStrings__DefaultConnection` | 同上 |
| `Cache:Provider` | `Cache__Provider` | 同上 |

### 7.4 测试夹具是"读文件"而不是"读环境变量"

```
BlogApiFactory.ResolveDevelopmentConnectionString()
  → 沿目录向上找 Blog.Backend.slnx（定位仓库根）
  → 读取 appsettings.Development.json 的连接串 → 只把 Database 换成随机测试库名
```

| 推论 | 说明 |
|---|---|
| CI 里**必须有** `appsettings.Development.json` | ✅ 它已被 git 跟踪，检出后就有 |
| **不能**靠环境变量覆盖连接串来改主机 | ❌ 夹具是从**文件**读的，环境变量在这里不起作用 |
| CI 里的 PG **必须**监听 `localhost:5432`、用开发配置里的用户与密码 | 否则连不上 |

> 💡 让夹具**优先读环境变量、回退到文件**会更好，那样 CI 就能用任意凭证（登记在 [06-技术债与待办](../docs/06-技术债与待办.md) §3）。

## 8. 动手顺序（第一次接触照着做）

**不要一次把整条流水线写出来**，分阶段来，每阶段跑通了再进下一步——出问题时只需怀疑一个地方：
手工命令写成脚本 → 只跑编译 → 加前端作业 → **加后端测试（起 PG + Redis）** → 加缓存 →
加门禁（行尾检查 + 分支保护）→ 加依赖扫描 → 加覆盖率（先排除生成代码，再谈阈值）→ 加 CD →
加前端 ESLint 与 E2E（先全量清理存量）。每一步的完成判据都是**故意让它失败一次，确认它真的会红**。

> ⚠️ **整条路径上最关键的一句判据**：「**先在"坏"的代码上跑一遍、确认它会失败，再在"好"的
> 代码上跑通——否则你无法区分「真的通过了」和「测试根本没生效」。**」
> 它对整条流水线同样成立：**一条从来没红过的流水线，你并不知道它是否真的在检查。**
