## 1. C# 最小集【新增】

### 1.1 为什么先讲这个

本项目是 C# 写的。下面这张表覆盖你阅读源码时会遇到的绝大多数语法。
**它不是 C# 教程，是"读代码的快捷键"**——遇到不认识的写法先回来查表。

### 1.2 读代码要认得的 14 个写法

| 你会看到 | 它在说什么 | 本项目例子 |
|---|---|---|
| `class` / `record` | 引用类型；`record` 额外自带值相等、`ToString`、`with` | `Post`（实体，带行为）vs `PostDetailDto`（数据快照，§14） |
| `interface` + 实现类 | 只声明"能做什么"，不写怎么做 | `IPostRepository` → `PostRepository` |
| 泛型 + 约束 `where T : BaseEntity` | 一套代码服务多种类型，约束限定范围 | `BaseRepository<TEntity>` |
| 可空引用类型 `string?` | 编译器提醒"这里可能是 null" | `Post.CreatedByUserId` 是 `Guid?` |
| `{ get; init; }` | 只能在对象初始化时赋值（不可变） | `BaseEntity.Id` |
| `{ get; private set; }` | 外部只读、内部可改 | `Post.Title` —— 想改只能调 `Update()` |
| 表达式体 `=>` | 单表达式方法/属性的简写 | `public Guid? UserId => Current?.UserId;` |
| `?.` `??` `??=` | 空传播、空合并、空则赋值 | `PublishedAt ??= DateTimeOffset.UtcNow` |
| `is not null` / `switch` 表达式 | 模式匹配 | 请求日志按状态码分级，§24 |
| `Func<T>` vs `Expression<Func<T,bool>>` | 前者是**委托**（在内存里跑）；后者是**表达式树**（能被 EF 翻译成 SQL） | 仓储的 `QueryByConditionAsync` 用后者 |
| `IQueryable<T>` vs `IEnumerable<T>` | 前者"还没执行"，可以继续被翻译；后者"已经在内存里" | 投影查询必须保持 `IQueryable`（§17） |
| `async Task<T>` + `CancellationToken` | 异步方法签名与取消约定 | 几乎所有仓储/服务方法 |
| 特性 `[Authorize]` `[HttpGet]` | 声明式元数据，框架运行期读它 | 控制器与实体鉴权（§6） |
| `namespace X { }` / `using` | 代码分区与引用 | 全仓 |

### 1.3 两个最容易读错的地方

**① `record` 是引用类型**（`record struct` 才是值类型）。`with` 做的是**浅复制**：
新对象与旧对象共享引用类型的成员。本项目 DTO 全是不可变数据袋，所以感觉不到差别，
但不要以为 `with` 是深拷贝。

**② `IQueryable` 与 `IEnumerable` 的分界线是"执行"**。
一旦 `ToListAsync()` / `ToList()`，后面的 `Where` 就在内存里跑了——
这正是"N+1 查询"和"把整张表拉进内存"最常见的成因（详见 §18）。

## 3. Git 工作流与行尾（旧 §26）

### 3.1 行尾：一个"没有内容改动却整文件变红"的坑

Windows 用 `CRLF`（`\r\n`），Linux/macOS 用 `LF`（`\n`）。Git 默认可能做自动转换，
于是**整份文件被标记为改动，而实际内容一个字都没变**。

解法是 `.gitattributes` 统一行尾（`* text=auto eol=lf`，二进制文件 `binary`），
并用 `git ls-files --eol` 检查（`w/crlf` 正常应为空）。

> ⚠️ **真实教训 · 39 个文件的行尾噪声**
> 工作区一度有 39 个文件**仅存在 CRLF/LF 差异**（无真实内容变更），并被误纳入一次提交。
> 规则由此确定：① 行尾由 `.gitattributes` 统一，不靠各人编辑器；
> ② **不要整文件覆盖写回 CRLF**，否则会产生整文件 diff，把真实改动淹没在噪声里。

### 3.2 提交信息：唯一记录"当时为什么"的地方

格式用 Conventional Commits：`类型(范围): 描述`。

| 类型 | 含义 | 类型 | 含义 |
|---|---|---|---|
| `feat` | 新功能 | `perf` | 性能优化 |
| `fix` | 修 Bug | `test` | 测试 |
| `docs` | 文档 | `chore` | 杂项 |
| `refactor` | 重构（**不改变行为**） | `!` 后缀 | 破坏性变更 |

**为什么区分 `refactor` 与 `feat`/`fix`**：重构不改变行为，review 时可以只看"结构是否更好"，
不必担心行为变化。混在一起就丢失了这个信息——`git log` 是代码与文档都不记录的那部分历史。

### 3.3 本项目最痛的教训：误删文件

> ⚠️ **真实教训 · 无关文件被误删/误加并混入提交**
> 项目多次发生"无关文件混入提交"，其中原始需求文档在一个会话内被外部进程删除 3 次。
> 由此形成四条纪律：① 提交前 `git status --short` + `git show --stat HEAD` 复核范围；
> ② **按路径精确 `git add <path>`，慎用 `git add -A`**；③ 未跟踪文件丢失**不可恢复**，所以勤提交；
> ④ 文档里只写相对路径（仓库目录名含非 ASCII 字符）。
> `git show --stat HEAD` 是发现误删/误加的最后一道防线，成本只有几秒。

### 3.4 文档与代码必须同一次提交落地

改了代码之后：① 跑通构建/测试 → ② 打开受影响的文档**逐条核对**路径、字段名、端点、配置键 →
③ 更新文档的"最后核对"日期 → ④ 与代码在**同一个提交**里落地。

第 ② 步不能省。文档出错最典型的方式不是"写错了"，而是**"改代码时忘了同步某一张表"**。

# 阶段 1 · 一次请求的一生

> 目标：跟着一个 HTTP 请求走完全程。这四节合起来就是"框架是怎么把请求交给你的代码的"。
> 顺序即依赖：先有容器（DI）→ 再有管道（中间件）→ 再到端点（路由/授权）→ 全程读配置。

## 4. 依赖注入（DI）与生命周期（旧 §1）

### 4.1 为什么需要 DI

**依赖注入**是"控制反转"（IoC）的一种实现：类不在内部 `new` 自己的依赖，
而是**声明自己需要什么**，由外部容器构造并传进来。

```csharp
// ❌ 紧耦合：PostService 自己决定用什么仓储，无法替换、无法测试
private readonly PostRepository _repo = new PostRepository(new BlogDbContext(...));

// ✅ 依赖倒置：只声明接口需求，构造函数注入
public PostService(IPostRepository repo, IUnitOfWork uow) { ... }
```

值得的三个理由：**可替换实现**（换数据库、换缓存不动业务代码）、
**可测试**（注入 fake，不必连数据库）、**生命周期集中管理**（不必手工 `new`/`Dispose`）。

### 4.2 三种生命周期（最重要的知识点）

| 生命周期 | 注册方法 | 实例何时创建 | 何时释放 | 适用 |
|---|---|---|---|---|
| **Singleton** | `AddSingleton` | 首次被请求时，**全局唯一** | 应用关闭 | 无状态、线程安全、创建昂贵 |
| **Scoped** | `AddScoped` | **每个 HTTP 请求**一个 | 请求结束 | DbContext、仓储、业务服务 |
| **Transient** | `AddTransient` | **每次注入**都新建 | 随持有者 | 轻量、无状态的小对象 |

**记忆要点**：Scoped 的生命周期边界就是"一个请求"。

> ⚠️ **真实教训 · Singleton 不能依赖 Scoped**
> Singleton 活得比 Scope 长：它若持有 Scoped 实例（如 `DbContext`），
> 该实例在请求结束后已被释放，而 Singleton 仍握着这个失效引用。
> **好消息**：.NET 的容器在**启动时**就会校验并抛 `InvalidOperationException`，
> 问题在启动期暴露。同理**不要从 Singleton 里解析 Scoped 服务**；
> 确实需要时注入 `IServiceScopeFactory` 并显式创建 Scope。

### 4.3 三种注册写法

| 写法 | 场景 | 本项目 |
|---|---|---|
| `AddScoped<IPostRepository, PostRepository>()` | 最常用 | 全部仓储与 Service |
| `AddSingleton<IPasswordHasher>(_ => new Pbkdf2PasswordHasher())` | 无状态且已构造好的实例 | 密码哈希、JWT、限流器、文件存储 |
| 工厂委托 `sp => ...` | **按配置决定用哪个实现** | `ICacheService` 在三个实现间选择 |

**可以观察到的规律**：`DbContext`、`UnitOfWork`、仓储、Service 全是 **Scoped**；
缓存实现、限流器、`ICurrentUser` 之外的无状态工具类是 **Singleton**。
判断标准只有一句：**它是否持有"每请求不同"的状态**。

> 💡 **一个值得注意的细节**：Redis 缓存实现用 `Lazy<ConnectionMultiplexer>` **延迟建立连接**。
> 若在构造时就连接，Redis 未启动会导致**应用启动失败**——而缓存本应是"没有也能跑"的组件（§22）。

→ 实现见 [docs/02](../docs/02-架构与数据模型.md)（依赖注入组合）｜代码见总表 #4。

## 5. 中间件管道与顺序效应（旧 §4）

### 5.1 洋葱模型

ASP.NET Core 的请求处理是一条**管道**：每个中间件可以选择"处理请求 → 调用下一个 → 处理后返回的响应"。

```
请求 ──► [中间件A] ──► [中间件B] ──► [终结点]
响应 ◄── [中间件A] ◄── [中间件B] ◄──────┘
```

**注册顺序 = 请求经过的顺序，响应顺序正好相反。**
先注册的中间件"最早看到请求、最后看到响应"，所以它包在最外层。

### 5.2 `AddXxx` 与 `UseXxx` 的分工

| 形式 | 阶段 | 例子 |
|---|---|---|
| `builder.Services.AddXxx()` | **注册服务**（构建容器时） | `AddControllers()`、`AddAuthentication()` |
| `app.UseXxx()` | **装配管道**（决定运行时顺序） | `UseAuthentication()`、`UseAuthorization()` |

一句话：**Add 是"准备零件"，Use 是"决定装配顺序"**。新手最常把两者混为一谈。

### 5.3 三种写法

| 写法 | 何时用 |
|---|---|
| `app.UseMiddleware<ExceptionHandlingMiddleware>()` | **有依赖注入需求时**（约定式类） |
| `app.Use(async (ctx, next) => { ... })` | 逻辑很短、不值得单独一个类 |
| `app.Run(...)` | **终结**中间件，后面不再有中间件 |

约定式中间件的类约定：构造函数收 `RequestDelegate next`；`InvokeAsync` 的参数**会被从 DI 解析**
（所以 Scoped 服务可以在这里注入）。

### 5.4 顺序错了会怎样（两个真实案例）

> ⚠️ **真实教训 · 请求日志必须在异常处理的外层**
> 日志中间件若注册在 `ExceptionHandlingMiddleware` **里层**，
> `BusinessException` 会先冒泡穿过日志中间件，日志记录的是"异常发生时的 500 + 完整堆栈"，
> 而客户端实际收到的是映射后的 404/403/409——**日志与事实不符**，
> 排查时会被误导；且"文章不存在""邮箱重复"这类可预期的业务失败会**刷满 ERR 日志**，淹没真正的故障。
> 正确顺序：`UseSerilogRequestLogging()` 在前，`ExceptionHandlingMiddleware` 在后。

> ⚠️ **真实教训 · 解析登录用户必须排在 `UseAuthentication` 之后**
> 本项目自建的当前用户中间件要从 `context.User` 读 claims（由认证中间件填充）再去查库，
> 放在认证之前就什么也读不到，表现为"登录了却像没登录"。
> 正确顺序：`UseAuthentication()` → `CurrentUserResolutionMiddleware` → `UseAuthorization()`。

### 5.5 一个完整的中间件实例：解析当前登录用户

需求：每个请求都要知道"谁在访问"，且这个信息要能被 Service 层读取。两个难点：

1. 校验需要查数据库（账号是否存在、是否启用、`TokenVersion` 是否一致）→ **异步**
2. Service 层希望在属性 getter 里**同步**读取 → 不能在那里查库（见下面的教训）

解法：**在中间件里异步解析一次，结果存进 `HttpContext.Items`**，之后所有 getter 都是纯内存读取。
四条校验依次是：验签/验过期（JwtBearer 做）→ 账号存在且未软删除 → `IsActive` → claim 的 `tv == 库里的 TokenVersion`。

**两个刻意的设计**：

1. **校验失败不返回 401**，只是"不写用户信息"，拒绝与否交给后面的 `[Authorize]`。
   这样**公开接口即使带着一个过期 token 也照常访问**——否则一个过期 token 会让用户连首页都打不开。
2. `ICurrentUser` 是 **Scoped**（每请求一个），因为 `HttpContextAccessor` 是 Scoped 的。

> ⚠️ **真实教训 · 不要在属性 getter 里同步阻塞异步查询**
> 属性 getter 是同步签名。若 `ICurrentUser.UserId` 在 getter 里查库，就成了 sync-over-async：
> 高并发下会耗尽线程池。本项目的做法是**管道早期异步查一次，之后全是同步读内存**。

→ 实现见 [docs/02](../docs/02-架构与数据模型.md)（请求管道、当前用户解析）｜代码见总表 #5。

## 6. 路由、模型绑定与授权属性（旧 §5）

### 6.1 模型绑定：请求数据怎么进到参数里

| 来源 | 特性 | 例子 |
|---|---|---|
| 路由 | `[FromRoute]`（默认从路由模板推断） | `/api/posts/{id}` → `id` |
| 查询串 | `[FromQuery]` | `?page=1&pageSize=12` |
| 请求体 | `[FromBody]` | JSON 反序列化为 DTO |
| 表单 | `[FromForm]` | `multipart/form-data`（上传） |
| 请求头 | `[FromHeader]` | 少见 |
| — | `CancellationToken` | **特殊**：框架自动注入，不是绑定来源 |

**约定**：简单类型从路由/查询串绑定，复杂类型从请求体绑定。

### 6.2 路由约束：格式不对在路由层就被拒

`[HttpGet("{id:guid}")]` 里的 `:guid` 让"不是合法 GUID"直接 404，不必在 action 里写 `Guid.TryParse`。
同类还有 `:int`、`:length(1,10)` 等。

**顺序注意**：`{id:guid}` 与字面量路由 `archives` 能共存，因为 `archives` 不匹配 GUID 约束；
若两者都能匹配，**字面量优先级更高**。这条规则决定了 `/api/posts/search` 不会被当成 `{id}`。

### 6.3 统一响应体：为什么手动包装

本项目所有响应体都是 `{ code, message, data }`，且由控制器**手动包装** `ApiResponse<T>.Ok(...)`，
而不是用过滤器/`IActionResult` 统一处理：

- 控制器签名即契约，一眼看出这个端点返回什么类型；
- 错误路径由全局异常中间件统一处理，**控制器里没有 try/catch**。

### 6.4 授权属性：策略优于角色

| 写法 | 含义 |
|---|---|
| `[AllowAnonymous]` | 显式允许匿名（覆盖类级 `[Authorize]`） |
| `[Authorize]` | 仅需认证，不限角色 |
| `[Authorize(Policy = "AdminOnly")]` | 满足名为 `AdminOnly` 的策略 |
| `[Authorize(Roles = "Admin")]` | 直接限定角色（**本项目不用这种**，统一走策略） |

**策略 vs 角色的价值**：策略把授权规则**命名并集中定义**，控制器只引用名字。
规则将来变了（例如 Admin 也要二次验证），只改策略定义，不必碰每个控制器。
策略名用 `const` 而不是字符串字面量，避免拼写不一致——拼错时编译不过。

### 6.5 属性式鉴权的能力边界（最重要的一条）

`[Authorize]` 只能回答：**"这类角色能不能用这个端点"**。
它**不能**回答：**"这个人能不能操作这条数据"**——后者必须先查到数据才知道归属，因此只能写在 Service 层。

> ⚠️ **真实教训 · 用 `AuthorId` 判归属会互相越权**
> 项目最初用 `AuthorId`（署名）判断文章归属，但**多个账号可以关联同一个 `Author`**，
> 于是它们能互相修改对方的文章。**正确做法是只认 `CreatedByUserId`（账号维度）**。
> 这就是"资源级授权"（resource-based authorization）：它**永远属于业务逻辑层，不属于控制器**。
> 详见 [docs/02](../docs/02-架构与数据模型.md)（归属校验必须在 Service 层）。

> ⚠️ **真实教训 · 漏一个 `[Authorize]` 就是一个完全敞开的端点**
> 本项目真实发生过：分类、标签、站点、上传的写接口**全部漏了属性**，匿名即可调用。
> 根因是属性式鉴权**没有"默认拒绝"这一层兜底**，也没有编译期保障；
> 而**前端隐藏了按钮，界面上完全看不出来**。
> 现在的防线是：一张**可枚举的写端点清单 + 自动化断言**（匿名调用必须 401），新增写端点必须同时加进清单——
> 把"人肉逐个检查"变成"机器逐个检查"（历史见 [archive](../archive/问题排查记录.md)，当前状态见 [docs/06](../docs/06-技术债与待办.md)）。

### 6.6 HTTP 状态码与业务错误码：两种错误表达，各给谁看

| | 给谁看 | 作用 |
|---|---|---|
| **HTTP 状态码** | **通用基础设施**：浏览器、`fetch`、拦截器、监控、日志聚合 | 表达"这次请求成功了没有"。401 触发重新登录、429 触发退避、413 表示太大——都是**通用约定**，不该由业务方各自发明 |
| **业务 `code`** | **业务代码** | 表达"是哪一种失败"。同一个 `400` 下可以有多种业务原因（参数不合法 / 重复资源 / 乐观锁冲突） |

**典型错误做法**是在 action 里直接 `return ApiResponse.Fail(...)`：
ASP.NET Core 对"正常返回一个对象"一律给 **HTTP 200**，于是业务码在 body 里、状态码却在说"成功"，
后果是同一个语义**在上传接口是 200、在其它接口是 400**，而客户端的通用错误处理（401 跳登录、429 退避、5xx 告警）**全部失效**，
监控上看到 100% 成功率。**正确做法是抛业务异常，让全局中间件统一映射**。

> 💡 **一个自查信号**：某个错误码**定义了、也在映射表里，却从来没被抛出过**，
> 那多半说明**某条错误路径没走统一通道**。本项目就有一个错误码这样"躺"了很久，
> 直到修上传接口时才真正生效。完整的错误码表见 [docs/03](../docs/03-API参考.md)（错误码表）。

→ 实现见 [docs/03](../docs/03-API参考.md)（端点与权限标记）｜代码见总表 #6。

## 7. 配置系统与 Options 模式（旧 §6）

### 7.1 配置是分层覆盖的

```
appsettings.json
  → appsettings.{Environment}.json        （如 appsettings.Development.json）
  → 用户机密（user-secrets，仅开发）
  → 环境变量
  → 命令行参数                            （最高优先级）
```

环境变量的层级用**双下划线**表示：`Jwt__SigningKey` 等价于 `Jwt:SigningKey`。

> ⚠️ **真实教训 · WSL 里启动 Windows 的 exe，环境变量不传递**
> 在 WSL 里运行 Windows 编译的 `Blog.WebApi.exe` 时，`ASPNETCORE_ENVIRONMENT`
> **不会**传给 Windows 进程，于是读到的是没有连接串的 `appsettings.json`，应用启动失败。
> 解法是用**命令行参数**（优先级最高）显式指定环境。
> 环境相关的坑集中记录在 [docs/05](../docs/05-运维与部署手册.md)（环境陷阱清单）。

### 7.2 不要在业务代码里读配置字符串

**不要**写 `IConfiguration["Cache:Provider"]`。应该绑定到强类型类（`XxxOptions`）：

1. **编译期检查**：属性名拼错编译不过；
2. **默认值集中**：类里写的默认值就是兜底；
3. **节名用常量**（`SectionName`）：避免字符串在代码里重复出现。

| 注入接口 | 特点 | 何时用 |
|---|---|---|
| `IOptions<T>` | 单例，启动后不变 | **绝大多数场景** |
| `IOptionsSnapshot<T>` | Scoped，每请求重读 | 需要热更新 |
| `IOptionsMonitor<T>` | 单例 + 变更通知 | 需要监听变更 |

### 7.3 启动期校验：把危险配置变成"起不来"

最有力的配置用法是**在启动时拒绝危险配置**，这就是 Fail Fast：

- **签名密钥太短或缺失 → 直接抛异常**。静默使用弱密钥意味着"任何人都能伪造 token"，
  后果远比启动失败严重。
- **多实例却用内存缓存/内存限流 → 直接抛异常**（`DeploymentGuard`）。
  多实例下内存限流的实际阈值会被放大到"配置值 × 实例数"，限流形同虚设，
  而"静默降级"会让这个问题极难排查。

**共同的理念**：**能在启动期发现的错误，就不要留到运行期。**
把部署拓扑当作运维必须**显式声明**的输入，而不是让代码去猜。

> ⚠️ **真实教训 · 敏感配置绝不入库**
> 开发用的签名密钥放在 `appsettings.Development.json` 并明确标注"仅开发"；
> 生产用环境变量 / user-secrets / 密钥库。**生产 `appsettings.json` 里刻意不含 `Jwt:SigningKey`**，
> 因此忘记注入时应用会拒绝启动——这是**设计出来的失败**，不是缺陷。
> 前端同理：`VITE_` 前缀的变量会被**打包进客户端产物、任何人可读**，
> 只放公开配置（如兜底标题），密钥必须只存在于后端。

→ 实现见 [docs/01](../docs/01-快速开始.md)（配置项总表、环境变量）｜代码见总表 #7。

## 8. 认证与授权（旧 §15，★前移）

### 8.1 两个必须分清的概念

| | 认证（Authentication） | 授权（Authorization） |
|---|---|---|
| 回答 | **你是谁？** | **你能做什么？** |
| 失败返回 | **401** Unauthorized | **403** Forbidden |
| 本项目实现 | JWT | 角色策略 + 资源归属校验 |

> **命名陷阱**：HTTP 401 叫 "Unauthorized"，但它实际含义是**"未认证"**（Unauthenticated）。
> 403 才是真正的"无权限"。这个措辞错误来自 HTTP 规范，至今没改。

### 8.2 为什么用 JWT

**传统 Session**：服务端存 session，客户端拿 session id。问题是多实例必须共享 session 存储，
否则请求打到另一台就掉登录。**JWT**：服务端签发一个**自包含的签名令牌**，客户端每次带上，
服务端只需验签、**不需要查存储**——天然支持多实例。

三段结构：`header.payload.signature`。签名段用密钥对前两段签名以防篡改；
payload 是声明（claims）：`sub` `role` `exp` `jti`...

> **关键认知**：payload 是 **Base64 编码，不是加密**！任何人都能解开看内容。
> **绝不能在 JWT 里放敏感信息**（密码、身份证号）。你自己就能解开看——
> 见 [docs/05](../docs/05-运维与部署手册.md)（接口验证）里的解码命令。

### 8.3 JWT 的最大缺陷：无法主动失效

JWT 是**无状态**的，服务端不存它，因此：用户改了密码 → 旧 token 在过期前依然有效；
账号被停用 → 旧 token 依然有效；用户点"退出登录" → 只是前端删了 token，
**服务端无法阻止它被继续使用**。这是无状态性的**固有代价**，不是实现问题。

| 补偿方案 | 做法 | 代价 |
|---|---|---|
| 缩短有效期 | 30 分钟就过期 | 用户体验差（频繁重登） |
| **TokenVersion**（本项目） | 签发时写入版本号，每请求与库中比对；失效时 +1 | **每请求需查一次库** |
| Redis 黑名单 | 失效的 token 存 Redis | 引入 Redis 运行时依赖 |

**本项目选 `TokenVersion`，理由有两条**：① **不引入新的运行时依赖**（校验读库，不读 Redis）；
② **多实例下天然有效**（不需要跨实例共享状态）。

> ⚠️ **真实教训 · 版本号只在"失效场景"自增**
> 规则写在实体方法里：`ResetPassword()`（改密）、`SetActive(false)`（停用）、
> 主动注销才 `TokenVersion++`；**正常改资料不该把人踢下线**。
> 规则放在实体而不是 Service 里，是为了**无法被绕过**：将来新写一个 Service 也不会忘记自增。

### 8.4 token 存哪里：localStorage 还是 Cookie

| | `localStorage` | `HttpOnly Cookie` |
|---|---|---|
| XSS 风险 | ⚠️ JS 可读，XSS 即被窃取 | ✅ JS 读不到 |
| CSRF 风险 | ✅ **不会自动发送**，无 CSRF | ⚠️ 自动发送，需 CSRF token |
| 前端可读 | ✅ 可读用户信息 | ❌ 读不到 |

**本项目选 `localStorage`**：不引入 CSRF 问题，用"短有效期"补偿 XSS 风险。
这个选择没有绝对对错，取决于**更怕 XSS 还是更怕 CSRF**。
但一旦选 localStorage，**防 XSS 就成为硬性要求**（§10），不是可选项。

### 8.5 状态码与响应体：两处容易被忽略的细节

**① 401/403 必须映射成正确的 HTTP 状态码**，而不是统一 400。
理由：前端的 401 拦截器（自动清登录态并跳登录页）**依赖状态码**。
都返回 400 的话，前端无法区分"请求写错了"和"该重新登录了"。

**② 认证失败也要返回统一响应体**。ASP.NET Core 默认在认证失败时返回**空响应体 + 401**，
这会让前端的 `res.json()` 解析失败，只能靠状态码硬编码兜底。
解法是注册 `JwtBearerEvents` 的 `OnChallenge`（401）与 `OnForbidden`（403），
先 `context.HandleResponse()` 阻止默认空响应，再自己写入统一体。

→ 具体写法见 [docs/02](../docs/02-架构与数据模型.md)（JWT 的 401/403 也走统一响应体）。

### 8.6 一次带 token 的请求经历了什么

```
① UseAuthentication        验签 + 验过期 → 填充 HttpContext.User（仅此而已）
② 当前用户中间件 ★          查库二次校验（账号在、启用、TokenVersion 一致）→ 写入 HttpContext.Items
③ UseAuthorization         检查策略 → 不通过走 JwtBearerEvents（401/403 统一体）
④ Controller → Application Service → ⑤ 服务层归属校验 EnsureCanManage(post)
⑥ 仓储查询（带 CreatedByUserId 过滤）—— 草稿列表只能看到自己的
```

**关键点：①和②是两件不同的事**（这也是自建中间件的原因）：
① 验证的是 **token 本身**的真伪与时效（依据签名 + `exp`，**不查库**）；
② 确认的是这个**账号"现在"**还能用（依据数据库当前状态，**每请求查一次**）。

### 8.7 `HttpContext.User` 里有什么、缺什么

> **先纠正一个容易误解的前提**：本项目**并没有"不用框架的 `User`"**。
> 两个授权策略用的是 `policy.RequireRole(...)`，读的正是 `HttpContext.User` 的 role claim——
> **框架的 `User` 一直在用**。自建中间件不是替代它，而是在它之上**补一层**。

`HttpContext.User`（`ClaimsPrincipal`）里装的就是 JWT payload 的 claim：

| claim | 内容 | 谁在用 |
|---|---|---|
| `sub` | 账号 Id | token 解析 |
| `role` | `Admin` / `Author` | ✅ **框架的 `RequireRole` 直接读它** |
| `tv` | **签发时**的 `TokenVersion` | 与库中当前值比对 |
| `authorId` | 签发时关联的作者 Id | 解析成当前用户信息 |
| `jti` / `exp` / `iss` / `aud` | 唯一 id、过期、签发者、受众 | JwtBearer 校验 |

它**做不到**的三件事，正是中间件存在的理由：① claim 只是"**签发那一刻的快照**"——
改密码/停用后，旧 token 里的 `role`、`tv` 仍是旧值、**过期前一直有效**；
② 不知道账号**现在**是否还存在/启用——已停用甚至已删除的账号仍能用旧 token 操作；
③ `AuthorId` 变更**不会同步**——管理员改绑作者后，旧 token 仍按旧值判归属。

**为什么必须单独做一个中间件，而不是在用到的地方现查？** 三个理由：
**避免同步阻塞异步**（`ICurrentUser` 的属性是同步 getter，在里面查库就是 sync-over-async，§5.5）、
**一次请求只查一次**（多个服务都注入它，各自查库就是 N 次查询）、
**Application 层不依赖 HTTP**（服务层通过 `ICurrentUser` 知道"谁在操作"，保持可单元测试，§15）。

### 8.8 授权的四个层次

"授权"不是一个动作，而是**四道递进的关卡**。把它们分开放，是这一块设计的主线：

| 层 | 在哪 | 判断 | 本项目的实现 |
|---|---|---|---|
| ① 认证 | 管道 | **你是谁** | `UseAuthentication` + 当前用户中间件 |
| ② 端点授权 | 管道 | 你的**角色**能否访问这个端点 | 两个策略（`AdminOnly` / `ContentWriter`） |
| ③ 资源授权 | **服务层** | 这条**具体数据**是不是你的 | `PostService.EnsureCanManage(post)` |
| ④ 数据过滤 | **仓储查询** | 查询结果里**只应包含**你能看的 | `OwnedByUserId` 被强制注入 |

- **②是"逐个端点声明"的**：漏写一个 `[Authorize]`，那个端点就完全敞开（§6.5 的真实事故）。
- **③必须先查到数据才知道归属**，属性式鉴权做不到（§6.5）。
- **④是"看不见"而不是"打不开"**：作者看自己的草稿列表时，服务端直接把过滤条件设成"我创建的"，
  而不是"先查出全部再逐个过滤"。

**授权的三种模型**（了解术语即可，本项目只用了前两种）：

| 模型 | 判断依据 | 本项目 |
|---|---|---|
| **RBAC** 基于角色 | 主体属于哪个角色 | ✅ 只有 `Admin` / `Author` 两档，**刻意不做细粒度 RBAC** |
| **ReBAC** 基于关系 | 主体与资源的**关系** | ✅ 部分用了：归属校验本质是"**创建者**"关系 |
| **ABAC** 基于属性 | 属性 + 策略表达式组合 | ❌ 不用。个人博客用不到，且策略表达式难测试 |

### 8.9 自己动手追一遍（值得亲手做的 5 个实验）

命令见 [docs/05](../docs/05-运维与部署手册.md)（接口验证）——那里是命令的唯一权威。要做的实验是：

1. **登录拿 token** → 2. **把 token 解开看 claim**（最能建立直觉：payload 只是 Base64）；
3. **带 token 访问受保护接口** → 期望 200；4. **不带 token 访问同一接口** →
   期望 401 **且响应体是统一格式而不是空**（§8.5）；
5. **★ 用同一个 token 注销后再访问** → 期望 401。这一步证明 JWT 虽然无状态，
   但通过 `TokenVersion` 补上了"可主动失效"的能力。

> ⚠️ **真实教训 · 验证真伪要看后端日志**
> 某些工具的 localhost 请求可能被 mock 层拦截并返回**伪造的成功响应**。
> 可靠判据只有一个：**后端日志里有没有对应的请求记录**。

**推荐的代码阅读顺序**（跟着数据流走）：`AuthController` → `AuthService` → `User`（版本号在哪自增）→
`JwtTokenService`（claim 怎么装/怎么读）→ `Program.cs`（管道顺序、策略、401/403 统一响应）→
`CurrentUserResolutionMiddleware` → `HttpCurrentUser`/`ICurrentUser` → 前端 `stores/auth.ts`、`api/http.ts`。

## 9. 密码哈希与密码学基础（旧 §16）

### 9.1 哈希 ≠ 加密

| | 哈希（Hash） | 加密（Encryption） |
|---|---|---|
| 方向 | **单向**，不可逆 | 双向，可解密 |
| 用途 | 校验（密码、完整性） | 传输、存储机密 |
| 存密码 | ✅ 用哈希 | ❌ 绝不用加密 |

**密码校验流程**：不存密码，存哈希；登录时对输入**再算一次哈希**，与存储值比对。

**为什么绝不能明文存密码**：① 数据库泄露 = 所有用户密码泄露；
② 用户常在多个网站复用同一个密码，危害会扩散到其他服务；③ 法规（GDPR 等）明确要求。

### 9.2 为什么不能用 MD5/SHA256 直接哈希密码

它们是**快速**哈希函数——设计目标是"算得快"。对密码来说这正是灾难：

| 攻击方式 | 说明 |
|---|---|
| **暴力破解** | 现代 GPU 每秒可算数十亿次 MD5 |
| **彩虹表** | 预计算的"哈希 → 明文"映射表，常见密码瞬间反查 |
| **相同密码识别** | 相同密码产生相同哈希，一眼看出谁和谁密码一样 |

**正确方案 = 加盐 + 慢哈希**：

- **加盐**：给每个用户一个**随机值**与密码一起哈希。相同密码 → 不同哈希（彩虹表失效）；
  盐**不需要保密**，但要**每用户不同**。
- **慢哈希（KDF）**：故意设计得慢。`PBKDF2`（本项目）标准且广泛支持、可调迭代次数；
  `bcrypt` 经典；`scrypt` 内存硬（抗 ASIC）；`Argon2` 现代首选但需要额外库。

**本项目选 PBKDF2-HMAC-SHA512**，用**框架内置实现**（`Rfc2898DeriveBytes`），**不引入第三方包**。
参数（迭代次数、盐长度、输出长度）见 [docs/02](../docs/02-架构与数据模型.md)（密码哈希）——
它们的取值有明确依据，改动会影响已有密码的校验。

### 9.3 自描述的存储格式

存储串形如 `pbkdf2-sha512$<迭代次数>$base64(盐)$base64(哈希)`。

**为什么把算法与迭代次数也存进去**：将来提升迭代次数时，**旧密码依然能被校验**——
校验时按存储里记录的迭代次数重算。配合 `NeedsRehash()`，可以在用户登录成功时**静默升级**哈希参数。
这是"为将来留后路"的典型设计：**格式自身携带版本信息**。

### 9.4 时序攻击：比较也要恒定时间

普通的字符串比较在**第一个不同的字符**处就返回，比较耗时因此泄露"前几个字符猜对了"。
对密码哈希比对，这足够让攻击者逐字节猜出哈希。

> ⚠️ **真实教训 · 用恒定时间比较**
> 校验必须用 `CryptographicOperations.FixedTimeEquals(actual, expected)`：
> 无论内容如何都花同样的时间。**不要用 `==` 比较哈希**——
> 这类漏洞不会在功能测试里暴露，只会被计时探测发现。

> ⚠️ **真实教训 · 校验失败一律返回 false，不抛异常**
> 解析失败（段数不对、前缀不匹配、迭代次数不是数字、Base64 损坏）全部 `return false`。
> 原因：**不把"格式细节"暴露成可用信号**——攻击者不该能通过"这个错误 vs 那个错误"推断存储格式。

### 9.5 种子密码的教训

本项目**把管理员初始密码的哈希公开写在仓库里**（种子数据），让全新环境开箱即可登录后台。

**为什么可以这样做**：哈希**无法反推**密码（这正是哈希的意义）。
**但必须同时做到**三条：① 明确标注仅开发用；② **生产部署后立即修改密码**；
③ 生产不应长期依赖这个种子账号。

**这与"不能在代码里写密码"不矛盾**：区别在于**这个密码是公开的初始默认值**，
而不是某个真实用户的密码。它是"默认密码"，必须被替换——
上线清单里有一条就是这个（§29）。

→ 实现见 [docs/02](../docs/02-架构与数据模型.md)（密码哈希）｜代码见总表 #9。

## 10. 前端 XSS 防护（旧 §23）

### 10.1 什么是 XSS，为什么在这个项目里格外严重

**跨站脚本攻击**：攻击者让**你的页面**执行**他的脚本**。

| 类型 | 说明 |
|---|---|
| 存储型 | 恶意内容存进数据库，**所有访问者**中招 |
| 反射型 | 恶意内容在 URL 里，用户点击后触发 |
| DOM 型 | 前端 JS 把不可信数据写进 DOM |

> ⚠️ **真实教训 · localStorage 让 XSS 的后果升级**
> 本项目把 token 存在 `localStorage`（§8.4），**攻击者能直接读走 token**，
> 用受害者身份操作到 token 过期为止。
> 所以**防 XSS 是这个项目的硬性要求，不是可选项**。

### 10.2 关键风险点：Markdown 渲染

文章内容是 **Markdown**，前端用 `marked` 转成 HTML，再用 `v-html` 渲染。
这是典型的 XSS 场景：Markdown 允许内联 HTML，恶意作者（或被攻破的账号）可以嵌入
`<script>` 或 `<img onerror=...>`。

**为什么这一步不能省**：`v-html` 会**原样注入** HTML，Vue 的模板转义**对它无效**——
`v-html` 的语义就是"这是可信 HTML"。

解法：`DOMPurify.sanitize(marked.parse(md))`，按**白名单**过滤 HTML，
移除危险标签、`on*` 事件属性、`javascript:` 协议等。整个项目只有**一个渲染入口**，
所有文章都从这里过——`src/utils/markdown.ts`。

### 10.3 防护是分层的

| 层 | 措施 |
|---|---|
| 输出编码 | Vue 模板默认转义 `{{ }}` 插值（**不要用 `v-html` 除非必要**） |
| HTML 消毒 | `v-html` 前必须 `DOMPurify.sanitize()` |
| 输入校验 | 后端校验长度与格式（`PostService.ValidateInput` + `FieldLimits`） |
| CSP | 内容安全策略，限制可执行的脚本来源（部署层配置） |
| token 短有效期 | 限制 XSS 成功后的时间窗口 |

其他需要注意的场景：`:href="userUrl"`（`javascript:` 协议，要校验协议白名单）、
`innerHTML = x`（避免，必须时消毒）、`eval()` / `new Function()`（**绝不用**）、CSS `url()` 注入。

**一个值得思考的设计**：后端**不做 HTML 消毒**（存储原始 Markdown），消毒发生在**渲染时**。
因为消毒规则会演进（今天安全的标签明天可能被发现有问题），
存原始内容 + 渲染时消毒，意味着**改进规则能立刻保护所有历史内容**。

### 10.4 两个真实的渲染坑

> ⚠️ **真实教训 · 内联样式"打败"了主题变量**
> 现象：文章正文亮色主题正常，切到暗色主题**黑底黑字**读不了；查主题变量却完全正确。
> 真因：正文从富文本编辑器**粘贴**进来时夹带了内联样式（如 `<font style="color:rgb(15,17,21)">`），
> 而**内联 `style` 的优先级高于选择器规则**，自然盖过主题变量。
> **排查顺序**：遇到"主题/样式没生效"，先开 F12 看元素上挂了什么属性，再决定改 CSS 还是清内容。
> **修法**：渲染时剥掉内联样式——顺带堵掉一类 CSS 注入（`background: url(//evil.com/track)` 可在不执行 JS 的情况下追踪）。

> ⚠️ **真实教训 · 消毒时"删标签"会把正文一起删掉**
> DOMPurify 的 `FORBID_TAGS` 会**连同子节点一起删**：`<font style="...">这段话</font>` → 什么都没了。
> 我们要的是**保留文字、丢弃样式包装**（unwrap）：用 `uponSanitizeElement` 钩子把子节点上提、再删空壳。
> 两个坑：① `addHook` 是**全局**的，写在组件里会随组件反复挂载（或 HMR）**重复注册**——
> 必须放在模块顶层 + 模块级去重标志；② 该操作在 DOMPurify 遍历 DOM 时移动节点，
> **必须实测确认文字没被吞掉**（本项目用无头浏览器断言"文字无丢失、内联样式已清零"）。

→ 实现见 [docs/04](../docs/04-前端设计.md)（Markdown 渲染与消毒）｜代码见总表 #10。

## 11. 限流：令牌桶算法（旧 §18）

### 11.1 为什么需要限流

| 目的 | 说明 |
|---|---|
| 防滥用 | 防止单用户刷爆接口 |
| 保可用 | 保护后端不过载，其他用户仍可用 |
| 控成本 | 限制昂贵操作（搜索、上传）的调用频率 |

| 算法 | 思路 | 缺点 |
|---|---|---|
| 固定窗口 | 每分钟最多 N 次 | **临界问题**：窗口边界可放行 2N 次 |
| 滑动窗口 | 统计过去 N 秒 | 实现复杂，需存时间戳 |
| 漏桶 | 请求排队、匀速流出 | 不允许突发 |
| **令牌桶**（本项目） | 桶按速率积攒令牌，请求消费令牌 | 允许突发（桶容量内） |

**选令牌桶的理由**：它**允许一定的突发流量**，而真实用户行为本来就是突发的
（打开页面时并发几个请求）。两个参数分工明确：

| 参数 | 控制 |
|---|---|
| `Capacity` | **突发上限**（能一次性放行多少） |
| `TokensPerSecond` | **长期平均速率** |

### 11.2 分布式下的原子性

令牌桶的状态是"**读 → 算 → 写**"，并发请求会互相覆盖（两个请求都读到 5 个令牌、都写回 4，
实际消耗了 2 个却只记了 1 个）。

> ⚠️ **真实教训 · 必须用 Lua 脚本保证原子**
> Redis 单线程执行脚本、脚本内部不会被打断，所以"读-算-写"是原子的——
> 这是分布式令牌桶的**唯一正确实现方式**，先用应用层读再写一定会漏。
> 脚本里有两处容易漏的细节：① `retryAfter` 要按"差几个令牌 ÷ 速率"算，直接返回固定值会误导客户端；
> ② 必须给桶设**自动过期**，否则每个访问过的 IP 都留下永久 key，内存无限增长。

> ⚠️ **真实教训 · 内存实现"每实例一个桶"，多实例下限流形同虚设**
> 内存限流器在 2 个实例时，实际阈值是"配置值 × 2"，而这个问题**不会报错、只会静默失效**。
> 这正是 `DeploymentGuard` 存在的原因：多实例 + 非 Redis 时**启动即失败**（§7.3）。

### 11.3 粒度、转发头与规则顺序

| 粒度 | 桶 key 的标识 | 适用 |
|---|---|---|
| **Ip**（默认） | 客户端 IP | 防单用户滥用 |
| Global | 固定字符串 | 保护后端总容量 |
| Endpoint | 方法 + 路径 | 保护特定昂贵接口 |

> ⚠️ **真实教训 · 反向代理之后，"按 IP 限流"会退化成"全局限流"**
> 加了 Nginx 后 Kestrel 看到的来源 IP 全是 Nginx 的，于是**一个人刷爆、所有人被限流**。
> 解法是读转发头 `X-Forwarded-For` 的**第一个** IP（它是逗号分隔的列表，第一个才是真实客户端），
> 拿不到再回退到连接的对端地址。同一个坑在部署侧还会再出现一次（§29）。

**规则匹配：顺序即优先级，命中即停。** 因此**具体规则必须排在通用规则前面**
（`search`、`write` 都要在 `default` 之前，否则永远命中 `default`）。

**HTTP 语义**：触发限流返回 **429 Too Many Requests** + `Retry-After` 头（建议等待秒数），
响应体仍是统一格式；放行时返回剩余额度头，便于前端与调试观察。

→ 实现见 [docs/02](../docs/02-架构与数据模型.md)（限流）｜代码见总表 #11。

## 12. 文件存储与安全（旧 §19）

### 12.1 为什么不用静态文件中间件

ASP.NET Core 有 `UseStaticFiles()`，一行就能暴露一个目录。本项目选择**自己写文件接口**：

| 理由 | 说明 |
|---|---|
| 可做路径穿越防护 | 自己校验解析后的路径 |
| 精确控制缓存头 | 只在**命中**时下发缓存 |
| 可插入处理管线 | 上传时自动转 WebP |

### 12.2 路径穿越

**攻击方式**：请求 `/api/files/../../appsettings.json`。若服务端简单拼接路径（`Path.Combine(root, 用户输入)`），
就会把配置文件读出来。

> ⚠️ **真实教训 · 必须先 `GetFullPath` 规范化再比前缀**
> 校验步骤是：`Path.GetFullPath(Path.Combine(root, path))` → 与**规范化后的**根目录比前缀 →
> 不在根目录内就拒绝。**关键点：必须先用 `GetFullPath` 解析掉 `..`，然后再比较前缀**；
> 直接比较原始字符串会被 `..` 绕过。这条规则在读取层再实现一次（§12.7 纵深防御）。

### 12.3 一个真实的缓存头 Bug

> ⚠️ **真实教训 · 声明式特性作用于整个 action，包括失败分支**
> 现象：上传了背景图但前端一直显示空白，文件其实存在。
> 根因：用 `[ResponseCache(Duration = 86400)]` 标注 action——**特性作用于整个方法**，
> 于是"文件不存在"的 404 分支也被浏览器缓存了**一整天**，必须手动强刷才能恢复。
> **修法**：在方法体内、**确认命中后**才设置 `Cache-Control`；不命中走 `NotFound` 且不带缓存头。
> **通用规则**：声明式的特性无法表达"只在某分支生效"；当缓存语义有分支时，必须用命令式代码。

### 12.4 上传图片自动转 WebP：谨慎的"有损操作"

WebP 同等质量下比 PNG/JPEG 小 25–35%。本项目在保存前转换，但**极其谨慎**：

| 情况 | 行为 |
|---|---|
| 扩展名不在允许转换的列表 | 原样保存 |
| 是**动画**图片（多帧） | 原样保存（压成单帧是**数据损失**） |
| 文件损坏 / 无法解码 | 原样保存（**不丢用户的文件**） |
| 像素数超过上限 | 原样保存（防解压炸弹） |
| 转换后**更大** | 原样保存（否则反而浪费流量） |
| 其他 | 转为 WebP，必要时等比缩小 |

**核心原则：失败即原样保存**。优化失败绝不该导致上传失败——这是"**有损且静默**"的操作，
出错不会报错、只会让图片慢慢不对，所以要往保守的一侧设计。

**为什么锁定某个图片库大版本**：新版本要求构建期许可密钥，社区许可虽免费但需先申请，
否则**构建直接报错**；旧版本是纯托管实现、无原生依赖，部署最简。
升级前先确认许可与依赖，别把它当普通补丁升级。

### 12.5 上传大小限制有两层

| 层 | 归属 | 值的作用 |
|---|---|---|
| 框架层（`[RequestSizeLimit]`） | ASP.NET Core | 防止请求体撑爆内存，**先于业务检查生效** |
| 业务层（`FileStorage:MaxFileSize`） | 业务规则 | 超限返回业务错误码 |

**为什么要两层**：框架层必须在**读取请求体之前**就拒绝超大请求，业务层则要给出可读的错误语义。

### 12.6 写要鉴权，读要公开

上传要求 `ContentWriter`（Admin 或 Author）——上传是写操作，匿名开放会让任何人往服务器塞文件、耗尽磁盘。
**但读取接口保持公开**：文章封面与作者头像必须能被匿名访客加载。
**"写要鉴权、读要公开"是文件接口的正确默认。**

> ⚠️ **真实教训 · 这个属性曾经遗漏过（匿名可上传）**
> 与 §6.5 是同一类事故：**前端隐藏按钮不是安全边界**，属性式鉴权必须逐个端点检查，
> 并靠端点清单 + 自动化断言守住。历史记录见 [archive/问题排查记录.md](../archive/问题排查记录.md)。

### 12.7 白名单，而不是黑名单

头像、封面、站点 Logo、首屏背景图这类"图片地址"字段，本项目经历了"自由文本框 → 服务端白名单"的收紧：
早前后端**原样存库、原样下发**，于是任何能调写接口的人都能塞进任意 URL。

| 思路 | 写法 | 问题 |
|---|---|---|
| ❌ 黑名单 | 禁止 `http:`、`javascript:`、`data:`…… | 只能挡住**已经想到**的写法；明天冒出个新 scheme 就漏了 |
| ✅ 白名单 | 只认 `/api/files/` 前缀 + 受限字符集 | 挡得住**没想到**的写法——因为默认拒绝 |

本项目只放行两类取值：**空**（未设置），或 `/api/files/` 开头且路径部分只含受限字符集的地址。
这个字符集限制顺带挡掉了 `%`（编码绕过）、`:`（scheme）、`?`/`#`（查询/片段）、`\`（Windows 分隔符）。

> ⚠️ **真实教训 · 字符集过滤挡不住 `..` 和 `//`**
> 它们**完全由合法字符组成**，所以必须**单独判断**。这是写路径校验时最容易漏的一步。

**三条通用经验**：① 校验放**服务层**（多个服务都要用，且可纯单元测试、不依赖 HTTP）；
② **只测"拒绝"是不够的**——校验若被写成"一律拒绝"，负向断言照样全绿，必须同时写合法样本的断言；
③ **必须做端点级测试**：单元测试证明"判定逻辑对"，端点测试证明"判定**真的被调用**了"。

### 12.8 上传格式白名单：SVG 为什么不能收

别的图片格式是**纯数据**，而 SVG 是 **XML 文档**，可以内嵌 `<script>`：

| 加载方式 | 脚本会执行吗 |
|---|---|
| `<img src="/api/files/x.svg">` | ❌ 不会——`<img>` 里的 SVG 是"被动图像" |
| **浏览器直接打开**该 URL | ✅ **会执行**，而且是在**站点自己的源**上 |

所以"反正只允许用在 `<img>` 里"**不能**作为放过 SVG 的理由——那个 URL 本身就能被直接访问。
攻击链很短：有写权限的作者上传恶意 SVG → 把地址发给管理员 → 管理员点开 →
脚本以管理员身份在站点源上运行 → **存储型 XSS**。处理是双层的：从扩展名白名单移除 `.svg`，
**同时**移除 MIME 映射（兜底：手工放进媒体目录的 svg 也只会被当二进制下载）。

**通用经验**：上传白名单不只是"防磁盘塞满"，它同时是**内容安全边界**。判断一个格式能不能收，
要问的不是"它是不是图片"，而是**"它能不能携带可执行内容、会被以什么方式下发"**；改动前还要排查存量。

**纵深防御**：`MediaPath`（写入前拦）与文件读取层的路径校验是**两层，不是重复**（§12.2 与 §12.7）。

→ 实现见 [docs/02](../docs/02-架构与数据模型.md)（文件上传与图片优化）｜代码见总表 #12。

## 13. async / await 与异步编程（旧 §2）

### 13.1 异步买到的不是"更快"，是"更多并发"

**同步**：线程在等待 I/O（数据库、网络、磁盘）时被阻塞，什么也做不了。
**异步**：遇到 I/O 时把线程**还回线程池**，I/O 完成后再用某个线程继续。

对 Web 服务器，这直接决定**并发能力**：异步不会让单个请求更快，
但让服务器在同样的线程数下能同时处理更多请求。这就是"全链路 async"的意义。

**四条核心规则**：① `async` 方法返回 `Task` / `Task<T>`（**不要把 `async void` 用于非事件处理器**）；
② 一路 `await` 到底；③ 异步方法名以 `Async` 结尾；④ 传递 `CancellationToken`，让请求取消能向上传播。

> ⚠️ **真实教训 · 不要用 `.Result` / `.Wait()` 阻塞异步结果**
> 在旧 ASP.NET、WPF 这类**有同步上下文**的环境里，`.Result` 会真的**死锁**
> （原线程被阻塞，而 `await` 完成后要回到原上下文）。
> ASP.NET Core 没有同步上下文、通常不会死锁，但**仍然会阻塞线程**（失去异步的全部意义），
> 且异常被包成 `AggregateException`，难以排查。所以规则是：**一律 async 到底**。
> 属性 getter 里尤其危险——它是同步签名（§5.5）。

**`Task` vs `ValueTask`**：默认用 `Task`；`ValueTask` 只在"结果经常同步可得且调用频繁"时用来省分配。
它有额外约束（不能多次 await），不是性能银弹。本项目在 EF 拦截器的重写上用到它（框架签名要求）。

**`CancellationToken` 的传递**：控制器接收它 → 一路传给 Service → Repository → EF Core
（EF 的每个异步查询方法都接受它）。这让"客户端断开连接"能中止后端正在做的无用功。

→ 相关实现见 [docs/03](../docs/03-API参考.md)（端点签名与分页）｜代码见总表 #13。

## 14. record 与 DTO 设计（旧 §3）

### 14.1 `record` 是什么

`record` 是 C# 9 引入的引用类型，编译器自动生成**值相等性**、`ToString`、
以及非破坏性修改的 `with` 表达式。属性默认是 `init`（只能初始化时赋值），因此**天然不可变**。

```csharp
public record TagBriefDto(Guid Id, string Name);
var b = a with { Name = ".NET" };   // 复制并改一个字段，原对象不变
```

**DTO 用 `record` 而不是 `class` 的四个理由**：不可变（数据快照不该在传递中被改）、
少写代码（一行替代几十行）、值语义（便于断言与比较）、`with` 优雅。

### 14.2 DTO 与实体是两种东西

| | 实体 Entity | DTO |
|---|---|---|
| 位置 | Domain 层 | Application 层 |
| 目的 | 表达**业务概念与不变量** | 表达**接口契约** |
| 可变性 | 有行为方法（`Publish()`、`Update()`） | 不可变数据袋 |
| 序列化 | **不应该**直接对外序列化 | 专为序列化设计 |

**为什么不直接返回实体**：① **安全**——实体会带出不该暴露的字段（`User.PasswordHash`！）；
② **解耦**——数据库结构调整不该自动改变 API 契约；
③ **防懒加载意外**——序列化实体可能触发意外的关联查询或循环引用。

**本项目不用 AutoMapper**，DTO 全部手写映射。理由：映射代码是显式的，出错时**编译期**就能发现；
而 AutoMapper 的配置错误只在**运行期**暴露，且"魔法映射"让"这个字段从哪来"难以追踪。

### 14.3 请求 DTO 与响应 DTO 分开

响应里包含服务端生成的字段（`Id`、`CreatedAt`、`Version`）；请求里不含。
把"创建请求"与"更新请求"也分开，而不是用一个 DTO 加可空字段：

- 创建**不需要**版本号、更新**必须**有——用不同类型表达，**编译器帮你检查**；
- 语义清晰：看到 `UpdatePostRequest` 就知道这是更新。

`with` 在服务层的实际用途：**强制给查询加上归属过滤，而不修改调用方传来的对象**——
`normalized = normalized with { OwnedByUserId = _currentUser.UserId };`
这是"不可变对象 + 微调副本"最典型的生产用法（§8.8 的第 ④ 层授权）。

## 15. 整洁架构与依赖倒置（旧 §8）

### 15.1 依赖倒置：为什么"数据库依赖业务"而不是反过来

**依赖倒置原则（DIP）**：高层模块不应依赖低层模块，两者都应依赖**抽象**。
于是 **Infrastructure（数据库实现）依赖 Domain（实体与仓储接口）**，而不是反过来——
业务核心完全不知道 PostgreSQL 的存在。

```
WebApi（HTTP、中间件、组合根）        最外层：易变的细节
  └ Infrastructure（EF、Redis…）
      └ Application（用例编排）
          └ Domain（业务核心）         最内层：最稳定
               依赖方向：外 → 内（只能这样）
```

**收益是具体的**：可以换数据库实现、可以给 Domain/Application 写不连库的单元测试、
可以给 Application 注入 fake 仓储。**代价**是同一个功能要穿过几层、接口变多——
这是自觉的取舍，不是教条（§18.1 会看到它甚至被质疑）。

### 15.2 一个具体例子：全文检索列如何不污染 Domain

Post 的中文全文检索列需要 Npgsql 的 `tsvector` 类型，但 Npgsql 是外部依赖，
**不能出现在 `Blog.Domain`**（那里的硬约束是零依赖）。

解法：在 Infrastructure 里把它声明为**影子属性**（shadow property）——
能被 EF 映射，但**不存在于 C# 实体类上**，只在 `BlogDbContext` 里定义。
查询时用原生 SQL 访问（§23）。

> 💡 **这个约束的价值在这里体现得非常清楚**：如果没有"Domain 零依赖"这条规则，
> 最省事的做法就是给 `Post` 加一个 `NpgsqlTsVector` 属性——
> 但那会让业务实体绑定到特定数据库，Domain 项目再也无法脱离 Npgsql 编译。
> **代价**：影子属性导致 EF 的可翻译性下降（§23.5 的两个坑）。**这是自愿承担的复杂度。**

### 15.3 接口放在哪一层

**规则：接口放在"使用方"所在层，实现放在外层。**

| 接口 | 位置 | 谁用 | 谁实现 |
|---|---|---|---|
| `IPostRepository` 等仓储 | **Domain**（`IRepository/`） | Application | Infrastructure |
| `ICacheService`、`ICurrentUser`、`ITokenService` | **Application**（`Interfaces/`） | Application | Infrastructure |

为什么仓储接口在 Domain 而不是 Application？因为它操作的是 **Domain 实体**，属于领域概念的一部分；
而缓存、当前用户这类不涉及领域概念，是纯粹的技术能力，所以放 Application。

**读写分离的仓储（CQRS 的轻量版）**：写侧仓储返回**实体**（取实体 → 调领域方法 → 保存）；
读侧查询仓储**直接投影成 DTO**（一次查完，避免 N+1 和无谓的实体追踪）。
两种诉求放同一个接口会互相牵制。

> **N+1 是 ORM 开发里最常见的低性能写法**：本来一次查询能拿到数据，却变成
> "1 次查主数据 + N 次查关联数据"（典型成因是在 C# 循环里调用仓储）。
> **本项目靠 DTO 投影规避**：列表查询在一个投影表达式里把关联字段一起给出，
> 不在循环里查询。验证方法是打开 SQL 日志看实际发出的语句（§17.2）。
> 同一个类可以**显式实现两个接口**（分类与标签的查询逻辑完全一致），
> 从而让"同名但返回类型不同"的方法共存。

> 然后才讲**仓储与工作单元**（它建立在两者之上），最后是软删除、乐观锁、索引三个具体机制。
> 旧版把仓储排在 EF 之前，读者不知道"为什么仓储要 `AsNoTracking`、为什么 `Remove` 只是打标记"（★前移）。

## 16. SQL 与 PostgreSQL 最小集【新增】

### 16.1 为什么在 ORM 时代还要学 SQL

EF Core 帮你**生成** SQL，但它不替你**判断** SQL 好不好：
索引有没有用上、有没有 N+1、为什么这条查询在数据量上来后突然变慢——
这些都要能看懂实际执行的语句。而且本项目有**原生 SQL**（全文检索，§23），
看不懂 SQL 就无法维护那部分。

### 16.2 关系模型最小集

| 概念 | 一句话 | 本项目的例子 |
|---|---|---|
| 表 / 行 / 列 | 数据放在二维表里 | `Posts`、`Users` |
| **主键** | 唯一标识一行 | `Posts.Id`（Guid，**由应用侧生成**，不是数据库自增） |
| **外键** | 引用另一行的主键 | `Posts.CategoryId` → `Categories.Id` |
| **唯一约束** | 该列（或组合）不允许重复 | `Users.Email` |
| **索引** | 加速查找的辅助结构（§21） | `IX_Posts_IsDeleted_PublishedAt` |
| **事务** | 一组操作要么全部生效、要么全不生效 | 工作单元的 `SaveChangesAsync`（§18.1） |

**为什么本项目主键用 Guid 而不是自增整数**：Id 可以在**插入数据库之前**就确定
（便于构造对象图、便于幂等），代价是索引更大、写入更分散。

### 16.3 五类语句与查询骨架

`SELECT` / `INSERT` / `UPDATE` / `DELETE`，加上 `CREATE`、`ALTER` 之类的 DDL；日常 90% 的时间在查询上。
一条查询的骨架是：**`SELECT 列 FROM 表 JOIN 另一张表 ON 条件 WHERE 行条件 GROUP BY 分组列
HAVING 组条件 ORDER BY 排序列 LIMIT n OFFSET m`**。

四个最容易混的点：**`WHERE` 过滤行、`HAVING` 过滤组**（`WHERE` 里不能放聚合函数）；
**`LEFT JOIN` 没匹配时右表列是 `NULL`**（不是 0、不是空串），判断要用 `IS NULL`；
**深分页 `OFFSET` 越大越慢**（数据库仍要扫过前面所有行）；
**子查询与 CTE（`WITH`）** 用来把复杂查询拆成可读的步骤——本项目的相关度排序正是
用 CTE 先算分数再排序（§23.5）。

### 16.4 PostgreSQL 的六个特性（写 SQL 前必须知道）

| 特性 | 说明 | 对本项目的影响 |
|---|---|---|
| **标识符大小写** | 不加双引号的标识符会被**折叠成小写** | 本项目的表名列名是 PascalCase，所以**手写 SQL 必须加双引号**：`"Posts"`、`"IsDeleted"` |
| `boolean` | 真值是 `true` / `false`，不是 0/1 | 软删除条件写作 `"IsDeleted" = false` |
| 时间类型 | `timestamptz` 带时区；C# 侧对应 `DateTimeOffset` | 全项目统一用 **UTC**（`DateTimeOffset.UtcNow`） |
| 文本类型 | `text`（不限长）/ `varchar(n)`（有上限） | 有业务上限的字段用 `varchar(n)`，超长写入直接报错——这是一层数据库级护栏 |
| **扩展** | `CREATE EXTENSION` 才能用非内置能力 | 中文分词扩展必须手工编译安装（§23.6） |
| `EXPLAIN` | 打印执行计划 | "这条查询为什么慢"的唯一入口 |

**看到报错 `column "isdeleted" does not exist` 时**：不是列不存在，而是你**忘了加双引号**，
PostgreSQL 把你的 `"IsDeleted"` 折叠成了小写去找。这是初学者在 PG 上最常见的第一个坑。

### 16.5 怎么判断一条查询行不行

| 现象 | 先看什么 |
|---|---|
| 偶发慢、数据量上来后变慢 | `EXPLAIN ANALYZE` 看是**全表扫描**还是走了索引 |
| 应用侧只发了一条请求，数据库却收到很多条 | ORM 的 N+1（§15.3）：打开 SQL 日志数语句条数 |
| 写入变慢 | 索引太多（§21.1）：每个索引都要在写入时维护 |
| 时间/条件对不上 | 时区与类型：UTC？`timestamptz`？字符串当日期比？ |

**永远不要拼接 SQL 字符串**（SQL 注入）。参数化查询把"值"与"语句结构"分开传输，
本项目用 `FromSqlInterpolated` 这类**自动参数化**的 API，不存在注入问题（§23.5）。

> 💡 **一个很值得学的读侧/写侧不对称设计**：本项目站点配置的值存在普通文本列里，
> 其中有的值是 **JSON 数组字符串**（历史数据里还存过裸地址）。
> 处理原则是 **读侧宽容、写侧严格**：读侧对历史形态保持兼容（不把老数据读崩），
> 写侧校验失败直接报错、**不做静默兜底**（否则脏数据会越写越多）。
> 这个原则在数据格式演进时到处适用，实现见 [docs/02](../docs/02-架构与数据模型.md)（媒体地址白名单）。

→ 本项目该看哪个：迁移文件里的 SQL 是最好的活教材（§21、§23 都会引用）；
模型定义看 `BlogDbContext`；查询看各 `*Repository`。｜代码见总表 #16。

## 17. EF Core 变更跟踪与导航属性（旧 §10，★前移）

### 17.1 变更跟踪：EF 怎么知道要 UPDATE 什么

EF Core 默认**跟踪**它查出来的实体：记住原始值，`SaveChanges()` 时对比当前值生成 `UPDATE`。
所以"改内存对象 → 保存"就够了，不必手写 UPDATE 语句。

**跟踪的代价**是内存占用 + 快照比较开销。**只读查询应该关掉**：
`AsNoTracking()`。本项目的 `GetAllAsync` / `QueryByConditionAsync` 都用了它——
它们返回的数据只用于展示，不会被修改。

**判据只有一条**：**这条数据接下来会不会被改并保存？** 会 → 跟踪；只是展示 → 关掉。

### 17.2 四种加载关联数据的方式

| 策略 | 写法 | 说明 |
|---|---|---|
| **预先加载**（Eager） | `.Include(p => p.Tags)` | 一次查询带出关联（**推荐**） |
| **显式加载**（Explicit） | `.Entry(p).Collection(x => x.Tags).LoadAsync()` | 需要时再查 |
| **延迟加载**（Lazy） | 需要代理包 + 属性 `virtual` | **本项目未启用**（易产生 N+1） |
| **投影**（Projection） | `.Select(p => new PostCardDto(...))` | 直接查成 DTO，**最高效** |

**为什么关闭延迟加载**：它让"访问一个属性"意外触发一次数据库查询，
在循环里就是经典的 **N+1**（1 次查列表 + N 次查关联）。

**投影是最优解**：只查需要的列、不构造实体、也不需要跟踪。本项目的读侧查询仓储正是这样做的。

> 💡 **一个常见困惑的答案**："不用 `Include` 会导致数据为空"这个现象，
> **只发生在查询返回的是"实体"时**，不会发生在"投影成 DTO"时。
> 因为投影会直接生成一条连表 SQL，根本不存在"导航属性没加载"这回事。
> 反过来，返回实体时导航集合默认是空的——这正是 §18.2 主键冲突的根源。

### 17.3 多对多的两种建模

| 建模 | 什么时候用 | 本项目 |
|---|---|---|
| **隐式**（EF 自动生成连接表） | 连接表**只有两列** | 文章 ↔ 标签 |
| **显式**（自己声明连接实体） | 连接表要携带**额外数据** | 文章 ↔ 专栏（需要排序字段） |

显式连接实体用**复合主键** `(PostId, CollectionId)`：多列共同构成主键，
天然实现"同一文章不能重复加入同一专栏"的约束。
注意这种纯连接行**不继承** `BaseEntity`（它没有 Id、没有软删除字段），
与业务实体不是一类东西——判断"它要不要软删除"，取决于它是"业务对象"还是"关系"。

### 17.4 充血模型：把业务规则放进实体

本项目的实体不是"只有属性的数据袋"，关键规则写在方法里：
`Publish()`（幂等：重复发布不覆盖首次发布时间，否则归档排序会乱）、
`ResetPassword()`（改密同时让旧 token 失效）、`SetActive(false)`（停用即踢下线）。

**为什么放在实体里**：它**无法被绕过**。若放在 Service 里，将来新写一个 Service
就可能忘记自增 `TokenVersion`——这类漏洞不会报错，只会静默地让旧 token 继续有效。
**代价**：属性需要 `private set`，构造与修改都要通过方法，代码略啰嗦。
**这是"用一点啰嗦换一条不可能被忘记的规则"，通常划算。**

→ 实现见 [docs/02](../docs/02-架构与数据模型.md)（实体模型）｜代码见总表 #17。

## 18. 仓储模式与工作单元（旧 §9）

### 18.1 仓储：把"数据访问"抽象成"集合操作"

```csharp
public interface IBaseRepository<TEntity> where TEntity : BaseEntity
{
    Task<TEntity> AddAsync(TEntity entity, CancellationToken ct = default);
    Task<TEntity?> GetByIdAsync(Guid id, CancellationToken ct = default);
    Task<IEnumerable<TEntity>> QueryByConditionAsync(Expression<Func<TEntity, bool>> where, CancellationToken ct = default);
    void Update(TEntity entity);
    void Remove(TEntity entity);
}
```

> ⚠️ **一个诚实的评价（不是教训，是取舍）**
> 在 EF Core 之上再加仓储层，学术界有争议——`DbContext` 本身已经是 Unit of Work + Repository。
> 本项目的选择是**保留仓储**，因为它让 Application 层**不依赖 EF Core**，守住整洁架构的边界。
> **这是自觉的取舍，不是"最佳实践"。**

**工作单元（Unit of Work）**：把多个仓储的修改聚合成**一个事务**。
本项目里多个仓储共享**同一个 `DbContext` 实例**（都是 Scoped），因此一次 `SaveChangesAsync` 天然是原子的。
**为什么不由它 `Dispose` `DbContext`**：生命周期归 DI 容器管，`UnitOfWork` 只负责释放**自己显式开启的事务**；
重复释放会导致问题。

**软删除与仓储**：仓储的 `Remove` **不删数据**，只打标记（`IsDeleted = true`）。
真正的"排除已删除"由全局查询过滤器自动完成（§19）。

### 18.2 一个真实教训：不加载导航集合会导致主键冲突

> ⚠️ **真实教训 · 改多对多关系前必须先 `Include` 导航集合**
> 现象：更新专栏的文章列表**必现 500**，日志是唯一约束冲突（`duplicate key ... PK_PostCollections`）。
> 根因：`GetByIdAsync` **不加载导航集合**，`collection.PostLinks` 是**空集合**，
> 于是 EF 认为"这些连接行都是新的"，对**已存在**的行执行 INSERT → 唯一约束冲突。
> **解法**：用专门的方法带上 `Include`（如 `GetWithPostsAsync`）再修改关系；**通用规律：修改多对多关系前必须先加载导航集合**。
> 同理，文章标签同步采用**增量同步**（只增/删差异项）而不是整体替换，避免"先删光再重建"的无谓写放大。

→ 实现见 [docs/02](../docs/02-架构与数据模型.md)（仓储与 UnitOfWork）｜代码见总表 #18。

## 19. 软删除与全局查询过滤器（旧 §11）

### 19.1 麻烦与解法

**软删除**：不真的 `DELETE`，而是标记 `IsDeleted = true`，数据保留、可用于恢复与审计。
**麻烦**：每个查询都必须记得加 `WHERE IsDeleted = false`，漏一个就会把已删除的数据展示出来。

**解法：全局查询过滤器**——EF Core 自动为每个查询追加条件（`HasQueryFilter(e => !e.IsDeleted)`）。
之后应用层**不需要也不应该**手写这个条件。

### 19.2 两个必须注意的点

**① 过滤器可以被 `IgnoreQueryFilters()` 绕过**（用来查"含已删除"的数据）。
本项目**没有使用**它（没有回收站功能）——换句话说，全项目所有查询都看不到已删除数据。

**② 过滤唯一索引（partial unique index）**：软删除与唯一约束会冲突——
删掉分类"技术"后就再也建不了同名分类（唯一约束仍占着）。
解法是**只在未删除的行之间保证唯一**：

```sql
CREATE UNIQUE INDEX "IX_Categories_Name" ON "Categories" ("Name") WHERE "IsDeleted" = false;
```

> 💡 **PostgreSQL 的标识符大小写敏感**（§16.4）：EF 建的表名列名是 PascalCase，
> 所以手写这类 SQL 时 `"IsDeleted"` **必须带双引号**，不加会被折叠成小写、找不到列。

### 19.3 查询过滤器与必需导航的冲突

纯连接行没有软删除（随文章/专栏级联删除），而它引用的实体**有**查询过滤器，
EF Core 因此警告"必需端被过滤可能导致意外结果"（父被过滤掉时子会莫名消失）。

本项目**从不单独查询连接行**（始终经导航访问），因此该场景不会发生，
于是在 `OnConfiguring` 里显式抑制该警告，避免日志噪音。

> ⚠️ **真实教训 · 关警告前必须能说清为什么安全**
> 这是"我们知道自己在做什么，所以关掉警告"，**不是"警告太烦所以关掉"**。
> 关掉一条警告的同时必须写下**它能发生的唯一前提为什么不成立**，
> 否则下一个改代码的人会在一片安静的日志里踩中它。

→ 实现见 [docs/02](../docs/02-架构与数据模型.md)（软删除与查询过滤器）｜代码见总表 #19。

## 20. 乐观锁与并发控制（旧 §12）

### 20.1 两种并发策略

| | 悲观锁 | 乐观锁 |
|---|---|---|
| 思路 | 先锁住，别人等着 | 先改，提交时检查有没有人改过 |
| 实现 | `SELECT ... FOR UPDATE`、事务隔离 | 版本号 / 时间戳 |
| 适合 | 冲突频繁 | **冲突稀少**（绝大多数 Web 场景） |
| 代价 | 锁等待、死锁风险 | 冲突时需重试 |

**Web 应用的常态是"读多写少、冲突稀少"**，因此乐观锁更合适。

### 20.2 本项目的实现：`int Version` + SQL 条件

每行有 `Version`（从 1 开始）。更新时带上客户端持有的版本号，
生成的 SQL 形如 `UPDATE ... SET "Version" = @expected + 1 WHERE "Id" = @id AND "Version" = @expected`。
**受影响行数为 0** → 说明有人先改过 → EF 抛并发异常 → 映射为 **409**。

**为什么不用 EF 的 `byte[] RowVersion` / `[Timestamp]`**：那是 SQL Server 的 `rowversion` 机制，
在别的数据库上需要额外支持。**整数版本号与数据库无关**，可跨 PostgreSQL / MySQL / SQLite 通用。

**关键理解 `OriginalValue` 与 `CurrentValue`**：

- `OriginalValue` = "我认为数据库里现在是什么" → EF 用它生成 **`WHERE`**；
- `CurrentValue` = "我想把它改成什么" → EF 用它生成 **`SET`**。

配合把 `Version` 标记为并发令牌，EF 才会把 `OriginalValue` 加进 `WHERE`。
本项目在模型配置里用**循环**给所有带 `Version` 的实体统一设置并发令牌，
这样**新增实体自动获得乐观锁，不会漏配**——与"逐个端点加 `[Authorize]`"（§6.5）形成鲜明对比：
能自动化的一致性，就不要靠人记。

### 20.3 乐观锁是全链路约定

① 详情接口返回 `version` → ② 前端保存时**原样回传** → ③ 不匹配则 409，
前端提示"数据已被其他请求修改，请刷新后重试"。
前端在发请求前甚至会直接断言"更新必须携带版本号"——**让错误在客户端就爆出来**，
而不是等后端返回 4001。

> ⚠️ **真实教训 · 什么时候不该用乐观锁**
> **浏览量累加**不该用：它是高频写、允许丢精度。用了乐观锁，
> "两个人同时看同一篇文章"就会有一方收到 409——**荒谬的体验**。
> 本项目的做法是用**数据库侧原子自增**（`UPDATE ... SET ViewCount = ViewCount + 1`）绕过乐观锁。
> **教训：并发控制不是"越严格越好"，而是与业务语义匹配。**

### 20.4 写入语义的统一约定

全项目遵循一条规则，避免各处判断不一致：

| 情形 | 语义 |
|---|---|
| 实体/Key **不存在** | 视为**新增**，忽略传入的 version |
| 实体/Key **已存在** | 走**乐观锁**，version 必须 ≥ 1，否则返回参数错误 |

站点配置的逐项更新就依赖它（前端对不存在的 Key 传 `version = 0`）。
**把这条例外写下来**，比在每个 Service 里各判一次要安全得多。

→ 实现见 [docs/02](../docs/02-架构与数据模型.md)（乐观锁实现）｜代码见总表 #20。

## 21. 索引设计（旧 §13）

### 21.1 直观理解与代价

没有索引，数据库要**全表扫描**（逐行检查）；有索引，就能像查字典一样快速定位。
**代价**：索引占空间，且**每次写入都要维护索引**。因此索引不是越多越好，
而是"**为高频查询建**"——这也是 §16.5 里"写入变慢先怀疑索引太多"的原因。

### 21.2 本项目的索引服务哪些查询

| 索引 | 服务的查询 |
|---|---|
| `(IsDeleted, PublishedAt)` 复合索引 | 首页列表（未删除 + 按时间倒序） |
| `PublishedAt` | 归档分组 |
| `CategoryId` / `AuthorId` / `CreatedByUserId` | 按分类、按署名作者、作者工作区（我创建的） |
| 标签连接表的 `TagsId` | 按标签筛选 |
| `Collections.Slug`（唯一）/ `SortOrder` | 按 slug 取专栏 / 专栏列表排序 |
| `Users.Email`（唯一）/ `SiteConfigs.Key`（唯一） | 登录查账号 / 取配置 |
| 分类与标签的 `Name`（唯一 + **过滤**） | 名称唯一性 + 等值查找 |
| `SearchVector`（**GIN**） | 全文检索（§23） |

### 21.3 复合索引的"最左前缀"

复合索引 `(IsDeleted, PublishedAt)` **只能被"从最左列开始连续匹配"的查询使用**：

| 查询条件 | 能否用该索引 |
|---|---|
| `WHERE IsDeleted = false AND PublishedAt > X` | ✅ 能 |
| `WHERE IsDeleted = false` | ✅ 能（只用第一列） |
| `WHERE PublishedAt > X` | ❌ **不能**（跳过了第一列） |

所以**列的顺序很重要**：**等值条件列放前面，范围条件列放后面**。

### 21.4 外键索引：PostgreSQL 不会自动建

（与 MySQL 不同！）外键索引加速两类操作：① **JOIN**（按 `CategoryId` 查文章）；
② **级联 / SetNull 删除**（删一个分类时，要找到所有引用它的文章）。
没有索引，删一个分类就会全表扫描文章表。

### 21.5 过滤唯一索引：软删除与唯一约束共存的标准做法

`WHERE` 子句让索引**只覆盖部分行**，于是同时解决两个问题：
未删除的行之间名称唯一；**软删除的行不参与唯一性检查**，可以重建同名。

> 💡 **这是软删除与唯一约束共存的正确做法**，值得记住：
> 每当"唯一约束"与"逻辑删除"同时出现，就需要它（§19.2）。

→ 实现见 [docs/02](../docs/02-架构与数据模型.md)（数据库与索引）｜代码见总表 #21。

# 阶段 5 · 性能与检索

> 目标：怎么变快（缓存）、怎么找得到（全文检索）、出事怎么看得见（日志）。
> 三节共同的思维是**"先能观测，再谈优化"**——没有日志与指标，性能工作就是盲猜。

## 22. 缓存与三大经典问题（旧 §17）

### 22.1 为什么用缓存，代价是什么

**根本矛盾**：读远多于写，而数据库是最难横向扩展的一层。缓存把热点数据放到更快的地方（内存），
减少数据库压力、降低响应时间。**代价是一致性**：缓存与数据库可能不同步。
因此缓存的真正难点不是"怎么存"，而是**"什么时候失效"**。

### 22.2 三大经典问题（面试必考，工程必防）

| 问题 | 现象 | 解法 |
|---|---|---|
| **穿透** | 查**不存在**的数据：缓存里没有 → 每次都查库 | **空值哨兵**：把"查不到"也缓存起来 |
| **击穿** | 某个**热点 key 过期**的瞬间，大量并发同时回源 | **互斥重建**：只让一个请求去重建，其他等待或直接回源 |
| **雪崩** | **大批 key 同时过期**，请求一起涌向数据库 | **TTL 随机抖动**：给过期时间加随机偏移 |

三者的共同点是"**让缓存不去保护数据库**"，差别只在触发条件（不存在 / 单点过期 / 集体过期）。

> ⚠️ **真实教训 · 空值哨兵的 TTL 必须比正常 TTL 短，且不能所有查询都缓存空值**
> 若哨兵和正常缓存一样久，"新建了一条数据但缓存里还是空的"会持续很久；
> 短 TTL 让新增数据很快可见。同时**列表类查询**缓存空值（查不到就是查不到，防穿透），
> **详情类查询不缓存空值**（避免"新建后立即读到空哨兵"）。
> 互斥重建也有一个关键取舍：**抢不到锁的请求超时后直接回源，不无限阻塞**——
> 宁可多一次数据库查询，也不要让请求卡住。

> ⚠️ **真实教训 · 缓存故障必须降级，不能报错**
> **缓存是优化，不是必需品。** Redis 挂了，正确行为是"直查数据库（慢一点）"，
> **而不是返回 500**。实现上把连接异常收敛成一个"返回 null → 调用方直接回源"的入口，
> 并把这条契约写进接口注释——**契约写在接口上，实现者才不敢违反**。
> 同理，Redis 连接要用**延迟建立**，否则"缓存没起来"会变成"应用起不来"（§4.3）。

### 22.3 三级实现与 key 设计

本项目提供三个实现，用**工厂委托**按配置选择：`NullCacheService`（完全旁路）、
`MemoryCacheService`（单实例）、`RedisCacheService`（多实例/共享）。
**`NullCacheService` 的价值在可运维性**：怀疑"问题是不是缓存引起的"时，
一个开关就能完全旁路缓存，不必改代码、不必重启调试器。

**key 规范**：`blog:{模块}:{操作}:v{版本}:{固定维度}:{可选hash}` —— 四个设计点各有理由：

| 设计点 | 理由 |
|---|---|
| 前缀 `blog:` | 便于按前缀失效；与其他应用共用 Redis 时不冲突 |
| `v{版本}` | **缓存结构不兼容变更时整体失效**：改版本号即可，旧 key 靠 TTL 自然消失，**无需 `SCAN` 清理** |
| 固定维度、缺省值占位 | 保持 key 段数固定，便于排查 |
| 长文本取 SHA256 前若干位 | 避免超长/特殊字符污染 key |

> 💡 **`v{版本}` 特别值得学**：它把"缓存与代码结构不一致"这个运维难题，
> 简化成"改一个常量"。这是**为可运维性而设计**的典型例子。

**使用模式是 `GetOrCreateAsync`**：调用方只提供"怎么取数据"（factory），缓存逻辑全在内部。
**好处**：缓存策略集中，不会出现"某处忘了写缓存"。

**一致性策略**：写操作后**删除**缓存（而不是更新缓存）——
更新缓存需要两步（改库、改缓存），中间可能失败导致不一致；删除后下次读会自然回源重建。
少数场景例外（如浏览量：更新库后同步刷新详情缓存），逐条列在
[docs/02](../docs/02-架构与数据模型.md)（缓存设计）。

→ 实现见 [docs/02](../docs/02-架构与数据模型.md)（缓存设计）｜代码见总表 #22。

## 23. PostgreSQL 全文检索与中文分词（旧 §14）

### 23.1 为什么 `LIKE '%关键词%'` 不够

- **用不上索引**（前置通配符）→ 全表扫描；
- **无语言学处理**：`running` 匹配不到 `run`；
- **无相关度排序**：要么匹配要么不匹配；
- **中文更糟**：中文没有空格分隔，只能做子串匹配。

**全文检索的思路**：分词 → 归一化（小写/词干）→ 倒排索引（词 → 文档）→
查询也分词后求交并 → 按相关度排序。

### 23.2 PostgreSQL 的 FTS 三件套

| 概念 | 说明 |
|---|---|
| `tsvector` | 文档的词元集合，带位置与权重 |
| `tsquery` | 查询条件（`&` `\|` `!` 组合词元） |
| `@@` | `tsvector @@ tsquery` 判断是否匹配 |

**用 `plainto_tsquery` 而不是 `to_tsquery`**：后者解析 `&`/`|`/`!` 语法，
**用户输入含特殊字符会直接语法错误**；前者把输入安全转成 AND 查询，特殊字符被当普通文本。
既避免报错，也避免用户构造恶意查询。

### 23.3 中文的坑：必须装分词器

> ⚠️ **真实教训 · PostgreSQL 内置分词器对中文等于没有分词**
> 内置分词器只按空格和标点切分，中文整句会被当成**一个词元**，于是搜"数据库"匹配不到。
> **必须安装中文分词器（zhparser，依赖 SCWS 词法库）**并创建 `chinese` 配置，
> 映射名词/动词/形容词等 token 类型到 `simple` 字典——
> 选 `simple` 是因为中文不需要词干还原，且能让中英混合文本里的英文词原样保留。

### 23.4 生成列与权重

**生成列**：值由数据库根据表达式计算并**存储**，插入/更新文章时数据库自动维护，
**应用层永远不用管它**，不可能出现"忘了更新索引"的不一致。
多列拼接时用 `setweight` 给不同来源的词元打权重（标题 > 摘要 > 正文）——
**权重只影响相关度评分，不影响是否匹配**。

### 23.5 两个必踩的 EF Core 坑

> ⚠️ **真实教训 · 影子属性 + 参数会被判"客户端求值"**
> 因为检索列是**影子属性**（不存在于 C# 实体上），EF Core 无法把这种组合翻译成 SQL，
> 于是回退到"把数据拉到内存再算"——表现为查询报错或结果**完全不正确**（不会报异常的那种错）。
> **解法：改用参数化原生 SQL**；且 `plainto_tsquery` 必须**显式 `::regconfig` 转型**——
> 参数化后驱动把参数当 `text`，于是去匹配 `(text, text)` 重载，报 "function does not exist"。
> **通用经验**：当 ORM 的翻译失败时，**不要与它搏斗**——先让功能正确（原生 SQL），再考虑优化。

> ⚠️ **真实教训 · 相关度排序：`ts_rank` 不能写进 `WHERE`**
> 它属于窗口函数类，PostgreSQL 直接拒绝；正确做法是**用 CTE 先算 rank 再排序**。
> 另两条路都走不通：映射成无键实体后用 `Join` 带出 rank 列会让"投影关联集合"报无法关联；
> 直接 `ORDER BY + LIMIT` 又会让分类/标签等过滤无法安全叠加，出现"先分页再过滤"的错页。
> **最终方案**：用标量原生查询拿到"按相关度排好序的 Id 列表"，外层仍用 `Contains` 组合过滤——
> **既拿到能力，又不破坏可组合性**。

> 💡 **为什么用 `Id IN (子查询)` 而不是用 `FromSql` 包整表**：
> `FromSql` 之后不能随意追加任意 LINQ，包整表会严重限制后续组合
> （分类、标签、作者、分页都要能自由叠加）。只查 Id 则外层仍是正常 LINQ。
> 参数由自动参数化的 API 处理，**不存在 SQL 注入**。

### 23.6 扩展的部署难题

中文分词扩展**不在官方镜像里**，必须自行编译。如果只在容器里手工编译，
**容器一重建就全丢**，搜索立即报错"配置不存在"。

**正确做法是把编译步骤固化进镜像**，并做**双重保障**：

| 保障 | 覆盖场景 |
|---|---|
| **EF 迁移中的 SQL（权威来源）** | **全新库 + 已有库都覆盖**——迁移每次启动都会应用 |
| 自定义镜像 + 初始化脚本 | 全新环境开箱即用（**不是必需的前置条件**） |

> ⚠️ **真实教训 · 官方镜像的初始化脚本只在"数据目录为空"时执行**
> 因此对**已存在**的库它**不会重跑**——扩展的权威来源必须是**迁移**。
> 而且这些 SQL 在迁移链里的**顺序有约束**：创建文本搜索配置必须排在"新增引用它的生成列"**之前**，
> 否则迁移链**无法从零建库**，失败表现为**应用起不来**
> （详见 [archive](../archive/问题排查记录.md)、当前状态见 [docs/06](../docs/06-技术债与待办.md)）。
> 这类顺序依赖是隐形的：日常开发遇不到，只在"从零建库"时暴露——**每次新增迁移都要验证一次从零建库**。

→ 实现见 [docs/02](../docs/02-架构与数据模型.md)（中文全文检索）｜代码见总表 #23。

## 24. 日志与可观测性（旧 §7）

### 24.1 结构化日志

`Console.WriteLine("user " + id + " failed")` 无法检索、无法聚合、无法告警。
**结构化日志**把日志当作**带字段的事件**（`LogWarning("业务异常 {Code}: {Message} {Path}", ...)`）：
占位符是**命名字段**而不是字符串拼接，日志系统可以按 `Code = 4040` 检索，而不是靠正则匹配文本。

### 24.2 级别：Warning 与 Error 的分界线

| 级别 | 何时用 | 本项目例子 |
|---|---|---|
| `Information` | 正常业务事件 | 请求完成（2xx/3xx） |
| `Warning` | **可预期**的问题 | 业务异常、权限失败、限流触发、慢查询 |
| `Error` | **故障** | 未处理异常、5xx |
| `Critical` | 应用无法继续 | 启动失败 |

> **关键区分**：`Warning` 是"预期内的不好结果"，`Error` 是"我们没预料到的故障"。
> 把两者混起来，`Error` 就失去信号价值——这正是本项目**请求日志按状态码分级**的原因：
> 5xx 记 Error、4xx 记 Warning。

### 24.3 两个实用配置与一个教训

**Bootstrap Logger**：在 DI 容器建好之前就要能记日志，否则"启动阶段崩溃"没有任何记录——
用 `CreateBootstrapLogger()` 先接上控制台，容器建好后换成正式配置。

> ⚠️ **真实教训 · `HostAbortedException` 必须排除**
> `dotnet ef` 设计期工具会**正常中止宿主**，那不是启动失败。
> 之前没排除，导致每次执行 EF 命令都记一条 Fatal 日志——
> 假故障日志比没有日志更糟：它会训练人忽略 Fatal。

**滚动文件**：按天滚动并保留有限天数，避免磁盘被日志吃满。

### 24.4 慢查询监控

EF Core 提供 `DbCommandInterceptor` 钩子，本项目在所有命令执行后检查耗时，
超过阈值就记 Warning（含 SQL 文本）。

> 💡 **一个实现细节值得注意**：需要重写 Reader / NonQuery / Scalar 的**同步与异步共 6 个**
> `...Executed` 方法；异步方法返回 `ValueTask<T>`（框架签名），
> 直接返回 `base.XxxAsync(...)` 即可——**没有后续逻辑要在 await 之后执行**时，
> 不必写 `async/await`（§13.1 的 `ValueTask` 场景）。

→ 实现见 [docs/02](../docs/02-架构与数据模型.md)（日志与可观测性）｜代码见总表 #24。

## 25. Vue 3 与组合式 API（旧 §20）

### 25.1 组合式 API 与 Options API

本项目用**组合式 API**：按**逻辑关注点**组织代码，复用靠**组合式函数**（显式、类型安全），
类型推断强；Options API 按选项分组（data / methods / computed）、复用靠 mixins（来源不清晰、命名冲突）。
收益在**大型组件**上才明显：相关逻辑可以写在一起，而不是"数据、方法、副作用"三处跳。
`<script setup>` 里声明的顶层变量**自动暴露给模板**，不需要 `return`。

### 25.2 响应式：五个 API 与两个陷阱

| API | 用途 | 注意 |
|---|---|---|
| `ref(x)` | 包装任意值 | 脚本里用 `.value`，**模板里自动解包** |
| `reactive(obj)` | 包装对象 | 不能替换整个对象，**解构会失去响应性** |
| `computed(fn)` | 派生值 | 有缓存，依赖不变则不重算 |
| `watch(src, fn)` | 副作用 | 异步、可拿到新旧值 |
| `watchEffect(fn)` | 自动追踪依赖 | 立即执行 |

```typescript
const { open } = reactive({ open: false })      // ❌ 解构后丢失响应性
const open = ref(false)                          // ✅
const double = computed(() => count + 1)         // ❌ count 是 ref，忘了 .value
```

### 25.3 模板语法与生命周期

| 语法 | 说明 |
|---|---|
| `v-if` / `v-else-if` / `v-else` | 条件渲染（**销毁/重建**） |
| `v-show` | 切换 `display`（**保留 DOM**） |
| `v-for` + `:key` | 列表渲染，**`:key` 必须稳定唯一** |
| `:prop` / `@event` / `v-model` | 属性绑定 / 事件 / 双向绑定 |
| `v-html` | **渲染原始 HTML → XSS 风险**（§10.2） |

**`v-if` 与 `v-show` 的选择**：前者有切换开销（销毁重建组件），后者有初始渲染开销（总是渲染）——
**高频切换用 `v-show`**。
**`:key` 为什么要稳定唯一**：Vue 用它判断"哪个元素是哪个"；用数组下标做 key，
在列表插入/删除时会导致状态错乱（如输入框内容跑到别的行）。

**生命周期**：`onMounted`（发请求取数据的常见位置）、`onUpdated`、`onBeforeUnmount` / `onUnmounted`。
**必须清理的资源**：`setTimeout` / `setInterval` / 全局事件监听 / WebSocket，
否则组件已销毁而回调还在跑，造成内存泄漏。应用级的全局监听（如快捷键）不需要清理。

**何时用自定义指令而不是组件**：需要"直接操作 DOM 元素"且**不引入额外 DOM 结构**时。
本项目用它封装打字机效果（操作文本节点内容），而不是包一层组件。

→ 实现见 [docs/04](../docs/04-前端设计.md)（组件与目录结构）｜代码见总表 #25。

## 26. 前端路由与守卫（旧 §21）

### 26.1 History 模式：一个只在部署后才暴露的坑

| 模式 | URL | 刷新行为 |
|---|---|---|
| Hash | `/#/post/123` | 总是正常（`#` 后不发请求） |
| **HTML5 History**（本项目） | `/post/123` | ⚠️ **刷新会 404** |

**为什么**：URL `/post/123` 在服务器磁盘上**不存在**文件。点链接时由前端 JS 接管（不发请求），
但**直接刷新**时浏览器会真的请求这个路径。

> ⚠️ **真实教训 · 开发期测不出来，上线才 404**
> **Vite dev server 内置了 fallback**，所以在开发环境刷新一切正常；
> 上线后由 Nginx 提供静态文件，必须有 `try_files $uri $uri/ /index.html` 兜底，
> 否则用户刷新文章页就是 404。**这类"开发环境帮忙掩盖了的问题"清单**，
> 是部署前检查的重点（§29）。

### 26.2 路由组织：嵌套、布局与代码分割

**父路由挂布局组件，子路由渲染到它的 `<RouterView>`**（`App.vue` 只留一个顶层 `<RouterView>`）。
**为什么用响应式导入**（`() => import(...)`）：**代码分割**——每个页面单独打包，
首屏只加载需要的代码。

`meta` 是路由上的自定义数据（`requiresAuth`、`roles`、`guestOnly`）。
为了类型安全，需要**扩展 `RouteMeta` 接口**，否则 `to.meta.requiresAuth` 是 `any` 或直接报错。

### 26.3 全局前置守卫

守卫负责三件事：**仅未登录可访问的页面**（已登录则送回各自首页）、
**需要认证的页面**（未登录跳登录并带上 `returnUrl`）、
**角色不足**（回到自己的地盘，而不是显示 403 页）。

**两个值得注意的设计决策**：① 用"返回 `false` / 路由对象"来取消或重定向，
而不是调用 `next()`（新版风格）；② **角色不足时送回自己的地盘**——
作者误入管理端时直接被送到自己的文章列表，不需要理解"权限不足"这个抽象概念。
**`returnUrl` 的价值**：用户被中断的意图被保存，登录后能回到原处。

> ⚠️ **真实教训 · 守卫不是安全边界**（§8 已从后端角度讲过）
> 它只是体验优化：可以被完全绕过（改 JS、或直接调 API）。
> **真正的安全边界永远在服务端**；前端守卫的作用是"让用户不去撞墙"，不是"阻止用户撞墙"。

**两个容易被忽略的细节**：
① **旧链接用重定向而不是删除**（用户收藏了旧链接、或某处还有硬编码引用，删除就是 404，
一个重定向成本极低、收益是不断链）；
② **404 要用真实的 404 页面**，早期"静默重定向到首页"会产生**软 404**——
搜索引擎和用户都无法判断"这条 URL 不存在"。
滚动行为则用保存的位置优先、否则回到顶部（前进/后退恢复位置）。

→ 实现见 [docs/04](../docs/04-前端设计.md)（路由与守卫）｜代码见总表 #26。

## 27. 前端状态管理与循环依赖（旧 §22）

### 27.1 为什么需要集中式 store

多个组件需要共享状态（如"当前登录用户"），用 props 逐层传递（prop drilling）在深层次时极其痛苦。
**Pinia** 提供集中式 store：任何组件都能读写，且是响应式的。
store 由三部分组成：`state`（数据）、`getters`（派生值，有缓存）、`actions`（方法，可异步）。

**两个约定**：`state` **必须是函数**（返回对象，保证每个实例状态独立，而不是共享同一个引用）；
`getters` 里用 `this` 时**不能**用箭头函数（箭头函数不绑定 `this`）。

### 27.2 循环依赖：前端也需要依赖倒置

```
http.ts ──需要 token──► auth store
   ▲                        │
   └──────store 调 api──────┘
```

如果 HTTP 层直接 `import` store，而 store 又 import API 模块，就形成循环。
JavaScript 的模块系统能处理一部分循环，但常导致**运行时 `undefined`**
（依赖在初始化时还没赋值）——**这种错误不会在编译期报，只在某个启动顺序下偶发**。

> ⚠️ **真实教训 · 用"回调注入"打断循环**
> HTTP 层只声明"我需要什么"（一个取 token 的函数、一个 401 处理器），
> **不 import store**；由 `main.ts` 在启动时"接线"，把 store 的函数传进去。
> **这是依赖倒置在前端的应用**（§15.1）：HTTP 层定义抽象，组合根提供实现，
> 因此它**不知道 Pinia 的存在，可独立测试**。

### 27.3 401 处理与应用启动顺序

**401 处理有一个易漏的细节**：已经在登录页时**不要再跳转**——
用户输错密码 → 后端 401 → 触发处理器 → 若不加判断会重新导航到登录页 →
**页面重载、错误提示消失**，用户以为"点了没反应"。

**会话恢复（`restore`）**：启动时从本地存储读 token → 若本地已知过期就直接清理（省一次请求）→
否则向后端确认一次身份。它有一个本地判断做不到的价值：能正确处理
**"token 未过期但账号已被停用/改密"**——本地看 token 还有效，后端 `TokenVersion` 校验会拒绝（§8.3）。
用一个"已验证"标志避免每次路由导航都请求身份接口。

**启动顺序**：先装 pinia → 装 router → 立刻应用主题（避免闪烁）→ 接线 HTTP →
**等会话恢复完成后再挂载应用**。最后这一步是为了避免首屏短暂显示"未登录"、
再闪变成已登录的视觉抖动。

→ 实现见 [docs/04](../docs/04-前端设计.md)（状态管理）｜代码见总表 #27。

## 28. 单元测试（旧 §24）

### 28.1 测试金字塔与"好测试"的五个特征

```
   ╱╲        E2E（少、慢、脆）
  ╱──╲       集成测试（中）
 ╱────╲      单元测试（多、快、稳）
```

越往上越接近真实、越慢、越容易因无关改动而失败。**大多数测试应该是单元测试。**

| 特征 | 说明 |
|---|---|
| **快速** | 毫秒级，不碰数据库/网络 |
| **独立** | 不依赖其他测试的执行顺序 |
| **可重复** | 任何环境、任何次数结果一致（**固定随机种子**） |
| **自验证** | 通过/失败无需人工判断 |
| **及时** | 与代码同步编写 |

### 28.2 优先测什么：有损的、静默失败的操作

本项目最早、也最值得测的是**图片优化器**：它**有损**（转错了不可逆，用户的原图没了）、
**失败是静默的**（没有报错，只是图片不对了，可能很久才发现）、边界情况多
（动画、损坏文件、超大图、转换后更大）。

**测试设计的重点因此是"不该转的情况一个都不能转错"**，而不是"转换功能正常"。
构造测试数据时用**固定随机种子**生成有渐变与噪点的图——
纯色图会被压得极小、不适合观察压缩效果；固定种子保证偶发失败可以复现。

**框架与依赖替换**：xUnit + 覆盖率收集器 + xUnit 内置断言。
日志与配置依赖用 `NullLogger<T>` / `Options.Create(...)` 满足，
**不需要引入 Mock 框架**就能构造被测对象。测试名用"方法_场景_期望"，
并用中文注释说明"**为什么测这个**"——半年后你只会记得名字，不会记得意图。

### 28.3 覆盖率与真实缺口

> ⚠️ **真实教训 · 覆盖率数字的口径比数字本身重要**
> 同一份代码，**排除 EF 迁移与源生成代码**后行覆盖明显下降、分支覆盖反而上升；不排除时数字虚高。
> 所以本项目**规定覆盖率必须带 `coverage.runsettings`**：覆盖率是**发现盲区的工具**，不是目标——
> 用它按风险排序，找出真正"裸奔"的地方：**限流中间件**（安全控制，集成测试里被关掉了）、
> **健康检查**、**内存缓存/内存限流器**（只在开发环境复现）、**部署校验**、若干业务写路径。
> **具体数字与清单会变，实测见 [docs/05](../docs/05-运维与部署手册.md)**（构建、测试与迁移）。

**已经守得很好的部分**：端点级权限矩阵、草稿保护、乐观锁、媒体地址白名单、字段长度护栏、图片优化边界。
它们的共同点是"**漏了会静默出事**"——这正是值得写测试的地方。

→ 运行方式见 [docs/05](../docs/05-运维与部署手册.md)｜代码见总表 #28。

## 29. 部署与反向代理（旧 §25）

### 29.1 部署形态与为什么需要反向代理

```
浏览器 ──► Nginx（TLS 终止、静态文件、统一入口）
              ├─ 静态文件 → 前端构建产物
              └─ /api    → Kestrel（ASP.NET Core）
                              ├─ PostgreSQL（+中文分词扩展）
                              └─ Redis
```

反向代理承担五件事：**TLS 终止**、**静态文件**（比 Kestrel 高效）、**负载均衡**、
**缓冲慢请求**（保护应用）、**统一入口**（前后端同源，避免 CORS）。

### 29.2 三个必须处理的点

| 点 | 不做的后果 | 解法 |
|---|---|---|
| **SPA history fallback** | 刷新 `/post/xxx` 得到 404（§26.1） | 静态站点配置 `try_files ... /index.html` |
| **`X-Forwarded-For`** | "按 IP 限流"退化成"全局限流"（§11.3） | 代理转发真实 IP + 应用侧读转发头 |
| **工作目录** | 日志与上传文件散落到意外位置 | 固定工作目录，或把存储路径配成绝对路径 |

### 29.3 容器化 PostgreSQL 与扩展

**核心难题**：中文分词扩展不在官方镜像中，必须自行编译。**只写文档记录手工步骤是不够的**——
换人/换机/CI 起干净环境时必然出错。正确做法是把编译步骤**固化进 Dockerfile**（§23.6）。

> ⚠️ **真实教训 · 迁移链的顺序依赖是隐形的**
> 创建文本搜索配置的两段 SQL 必须排在"新增引用它的生成列"**之前**，
> 否则迁移链**无法从零建库**，而失败发生在应用启动时，表现为**应用起不来**。
> 这类问题的特征是：**日常开发永远遇不到**（库已存在），只有新环境/CI 才炸。
> 所以每次新增迁移，都要**在空库上验证一次完整迁移链**。

**构建期的坑也值得记录**（它们都属于"只有从零构建才暴露"的一类）：
基础镜像里缺开发包、上游仓库没有预期的构建脚本、源码里的注释会让构建工具报错——
处理方式只能是改源码或换构建步骤。完整清单见 [docs/05](../docs/05-运维与部署手册.md)。

### 29.4 上线前的安全清单与启动期校验

| 项 | 要求 |
|---|---|
| JWT 签名密钥 | 环境变量注入（足够长）；**生产配置文件里没有这一项**（§7.3） |
| 管理员密码 | **立即修改种子密码**（公开在仓库里，§9.5） |
| CORS 来源 | 按实际域名配置（同源部署其实不需要 CORS） |
| 缓存提供者 | 多实例必须 Redis，否则**启动失败**（§7.3） |
| 部署实例数 | 与实际实例数一致，否则部署校验失效 |
| PostgreSQL | 必须带中文分词扩展（§23.6） |
| HTTPS / 日志 | 必须启用；确认日志目录可写且会轮转 |

**启动期校验的价值**在于把"危险配置"变成"启动失败"：
`DeploymentGuard` 与签名密钥校验体现的是同一个理念（§7.3）。
**好的错误信息包含三要素**：现状（配置值是什么）、原因（为什么不行）、解法（怎么改）——
它把一次线上排障变成一次照着做的操作。

→ 实现见 [docs/05](../docs/05-运维与部署手册.md)（部署与回滚）｜代码见总表 #29。
